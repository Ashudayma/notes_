Video 1: GenAI Roadmap — Introduction

What is GenAI?

⭐ Interview Important — Definition:
"Generative AI is a type of AI that creates new content such as text, images, music, and even code by learning patterns from existing data, mimicking human creativity."
  • AI research has existed for ~60-70 years, producing many techniques: Symbolic AI, Expert Systems (1980s), Fuzzy Logic, Evolutionary Algorithms, NLP, Computer Vision.
  • Machine Learning had the biggest impact among all AI techniques: learn a statistical/mathematical pattern from data so the model can predict on new data. Still relevant and in-demand today.
  • Traditional ML model types:
    • Regression — predict a number (e.g., stock price prediction).
    • Classification — predict a category (e.g., cat vs dog).
    • Ranking — recommend/rank similar items (recommendation systems).
  • Traditional ML was never used for tasks requiring human creativity. GenAI changed this — it can generate new text, images, video, code.
⭐ Interview Important: Until ~2 years before GenAI, the belief was "AI can't replace human creativity." GenAI's biggest differentiator/"superpower" is that it broke this assumption — it can mimic human creativity.

AI Hierarchy (⭐ Interview Important — common diagram)

GenAI Impact Areas

Four major areas most impacted by GenAI:

  1. Customer Support — Companies previously needed large call-center teams to handle customer queries at scale (costly). Now GenAI chatbots handle first-level support, escalating only complex issues to humans. Result: a task that needed ~10 people may now need only 2-3.
  2. Content Creation — Text (blogs), video, and other content creation is heavily penetrated by GenAI tools; AI-written content is often indistinguishable from human-written content.
  3. Education — GenAI tools (e.g., ChatGPT) act like a personal tutor available anytime — for curriculum planning, doubt-solving, practice questions.
  4. Software Development — GenAI models are very good at writing production-ready code, reducing team size needed for a task (e.g., 5 programmers → 2-3).

Is GenAI a Successful Technology?

Framework: compare GenAI against Internet (highly successful) and Blockchain/Crypto (hasn't reached full potential).

⭐ Interview Important — Criteria to judge if a technology is "successful":
  1. Does it solve real-world problems? → Yes (customer support, education, etc.)
  2. Is it useful on a daily basis? → Yes
  3. Is it impacting world economics? → Yes — e.g. China's DeepSeek R1 release wiped out ~$1 trillion (~80 lakh crore INR) from US tech stocks in a single day.
  4. Is it creating new jobs? → Yes — the AI Engineer role has emerged and demand is rising steadily.
  5. Is it accessible? → Yes — no coding required; usable via natural language by non-technical people.

Conclusion: Since all answers are "yes," GenAI is on the path of a successful technology (like the Internet), not a bubble (like crypto so far).

The Solution: A Mental Model Centered on "Foundation Models"

⭐ Interview Important — Foundation Models definition:
Foundation Models are large-scale AI models trained on massive amounts of data (comparable to most of the internet's data) using huge compute (many GPUs, costing crores of rupees).
  • Key property: Unlike traditional ML models (which are task-specific), Foundation Models are generalized — they can perform multiple tasks (text generation, sentiment analysis, summarization, Q&A, etc.) because of large architecture (huge parameter count) + massive training data.
  • LLMs (Large Language Models) are the best example of foundation models — backbone of GenAI today.
⭐ Interview Important: Foundation Models ⊃ LLMs. Foundation models also include LMMs (Large Multimodal Models) — models that work with images, video, and audio, not just text.

Video 3: What is LangChain & Why Do We Need It?

What is LangChain?

⭐ Interview Important — Definition:
"LangChain is an open-source framework for developing applications powered by an LLM."

To truly understand why LangChain is needed, the video builds a real example: a "chat with your PDF" application.

Example App: Chat with a PDF (motivating example)

Idea: a user uploads a PDF (e.g., a Machine Learning textbook) and can both read it and chat with it — e.g., "explain page 5 like I'm 5 years old," "generate true/false questions on Linear Regression," "generate notes on Decision Trees."

High-Level System Flow

⭐ Interview Important — Keyword Search vs Semantic Search:
  • Keyword search: matches exact words anywhere in the text → inefficient, returns too many irrelevant pages.
  • Semantic search: understands the meaning of the query and matches meaning, not exact words → returns fewer but more contextual results.

Why not just send the whole book instead of doing semantic search first? Analogy: asking a teacher "here's the whole book, I have a doubt" vs. "I have a doubt specifically on page 155" — the second gets a faster, more precise answer. Sending the whole document is also computationally expensive and can yield worse results than sending only the relevant, targeted context.

How Semantic Search Actually Works

⭐ Interview Important — Embeddings/Vectors:
Text is converted into embeddings — vectors (sets of numbers) that represent the semantic meaning of the text (via Word2Vec, Doc2Vec, BERT embeddings, etc.). Similar meanings → vectors close to each other in vector space.

Detailed (Low-Level) System Design of the RAG Pipeline

Three Big Challenges in Building This System (⭐ Interview Important)

ChallengeSolved ByNotes
1. Building the "brain" (NLU + context-aware text generation)LLMsWas an unsolved NLP problem until the 2017 Transformer paper, followed by BERT/GPT — now solved by simply using an existing LLM.
2. Hosting/computation for running a huge LLM (engineering + cost)LLM APIsCompanies like OpenAI/Anthropic host the LLM on their own servers and expose an API — you pay only for what you use, no need to host the model yourself.
3. Orchestrating the whole system (many moving components/tasks)LangChainComponents: S3 storage, text splitter, embedding model, vector database, LLM. Hand-coding all interactions (and swapping components, e.g., OpenAI → Google, or AWS → GCP) is very difficult — this is exactly the orchestration problem LangChain solves.

Benefits of LangChain (⭐ Interview Important)

  1. Chains — the core concept (source of the name "LangChain"). Lets you connect components/tasks into a pipeline where one component's output automatically becomes the next component's input, without manual wiring code. Supports complex, parallel, and conditional chains.
  2. Model-agnostic development — swap the underlying LLM, embedding model, vector DB, or cloud provider with minimal code changes (e.g., OpenAI → Google) since you focus on business logic, not component wiring.
  3. Complete ecosystem — wide variety of document loaders, ~50 kinds of text splitters, many embedding models, and many vector databases are available out-of-the-box; virtually any component your company wants to use has a LangChain interface.
  4. Memory and state handling — via a conversation memory concept, follow-up questions (e.g., "also give me interview questions on this algorithm" after discussing Linear Regression) can be understood in context without re-mentioning the topic.

What Can You Build With LangChain?

  1. Conversational chatbots — most popular use case. Internet-based companies (e.g., food delivery, e-commerce) use chatbots as a first layer of customer support to handle scale, escalating to humans only when needed.
  2. AI knowledge assistants — a chatbot with access to your own specific data (e.g., a chatbot embedded in a course platform that can answer a student's doubt about the specific lecture they're watching).
  3. AI Agents — "chatbots on steroids" that can not just talk but also perform actions/tasks (e.g., a travel-booking agent that actually books the cheapest flight for a given date/route, useful for users like senior citizens who aren't comfortable navigating booking websites themselves).
  4. Workflow automation — personal, professional, or company-level workflow automation using LLMs.
  5. Summarization & research helpers — e.g., a company-internal "ChatGPT-like" tool that can process very large documents (beyond typical context-length limits) and also work with private company data that can't be uploaded to public tools like ChatGPT.

Alternatives to LangChain

  • LlamaIndex — quite popular, has dedicated courses on CampusX's website.

1. Models

⭐ Interview Important — Definition:
"Models are the core interface through which you interact with AI models" in LangChain.

Backstory: how this component came to be necessary

Building a chatbot (NLP's most sought-after application) historically had two big unsolved problems:

  1. NLU (Natural Language Understanding) — getting the bot to understand what the user means.
  2. Context-aware text generation — getting the bot to reply appropriately even after it understands.

LLMs solved both problems at once, because they were trained on almost the entire internet's text — this gave them both language understanding and context-aware generation.

This created a new problem: LLMs, being trained on internet-scale data, have billions of parameters, so model files are huge (good market LLMs are >100GB). No individual, and no small company, can realistically host/run such a model on their own hardware (cost of compute/cloud would be unaffordable).

Solved by APIs: Large companies (OpenAI, etc.) host the LLM on their own infrastructure and expose it via an API. Anyone can hit the API with a query and get a response back — you pay only for what you use, without hosting anything yourself.

This created a third problem: implementation/standardization. Different LLM providers wrote their APIs differently — different request formats, different response formats. If an app needs to talk to two different LLM providers, it needs two different pieces of integration code, and switching providers later means rewriting that code.

⭐ Interview Important — Problem the Models component solves:
LangChain's Models component standardizes the interface for talking to any AI model provider. Switching from, say, OpenAI to Claude/Gemini typically needs only 1-2 lines of code changed (the import/class name), not a rewrite — the calling code and response-parsing code stay the same.

2. Prompts

⭐ Interview Important — Definition:
Prompts are the inputs provided to an LLM.
⭐ Interview Important: LLM output is highly sensitive to the prompt — even a single word change (e.g., "explain in an academic tone" vs. "explain in a fun tone") can produce very different output. This sensitivity gave rise to the field of Prompt Engineering and the job role of Prompt Engineer.

LangChain provides flexible ways to build prompts:

  1. Dynamic & reusable prompts — a template with placeholders (e.g., "Summarize {topic} in {tone} tone") filled in per-request, so the same template serves many different queries.
  2. Role-based prompts — a system-level prompt sets the LLM's persona/role (e.g., "You are an experienced {profession}") combined with a user-level prompt (e.g., "Tell me about {topic}") — e.g., "You are an experienced doctor. Tell me about viral fever."
  3. Few-shot prompting — show the LLM several worked examples (e.g., labeled customer-support tickets: billing issue / technical issue / general inquiry) before asking it to classify a new, unseen input using the same categories.

3. Chains

⭐ Interview Important: Chains are the component the framework is named after — its most important concept. A Chain lets you build a pipeline in LangChain: any LLM application can be shaped as a pipeline of steps.
⭐ Interview Important — Core benefit of Chains:
The output of one step in a Chain automatically becomes the input of the next step — no manual code needed to wire outputs to inputs.

Example: Sequential Chain

Task: take a large (~1000-word) English text as input, output a Hindi summary in under 100 words.

Without Chains: you'd manually call LLM-1 (translate English → Hindi), grab its output, manually pass it as input to LLM-2 (summarize the Hindi text to <100 words), and manually handle the final result.

With Chains: define the pipeline once; then just call the chain with the English text, and the translate → summarize hand-off between steps happens automatically behind the scenes.

Example: Parallel Chain

Task: user gives a topic (e.g., "911 incident"), app must return one combined detailed report. Multiple LLMs process the same input simultaneously, and a final LLM merges their outputs.

Example: Conditional Chain

Task: an AI agent receives customer feedback. An LLM classifies the feedback; if it's good, reply "thank you"; if it's bad, immediately email the customer support team.

These are just a few examples — LangChain supports many other chain compositions. Chains handle all of this pipeline "heavy lifting" behind the scenes, drastically reducing manual wiring code.

4. Indexes

⭐ Interview Important — Definition:
Indexes connect your application to external knowledge sources such as PDFs, websites, and databases.
⭐ Interview Important — 4 sub-components of Indexes:
  1. Document Loader
  2. Text Splitter

5. Memory

⭐ Interview Important — Core problem:
LLM API calls are stateless — each request is independent and has no memory of previous requests.

Example: ask "Who is Narendra Modi?" → get a correct answer. Then ask "How old is he?" in a separate API call → the model responds it has no idea who "he" refers to, because it has no memory of the earlier exchange. This would make a chatbot extremely frustrating to use, since the user would have to re-state context on every message.

LangChain's Memory component solves this by letting you add memory to a conversation.

Types of Memory in LangChain (⭐ Interview Important)

Memory TypeHow it worksTrade-off
Conversation Buffer MemoryStores the entire chat history; the full history is sent along with every new API call.If the conversation grows very large, the history (and thus cost) grows large too.
Conversation Buffer Window MemoryStores only the last N interactions (e.g., last 100 messages); the window keeps sliding/updating.Bounded cost, but older context beyond the window is lost.
Summarizer-based MemoryKeeps a running summary of the chat history so far, and sends that summary (not the full text) with each API call.Saves tokens/cost vs. buffer memory, at the cost of some detail.
Custom MemoryStores specialized pieces of information for advanced use cases — e.g., user preferences, specific facts/figures about the user — kept around to make future conversation easier.Requires custom design per use case.

6. Agents

⭐ Interview Important: An AI Agent is essentially "a chatbot with superpowers" — an evolved form of chatbot that can also take actions, not just talk.

Chatbot vs. AI Agent — the key difference (⭐ Interview Important)

Example: a travel-website chatbot.

  • Plain chatbot: Ask "best travel destination in India in summer?" → answers from its trained knowledge (e.g., "Shimla, Manali" — hill stations are best in summer).
  • AI Agent: Ask "cheapest flight from Delhi to Shimla on 24th January?" → it hits a live flight-search API and returns the actual cheapest option. Ask further "book the flight" → it can actually perform the booking on the website.
⭐ Interview Important — What an AI Agent has that a chatbot doesn't:
  1. Reasoning capability — can reason about what exactly needs to be done to answer a query.
  2. Access to tools — can call external tools/APIs to fetch information or perform actions.

Worked Example: Agent With Calculator + Weather API Tools

Setup: an agent is given two tools — a calculator (for math) and a weather API (to fetch a city's weather/temperature on any date).

Query: "Can you multiply today's temperature of Delhi with 3?"

⭐ Interview Important — Chain of Thought (CoT) reasoning:
One popular reasoning technique agents use is Chain of Thought prompting, where the agent breaks the query down step-by-step and reasons through each step before acting.
⭐ Interview Important — Summary, Chatbot vs. Agent:
An AI Agent is just an evolved chatbot that can perform actions, made possible specifically by two additional capabilities: reasoning and tool access. LangChain makes building such agents significantly easier.

Internally, all LangChain LLM wrapper classes inherit from a common BaseLLM class, and all Chat Model wrapper classes inherit from a common BaseChatModel class — this shared inheritance is what makes the interface consistent no matter which provider you switch to.

⭐ Interview Important — Correction (from Video 6): what temperature really controls.
The precise mechanism is about repeatability, not just a vague "creativity" dial: at temperature ≈ 0, sending the exact same prompt to the LLM any number of times returns the same output every time (deterministic/reproducible). As temperature rises toward 1.5–2, sending the exact same prompt repeatedly returns a different output each time (non-reproducible, creative). Use low temperature when an application must give every user a consistent answer to the same input; use high temperature when varied/creative output is desired even for repeated identical input.

Open-Source Models

⭐ Interview Important — Definition:
"Open-source models are freely available AI models that can be downloaded, modified, fine-tuned, and deployed without restrictions from a central provider." Unlike closed-source models (GPT, Claude, Gemini), open-source models allow full control and customization.

Two Ways to Use an Open-Source Model (⭐ Interview Important)

  1. Hugging Face Inference API — similar to using OpenAI's API: the model stays hosted on Hugging Face's servers, and you call it remotely. Free up to a usage limit, then paid. Gives access to thousands of hosted models without needing local compute. In LangChain: HuggingFaceEndpoint (to configure the remote LLM) + ChatHuggingFace (to wrap it as a chat model).
  2. Local download — download the model's weights directly onto your own machine (via Hugging Face) and run inference locally, with an internet connection needed only once. In LangChain: HuggingFacePipeline.from_model_id(...) + ChatHuggingFace. Example used: TinyLlama (a small, 1.1-billion-parameter fine-tuned version of LLaMA 2, ~500MB download).
⭐ Interview Important — Disadvantages of open-source models:
  1. Hardware requirements — running larger models locally needs a strong GPU; even a small model like TinyLlama was very slow (~10 minutes for one response) on a weak machine (8GB RAM, low SSD space) and could hang the system.
  2. Complex setup — downloading weights, tokenizers, and config files, and managing local environment/cache paths, is more involved than calling an API.
  3. Less refined responses — open-source models generally receive less RLHF (Reinforcement Learning from Human Feedback) fine-tuning than closed-source models, so responses can feel less polished by comparison.
  4. Limited multimodal ability — most freely available open-source options are still text-only; strong open multimodal (image/audio) models are comparatively rare.

Embedding Models

Recap: an embedding model converts text into a vector (list of numbers) that captures its semantic/contextual meaning — used for semantic search.

OpenAI Embeddings

  • Class: OpenAIEmbeddings (from langchain_openai), e.g. model text-embedding-3-large.
  • .embed_query(text) — generates the embedding vector for a single piece of text.
  • .embed_documents([text1, text2, ...]) — generates embeddings for multiple texts/documents at once, returning a 2D list (one vector per document).
  • A dimensions parameter controls the output vector's length — default is 1536 for small models and 3072 for large models, but can be set smaller (e.g., 32) explicitly.
⭐ Interview Important — Embedding dimension trade-off:
A larger output vector (more dimensions) captures more contextual meaning but costs more (and is more expensive to store/compare); a smaller vector is cheaper but captures less context. OpenAI embedding cost is very low (~$0.02 per million tokens) since the model only outputs numbers, not text.

Open-Source Embeddings

Class: HuggingFaceEmbeddings (from langchain_huggingface). Example model: sentence-transformers/all-MiniLM-L6-v2 — a small (~90MB) sentence-transformer model that maps sentences/paragraphs to a 384-dimensional dense vector space, well-suited for clustering and semantic search. Same .embed_query() / .embed_documents() methods apply. In general experience, free/open-source embeddings tend to be somewhat less accurate than OpenAI's paid embeddings.

Worked Example: Document Similarity Search

Goal: given a fixed set of documents (5 short bios of Indian cricketers) and a user query (e.g., "Tell me about Virat Kohli"), find which document is most relevant.

Implementation notes:

  • sklearn.metrics.pairwise.cosine_similarity(query_vector_2d, document_vectors_2d) — both arguments must be 2D lists/arrays (the query vector wrapped in an extra list even though it's a single vector).
  • To find the best match without losing track of which score belongs to which document, pair each score with its original index via enumerate() before sorting — then sort by score and take the last (highest) entry.
  • Query "Tell me about Virat Kohli" → correctly matched the Virat Kohli document with the highest similarity score; changing the query to "Tell me about Bumrah" correctly switched the top match.
⭐ Interview Important: Recomputing document embeddings on every run is wasteful/costly — in a real system, document embeddings are generated once and stored in a vector database (covered later), while query embeddings are generated fresh on each request. Comparing a fresh query embedding against stored document embeddings is exactly the retrieval step of a RAG pipeline.

Video 6: Prompts — Static/Dynamic Templates, Messages & Chat History

Second LangChain component, deep dive. Focus is entirely on text-based prompts (multimodal prompts — image/audio/video inputs — exist but are out of scope; text is ~99% of real-world usage today).

What Is a Prompt?

⭐ Interview Important — Definition:
A prompt is simply the message/input you send to an LLM. Nothing new conceptually — every message sent to model.invoke() so far has already been a prompt.
⭐ Interview Important: LLM output is extremely sensitive to the exact wording of the prompt — a small change in phrasing can produce a very different output. This sensitivity is why an entire discipline/job role, Prompt Engineering, exists around designing prompts well.

Static vs. Dynamic Prompts

Motivating example: a "Research Paper Summarizer" web app (built with Streamlit) — a user pastes a prompt into a text box and clicks "Summarize."

⭐ Interview Important — Static Prompt, and why it's problematic:
A static prompt is one where the entire prompt text is typed freely by the end user (e.g., a raw text box: "Summarize the Attention Is All You Need paper in simple fashion"). Problems:
  1. The user may mistype or not know the exact paper title/name → the LLM gets a wrong/ambiguous input and may hallucinate or produce a poor answer.
  2. Users phrase requests inconsistently (one asks for "5 lines," another for "math-heavy," another for "code-heavy") → no consistent user experience across users, even though the app's whole value is in the quality/format of its summaries.
⭐ Interview Important — Dynamic Prompt (the fix):
A dynamic prompt is a prompt template designed in advance by the developer, with a few explicit placeholders. Instead of a free-text box, the UI constrains the user to fixed choices (e.g., dropdowns for: which paper, explanation style — Simple / Math-Heavy / Code-Heavy, explanation length — Short / Medium / Long). The selected values fill the template's placeholders at runtime. This removes typos/ambiguity and guarantees every user gets the same structured, high-quality prompt shape.

The example template also explicitly instructs the LLM: include math equations only if present in the source, explain math with simple intuitive code snippets where applicable, add relatable analogies, and — instead of hallucinating — reply "insufficient information available" when a requested piece of information isn't in the paper.

The PromptTemplate Class

From langchain_core.prompts: build a template string with {placeholder} markers, list their names in input_variables, then fill it at runtime:

from langchain_core.prompts import PromptTemplate

template = PromptTemplate(
    template=template_text,   # contains {paper_input}, {style_input}, {length_input}
    input_variables=["paper_input", "style_input", "length_input"],
)
prompt = template.invoke({
    "paper_input": paper_input,
    "style_input": style_input,
    "length_input": length_input,
})
result = model.invoke(prompt)

A large template is best kept out of application code entirely: save it once to a JSON file (template.save("template.json")) and reload it wherever needed (load_prompt("template.json")) — see reason 2 below.

Why Use PromptTemplate Instead of Plain f-strings? (⭐ Interview Important)

An f-string with placeholders can technically do the exact same substitution — so why does LangChain have a dedicated class? Three reasons:

ReasonWhat it gives you
1. Built-in validationPass validate_template=True and LangChain checks, at development time, that every placeholder in the template string exactly matches the names in input_variables — a missing or an extra/misspelled variable name throws an error immediately, instead of silently breaking (or crashing) only later, in production on a live server.
2. ReusabilityA template can be authored once, saved as its own JSON file, and load_prompt()-ed into any other file/page of the app that needs it — avoids duplicating a big prompt string inline everywhere and keeps the template as a single source of truth.
3. Ecosystem integrationA PromptTemplate object can be combined directly with a model into a Chain — e.g., a chain built from the steps [template, model] — so a single chain.invoke({...}) call replaces two separate calls (one to fill the template, one to call the model). A plain f-string cannot participate in a Chain this way. (Chains are covered in full in a later video.)

Messages: Why a Chatbot Needs Role-Labeled History

Building a minimal console chatbot: a while True loop reads user input, sends it to model.invoke(), prints result.content, and exits on typing "exit." No template is needed here since nothing in the prompt is templatized — it's just the raw user string sent as-is (a static prompt).

⭐ Interview Important — The stateless-LLM problem, demonstrated:
Each invoke() call is independent — the model has no memory of earlier turns. Demonstrated live: asking "which is greater, 2 or 0?" → correctly answers "2"; then asking "now multiply the bigger number by 10" → the model has no idea "the bigger number" refers to 2 (answers symbolically, e.g. "if the bigger number is x, then 10x"), because that context from the previous turn was never sent.

Fix, attempt 1: maintain a running chat_history list; append every user message and every AI response to it; send the entire list to model.invoke() on each turn (LangChain's invoke() accepts either a single string or a list of messages). This correctly restores context — the follow-up "multiply the bigger number by 10" now resolves to 20.

⭐ Interview Important — Remaining problem: history needs role labels.
Storing chat history as a flat list of raw content strings loses who said what — there's no way to tell which entries came from the user and which came from the AI. As the conversation grows, this ambiguity makes it harder for the LLM to reliably track the conversation. The fix is to label every entry with its role.
⭐ Interview Important — The 3 Message Types in LangChain:
  • SystemMessage — a one-time, top-of-conversation instruction that sets the LLM's persona/role/behavior (e.g., "You are a helpful assistant" / "You are an experienced doctor").
  • HumanMessage — a message sent by the user (e.g., "What is the capital of India?").
  • AIMessage — a message returned by the model (e.g., "The capital of India is New Delhi.").
Imported from langchain_core.messages. Rebuilding the chatbot with these classes: start chat_history with a SystemMessage; each turn appends HumanMessage(content=user_input), then, after the call, AIMessage(content=result.content). Now every entry is unambiguously labeled, no matter how long the conversation grows.

ChatPromptTemplate — Dynamic Lists of Messages

⭐ Interview Important: ChatPromptTemplate is the dynamic counterpart of PromptTemplate — used when you need a list of messages where one or more of them (e.g., the system persona, or the human question) has a placeholder to fill at runtime. Example: SystemMessage = "You are a helpful {domain} expert," HumanMessage = "Explain in simple terms what is {topic}."
⭐ Interview Important — A known gotcha:
Building a ChatPromptTemplate by passing already-constructed SystemMessage(content="...{domain}...") / HumanMessage(content="...{topic}...") objects directly does not fill their placeholders — LangChain treats a pre-built message's content as final text, so invoke() leaves the literal {domain}/{topic} unfilled. This is called out in the video as inconsistent/immature behavior in the library.

Correct, recommended approach (per current LangChain docs): describe each message as a (role, template_string) tuple instead of a Message object:

from langchain_core.prompts import ChatPromptTemplate

chat_template = ChatPromptTemplate([
    ("system", "You are a helpful {domain} expert"),
    ("human", "Explain in simple terms, what is {topic}"),
])
prompt = chat_template.invoke({"domain": "cricket", "topic": "doosra"})

This correctly substitutes both placeholders. ChatPromptTemplate.from_messages([...]) with the same tuple list produces the identical result — either syntax works, but tuples (not raw Message objects) are required for placeholders to actually fill.

MessagesPlaceholder — Injecting a Stored Chat History

⭐ Interview Important — Definition:
MessagesPlaceholder is a special slot inside a ChatPromptTemplate used to dynamically insert an entire previously stored list of messages (a chat history) at runtime — not just a single value like other placeholders.

Motivating example: a customer-support chatbot. On day 1, a customer asks for a refund and the bot replies; that exchange (as HumanMessage/AIMessage objects) is saved externally (a database in production; a plain text file in the demo). On day 2, the same customer starts a new chat session and asks "Where is my refund?" — answering this correctly requires first reloading yesterday's saved conversation as context, then combining it with today's new question inside the same template.

from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

chat_template = ChatPromptTemplate([
    ("system", "You are a helpful customer support agent"),
    MessagesPlaceholder(variable_name="chat_history"),
    ("human", "{query}"),
])

# chat_history loaded from file/DB as a list of HumanMessage/AIMessage objects
prompt = chat_template.invoke({
    "chat_history": chat_history,
    "query": "Where is my refund?",
})

The resulting prompt is the fully assembled, correctly ordered message list — system message, then every prior saved turn, then today's new question — ready to send to the LLM, which can now resolve "my refund" using yesterday's context.

Video 7: Structured Output — TypedDict, Pydantic & JSON Schema

Previous video covered input to an LLM (Prompts). This video and the next cover processing the LLM's output. Big motivation: this unlocks LLMs talking to other machines/systems (databases, APIs, tools) — not just humans — and is foundational for AI Agents (covered later).

What Is Structured Output?

⭐ Interview Important — Definition:
By default, an LLM's response is plain text (unstructured output — text has no enforced structure). Structured output means having the language model return its response in a well-defined data format (e.g. JSON) instead of free text, so the output is easy to parse and work with programmatically.

Example: prompt "Create a one-day travel itinerary for Paris" → unstructured reply is a paragraph of prose. A structured reply instead returns a JSON list of {time, activity} objects — directly loopable/storable in code.

Why Do We Need Structured Output? (⭐ Interview Important — 3 use cases)

Use CaseExample
Data ExtractionA job portal (e.g. Naukri.com) extracts fields (name, last company, 10th/12th marks, college marks) from an uploaded resume's raw text and inserts them into a database.
Building APIsAn e-commerce app (e.g. Amazon) turns long unstructured product reviews into structured fields — key themes discussed, pros, cons, overall sentiment — then exposes that as an API (via Flask/FastAPI) for anyone to consume.
Building AI AgentsAgents act via tools (e.g. a calculator tool), and tools expect structured arguments, not raw text. "Find the square root of 2" must first become structured data like {"operation": "sqrt", "value": 2} before it can be sent to the calculator tool.
⭐ Interview Important — The core benefit: Previously, LLMs could only talk to humans (text in, text out — both sides understood prose). Since raw LLM output is unstructured text, it could not be wired into other systems. Structured output gives the LLM's response a data format, which is what lets an LLM talk to other machines (databases, APIs) — not just humans.

Two Ways to Get Structured Output

Some LLMs (e.g. OpenAI's GPT models) are trained to natively emit structured output when asked. Others have no such built-in capability at all.

The with_structured_output() Function

⭐ Interview Important: Only one change to the usual flow: instead of calling model.invoke(...) directly, first call model.with_structured_output(schema) to get a new "structured model," then call .invoke(...) on that. The schema can be defined 3 ways: TypedDict, Pydantic, or JSON Schema.
⭐ Interview Important — What happens behind the scenes: Passing a schema to with_structured_output causes LangChain to auto-generate a hidden system prompt (roughly: "You are an AI assistant that extracts structured insights from text... return the response in JSON format" + the schema's field descriptions), which gets prepended to your actual input before it reaches the model. Since the underlying model is trained to return JSON on request, it replies in JSON — which LangChain then parses into a Python dict/object for you.

Schema Style 1: TypedDict

⭐ Interview Important — Definition:
TypedDict (from Python's typing module) lets you define what keys a dictionary should have and what data type each value should be — giving your editor/IDE type hints. Key limitation: it performs no runtime validation — if you declare a field as int but assign it a str, Python raises no error; the code still runs.
from typing import TypedDict

class Person(TypedDict):
    name: str
    age: int

new_person: Person = {"name": "Nitish", "age": 32}  # editor hints types; nothing enforces them at runtime

Applied to extracting structured data from a phone review (key themes, summary, sentiment, pros/cons, reviewer name):

from typing import TypedDict, Annotated, Optional, Literal
from langchain_openai import ChatOpenAI

class Review(TypedDict):
    key_themes: Annotated[list[str], "Write down all the key themes discussed in the review in a list"]
    summary: Annotated[str, "A brief summary of the review"]
    sentiment: Annotated[Literal["pos", "neg"], "Return sentiment of the review, either negative or positive"]
    pros: Annotated[Optional[list[str]], "Write down all the pros inside a list"]
    cons: Annotated[Optional[list[str]], "Write down all the cons inside a list"]
    name: Annotated[Optional[str], "Write the name of the reviewer"]

model = ChatOpenAI()
structured_model = model.with_structured_output(Review)
result = structured_model.invoke(review_text)
print(result["summary"])       # plain dict access
print(result["sentiment"])
⭐ Interview Important — Annotated and Optional:
  • Annotated[type, "description"] attaches a human-readable description to a field. Without it, the LLM may still infer the right behavior from the field name alone (e.g. summary is fairly unambiguous), but a description removes ambiguity and reduces the chance of the LLM misinterpreting a field — this description text becomes part of the hidden system prompt sent to the model.
  • Optional[...] marks a field as not guaranteed to be present (e.g. a review may not mention any cons, or not state the reviewer's name) — the key may simply be absent/None in the result rather than forcing the LLM to fabricate a value.
  • Literal["pos", "neg"] restricts a field to a fixed set of exact values (here, forcing the sentiment field to only ever be "pos" or "neg", never a full word or a third option like "neutral").
⭐ Interview Important — Prompting still matters even with a schema: Marking a field Optional is a hint, not a hard rule — demonstrated live: even after removing "cons" content from the review text, the model still generated a cons list by inferring negatives from the review's wording. Getting the model to reliably omit a field may still require an explicit instruction (e.g. "do not include cons unless explicitly mentioned").

Schema Style 2: Pydantic

⭐ Interview Important — Definition:
Pydantic is a data validation and data parsing library for Python — commonly used with FastAPI. Unlike TypedDict, Pydantic actually enforces the types/constraints you declare and raises an error if violated, making it the more powerful/reliable choice for LLM structured output.
from pydantic import BaseModel

class Student(BaseModel):
    name: str = "Nitish"           # default value

new_student = {"name": 32}          # wrong type
student = Student(**new_student)    # raises: "Input should be a valid string"

Key Pydantic Features (⭐ Interview Important)

FeatureWhat it does
Default valuesname: str = "Nitish" — used if no value is supplied.
Optional fieldsage: Optional[int] = None — field may be absent; falls back to None (must explicitly default to None, unlike TypedDict).
Runtime validationPassing an int where str is declared (or vice versa where coercion isn't possible) raises an error immediately — this is the core difference from TypedDict.
Type coercionIf a value is convertible, Pydantic auto-converts it rather than erroring — e.g. age sent as the string "32" is silently coerced to the integer 32.
Built-in validatorsSpecial types like EmailStr validate format automatically (e.g. rejects "abc", accepts "abc@gmail.com").
Field() functionAttach constraints (gt=, lt=), default values, a description, or even regex patterns to a field.

from pydantic import BaseModel, Field, EmailStr
from typing import Optional

class Student(BaseModel):
    name: str = "Nitish"
    age: Optional[int] = None
    email: EmailStr
    cgpa: float = Field(gt=0, lt=10, default=5,
        description="A decimal value representing the CGPA of the student")

new_student = {"age": "32", "email": "abc@gmail.com"}   # age as string
student = Student(**new_student)   # age auto-coerced to int 32; name falls back to default

student_dict = student.model_dump()
student_json = student.model_dump_json()

Applied to the same review-extraction task — identical structure to the TypedDict version, but each field uses Pydantic's Field(description=...) instead of Annotated:

from pydantic import BaseModel, Field
from typing import Optional, Literal

class Review(BaseModel):
    key_themes: list[str] = Field(description="Write down all the key themes discussed in the review in a list")
    summary: str = Field(description="A brief summary of the review")
    sentiment: Literal["positive", "negative"] = Field(description="Return sentiment of the review, either negative or positive")
    pros: Optional[list[str]] = Field(default=None, description="Write down all the pros inside a list")
    cons: Optional[list[str]] = Field(default=None, description="Write down all the cons inside a list")
    name: Optional[str] = Field(default=None, description="Write the name of the reviewer")

structured_model = model.with_structured_output(Review)
result = structured_model.invoke(review_text)
print(result.summary)      # dot access — it's a Pydantic object, not a dict

Note the access pattern change: a TypedDict/JSON-schema result is accessed like a dict (result["summary"]); a Pydantic result is accessed via dot notation (result.summary), since it returns an actual Pydantic object.

Schema Style 3: JSON Schema

⭐ Interview Important — When to use: Use JSON Schema when the schema needs to be shared across multiple programming languages in the same project (e.g. a Python backend + a JavaScript frontend) — JSON is a universal, language-agnostic data format that both sides can read, unlike TypedDict/Pydantic which are Python-only.

A JSON Schema needs: title, an optional description, a type (an object/dict-shaped schema is typed "object"), a properties block listing every field (with its own type and description), and a required array naming which fields must be present.

{
  "title": "Student",
  "description": "Schema about students",
  "type": "object",
  "properties": {
    "name": { "type": "string" },
    "age": { "type": "integer" }
  },
  "required": ["name"]
}

The equivalent of the review schema in JSON Schema form (excerpt — same 6 fields as the TypedDict/Pydantic versions): key_themes/pros/cons are typed as "array" of "string" (optional fields allow "array" or "null"); sentiment uses "enum": ["positive", "negative"] instead of Pydantic's Literal; required lists key_themes, summary, sentiment. Passed the same way:

structured_model = model.with_structured_output(json_schema)   # a Python dict holding the JSON schema
result = structured_model.invoke(review_text)
print(result["key_themes"])   # plain dict access, same as TypedDict

  • Pydantic — use when you need data validation, default values, or automatic type coercion (e.g. guarding against the LLM occasionally sending a slightly wrong type).   • method parameter of with_structured_output: controls how the model is asked to produce structured output.

What Are Output Parsers?

⭐ Interview Important — Definition:
Output Parsers are classes in LangChain that help convert raw LLM responses (plain text) into structured formats like JSON, CSV, or Pydantic models. They ensure consistency, (optionally) validation, and ease of use in applications.
⭐ Interview Important — Output Parsers vs. with_structured_output: Output Parsers work with both categories of models — those that natively support structured output and those that don't. with_structured_output only works with the former. This is the main reason Output Parsers still matter even after learning with_structured_output.

LangChain ships many output parsers (CSV, list, datetime, enum, markdown, an "output-fixing" parser that retries malformed output, etc.) but four cover the vast majority of real use cases — this video focuses on those four:

  1. StrOutputParser
  2. JsonOutputParser
  3. StructuredOutputParser
  4. PydanticOutputParser

1. StrOutputParser

⭐ Interview Important — Definition:
The simplest output parser. It takes the LLM's response object and extracts just the plain string content — nothing more.

Without it, every LLM call returns a response object bundled with metadata (token usage, completion tokens, model name, etc.), forcing you to always write result.content to get the actual text. StrOutputParser does that extraction for you — its real value shows up once you chain multiple LLM calls together.

Motivating Example: Two Chained LLM Calls

Task: (1) ask the LLM for a detailed report on a topic, (2) feed that report back into the LLM asking for a 5-line summary.

Without a parser — every intermediate step needs manual .content extraction:

template1 = PromptTemplate(template="Write a detailed report on {topic}", input_variables=["topic"])
template2 = PromptTemplate(template="Write a 5 line summary on the following text:\n{text}", input_variables=["text"])

prompt1 = template1.invoke({"topic": "black hole"})
result = model.invoke(prompt1)

prompt2 = template2.invoke({"text": result.content})   # manual .content extraction
result = model.invoke(prompt2)

print(result.content)                                   # manual .content extraction again

With StrOutputParser and a Chain — no manual extraction anywhere:

from langchain_core.output_parsers import StrOutputParser

parser = StrOutputParser()
chain = template1 | model | parser | template2 | model | parser
result = chain.invoke({"topic": "black hole"})
print(result)
⭐ Interview Important — Why this matters: A Chain (LangChain's core pipeline concept) only works cleanly when each step's raw output is immediately usable as the next step's input. The parser sits between the model and the next template in the pipeline, stripping away metadata so the report text can flow straight into the summary template — without it, this single-chain approach wouldn't be possible at all; you'd need to break it into two separate chains with manual extraction in between.

2. JsonOutputParser

⭐ Interview Important — Definition:
Forces the LLM to respond in JSON format, and parses that JSON string into a Python dict. The quickest possible way to get JSON output from an LLM — but with no control over the JSON's internal structure (see flaw below).

Key mechanic: parser.get_format_instructions() returns an auto-generated instruction string (e.g. "Return a JSON object") that gets injected into the prompt template as a partial variable — a placeholder filled at template-construction time (via a function call), not at invoke()/runtime like a regular input variable.

from langchain_core.output_parsers import JsonOutputParser
from langchain_core.prompts import PromptTemplate

parser = JsonOutputParser()

template = PromptTemplate(
    template="Give me the name, age and city of a fictional person \n{format_instruction}",
    input_variables=[],
    partial_variables={"format_instruction": parser.get_format_instructions()},
)

prompt = template.format()
result = model.invoke(prompt)
final_result = parser.parse(result.content)
print(final_result["name"])   # a plain dict

# Equivalently, as a chain (parser.parse is called automatically):
chain = template | model | parser
final_result = chain.invoke({})   # empty dict required even with zero input variables
⭐ Interview Important — Biggest flaw: JsonOutputParser gets you a JSON object, but you cannot enforce its internal schema (key names / nesting) — the LLM decides that on its own. Demonstrated live: asking for "5 facts about a topic" returned {"facts_about_black_holes": [...]} (one key holding a list) rather than a requested {"fact_1": ..., "fact_2": ..., "fact_3": ...} shape — no way to force the latter.

3. StructuredOutputParser

⭐ Interview Important — Definition:
An output parser that extracts structured JSON from LLM responses based on a predefined field schema. Unlike JsonOutputParser, you provide the schema up front (via a list of ResponseSchema objects), and the LLM follows it — this is the core difference and its main benefit over JsonOutputParser: schema enforcement.
from langchain.output_parsers import StructuredOutputParser, ResponseSchema

schema = [
    ResponseSchema(name="fact_1", description="Fact 1 about the topic"),
    ResponseSchema(name="fact_2", description="Fact 2 about the topic"),
    ResponseSchema(name="fact_3", description="Fact 3 about the topic"),
]
parser = StructuredOutputParser.from_response_schemas(schema)

template = PromptTemplate(
    template="Give 3 facts about {topic} \n{format_instruction}",
    input_variables=["topic"],
    partial_variables={"format_instruction": parser.get_format_instructions()},
)

chain = template | model | parser
result = chain.invoke({"topic": "black hole"})
# {"fact_1": "...", "fact_2": "...", "fact_3": "..."}
⭐ Interview Important — langchain vs. langchain_core: StructuredOutputParser/ResponseSchema import from langchain.output_parsers, not langchain_core — unlike the other three parsers here. langchain is the overall "umbrella" library; langchain_core is a smaller library holding only the most important, most reused components. StructuredOutputParser wasn't considered reusable/important enough to live in langchain_core, so it stays in the main langchain package.
⭐ Interview Important — Biggest flaw: StructuredOutputParser enforces the shape of the JSON but performs no data validation on values. E.g. declaring an "age" field intended as an integer does not stop the LLM from returning a string like "35 years" — there is no mechanism here to catch or coerce that.

4. PydanticOutputParser

⭐ Interview Important — Definition:
A structured output parser that uses a Pydantic model (BaseModel) to enforce schema and validate data when processing LLM responses. Combines the best of both previous parsers: schema enforcement (like StructuredOutputParser) plus real data validation/type coercion (like Pydantic itself, covered in the previous video).
from langchain_core.output_parsers import PydanticOutputParser
from pydantic import BaseModel, Field

class Person(BaseModel):
    name: str = Field(description="Name of the person")
    age: int = Field(gt=18, description="Age of the person")
    city: str = Field(description="Name of the city the person belongs to")

parser = PydanticOutputParser(pydantic_object=Person)

template = PromptTemplate(
    template="Generate the name, age and city of a fictional {place} person \n{format_instruction}",
    input_variables=["place"],
    partial_variables={"format_instruction": parser.get_format_instructions()},
)

chain = template | model | parser
final_result = chain.invoke({"place": "Sri Lankan"})
print(final_result)   # a validated Person object — age is guaranteed a valid int > 18

Core mechanic is unchanged from the earlier parsers: get_format_instructions() auto-generates a detailed instruction block (JSON-schema-shaped) describing the exact fields/types/constraints, and that text is injected into the prompt as a partial variable — the model then replies to that expanded prompt, and parser.parse(...) (or the chain, automatically) turns the JSON text into a validated Person instance.

What & Why

Any LLM application is built from several small steps. Even a minimal app has three: (1) take a prompt from the user, (2) send it to the LLM, (3) process and display the LLM's response.

⭐ Interview Important — The problem chains solve:
Without chains, each step must be invoked manually and individually — build the prompt with prompt.invoke(), manually pass its output to model.invoke(), then manually pass the model's response to a parser. This is workable for a small app but becomes very hard to manage as an application grows to many steps.
⭐ Interview Important — Definition:
A chain lets you connect the small steps of an LLM application into a pipeline. The defining property of a pipeline: the output of one step automatically becomes the input of the next step. Once built, you only provide input to the first step and trigger the pipeline — every downstream step fires automatically in sequence, and you get the final step's output back.

Simple Chain

App: take a topic from the user, generate 5 interesting facts about it.

from langchain_openai import ChatOpenAI
from langchain_core.prompts import PromptTemplate
from langchain_core.output_parsers import StrOutputParser
from dotenv import load_dotenv

load_dotenv()

prompt = PromptTemplate(
    template="Generate 5 interesting facts about {topic}",
    input_variables=["topic"],
)
model = ChatOpenAI()
parser = StrOutputParser()

chain = prompt | model | parser

result = chain.invoke({"topic": "cricket"})
print(result)
⭐ Interview Important — LCEL (LangChain Expression Language): The | (pipe) operator syntax used to declaratively wire components into a chain (prompt | model | parser) is called LangChain Expression Language. It's a declarative way of saying "my pipeline starts at the prompt, then goes to the model, then goes to the parser." Full internal mechanics covered in the next video (Runnables).

Any chain can be visualized with chain.get_graph().print_ascii() — it prints the pipeline's steps in order, useful for debugging/understanding a chain you didn't write.

3. Conditional Chain

App: given product feedback, classify its sentiment (positive/negative), then reply differently depending on which sentiment was found — only one of the two reply paths ever runs per call (unlike parallel chains, where both always run).

Step A — Structuring the classifier's output

⭐ Interview Important — Why a plain string won't work here: Classifying with StrOutputParser gives no guarantee about the exact returned text — the LLM might return "negative", or a full sentence like "the sentiment is negative", inconsistently across calls. Since the next branching step's logic depends on comparing this value exactly (e.g. == "positive"), the output must be structured/constrained, not free text.

Solution: a Pydantic schema with a Literal["positive", "negative"] field, parsed via PydanticOutputParser, so the sentiment value is always consistently one of exactly those two words.

from langchain_core.output_parsers import PydanticOutputParser, StrOutputParser
from pydantic import BaseModel, Field
from typing import Literal

class Feedback(BaseModel):
    sentiment: Literal["positive", "negative"] = Field(
        description="Give the sentiment of the feedback"
    )

parser2 = PydanticOutputParser(pydantic_object=Feedback)

prompt1 = PromptTemplate(
    template="Classify the sentiment of the following feedback text into positive or negative \n {feedback} \n {format_instruction}",
    input_variables=["feedback"],
    partial_variables={"format_instruction": parser2.get_format_instructions()},
)

classifier_chain = prompt1 | model | parser2

Step B — Branching with RunnableBranch

⭐ Interview Important — RunnableBranch: The Runnable used to build if/elif/else-style logic between chains. Takes multiple (condition, chain) tuples, checked in order, plus one final default chain that runs if no condition matched.
⭐ Interview Important — RunnableLambda: A plain Python function (e.g. a lambda) is not a Runnable/chain by itself and cannot be plugged into RunnableBranch directly. RunnableLambda wraps that function, converting it into a Runnable so it can be used as the default/fallback chain.
from langchain_core.runnables import RunnableBranch, RunnableLambda

prompt2 = PromptTemplate(
    template="Write an appropriate response to this positive feedback \n {feedback}",
    input_variables=["feedback"],
)
prompt3 = PromptTemplate(
    template="Write an appropriate response to this negative feedback \n {feedback}",
    input_variables=["feedback"],
)

branch_chain = RunnableBranch(
    (lambda x: x.sentiment == "positive", prompt2 | model | parser),
    (lambda x: x.sentiment == "negative", prompt3 | model | parser),
    RunnableLambda(lambda x: "could not find sentiment"),
)

chain = classifier_chain | branch_chain

result = chain.invoke({"feedback": "This is a terrible smartphone"})
print(result)

Why Do Runnables Exist? (A Flashback)

⭐ Interview Important — Origin, problem 1 (model fragmentation): Around ChatGPT's Nov-2022 release, OpenAI opened its APIs to the public, and the LangChain team foresaw that LLM-based applications would explode in demand. Soon multiple companies (OpenAI, Anthropic, Google, Mistral, ...) each shipped LLMs with differently-behaving APIs. LangChain's first big win: build standardized wrapper classes per provider, so any engineer can talk to any company's LLM with minimal code changes.

This made LangChain popular. The LangChain team then noticed a second gap: talking to the LLM is only a small part of a real LLM application. A "chat with your PDF" app, for example, needs many more steps:

  1. Load the document (e.g. from cloud storage)
  2. Split it into chunks (by chapter/page/paragraph)
  3. Generate an embedding for each chunk
  4. Store the embeddings in a vector database
  5. Build a retriever that semantically searches for the most relevant chunk(s)
  6. Send the retrieved chunk + query to the LLM
  7. Display the LLM's response
⭐ Interview Important — Origin, problem 2 (missing components) → solution: LangChain's team broke every LLM-app use case they could find into small reusable parts, and shipped a dedicated component class for each: Document Loaders, Text Splitters, Embedding Models, Vector Stores, Retrievers, Output Parsers, Memory — in addition to the LLM/Prompt components. This is what turned LangChain into a genuinely powerful library: an AI engineer could now pick up these components and wire them together into almost any LLM application.

Demonstrated live: a simple LLM app (topic → prompt → LLM → display) and a full PDF-reader/RAG app (load → split → embed → store → retrieve → prompt → LLM → display) were both built in just a few dozen lines of code, purely by plugging these components together.

The Chains Idea — and Its Eureka Moment

The LangChain team then noticed something common across every LLM app built this way: certain component sequences repeat constantly. The most universal one — build a prompt, then send it to the LLM — appears in literally every app (chatbot, PDF reader, agent, ...).

⭐ Interview Important — Birth of Chains: Instead of engineers manually calling prompt_template.format(...) and then llm.predict(...) by hand every time, the team built a built-in function that takes an LLM + a prompt template and automatically does both steps internally. Since this connects two-or-more components into a pipeline, they called this pattern a Chain — and the simplest one, connecting just a prompt + an LLM, was called LLMChain.

The team kept finding more repeating patterns and kept shipping matching chain classes — e.g. RetrievalQA chain (LLM + retriever → automatically does semantic search, prompt-merging, and LLM call for a RAG app). A PDF-reader app that took ~36 lines of manual code dropped to ~32 lines using RetrievalQA — but more importantly, the whole retrieval task became a single reusable call.

The Problem: Too Many Chains

The team didn't stop at two chains — they kept analyzing use cases and shipping a new chain class for each one: SimpleSequentialChain, SequentialChain, chains for SQL databases, APIs, math problems, and many more (LangChain's docs list dozens; this is not an exhaustive list).

⭐ Interview Important — The two disadvantages of "too many chains":
  1. Codebase bloat — a huge number of chain classes meant a huge, hard-to-maintain codebase.
  2. Steep learning curve — new AI engineers struggled to know which of 50+ chain types to use for a given use case, making LangChain harder to learn, not easier.

Ironically, the team's original intent was to help engineers combine components like Lego blocks — plug any two together seamlessly, for any workflow. Instead, they ended up hand-writing a bespoke "chain" class per use case.

Root Cause (⭐ Interview Important)

⭐ Interview Important: LangChain's components were built independently, with no shared interface — each was designed in isolation and exposed a different method name for "do your job":
ComponentMethod used to interact with it
LLM.predict(prompt)
Prompt Template.format(input_dict)
Retriever.get_relevant_documents(query)
Output Parser.parse(response)

Because no two components spoke the same "language," connecting any pair required hand-written glue code — and that glue code is exactly what each Chain class was. Every new use case meant writing yet another custom chain. The fix: rebuild every component so they all follow one common, standardized interface — this is exactly what Runnables are.

What Are Runnables? (⭐ Interview Important — Definition)

⭐ Interview Important: A Runnable is best understood as a unit of work: it takes some input, processes it, and returns an output. Every Runnable in LangChain has four defining characteristics:
  1. Represents a single unit of work — one component, one job.
  2. Follows a common interface — every Runnable exposes the same set of methods, regardless of what it does internally. The most important is invoke() (single input → single output); also batch() (process multiple inputs → multiple outputs at once) and stream() (get output as a stream, token by token).
  3. Composable — because every Runnable shares the same interface, any two (or more) Runnables can be connected; the first's output automatically becomes the second's input, forming arbitrarily complex workflows.
  4. A composed workflow is itself a Runnable — connect R1→R2→R3 into "Workflow A," and R4→R5 into "Workflow B": both workflows are themselves valid Runnables, so they too can be connected into an even bigger workflow — recursively, without limit.

Dummy components with non-standard methods

import random

class FakeLLM:

Used manually: template.format({"topic": "India"}) builds the prompt string, then llm.predict(prompt) gets a response — two separate manual calls, exactly the pain point described above.

A "Chain" class to automate the two calls (mirrors real LLMChain)

class FakeLLMChain:
    def __init__(self, llm, prompt):
        self.llm = llm
        self.prompt = prompt

    def run(self, input_dict):
        final_prompt = self.prompt.format(input_dict)
        result = self.llm.predict(final_prompt)
        return result["response"]

chain = FakeLLMChain(llm=FakeLLM(), prompt=template)
print(chain.run({"length": "short", "topic": "India"}))
⭐ Interview Important — Why this "chain" approach doesn't scale: FakeLLMChain works for exactly this one use case, but it is not flexible. E.g. a "generate a joke, then explain the joke" app needs two LLM calls — there's no reasonable way to write generic code inside .run() that handles an arbitrary number of calls, because the underlying components (.format() vs. .predict()) don't share an interface. This is precisely why LangChain's team kept having to write a brand-new chain class per use case.

Code Demo, Part 2 — The Fix: Standardize via an Abstract Base Class

Solution: force every component to inherit from one abstract class and implement the same method (invoke), using Python's ABC/abstractmethod.

from abc import ABC, abstractmethod

class Runnable(ABC):
    @abstractmethod
    def invoke(self, input_data):
        pass
class FakeLLM(Runnable):
    def __init__(self):
        print("LLM created")

    def invoke(self, prompt):
        response_list = [
            "Delhi is the capital of India",
            "IPL is a cricket league",
            "AI stands for Artificial Intelligence",
        ]
        return {"response": random.choice(response_list)}

    def predict(self, prompt):
        # kept for backward compatibility with old code that still calls .predict()
        print("This method is deprecated, please use invoke instead")
        return self.invoke(prompt)


class FakePromptTemplate(Runnable):
    def __init__(self, template, input_variables):
        self.template = template
        self.input_variables = input_variables

    def invoke(self, input_dict):
        return self.template.format(**input_dict)

    def format(self, input_dict):
        # kept for backward compatibility with old code that still calls .format()
        print("This method is deprecated, please use invoke instead")
        return self.invoke(input_dict)
⭐ Interview Important: Subclassing an ABC with an @abstractmethod forces every subclass to implement invoke() — trying to instantiate a subclass that skips it raises TypeError: Can't instantiate abstract class ... with abstract method invoke. This is the mechanism LangChain relies on to guarantee every component shares the same interface. Old methods (predict, format) aren't deleted outright (that would break existing users' code) — they're kept as thin wrappers around invoke() with a deprecation notice, a realistic API-evolution pattern.

RunnableConnector — chaining any list of standardized components

class RunnableConnector(Runnable):
    def __init__(self, runnable_list):
        self.runnable_list = runnable_list

    def invoke(self, input_data):
        for runnable in self.runnable_list:
            input_data = runnable.invoke(input_data)
        return input_data

template = FakePromptTemplate(
    template="Write a {length} poem about {topic}",
    input_variables=["length", "topic"],
)
llm = FakeLLM()

chain = RunnableConnector([template, llm])
print(chain.invoke({"length": "long", "topic": "India"}))

Adding a third standardized component extends the same chain with zero new custom code:

class FakeStrOutputParser(Runnable):
    def invoke(self, input_data):
        return input_data["response"]

parser = FakeStrOutputParser()
chain = RunnableConnector([template, llm, parser])
print(chain.invoke({"length": "long", "topic": "India"}))
# now prints a plain string instead of a dict

1. RunnableSequence

⭐ Interview Important — Definition: Connects two or more Runnables sequentially — the first Runnable's output automatically becomes the next Runnable's input. No limit on how many Runnables can be chained this way.
from langchain_openai import ChatOpenAI
from langchain_core.prompts import PromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain.schema.runnable import RunnableSequence
from dotenv import load_dotenv

load_dotenv()

prompt = PromptTemplate(template="Write a joke about {topic}", input_variables=["topic"])
model = ChatOpenAI()
parser = StrOutputParser()

chain = RunnableSequence(prompt, model, parser)
print(chain.invoke({"topic": "AI"}))

Extending to a longer sequential chain (generate a joke, then explain it — six Runnables total):

prompt1 = PromptTemplate(template="Write a joke about {topic}", input_variables=["topic"])
prompt2 = PromptTemplate(template="Explain the following joke {text}", input_variables=["text"])

chain = RunnableSequence(prompt1, model, parser, prompt2, model, parser)
print(chain.invoke({"topic": "AI"}))
# only the FINAL step's output (the explanation) is printed — the joke itself isn't surfaced
⭐ Interview Important: In a plain RunnableSequence, only the last step's output is returned — an intermediate result (like the joke itself, before its explanation) is not automatically exposed. Solving that need is exactly what RunnablePassthrough (below) is for.

2. RunnableParallel

⭐ Interview Important — Definition: Executes multiple Runnables in parallel. Every branch receives the same input and processes it independently; the combined result comes back as a dictionary keyed by each branch's name.

Example: from one topic, generate a tweet (via one LLM/prompt) and a LinkedIn post (via another) at the same time.

from langchain.schema.runnable import RunnableSequence, RunnableParallel

prompt1 = PromptTemplate(template="Generate a tweet about {topic}", input_variables=["topic"])
prompt2 = PromptTemplate(template="Generate a Linkedin post about {topic}", input_variables=["topic"])
model = ChatOpenAI()
parser = StrOutputParser()

parallel_chain = RunnableParallel({
    "tweet": RunnableSequence(prompt1, model, parser),
    "linkedin": RunnableSequence(prompt2, model, parser),
})

result = parallel_chain.invoke({"topic": "AI"})
print(result["tweet"])
print(result["linkedin"])

3. RunnablePassthrough

⭐ Interview Important — Definition: A special Runnable that returns its input completely unchanged — no processing at all. passthrough.invoke(2) returns 2; passthrough.invoke({"name": "nitish"}) returns that same dict back.

Why it's useful: in a sequential chain, only the last step's output survives. If you need an earlier intermediate value to also appear in the final output (e.g. the joke itself, alongside its explanation), route that value through a RunnablePassthrough branch inside a RunnableParallel, in parallel with the branch that keeps processing it further.

from langchain.schema.runnable import RunnableSequence, RunnableParallel, RunnablePassthrough

prompt1 = PromptTemplate(template="Write a joke about {topic}", input_variables=["topic"])
prompt2 = PromptTemplate(template="Explain the following joke {text}", input_variables=["text"])
model = ChatOpenAI()
parser = StrOutputParser()

joke_gen_chain = RunnableSequence(prompt1, model, parser)

parallel_chain = RunnableParallel({
    "joke": RunnablePassthrough(),
    "explanation": RunnableSequence(prompt2, model, parser),
})

final_chain = RunnableSequence(joke_gen_chain, parallel_chain)
result = final_chain.invoke({"topic": "cricket"})
print(result)   # {"joke": "...", "explanation": "..."}

4. RunnableLambda

⭐ Interview Important — Definition: Converts any plain Python function (including a lambda) into a Runnable — so custom logic that isn't one of LangChain's built-in components can still be plugged into a chain and connected to other Runnables.

Common use cases mentioned: text pre-processing before an LLM call (lowercasing, removing HTML tags/punctuation/emojis, lemmatization) so "dirty" data doesn't degrade LLM performance; or, as demoed, deterministic post-processing an LLM shouldn't be trusted to do itself (e.g. counting words).

from langchain.schema.runnable import RunnableLambda

def word_counter(text):
    return len(text.split())

runnable_word_counter = RunnableLambda(word_counter)
print(runnable_word_counter.invoke("hi my name is nitish"))   # 5

# equivalent, more compact form (the reason it's called "Runnable-Lambda"):
runnable_word_counter = RunnableLambda(lambda x: len(x.split()))

Plugged into a chain — generate a joke, and report its word count alongside it, without asking the LLM to count (LLMs are unreliable at counting):

joke_gen_chain = RunnableSequence(prompt, model, parser)

parallel_chain = RunnableParallel({
    "joke": RunnablePassthrough(),
    "word_count": RunnableLambda(lambda x: len(x.split())),
})

final_chain = RunnableSequence(joke_gen_chain, parallel_chain)
result = final_chain.invoke({"topic": "AI"})

final_result = "{} \nword count - {}".format(result["joke"], result["word_count"])
print(final_result)

Structurally this is the same passthrough-plus-parallel-branch shape as above, with the second branch being a RunnableLambda instead of a full LLM sub-chain — {"joke": RunnablePassthrough(), "word_count": RunnableLambda(...)} replaces {"joke": ..., "explanation": ...}.

5. RunnableBranch

⭐ Interview Important — Definition: LangChain's if/else construct for Runnables — routes execution down exactly one of several branches based on a condition, useful whenever downstream processing depends on some property of the upstream output (e.g. classify a customer email as complaint / refund request / general query, and handle each differently).

Demo: generate a detailed report on a topic; if the report exceeds 500 words, summarize it with another LLM call; otherwise, print it as-is.

from langchain.schema.runnable import RunnableSequence, RunnableBranch, RunnablePassthrough

prompt1 = PromptTemplate(template="Write a detailed report on {topic}", input_variables=["topic"])
prompt2 = PromptTemplate(template="Summarize the following text \n {text}", input_variables=["text"])
model = ChatOpenAI()
parser = StrOutputParser()

report_gen_chain = RunnableSequence(prompt1, model, parser)

branch_chain = RunnableBranch(
    (lambda x: len(x.split()) > 500, RunnableSequence(prompt2, model, parser)),
    RunnablePassthrough(),   # default: report is short enough, print as-is
)

final_chain = RunnableSequence(report_gen_chain, branch_chain)
print(final_chain.invoke({"topic": "Russia vs Ukraine"}))
⭐ Interview Important — RunnableBranch syntax: Takes any number of (condition, runnable) tuples, checked in order — like if/elif — plus one final Runnable (no condition) that acts as the else/default. Each condition is itself just a function (often a lambda) receiving the previous step's output.

LCEL — LangChain Expression Language

⭐ Interview Important: The LangChain team noticed that building a RunnableSequence is by far the most common pattern — it shows up inside parallel branches, passthrough branches, branch arms, everywhere. So they introduced a shorter, declarative syntax for exactly this case: the | (pipe) operator.
# these two are equivalent:
chain = RunnableSequence(prompt, model, parser)
chain = prompt | model | parser

This pipe syntax — LCEL — is confirmed to work as a drop-in replacement everywhere a RunnableSequence is used, including nested inside a RunnableBranch tuple.

⭐ Interview Important — current scope of LCEL: As of this video, the declarative | syntax exists only for RunnableSequence. RunnableParallel, RunnableBranch, etc. must still be written out explicitly (e.g. as a dict for parallel). The presenter's expectation (speculative, not a confirmed roadmap item): future LangChain versions may extend LCEL with declarative syntax for the other primitives too (e.g. a hypothetical R1 & R2 for parallel execution).

What Is RAG? (⭐ Interview Important)

Plain chat-based LLM tools (e.g. ChatGPT) fail in specific situations:

  • Current affairs — the model was trained on data up to some past cutoff, so it can't know about today's/yesterday's events.
  • Personal data — e.g. questions about your own recent emails, which the model has never seen.
  • Private/internal data — e.g. questions about your company's internal documentation.
⭐ Interview Important — Definition:
RAG is a technique that combines information retrieval with language generation: a model retrieves relevant documents from an external knowledge base and then uses them as context to generate accurate, grounded responses.

The "external knowledge base" can be anything — a company database, a pile of PDFs, personal documents — connected to the LLM so it can look up an answer it doesn't already know.

⭐ Interview Important — Benefits of RAG:
  1. Up-to-date information — answers can reflect current, non-training data.
  2. Privacy — sensitive/confidential documents never need to be uploaded to a third-party chat tool; they stay in your own connected knowledge base.
  3. No document size limit — a huge document doesn't fit in an LLM's context window if uploaded whole, but RAG splits it into chunks and only retrieves the relevant ones per query.

The Four Core RAG Components (⭐ Interview Important)

Almost any RAG application, however complex, is built from just four components: Document Loaders, Text Splitters, Vector Databases, and Retrievers. This video covers the first: Document Loaders. The rest follow in later videos, before finally building a full RAG application.

What Are Document Loaders? (⭐ Interview Important)

⭐ Interview Important — Definition:
Document Loaders are LangChain components used to load data from various sources into a standardized format — usually as Document objects — which can then be used for chunking, embedding, retrieval, and generation.

Data can live in wildly different sources (PDFs, text files, databases, cloud storage...). Every Document Loader's job is to fetch from its specific source and hand back data in the exact same shape: a Document object, containing:

  • page_content — the actual text content.
  • metadata — surrounding info such as source, creation/modification date, author, page number, etc.
⭐ Interview Important: Every Document Loader in LangChain, regardless of source, returns its result as a list of Document objects — this is a universal pattern worth memorizing before learning any individual loader.

All document loaders live in the langchain_community.document_loaders package (community-contributed and maintained).

1. TextLoader

The simplest loader — reads a plain text file and wraps it as a single Document. Good for log files, code snippets, or transcripts (e.g. a YouTube transcript saved as .txt).

from langchain_community.document_loaders import TextLoader

docs = loader.load()

print(type(docs))          # <class 'list'>
print(len(docs))           # 1
print(type(docs[0]))       # <class 'langchain_core.documents.base.Document'>
print(docs[0].page_content)
print(docs[0].metadata)

Feeding the loaded text straight into a chain (e.g. summarize the loaded poem):

What Is Text Splitting & Why It Matters (⭐ Interview Important)

⭐ Interview Important — Definition:
Text splitting is the process of breaking large chunks of text (articles, PDFs, HTML pages, books) into smaller, manageable pieces that an LLM can handle effectively. The code/component that does this is a Text Splitter.

Four concrete reasons text splitting is essential when building LLM-powered applications:

  1. Model context-length limits — every LLM has a maximum input size (e.g. 50,000 tokens). A document with 100,000+ words simply cannot be sent in one call; splitting is the only way to process it at all.
  2. Better embeddings — embedding a very large piece of text into one vector captures its semantic meaning poorly (too much is being compressed into too few numbers). Splitting into smaller chunks and embedding each separately captures meaning much more precisely (e.g. a paragraph about CSK, one about RCB, one about MI embed far better as three separate chunks than as one).
  3. Better semantic search — search accuracy against chunked, separately-embedded documents is empirically better than searching over one giant embedded blob.
  4. Better summarization & other downstream tasks — LLMs given a very large document to summarize can drift off-topic or even hallucinate content not present in the source; splitting first and processing chunk-by-chunk gives more reliable results.
  5. Computational efficiency — smaller chunks need less memory and can be processed in parallel.

Four text-splitting techniques are covered: length-based, text-structure-based, document-structure-based, and semantic-meaning-based.

1. Length-Based Text Splitting

⭐ Interview Important — Definition: The simplest and fastest splitting method. You pre-decide a fixed chunk size (in characters or tokens) and the splitter walks through the text, cutting a new chunk every time that size is reached — with zero regard for words, sentences, or meaning.
from langchain.text_splitter import CharacterTextSplitter

splitter = CharacterTextSplitter(
    chunk_size=100,
    chunk_overlap=0,
    separator="",   # cut purely on character count
)
chunks = splitter.split_text(text)
print(len(chunks))
print(chunks[0])

Combined with a Document Loader (splitting an already-loaded PDF's pages):

from langchain_community.document_loaders import PyPDFLoader

loader = PyPDFLoader("dl-curriculum.pdf")
docs = loader.load()

chunks = splitter.split_documents(docs)   # note: split_documents, not split_text
print(chunks[0].page_content)             # each chunk is itself still a Document object
⭐ Interview Important — Pros/Cons: Advantage: conceptually trivial, easy to implement, very fast. Disadvantage: ignores linguistic structure, grammar, and meaning entirely — text routinely gets cut mid-word, mid-sentence, or mid-paragraph, which can badly hurt embedding quality since related information ends up split across two disconnected chunks. Rarely used in practice for this reason.

chunk_overlap

⭐ Interview Important — Definition: The number of characters repeated at the boundary between two consecutive chunks. Its purpose is to prevent context loss at a cut: each new chunk starts a little before the previous one ended, so information that would otherwise be split awkwardly is preserved in both chunks.
⭐ Interview Important — Trade-off & rule of thumb: More overlap → more preserved context, but more total chunks → more compute. Less overlap → cheaper, but more risk of losing context at cuts. Rough guideline for RAG applications: overlap of 10–20% of chunk_size (e.g. chunk_size 100 → overlap 10–20).

2. Text-Structure-Based Splitting (RecursiveCharacterTextSplitter)

⭐ Interview Important — Definition: Exploits the fact that text is inherently hierarchically organized — paragraphs, made of sentences, made of words, made of characters. This is one of the most widely used text splitters in LangChain.

It tries a sequence of separators, from coarsest to finest, falling back only when a piece still exceeds chunk_size:

⭐ Interview Important: After breaking at a given level, the algorithm greedily re-merges adjacent small pieces back together (without exceeding chunk_size) so chunks are as large as allowed while still respecting structure — this is why increasing chunk_size makes it naturally settle at paragraph-level splits, while a very small chunk_size forces it down to word- or character-level splits.
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(chunk_size=100, chunk_overlap=0)
chunks = splitter.split_text(text)
print(len(chunks))
print(chunks[0])
⭐ Interview Important: This is the most commonly used text splitter in practice, because it respects sentence/paragraph boundaries far better than plain length-based splitting, which usually means better downstream context preservation.

3. Document-Structure-Based Splitting

⭐ Interview Important: Some documents aren't plain natural-language text organized into paragraphs/sentences — e.g. source code (organized by class/def/loops) or Markdown (organized by headings/lists). This technique is really just RecursiveCharacterTextSplitter with a different, language-aware separator list in place of paragraph/sentence separators.
from langchain.text_splitter import RecursiveCharacterTextSplitter, Language

python_splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.PYTHON,
    chunk_size=300,
    chunk_overlap=0,
)
chunks = python_splitter.split_text(python_code)
print(chunks[0])   # e.g. everything up through the class's constructor

Same idea works for Markdown (splitting at headings) and many other languages (JavaScript, Java, PHP, HTML, ...) via Language.MARKDOWN, Language.JS, etc. — LangChain ships separator presets per language/format.

md_splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.MARKDOWN,
    chunk_size=200,
    chunk_overlap=0,
)
⭐ Interview Important: As with plain RecursiveCharacterTextSplitter, chunk_size must be tuned per document — too small and even a code file gets cut mid-construct; a well-chosen size lets the splitter land cleanly on structural boundaries (e.g. one chunk = one class's constructor, one chunk = one method).

4. Semantic-Meaning-Based Splitting

Both length-based and structure-based splitting can fail on a specific case: a single paragraph that actually covers multiple unrelated topics (e.g. one paragraph discussing both agriculture and, mid-paragraph, cricket — followed by a second paragraph about terrorism). Splitting purely by paragraph/sentence boundaries would still lump the two unrelated agriculture/cricket ideas into one chunk.

⭐ Interview Important — Definition: Semantic-meaning-based splitting decides where to split based on the actual meaning of the text, not its length or structure. It embeds each sentence, then compares the embedding similarity of each consecutive sentence pair using a sliding window; wherever similarity suddenly drops, that's treated as a topic boundary and a split point.

How "suddenly low" is decided: a threshold type is configured — common options are percentile, standard deviation, interquartile range, or gradient. E.g. with standard deviation: compute the similarity (or distance) for every consecutive sentence pair, take the standard deviation of that whole set of numbers, and treat any pair whose distance exceeds N standard deviations as a break point.

from langchain_experimental.text_splitter import SemanticChunker
from langchain_openai import OpenAIEmbeddings

splitter = SemanticChunker(
    OpenAIEmbeddings(),
    breakpoint_threshold_type="standard_deviation",
    breakpoint_threshold_amount=1,   # split wherever distance > 1 standard deviation
)
docs = splitter.create_documents([text])
print(len(docs))
⭐ Interview Important: SemanticChunker currently lives in langchain_experimental, not the main library — it's explicitly experimental. Raising the threshold (e.g. to 3 standard deviations) makes the splitter much more tolerant of context change, producing fewer/larger chunks; lowering it produces more, smaller chunks. In hands-on testing, results were inconsistent (topic boundaries sometimes landed in the wrong chunk) — promising, but not yet as reliable as RecursiveCharacterTextSplitter.

Video 14: Vector Stores & Chroma DB

Third of the four core RAG components: Vector Stores.

Why Vector Stores? A Movie Recommender Case Study

Motivating example: building an IMDb-style movie catalog site with a recommender ("if you liked this movie, you'll like these too").

⭐ Interview Important — Naive approach and its flaw: keyword matching. A simple recommender compares movies on metadata fields (director, actor, genre, release date) — if enough of these match, the movies are called "similar."
  • False positive: My Name Is Khan and Kabhi Alvida Naa Kehna share director (Karan Johar), lead actor (Shah Rukh Khan), similar era, and genre (drama) — so keyword matching rates them highly similar. But their actual stories are completely different, so this is a bad recommendation.
  • False negative: Taare Zameen Par and A Beautiful Mind are thematically very similar (a central character with a struggle who is also brilliant in another way) but share almost no metadata keywords (different director, actor, era) — so keyword matching would never surface them as similar, even though they should be.
⭐ Interview Important — The fix: compare plot/story via embeddings, not keywords. If two movies' plots are semantically similar, the movies are similar — regardless of who directed/acted in them. This requires: (1) each movie's full plot text, (2) an embedding model to convert each plot into a numerical vector capturing its meaning, (3) comparing vectors (e.g. via cosine similarity / angular distance) to find the closest ones.

Three Challenges of Building This — Solved by Vector Stores (⭐ Interview Important)

  1. Generating embeddings — potentially millions of movies each need an embedding vector generated.
  2. Storage — these vectors are generated once and reused repeatedly for similarity search; but a normal relational database (MySQL, Oracle) can't compute similarity between vectors — a different, purpose-built kind of storage is needed.
  3. Efficient semantic search — naively comparing a query vector against every one of, say, 1,000,000 stored vectors (linear, O(n) search) is far too slow for real applications.
⭐ Interview Important: All three challenges are exactly what a Vector Store is built to solve.

What Is a Vector Store? (⭐ Interview Important)

⭐ Interview Important — Definition:
A vector store is a system designed to store and retrieve data represented as numerical vectors.

Four key features of any vector store:

  1. Storage — stores vectors and their associated metadata, either in-memory (fast, non-persistent — gone when the app closes) or on-disk (persistent — survives restarts; used for larger/production-scale applications).
  2. Similarity search — retrieves the vectors most similar to a given query vector.
  3. Indexing — a data structure/method enabling fast similarity search over high-dimensional vectors, so you don't have to linearly compare against every stored vector.
  4. CRUD operations — add, retrieve, update, and delete vectors, same as any database.

How Indexing Works — a Clustering Example

Comparing a query vector against 1,000,000 stored vectors one-by-one is O(n) and far too slow. A common indexing approach: cluster all vectors first (e.g. via a clustering algorithm), then only search within the most relevant cluster.

Use Cases

Recommender systems, semantic search over any domain, RAG applications (heavy use — covered in depth soon), and search over images/other multimedia. Any application storing/retrieving vectors will perform far better with a vector store than with a traditional relational database, which isn't built for vector storage or similarity computation.

Vector Store vs. Vector Database (⭐ Interview Important)

These two terms are frequently used interchangeably online, which is a common source of confusion.

⭐ Interview Important — The distinction: A vector store is a lightweight library/service focused on just two things: storing vectors and performing similarity search. A vector database is a vector store plus traditional database-style features: distributed architecture (for scaling), durability (backup/restore), ACID transactions, concurrency control (multiple simultaneous users), and authentication/authorization.
⭐ Interview Important: Every vector database is a vector store, but not every vector store is a vector database. Lightweight vector-store examples: FAISS (Facebook), ideal for prototyping/small-scale apps. Full vector-database examples: Milvus, Qdrant, Weaviate, Pinecone — used in production, at scale.

Vector Stores in LangChain (⭐ Interview Important)

⭐ Interview Important: LangChain's creators anticipated early that embedding vectors — and therefore vector stores/databases — would be central to LLM applications (especially RAG). So LangChain ships wrapper components for essentially every major vector store (FAISS, Pinecone, Chroma, Qdrant, Weaviate, ...), and critically, all these wrappers share the same method signatures (from_documents/from_texts to create, add_documents/add_texts to insert, similarity_search to query, metadata filtering, etc.). This means swapping the underlying vector store (e.g. Chroma → Pinecone as an app scales) requires almost no code changes elsewhere.

Chroma DB

⭐ Interview Important — Definition: Chroma is a lightweight, open-source vector database, especially friendly for local development and small-to-medium production needs. It sits between a pure vector store and a full vector database — lighter than something like Pinecone, but with more database-like structure than a minimal library like FAISS.

Chroma's data hierarchy: Tenant (a user/organization/team) → can create multiple Databases → each Database can hold multiple Collections (conceptually like a table in a relational DB) → each Collection stores multiple Documents, where each Document is an embedding vector plus its metadata.

What Are Retrievers? (⭐ Interview Important)

⭐ Interview Important — Definition:
A retriever is a component in LangChain that fetches relevant documents from a data source in response to a user's query.

A data source can be anything (a vector store, an external API, a website...). The retriever takes a user query, searches the data source, decides which documents are most relevant, and fetches them back.

⭐ Interview Important — Three key points:
  1. LangChain ships many different retrievers (20-30+), not just one — each suited to different data sources or search needs.
  2. Every retriever in LangChain is a Runnable — same as models, prompts, parsers — so it exposes invoke() and can be plugged directly into chains alongside other components.

Two Ways to Categorize Retrievers (⭐ Interview Important)

Categorization axisMeaningExamples
By data sourceWhat kind of source the retriever searches overWikipediaRetriever, Vector Store Retriever, Arxiv Retriever (research papers)
By search strategyWhat mechanism/algorithm the retriever uses to decide relevanceMMR, Multi-Query Retriever, Contextual Compression Retriever

This video covers the most useful retrievers of each kind; LangChain's docs list every retriever type for less common needs.

1. WikipediaRetriever (data-source-based)

⭐ Interview Important — Definition: Queries the Wikipedia API to fetch relevant content for a given query, returned as LangChain Document objects.
from langchain_community.retrievers import WikipediaRetriever

retriever = WikipediaRetriever(top_k_results=2, lang="en")

query = "the geopolitical history of india and pakistan from the perspective of a chinese person"
docs = retriever.invoke(query)

for doc in docs:
    print(doc.page_content)
⭐ Interview Important — Why this is a retriever, not a document loader: It doesn't load all of Wikipedia — internally it performs keyword-based matching against the query to decide which articles are most relevant before fetching only those. That decision-making step (a form of search/intelligence) is exactly what makes it a retriever rather than a loader.

2. Vector Store Retriever (data-source-based)

⭐ Interview Important — Definition: The most common retriever type — searches and fetches documents from a vector store based on semantic similarity via embeddings.
from langchain_openai import OpenAIEmbeddings
from langchain.vectorstores import Chroma

vector_store = Chroma.from_documents(docs, embedding=OpenAIEmbeddings(), collection_name="sample")
retriever = vector_store.as_retriever(search_kwargs={"k": 2})

results = retriever.invoke("What is Chroma used for?")
⭐ Interview Important — "Why not just call vector_store.similarity_search() directly?" You can — for plain similarity search they're equivalent. But similarity_search() only supports that one fixed strategy. Wrapping the vector store as a retriever (via as_retriever()) unlocks two real benefits: (1) it's a Runnable, so it plugs directly into chains; (2) it lets you swap in far more advanced search strategies (MMR, multi-query, contextual compression — below) that plain similarity_search() cannot do.

3. Maximum Marginal Relevance (MMR) — search-strategy-based

Problem with plain similarity search: it can return several top results that are all near-duplicates of each other (e.g. three near-identical "glaciers are melting" documents), wasting the result slots instead of surfacing genuinely different, still-relevant perspectives (deforestation, wildfires, coastal flooding).

⭐ Interview Important — Definition: MMR is an information retrieval algorithm that reduces redundancy in retrieved results while maintaining high relevance to the query. It picks the most relevant document first, then repeatedly picks the next document that is both relevant and as dissimilar as possible from what's already been picked.
retriever = vector_store.as_retriever(
    search_type="mmr",
    search_kwargs={"k": 3, "lambda_mult": 0.5},
)
results = retriever.invoke("What is Langchain?")
⭐ Interview Important — lambda_mult parameter: Ranges 0 to 1. 1 makes MMR behave exactly like plain similarity search (no diversity push); 0 maximizes diversity. A middle value (e.g. 0.5) balances relevance and diversity — this is the value to tune per use case.

4. Multi-Query Retriever — search-strategy-based

Problem: a user's query can be ambiguous — e.g. "How can I stay healthy?" could mean diet, exercise, or stress management — and a single vague query produces poor, unfocused search results.

⭐ Interview Important — Definition: Reduces query ambiguity by using an LLM to generate several reworded/related versions of the original query, running each through the base retriever, then merging and de-duplicating all the results into one final set.
from langchain.retrievers.multi_query import MultiQueryRetriever

similarity_retriever = vector_store.as_retriever(search_type="similarity", search_kwargs={"k": 5})

multiquery_retriever = MultiQueryRetriever.from_llm(
    retriever=vector_store.as_retriever(search_kwargs={"k": 5}),
    llm=ChatOpenAI(),
)

query = "How to improve energy levels and maintain balance?"
print(similarity_retriever.invoke(query))    # can drift — e.g. a stray "solar system" doc slips in
print(multiquery_retriever.invoke(query))    # stays focused on health/nutrition
⭐ Interview Important — Demonstrated result: Against a mixed document store (health/nutrition docs plus unrelated docs about the solar system, Python, etc.), a deliberately ambiguous query ("How to improve energy levels and maintain balance?") caused plain similarity search to mistakenly pull in an unrelated "solar system" document (its text happened to also mention "energy" and "balance"). MultiQueryRetriever avoided this — all 5 results stayed correctly focused on health/nutrition, because the LLM-generated query variants disambiguated intent before searching.

5. Contextual Compression Retriever — search-strategy-based

Problem: a single stored document/chunk can accidentally mix multiple unrelated topics (common when a text splitter cuts mid-paragraph) — e.g. one chunk covering both the Grand Canyon and photosynthesis. A query about photosynthesis correctly matches that chunk, but returning the whole chunk also hands the user irrelevant Grand Canyon text, hurting answer quality and wasting context length.

⭐ Interview Important — Definition: An advanced retriever that improves retrieval quality by compressing documents after retrieval — an LLM-based compressor strips each retrieved document down to only the parts relevant to the query, discarding the rest.
from langchain.retrievers.contextual_compression import ContextualCompressionRetriever
from langchain.retrievers.document_compressors import LLMChainExtractor

base_retriever = vector_store.as_retriever(search_kwargs={"k": 5})
compressor = LLMChainExtractor.from_llm(ChatOpenAI())

compression_retriever = ContextualCompressionRetriever(
    base_retriever=base_retriever,
    base_compressor=compressor,
)

docs = compression_retriever.invoke("What is photosynthesis?")
for doc in docs:
    print(doc.page_content)
# each result is now a single trimmed sentence about photosynthesis —
# the unrelated Grand Canyon / basketball / cinema sentences sharing the same
# original chunk are discarded
⭐ Interview Important — When to use it: Documents are long and may contain mixed information; you want to reduce how much context reaches the LLM (saving context-length budget); or you want to directly improve a RAG pipeline's answer accuracy.

Other Retrievers & Why So Many Exist

Additional retrievers not covered in depth here: Parent Document Retriever, Time-Weighted Vector Retriever, Self-Query Retriever, Ensemble Retriever, Multi-Retriever, and more — look these up in LangChain's retriever docs when a specific project need arises.

⭐ Interview Important — The real reason so many retrievers exist: A basic RAG system's out-of-the-box retrieval quality is often mediocre. The standard way to improve it is to swap the plain retriever for a more advanced one (MMR, multi-query, contextual compression, or others) and rebuild/re-test — this iterative retriever-swapping is the main lever used to improve a RAG pipeline's real-world performance. Video 16: RAG — Why It's Needed & How It Works

A conceptual deep dive (first of two RAG videos — the next builds a RAG system from scratch in LangChain). Goal: understand why RAG exists — via the history of what was tried before it — and exactly how a RAG pipeline works, step by step.

Why RAG? — LLMs and Parametric Knowledge

⭐ Interview Important — Parametric knowledge: LLMs are transformer-based neural networks pre-trained on massive amounts of data (roughly internet-scale). All the "knowledge" this produces is stored purely as numbers — the model's weights and biases. This is why it's called parametric knowledge, and why more parameters (7B → 13B → 70B...) generally means a more knowledgeable/capable model.

A user accesses this knowledge via prompting: send a prompt → the LLM interprets it → generates a response word-by-word by drawing on its parametric knowledge. This works well most of the time, but fails in three specific situations:

ProblemWhy it happens
1. Private dataAsking an LLM about your own company's internal docs, personal emails, or a specific course's video content — the model never saw this data during pre-training, so it cannot answer.
2. Recent / current dataEvery LLM has a knowledge cutoff date from pre-training. Questions about anything after that date (today's news, a just-released product) can't be answered from parametric knowledge alone. (ChatGPT can answer some current-events questions only because it has separate internet-search access — a base/open-source model without that access cannot.)
3. HallucinationLLMs generate text probabilistically, not by fact-lookup — so they can state fabricated information with high confidence (e.g. inventing that Einstein played football professionally). This isn't rare noise; it's an inherent risk of how generation works.

Attempt 1: Fine-Tuning

⭐ Interview Important — Definition: Fine-tuning takes an already-pretrained LLM and continues training it on a smaller, domain-specific dataset — so the model gains specialized knowledge on top of its general pre-trained knowledge.

Analogy: pre-training is like an engineering degree (broad foundational knowledge); fine-tuning is like a company's 2-3 month on-the-job training (narrow, job-specific skill on top of that foundation).

Types of Fine-Tuning

TypeHow it works
Supervised Fine-Tuning (SFT)Most common. Train on a labeled dataset of (prompt, desired output) pairs — typically 1,000 to 1,000,000 pairs.
Continued Pre-trainingUnsupervised — no labels; feed raw domain text (e.g. all your course transcripts) and continue training the same way pre-training worked, just on a smaller, domain-specific corpus.
RLHFReinforcement Learning from Human Feedback — teaches the model how to behave appropriately in real-world scenarios.
LoRA / QLoRAParameter-efficient fine-tuning techniques — freeze the base model's weights and train only a small additional set of weights, instead of retraining everything.

Supervised Fine-Tuning — 4 Steps (⭐ Interview Important)

  1. Collect domain data — a labeled dataset of (prompt, desired output) pairs.
  2. Choose a method — full-parameter fine-tuning (retrain all weights) vs. a parameter-efficient method like LoRA/QLoRA (freeze base weights, train a small additional set).
  3. Train — for a limited number of epochs (computationally expensive, so not trained excessively long).
  4. Evaluate — check exact-match accuracy against desired outputs, factuality, hallucination rate, safety, etc.

How Fine-Tuning Addresses the Three Problems — and Its Own Three Problems

Fine-tuning can solve all three: training on private data makes it part of the model's parametric knowledge; training on updated data helps with recency (within a specific domain); training with examples of "don't know → say so" reduces hallucination.

⭐ Interview Important — Why fine-tuning isn't always practical:
  1. Computationally expensive — training even a "small" dataset against a huge pretrained model costs real money/compute.
  2. Requires strong technical expertise — proper ML/AI engineers and data scientists are needed to run this correctly.
  3. Must be repeated for every update — e.g. every time a course catalog changes, fine-tuning has to be redone, and redone again for removals — costly and impractical for fast-changing domains.

Attempt 2: In-Context Learning

⭐ Interview Important — Definition: A core capability of large language models (GPT-3, Claude, LLaMA, ...) where the model learns to solve a task purely by seeing examples inside the prompt itself — without any weight updates at all.

Example (sentiment analysis via few-shot prompting):

Below are examples of text labeled with their sentiment. Use the examples to
determine the sentiment of the final text.

"I love this phone. It's so smooth." → Positive
"This app crashes a lot." → Negative
"The camera is amazing." → Positive
"I hate the battery life." → ?

The model infers the pattern from the examples and correctly answers "Negative" — without ever being retrained. The same technique works for other tasks (Named Entity Recognition, math problems, domain-specific tasks) just by showing example input/output pairs in the prompt.

⭐ Interview Important — In-context learning is an emergent property: An emergent property is a behavior that suddenly appears in a system once it crosses a certain scale/complexity threshold, without being explicitly designed for. Smaller models (GPT-1, GPT-2) did not reliably show in-context learning. Only once models reached GPT-3's scale (~175 billion parameters) did this capability reliably emerge — this is exactly what the landmark paper "Language Models are Few-Shot Learners" (the GPT-3 paper) documented and named.

That paper's core argument: standard NLP practice at the time (pre-train, then fine-tune per task) requires large labeled datasets (10,000–1,000,000 rows) per task, which is costly — whereas humans can generally learn a new task from just a few examples and simple instructions. The authors showed GPT-3 could do the same directly from prompt examples, no retraining needed. Later models (3.5, 4, ...) improved further on this via SFT and RLHF-style alignment.

From In-Context Learning to RAG

⭐ Interview Important — The key upgrade: Instead of giving the LLM a few generic examples of how to solve a task (few-shot prompting), give it the actual context needed to answer this specific query — injected directly into the prompt. This is exactly RAG.

Worked example: a 2-hour lecture on Linear Regression; a student's doubt is specifically about Gradient Descent (say, covered from minute 5 to minute 25). Rather than sending the whole 2-hour transcript, send only the relevant ~20-minute segment's transcript as context, alongside the student's question.

⭐ Interview Important — Definition:
RAG (Retrieval-Augmented Generation) is a way to make a language model smarter by giving it extra information at the time you ask your question.
You are a helpful assistant. Answer the question only from the provided context.
If the context is insufficient, just say "I don't know."

Context: {retrieved transcript segment}
Question: {student's question}

How RAG Works: The 4-Stage Pipeline (⭐ Interview Important)

At a high level, RAG marries two old ideas: Information Retrieval (a classic computer-science field) and Text Generation (popularized by LLMs). It breaks into four stages:

Stage 1 — Indexing

⭐ Interview Important — Definition: The process of preparing your knowledge base so it can be efficiently searched at query time. This builds the external knowledge base that context gets derived from — covered in full detail across the last four videos (Document Loaders, Text Splitters, Vector Stores, Retrievers). Four sub-steps:
  1. Document ingestion — load the source knowledge into memory (e.g. via LangChain's document loaders: PyPDFLoader, a YouTube loader, WebBaseLoader, ...) from wherever it lives (a server, Google Drive, S3, ...).
  2. Text chunking — split the large loaded text into smaller, semantically meaningful chunks (via a text splitter, e.g. RecursiveCharacterTextSplitter) — necessary because of LLM context-length limits and because semantic search quality is poor over huge blobs of text.
  3. Generate embeddings — convert each chunk into a dense vector capturing its semantic meaning, via an embedding model (OpenAI embeddings, sentence-transformer embeddings, ...).
  4. Store in a vector store — save each vector alongside its original chunk text and metadata in a vector database (FAISS, Chroma, Pinecone, Weaviate, Milvus, Qdrant, ...) — this vector store is the external knowledge base RAG draws context from.

Stage 2 — Retrieval

⭐ Interview Important — Definition: The real-time process of finding the most relevant pieces of information from the pre-built index, based on the user's question — "of everything I know, which 3-5 chunks are most helpful to answer this?"

Performed by a retriever component in four sub-steps:

  1. Convert the user's query into an embedding vector, using the same embedding model used during indexing (same dimensionality, comparable space).
  2. Search the vector store for the vectors closest to the query vector — a plain semantic/similarity search, or a more advanced strategy (MMR, contextual compression, ...).
  3. Rank the matched vectors by closeness (e.g. cosine similarity, or a more advanced re-ranking algorithm).
  4. Fetch the top-ranked chunks' original text — this becomes the context.

Stage 3 — Augmentation

⭐ Interview Important: The step where the user's query and the retrieved context are combined into a single prompt — this is literally where the LLM's parametric knowledge gets "augmented" with the extra retrieved knowledge.

Stage 4 — Generation

⭐ Interview Important: The augmented prompt is sent to the LLM, which uses its text-generation capability plus in-context learning to read the injected context and produce a response grounded in it.

How RAG Solves All Three Original Problems (⭐ Interview Important)

ProblemHow RAG solves it
Private dataThe external knowledge base is built directly from your own data — so retrieved context, and therefore the answer, naturally comes from your data.
Recent / current dataJust add new documents to the knowledge base (embed + store) — no retraining required at all, unlike fine-tuning.
HallucinationThe prompt explicitly instructs the model to answer only from the provided context, and to say "I don't know" when the context is insufficient — this grounds responses against real retrieved text instead of free-form generation.

RAG vs. Fine-Tuning (⭐ Interview Important)

⭐ Interview Important: RAG is generally cheaper and simpler than fine-tuning for these problems: no model training is involved at all — updating the knowledge base just means loading new documents into the vector store, not retraining weights. Fine-tuning remains useful for other goals (e.g. changing a model's behavior/style, not just its knowledge), but for keeping an LLM answering correctly about private, fast-changing, or grounding-sensitive information, RAG is the more practical default.

Video 17: Building a RAG System From Scratch — "YouTube Chat"

The practical follow-up to the previous conceptual video: building a real RAG pipeline in LangChain end-to-end, using the exact 4-stage architecture (Indexing → Retrieval → Augmentation → Generation) already covered.

Problem Statement

"YouTube Chat" — a system that lets you chat in real time with any YouTube video (ask whether a topic was discussed, request a summary, resolve a doubt about a specific part) instead of having to watch the whole thing, which matters most for long videos/podcasts (2-3+ hours).

Possible finished-product forms: a Chrome extension (needs HTML/CSS/JS), or a Streamlit website (paste a video URL, get a chat window). This video deliberately skips UI and focuses purely on the RAG functionality, built and run inside a Google Colab notebook.

Plan of Action (⭐ Interview Important — maps directly onto the 4-stage RAG architecture)

  1. Indexing — fetch the video's transcript → split it into chunks → embed the chunks → store them in a vector store.
  2. Retrieval — build a retriever; given a query, it embeds the query and semantically searches the vector store for the most relevant chunks.
  3. Augmentation — merge the retrieved chunks and the original query into a single prompt.
  4. Generation — send that prompt to an LLM and return its response.

The video builds each stage manually first (calling each piece by hand), then wires everything into a single LangChain chain so one invoke() call runs the whole pipeline automatically.

Step 1a — Fetching the Transcript

⭐ Interview Important: Rather than LangChain's own YoutubeLoader (found to be buggy/inconsistent across videos), this uses the youtube-transcript-api Python package directly against YouTube's own transcript API — more reliable in practice.
from youtube_transcript_api import YouTubeTranscriptApi, TranscriptsDisabled

video_id = "Gfr50f6ZBvo"  # only the ID from the URL, not the full link

try:
    transcript_list = YouTubeTranscriptApi.get_transcript(video_id, languages=["en"])
    transcript = " ".join(chunk["text"] for chunk in transcript_list)
except TranscriptsDisabled:
    print("No captions available for this video.")
⭐ Interview Important: The raw API returns a list of dictionaries, one per subtitle line, each with its text, a start timestamp, and a duration (how long it stays on screen) — exactly mirroring how captions actually appear/disappear during playback. These must be joined into one long string before further processing. If a video has no English captions (e.g. a Hindi video), pass languages=["hi"] (or whichever language is actually available) instead.

Step 1b — Text Splitting

from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)
chunks = splitter.create_documents([transcript])
# e.g. a ~2-hour podcast transcript → 168 chunks

Step 1c — Embeddings + Vector Store

from langchain_openai import OpenAIEmbeddings
from langchain_community.vectorstores import FAISS

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
vector_store = FAISS.from_documents(chunks, embeddings)
# each chunk is now assigned an ID and embedded into the vector store

Indexing is now complete: the transcript has been ingested, split, embedded, and stored — this is the external knowledge base the rest of the pipeline draws context from.

Step 2 — Retrieval

retriever = vector_store.as_retriever(search_type="similarity", search_kwargs={"k": 4})

results = retriever.invoke("What is deepmind?")
# returns the 4 chunks the retriever judges most relevant to this query
⭐ Interview Important: Always remember the retriever's contract: input is a query string, output is a list of Document objects — this held true and worked as expected when tested against the loaded transcript.

Step 3 — Augmentation

from langchain_openai import ChatOpenAI
from langchain_core.prompts import PromptTemplate

llm = ChatOpenAI(model="gpt-4o-mini")

prompt = PromptTemplate(
    template="""
      You are a helpful assistant.
      Answer ONLY from the provided transcript context.
      If the context is insufficient, just say you don't know.

      {context}
      Question: {question}
    """,
    input_variables=["context", "question"],
)

question = "Is the topic of nuclear fusion discussed in this video? If yes then what was discussed?"
retrieved_docs = retriever.invoke(question)

A retriever always returns a list of Document objects — but a prompt template needs a single string. So the retrieved documents' page_content must be manually joined:

context_text = "\n\n".join(doc.page_content for doc in retrieved_docs)
final_prompt = prompt.invoke({"context": context_text, "question": question})

Step 4 — Generation

answer = llm.invoke(final_prompt)
print(answer.content)
# e.g. "Yes, the topic of nuclear fusion is discussed in the video. ..."

All four stages now work — but each was called manually and separately (retriever invoked alone, then the prompt, then the LLM). The next step: wire it all into a single LangChain chain so one invoke() call runs the entire pipeline automatically.

Building the Full Chain

⭐ Interview Important — Chain structure: The final chain is really two chains combined. A simple chain (prompt | llm | parser) at the end needs two inputs the prompt template requires: context and question. question passes straight through from the user; context requires an extra step — the question must first go through the retriever, and the resulting document list must be formatted into a single string. This "get both inputs ready in parallel" shape is exactly what RunnableParallel + RunnablePassthrough + RunnableLambda (covered in the Runnable Primitives video) are for.
from langchain_core.runnables import RunnableParallel, RunnablePassthrough, RunnableLambda
from langchain_core.output_parsers import StrOutputParser

def format_docs(retrieved_docs):
    return "\n\n".join(doc.page_content for doc in retrieved_docs)

parallel_chain = RunnableParallel({
    "context": retriever | RunnableLambda(format_docs),
    "question": RunnablePassthrough(),
})

parallel_chain.invoke("Who is Demis?")
# {"context": "...", "question": "Who is Demis?"}
parser = StrOutputParser()
main_chain = parallel_chain | prompt | llm | parser

print(main_chain.invoke("Can you summarize the video?"))
# one call now runs retrieval, augmentation and generation automatically

Why Tools Exist — LLMs Can Think and Speak, But Not Act

⭐ Interview Important: LLMs have exactly two core capabilities: reasoning (breaking down how to answer a question) and language generation (producing the answer word by word). That's it — an LLM cannot fetch live weather data, reliably do complex math, call an external API, post a tweet, run code, or query a database. It literally cannot take real-world action.
⭐ Interview Important — The analogy: An LLM is like a human body with a brain that can think and a mouth that can speak, but no hands or legs — it can't do anything itself.

What Is a Tool? (⭐ Interview Important)

⭐ Interview Important — Definition:
A tool is just a Python function packaged in a way an LLM can understand and call when needed. Tools are the mechanism that gives an LLM "hands and legs" — connect a tool to an LLM, and the LLM can now actually execute that task (e.g. a function that books an IRCTC train ticket) instead of merely describing it.
⭐ Interview Important — Agent definition: An AI agent is an LLM-powered system that can autonomously think, decide, and take actions using external tools and APIs to achieve a goal. This is why Tools are just as foundational to building agents as the LLM itself — hence covering Tools before Tool Calling and Agents.

Built-in vs. Custom Tools

LangChain ships two kinds of tools:

  • Built-in tools — pre-built, production-ready, for popular use cases identified by the LangChain team; just import and use, no logic to write.
  • Custom tools — tools you build yourself for use cases specific to your own application (e.g. your company's internal API).

Building Custom Tools — Method 1: @tool Decorator

A custom tool is needed whenever: you want to call your own application's API (e.g. a travel-booking site's agent needs to actually create bookings); you want to encapsulate business logic unique to your app; or your LLM/agent needs to interact with your own database/product.

⭐ Interview Important — 3-step recipe:
  1. Write the function's logic (a plain Python function).
  2. Add type hints for every input and the return value.
  3. Decorate it with @tool.
Both the docstring (step 1) and type hints (step 2) are technically optional but highly recommended — they're exactly what lets the LLM understand what the tool does and what inputs/outputs it expects.
from langchain_core.tools import tool

@tool
def multiply(a: int, b: int) -> int:
    """Multiply two numbers"""
    return a * b

result = multiply.invoke({"a": 3, "b": 5})
print(result)  # 15

print(multiply.name)          # "multiply"
print(multiply.description)   # "Multiply two numbers"
print(multiply.args)          # {'a': {'title': 'A', 'type': 'integer'}, 'b': {...}}
⭐ Interview Important: Every tool object — built-in or custom — carries these same three attributes: .name, .description, and .args. This is also true for built-in tools like DuckDuckGoSearchRun (its name, description, and expected arguments can be inspected the same way).

What the LLM Actually Sees: the Tool's JSON Schema

⭐ Interview Important: When a tool is connected to an LLM, the LLM never receives the function's code/logic — it receives the tool's JSON schema (name, description, and a JSON-Schema-style spec of its arguments, generated from the docstring and type hints).
print(multiply.args_schema.model_json_schema())

Building Custom Tools — Method 2: StructuredTool + Pydantic

⭐ Interview Important — Definition: A stricter way to build a tool, where the tool's input follows a structured schema typically defined with a Pydantic model — instead of loosely inferring types from Python type hints alone.
from langchain.tools import StructuredTool
from pydantic import BaseModel, Field

class MultiplyInput(BaseModel):
    a: int = Field(required=True, description="The first number to add")
    b: int = Field(required=True, description="The second number to add")

def multiply_func(a: int, b: int) -> int:
    return a * b

multiply_tool = StructuredTool.from_function(
    func=multiply_func,
    name="multiply",
    description="Multiply two numbers",
    args_schema=MultiplyInput,
)

result = multiply_tool.invoke({"a": 3, "b": 3})
⭐ Interview Important: More mature/strict than the @tool decorator — the argument schema, name, and description are all explicitly declared in one place (from_function) rather than inferred from the function signature. Preferred for production-grade agents; the @tool decorator is sufficient for ~80-90% of ordinary use cases.

Building Custom Tools — Method 3: Subclassing BaseTool

⭐ Interview Important: BaseTool is the abstract base class every tool in LangChain ultimately inherits from — it defines the core structure/interface every tool must follow. Both @tool and StructuredTool are themselves built on top of BaseTool. This third method inherits from it directly for maximum control.
from langchain.tools import BaseTool
from typing import Type
from pydantic import BaseModel, Field

class MultiplyInput(BaseModel):
    a: int = Field(required=True, description="The first number to add")
    b: int = Field(required=True, description="The second number to add")

class MultiplyTool(BaseTool):
    name: str = "multiply"
    description: str = "Multiply two numbers"
    args_schema: Type[BaseModel] = MultiplyInput

    def _run(self, a: int, b: int) -> int:
        return a * b

multiply_tool = MultiplyTool()
result = multiply_tool.invoke({"a": 3, "b": 3})
⭐ Interview Important: The method must be named exactly _run — that's the interface BaseTool requires. This approach also uniquely supports defining an async version of a tool (useful for handling concurrency) — a capability neither @tool nor StructuredTool offers.

Toolkits

⭐ Interview Important — Definition: A toolkit is just a collection of related tools that serve a common purpose, packaged together for convenience and reusability (e.g. a "Google Drive Toolkit" bundling an upload tool, a search tool, and a read tool). LangChain ships built-in toolkits, and you can build custom ones the same way.

Video 19: Tool Calling — Binding, Calling & Executing Tools

Direct continuation of the Tools video: how an LLM and a tool actually get connected, and how the LLM invokes a tool when it needs to. This is a foundational step toward building real AI agents.

Recap

LLMs have two core powers — reasoning (breaking down a question) and language generation (producing an answer) — but no ability to act (no live API calls, no reliable math, no database access). Tools are the previously-covered fix: functions packaged so an LLM can understand and request them.

1. Tool Binding

⭐ Interview Important — Definition: Tool binding is the step where one or more tools are registered with an LLM, so the LLM knows: (1) what tools are available, (2) what each tool does (from its description), and (3) what input format/schema each tool expects.
from langchain_core.tools import tool
from langchain_openai import ChatOpenAI

@tool
def multiply(a: int, b: int) -> int:
    """Given 2 numbers a and b this tool returns their product"""
    return a * b

llm = ChatOpenAI()
llm_with_tools = llm.bind_tools([multiply])   # pass a list — can bind multiple tools
⭐ Interview Important: Not every LLM supports tool binding — only certain models have this capability (check LangChain's docs for which chat models support tool calling before relying on it).

2. Tool Calling

⭐ Interview Important — Definition: Tool calling is the process where, during a conversation, the LLM decides it needs a specific tool and generates a structured output naming that tool plus the arguments to call it with.
llm_with_tools.invoke("Hi, how are you?")
# a normal AIMessage with actual text content — no tool needed

response = llm_with_tools.invoke("can you multiply 3 with 10")
print(response.content)     # "" — empty!
print(response.tool_calls)  # [{'name': 'multiply', 'args': {'a': 3, 'b': 10}, 'id': '...', 'type': 'tool_call'}]
⭐ Interview Important: When the LLM decides a tool is needed, .content comes back empty and a new .tool_calls attribute appears instead — a list (multiple tools could be called at once), each entry giving the tool's name, its suggested args, a unique call id, and type: "tool_call".
⭐ Interview Important — Common misconception: The LLM does not actually run the tool. It only suggests the tool name and arguments — actual execution is handled by LangChain/the programmer. This is intentional: letting an LLM freely execute arbitrary tools on its own would be risky (it could pick a wrong or harmful action) — a human/program stays in control of actually running anything.

3. Tool Execution

⭐ Interview Important — Definition: The step where the programmer actually runs the suggested tool, using the exact arguments the LLM proposed during tool calling.
# Option A: pass just the args dict — get the raw return value
result = multiply.invoke(response.tool_calls[0]["args"])   # 30

# Option B: pass the entire tool_call dict — get a ToolMessage back
tool_message = multiply.invoke(response.tool_calls[0])
print(tool_message)
# ToolMessage(content='30', name='multiply', tool_call_id='...')
⭐ Interview Important — ToolMessage: A fourth message type in LangChain (alongside SystemMessage, HumanMessage, AIMessage) — produced when a tool is executed via its full tool-call dict. Its key property: it can be sent straight back to the LLM as part of the conversation, so the LLM can incorporate the tool's real result into its final answer.

Putting It Together: The Full Cycle

Building a running conversation history lets the final answer be grounded in the tool's actual output rather than the LLM guessing:

from langchain_core.messages import HumanMessage

query = HumanMessage("can you multiply 3 with 10")
messages = [query]

ai_message = llm_with_tools.invoke(messages)
messages.append(ai_message)          # [Human, AI(tool_calls=[...])]

tool_result = multiply.invoke(ai_message.tool_calls[0])
messages.append(tool_result)         # [Human, AI, Tool]

final = llm_with_tools.invoke(messages)
print(final.content)   # "The product of 3 and 10 is 30."

Full Example: Real-Time Currency Conversion

A more realistic use case: an LLM can't reliably answer currency-conversion questions because exchange rates fluctuate constantly and it only has stale training-time knowledge. Two tools fix this:

import requests
from langchain_core.tools import tool

@tool
def get_conversion_factor(base_currency: str, target_currency: str) -> float:
    """This function fetches the currency conversion factor between a given base currency and a target currency"""
    url = f"https://v6.exchangerate-api.com/v6/YOUR_API_KEY/pair/{base_currency}/{target_currency}"
    response = requests.get(url)
    return response.json()

@tool
def convert(base_currency_value: int, conversion_rate: float) -> float:
    """Given a currency conversion rate, this function calculates the target currency value from a given base currency value"""
    return base_currency_value * conversion_rate
llm_with_tools = llm.bind_tools([get_conversion_factor, convert])

messages = [HumanMessage(
    "What is the conversion factor between USD and INR, "
    "and based on that can you convert 10 USD to INR?"
)]
ai_message = llm_with_tools.invoke(messages)
messages.append(ai_message)

The Problem: Parallel Tool Calls With a Hidden Dependency

⭐ Interview Important — What went wrong: The LLM generated two tool calls at once for the combined question — get_conversion_factor (correctly) and convert. But convert needs conversion_rate as an input, and the LLM doesn't have that value yet (the first tool hasn't run). Rather than waiting, it hallucinated a plausible-looking rate from its stale training data (e.g. 73.73, an old USD→INR rate) and filled that in — silently breaking the intended sequential logic.

The Fix: InjectedToolArg

⭐ Interview Important — Definition: Marking a tool argument as InjectedToolArg tells the LLM "don't try to fill this in yourself — the developer will supply it after running earlier tools." The LLM then omits that argument from its tool call entirely, leaving it to the program to inject the real value.
from langchain_core.tools import InjectedToolArg
from typing import Annotated

@tool
def convert(base_currency_value: int, conversion_rate: Annotated[float, InjectedToolArg]) -> float:
    """Given a currency conversion rate, this function calculates the target currency value from a given base currency value"""
    return base_currency_value * conversion_rate

Now ai_message.tool_calls shows the convert call with only base_currency_value set — conversion_rate is left for the program to fill in:

import json

for tool_call in ai_message.tool_calls:
    if tool_call["name"] == "get_conversion_factor":
        tool_message_1 = get_conversion_factor.invoke(tool_call)
        conversion_rate = json.loads(tool_message_1.content)["conversion_rate"]
        messages.append(tool_message_1)

    if tool_call["name"] == "convert":
        # inject the real rate before executing this tool
        tool_call["args"]["conversion_rate"] = conversion_rate
        tool_message_2 = convert.invoke(tool_call)
        messages.append(tool_message_2)

final_response = llm_with_tools.invoke(messages)
print(final_response.content)
# "The conversion factor between USD and INR is X. Converting 10 USD to INR yields Y."
⭐ Interview Important: A raw API response is JSON, not a Python dict — tool_message.content must be parsed with json.loads(...) before a key like "conversion_rate" can be accessed from it.

This same pattern — loop over tool_calls, execute each in the correct order, append each resulting ToolMessage to messages, then make one final LLM call with the full history — generalizes to any number of dependent tools.

Is This an AI Agent? (⭐ Interview Important)

⭐ Interview Important — No, and here's why: The defining trait of an AI agent is autonomy — it breaks down a problem and works through it step by step on its own, without a human manually sequencing each call. In this video's currency example, the programmer wrote the loop, decided the execution order, and manually injected the conversion rate — all orchestration was hardcoded, not decided by the LLM itself. A true agent would independently reason: "I don't know the rate yet → call get_conversion_factor first → now I have the rate → call convert next" — with no human pre-wiring that sequence.

Why AI Agents? — The Goa Trip Example

Planning a trip (Delhi → Goa) manually requires visiting multiple sites and making many decisions: booking onward/return train or flight tickets, comparing prices and availability; booking a hotel (comparing price, reviews, breakfast options); researching attractions and building a day-by-day itinerary; booking local transport (e.g. scooter rentals); and handling payments across all of this. It's tedious, multi-step, research-heavy — genuinely hard for someone less comfortable with technology (e.g. an older user) to do alone.

⭐ Interview Important — What an agent changes: Instead of the user doing all of this manually across multiple websites, the user gives a travel agent one high-level goal ("plan a budget trip from Delhi to Goa, May 1st–7th") and the agent autonomously plans and executes each step — searching train/flight APIs and picking the cheapest option, filtering hotels by budget/location/reviews, building a day-by-day itinerary, booking local transport, and finally handling payment, calendar events, and reminders — checking in with the user only for preferences/confirmations along the way.

This is the core value proposition of agents: they make today's clunky, many-step web interactions feel like one natural conversation — hugely reducing user effort, in any domain (customer support, education, travel, etc.), not just travel booking.

What Is an AI Agent, Technically? (⭐ Interview Important)

⭐ Interview Important — Definition:
An AI agent is an intelligent system that receives a high-level goal from a user and autonomously plans, decides, and executes a sequence of actions using external tools, APIs, and knowledge sources — all while maintaining context, reasoning over multiple steps, adapting to new information, and optimizing for the intended outcome.
⭐ Interview Important — The core composition: An AI agent = an LLM (acting as the reasoning engine — understanding natural language, deciding what to do) + Tools (giving it the ability to actually take action — hit APIs, query databases, search the web). The LLM alone can reason and generate text but cannot act; tools alone have no judgment about when to fire. The combination is what makes an agent.

Characteristics of an AI Agent (⭐ Interview Important)

  1. Goal-driven — you state the what, not the how; the agent figures out the steps itself.
  2. Plans and breaks down problems — decomposes a goal into a sequence of steps and executes them one at a time.
  3. Tool-aware — knows which tools are available to it, and knows when each one is appropriate to use.
  4. Maintains context — keeps a memory of what's been done so far and what still needs to happen, across the whole interaction.
  5. Adaptive — if something changes mid-plan (e.g. an API stops working, new information appears), it can replan rather than getting stuck.

Coding a Basic ReAct Agent in LangChain

The example agent is deliberately simple at first: one tool (web search), so the underlying mechanics stay visible before adding complexity.

from langchain_community.tools import DuckDuckGoSearchRun
from langchain_openai import ChatOpenAI

search_tool = DuckDuckGoSearchRun()
llm = ChatOpenAI()

from langchain import hub
from langchain.agents import create_react_agent, AgentExecutor

prompt = hub.pull("hwchase17/react")   # a pre-built ReAct prompt from LangChain Hub

agent = create_react_agent(
    llm=llm,
    tools=[search_tool],
    prompt=prompt,
)

agent_executor = AgentExecutor(
    agent=agent,
    tools=[search_tool],
    verbose=True,   # prints the agent's live thought process
)

response = agent_executor.invoke({"input": "What are the three ways to reach Goa from Delhi?"})
print(response["output"])
⭐ Interview Important — LangChain Hub: A community-shared repository of ready-made prompts (like a "GitHub for prompts") — hub.pull("hwchase17/react") fetches a well-tested ReAct prompt authored by Harrison Chase (LangChain's creator), rather than writing one from scratch.

What Is ReAct? (⭐ Interview Important)

⭐ Interview Important — Definition: ReAct ("Reasoning + Acting") is a design pattern used in AI agents that lets a language model interleave internal reasoning with external actions in a structured, multi-step process — instead of a single-turn "one question → one answer" interaction.

Concretely, ReAct repeatedly cycles through three things until the agent has its final answer:

  • Thought — the agent reasons about what it still needs to find out.
  • Action — the agent picks a tool (and an input) to help with that thought.
  • Observation — the result the tool returns.
⭐ Interview Important — Why ReAct is useful: Excellent for multi-step problems (needing more than one fact/step to answer) and for tasks needing tools (web search, database lookups, APIs). Crucially, its reasoning is transparent and auditable — the user can see the full Thought/Action/Observation trace, not just a final black-box answer. ReAct was introduced in the 2022 paper "ReAct: Synergizing Reasoning and Acting in Language Models."

Agent vs. AgentExecutor (⭐ Interview Important)

⭐ Interview Important: These are easy to conflate as a beginner, but they have distinct jobs. The Agent is the "thinker" — given the user's query and the reasoning trace so far, it generates the next Thought and then either an Action (tool + input) or a final answer. The AgentExecutor is the "doer" — it orchestrates the whole loop: sends the query + trace to the Agent, actually executes whichever tool the Agent chose, collects the result as an Observation, updates the trace, and repeats — it does the heavier lifting.

Building the Agent — create_react_agent

agent = create_react_agent(llm=llm, tools=[search_tool], prompt=prompt)

Given an llm and a ReAct-style prompt (which must also list the available tools, since the prompt tells the LLM what it can use), this returns an Agent object. Given a user query and the current reasoning trace ("agent scratchpad"), that object can generate a Thought and then either an Action or a final answer.

Building the Orchestrator — AgentExecutor

agent_executor = AgentExecutor(agent=agent, tools=[search_tool], verbose=True)

Takes the agent plus the tool list; its two jobs are running the Thought/Action/Observation loop, and actually executing whichever tool the agent chose.

The Full ReAct Loop, Step by Step

⭐ Interview Important — Two internal object types: When the agent decides on a tool, it returns an AgentAction object (tool, tool_input, and the log so far). When it decides it has enough to answer, it returns an AgentFinish object (return_values holding the final answer, plus the log).

Worked Example: "What is the capital of France and its population?"

  1. Iteration 1: Thought — "I need to find the capital of France first." → Action: search tool, input "capital of France" → Observation: "Paris."
  2. Iteration 2: Thought — "Now I know the capital is Paris, I need its population." → Action: search tool, input "population of Paris" → Observation: "2.1 million."
  3. Iteration 3: Thought — "I now know the final answer." → AgentFinish: "Paris is the capital of France and has a population of 2.1 million." Loop exits, user gets the answer.
⭐ Interview Important: Each iteration re-sends the entire growing scratchpad (all prior Thought/Action/Observation text) back into the prompt alongside the original query — this is effectively a multi-turn LLM interaction disguised as a single user-facing question, and it's exactly how the agent "remembers" what it's already discovered.

Extending the Agent With a Second Tool

Adding a custom weather tool (hitting a weather API) alongside the search tool lets the same agent handle chained, tool-dependent queries:

import requests
from langchain_core.tools import tool

@tool
def get_weather_data(city: str) -> str:
    """This function fetches the current weather data for a given city"""
    url = f"https://api.weatherstack.com/current?access_key=YOUR_API_KEY&query={city}"
    response = requests.get(url)
    return response.json()

agent = create_react_agent(llm=llm, tools=[search_tool, get_weather_data], prompt=prompt)
agent_executor = AgentExecutor(agent=agent, tools=[search_tool, get_weather_data], verbose=True)

response = agent_executor.invoke({
    "input": "Find the capital of Madhya Pradesh, then find its current weather condition"
})

With verbose=True, the printed trace shows exactly the ReAct loop in action: Thought 1 ("I should first find the capital...") → Action: search tool → Observation: "Bhopal..." → Thought 2 ("Now that I know the capital is Bhopal, I can check its weather") → Action: get_weather_data("Bhopal") → Observation: weather JSON → Thought 3 ("I now know the final answer") → final answer combining both facts.

⭐ Interview Important: An LLM is fundamentally a large neural network — at a low level, just a huge collection of numbers (its weights and biases). Everything the model "learned" during training is encoded purely in these numbers.

What Is Ollama? (⭐ Interview Important)

⭐ Interview Important — Definition:
Ollama is a tool that lets you download, run, and manage open-source LLMs on your own local computer — handling storage, memory configuration, and compatibility for you, so you only need to focus on using the model.

Analogy: Ollama is like WhatsApp for open-source models — just as WhatsApp lets you focus purely on sending/receiving messages while it handles all the backend complexity, Ollama lets you focus purely on using a model while it handles downloading, storing, loading into memory, and routing requests to it.

Benefits of Using Ollama

  1. Privacy & data control — the model runs entirely on your own machine; your prompts/data never leave your computer. Models can even be used fully offline (after the initial download).
  2. Low latency & offline access — no network round-trip once the model is downloaded; works with zero internet connection thereafter.
  3. Cost predictability — no per-request billing; the model's raw files live on your machine and you use them freely.
  4. Simple installation & setup — a single installer; no ML engineering background required to run a model.
  5. Prebuilt model library — Ollama hosts a large repository of ready-to-download models across many families (DeepSeek, LLaMA, Qwen, Gemma, LLaVA, ...), pre-converted into an easily downloadable/usable format.
  6. Full customizability, no vendor lock-in — no IP-protection restrictions or usage rules to follow; the model is yours to use, fine-tune, or reconfigure however you want.
  7. Simple to run and manage — one-line commands to pull, run, list, or delete models.

The Ollama Model Library

Ollama's library (browsable at its model listing page) can be filtered by: family (Qwen, Mistral, LLaMA, Gemma, LLaVA, DeepSeek, Gemini-family, ...), capability (vision, thinking/reasoning, tool-calling, embeddings, cloud), and parameter size (e.g. Qwen3-VL is available from 2B up to 235B parameters) — so a model can be picked to fit both the task and the available hardware.

Using Ollama via the CLI

⭐ Interview Important: Ollama only manages downloading, running, and configuring models — it has no control over a model's actual output quality; that depends entirely on the model itself (e.g. a non-vision model simply cannot read an image, no matter what Ollama does).
CommandPurpose
ollama --versionConfirm Ollama is installed
ollama pull <model>Download a model locally (e.g. ollama pull mistral:3.8b)
ollama ls / ollama listList locally downloaded models
ollama run <model>Load a model into working memory (RAM/VRAM) and start chatting with it
/byeExit the currently loaded model's chat session
/show info / parameters / systemInspect a loaded model's architecture, parameters, context length, capabilities, or current system prompt
/set parameter <name> <value>Override a runtime parameter (e.g. top_p) for the current session
/set system "..."Set a system instruction for the current session
ollama rm <model>Delete a locally downloaded model
⭐ Interview Important — Vision example: Passing an image to llama3.2:1b (a text/tool-calling-only model) fails with "cannot summarize the image file" — it has no vision capability. Switching to gemma3:4b (which does have vision capability, per its model page) succeeds and produces an accurate image summary. Always check a model's listed capabilities before assuming it can handle images, tool calls, or embeddings.
⭐ Interview Important — CLI's real role: CLI commands are primarily used for quick experimentation and testing — trying different prompts, system instructions, and parameters interactively. Once a developer is satisfied with a configuration, that setup gets integrated into a real application via code (Python/JavaScript), not left as CLI commands.

Passing Images (Vision Models)

⭐ Interview Important: Images passed via the images parameter must be base64-encoded first — raw image files can't be passed directly.
import base64

with open("image.png", "rb") as f:
    image_b64 = base64.b64encode(f.read()).decode()

response = ollama.generate(
    model="gemma3:4b",
    prompt="Give a caption to the image",
    images=[image_b64],
)
print(response.response)

# multiple images: just pass more entries in the list
response = ollama.generate(model="gemma3:4b", prompt="Generate a story based on the images", images=[img1_b64, img2_b64])

System Instructions & Tuning Parameters in Code

response = ollama.generate(
    model="llama3.2:1b",
    prompt="Tell me about black holes",
    system="You are a funny assistant who jokes around.",
    options={"top_p": 0.9, "temperature": 0.7},   # any tunable model parameter
)

generate() vs. chat() — Conversation Memory (⭐ Interview Important)

⭐ Interview Important: ollama.generate() is stateless — one prompt, one response, with no memory of prior turns (unlike ChatGPT/Gemini's conversational history). For multi-turn conversations with context maintained across turns, use ollama.chat() instead, which is built for exactly this.

Other Python library methods mirror the CLI: ollama.list(), ollama.pull(), ollama.delete(), ollama.show().

Tool Calling With Ollama

⭐ Interview Important — Definition: Tool calling is a way to let an LLM perform tasks it inherently cannot do on its own (querying a database, fetching live weather, getting today's news) by giving it access to external Python functions ("tools"). The model's core limitations — a training knowledge cutoff and no ability to interact with the outside world — are exactly what tool calling works around.
⭐ Interview Important: Only models with tool-calling capability (as listed on their Ollama model page) can reliably perform tool calling — not every model supports it.

The Full Tool-Calling Workflow

import ollama, json

def check_inventory(product_name: str) -> dict:
    """Looks up a product in the inventory database."""
    ...  # returns stock + base price

def calculate_loyalty_discount(base_price: float, years_as_customer: int) -> float:
    """Calculates a final price after a loyalty discount (5%/year, capped at 30%)."""
    ...

tools_schema = [
    {"type": "function", "function": {
        "name": "check_inventory",
        "description": "Checks stock and price for a product",
        "parameters": {"type": "object", "properties": {
            "product_name": {"type": "string", "description": "Name of the product"}
        }, "required": ["product_name"]},
    }},
    {"type": "function", "function": {
        "name": "calculate_loyalty_discount",
        "description": "Calculates final price after loyalty discount",
        "parameters": {"type": "object", "properties": {
            "base_price": {"type": "integer", "description": "..."},
            "years_as_customer": {"type": "integer", "description": "..."},
        }, "required": ["base_price", "years_as_customer"]},
    }},
]

messages = [{"role": "user", "content": "I have been a customer for 5 years. What will be the final price of the laptop?"}]
response = ollama.chat(model="qwen3:8b", messages=messages, tools=tools_schema)
messages.append(response.message)

function_map = {"check_inventory": check_inventory, "calculate_loyalty_discount": calculate_loyalty_discount}

for tool_call in response.message.tool_calls:
    fn = function_map[tool_call.function.name]
    result = fn(**tool_call.function.arguments)
    messages.append({"role": "tool", "content": str(result)})

final = ollama.chat(model="qwen3:8b", messages=messages)
print(final.message.content)
⭐ Interview Important — Why chat(), not generate(): Tool calling requires the tools parameter, which only exists on the chat endpoint — generate has no tool-calling support at all. This mirrors the earlier point that generate() is a single-turn, memory-less call, while chat() is built around message history.
⭐ Interview Important — Demonstrated result: Given a query needing both tools in sequence (check stock, then apply a loyalty discount), the model correctly decided check_inventory had to run before calculate_loyalty_discount — since you can't apply a discount to an item that isn't in stock. This is the model's own reasoning about tool order, not something hardcoded.

Customizing Models With Modelfiles

⭐ Interview Important — The problem it solves: LLMs are general-purpose — the same model can write Shakespeare-style poetry or Python code. Real applications usually need specialized behavior (a polite support bot, a blunt code reviewer, a casual Gen-Z-style chatbot) without the cost of training a new model from scratch.
⭐ Interview Important — Definition: A Modelfile is a plain-text configuration file — not a model itself — that tells Ollama how an existing base model should behave (its parameters, system prompt, response format, few-shot examples, etc.). It doesn't touch the base model's learned weights at all; it only changes how that existing knowledge gets applied — like teaching an already-knowledgeable student a new shortcut for solving a problem, without changing what they fundamentally know.
# Modelfile
FROM llama3.2:1b

PARAMETER temperature 0.7
PARAMETER top_p 0.9

SYSTEM """
You are a sentiment analysis API.
You only output JSON in the following schema:
{"sentiment": "positive" | "negative" | "neutral", "score": float}
"""
# in the same directory as the Modelfile:
ollama create sentiment:latest -f modelfile

ollama run sentiment:latest
>>> I love the course
{"sentiment": "positive", "score": 0.95}

The same thing is possible from Python via a create-model API call, passing the model name and Modelfile contents directly — the CLI approach is generally simpler.

How Ollama Works Internally: REST API

⭐ Interview Important: Ollama works internally purely via a REST API. The CLI commands and the Python library are both just wrappers around this same underlying API — they convert a user-friendly command/function call into an HTTP request, send it, and convert the structured JSON response back into something readable.

This mirrors exactly how proprietary models work (user prompt → API request → cloud server → API response → readable output) — the only difference is where the server lives.

import requests

r = requests.post("http://localhost:11434/api/generate", json={"model": "llama3.2:1b", "prompt": "..."})
r2 = requests.get("http://localhost:11434/api/tags")   # equivalent to ollama list

Every CLI command and Python method maps to a specific REST endpoint (e.g. /api/generate for generation, /api/tags for listing models, hit with POST or GET respectively) — Ollama's full API reference documents every endpoint.

Using Ollama With LangChain

⭐ Interview Important: LangChain acts as an orchestration layer over the many components (input loading, chunking, embeddings, vector storage, retrieval, generation) that make up a real LLM application — most of these have nothing to do with the LLM itself. Rather than hand-coding every component from scratch, LangChain provides prebuilt components (including ones wrapping Ollama) that can be chained together, with one component's output automatically becoming the next's input.
LangChain classPurpose
ChatOllamaChat-style interaction with a local Ollama model
OllamaLLMPlain single-turn text generation (non-chat)
OllamaEmbeddingsGenerate embeddings (embed_query for one string, embed_documents for a list) via an Ollama embedding model
from langchain_ollama import ChatOllama, OllamaLLM, OllamaEmbeddings

chat_model = ChatOllama(model="llama3.2:1b")
print(chat_model.invoke("Explain quantum entanglement in one sentence").content)

llm = OllamaLLM(model="llama3.2:1b")
print(llm.invoke("What is the capital of France?"))

embeddings = OllamaEmbeddings(model="")
vector = embeddings.embed_query("What is LangChain?")
vectors = embeddings.embed_documents(["doc one content", "doc two content"])
⭐ Interview Important — Why bother with LangChain instead of the raw Ollama library: Tasks that are purely LLM-related (generation, embeddings) can be done directly via Ollama. But a real application has many non-LLM components too (document loading, chunking, vector stores, retrieval) — building the whole pipeline with LangChain components lets everything connect into one smooth chain; mixing raw Ollama calls with LangChain components elsewhere breaks that chain.

Ollama Cloud

⭐ Interview Important — The problem it solves: Large-parameter open-source models (e.g. 235B, 671B parameters) exist in Ollama's library, but most local machines cannot run them — their working-memory (RAM/VRAM) requirements exceed what a typical laptop provides, and forcing it would crash the system. Ollama Cloud runs that computation on Ollama-managed, data-center-grade hardware instead of the local machine, so even a modest laptop can use a massive model.
# one-time setup
ollama signin   # opens a URL to authenticate the CLI to your Ollama account

ollama run gpt-oss:120b-cloud
>>> What are the colors of a rainbow?
⭐ Interview Important — Key caveats:
  • Only models explicitly listed with cloud capability can run on Ollama Cloud — not every model in the library.
  • Requires being signed in (ollama signin) via CLI, Python, or REST — an unauthenticated request returns an "unauthorized" error.
  • Currently free, with a request-volume limit on the free tier (paid Pro/Max tiers exist for heavier usage) — the limit is on request count, not on which cloud-capable model you can use.
  • Privacy trade-off: unlike fully local usage, data now leaves your machine and travels to Ollama's servers. Ollama states it does not retain request data (processes then discards it), but the network path between your machine and their server is still a broader attack surface than a fully offline local setup — a genuine trade-off between access to huge models and maximum data privacy.
