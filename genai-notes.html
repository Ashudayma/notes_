Video 1: GenAI Roadmap — Introduction

What is GenAI?

⭐ Interview Important — Definition:
"Generative AI is a type of AI that creates new content such as text, images, music, and even code by learning patterns from existing data, mimicking human creativity."
  • ~60-70 years of AI research: Symbolic AI, Expert Systems (1980s), Fuzzy Logic, Evolutionary Algorithms, NLP, Computer Vision.
  • Machine Learning had the biggest impact: learn a statistical pattern from data to predict on new data. Still in demand.
  • Traditional ML types: Regression (number, e.g. stock price), Classification (category, e.g. cat vs dog), Ranking (recommendation systems).
  • Traditional ML never did human-creativity tasks; GenAI generates text, images, video, code.
⭐ Interview Important: The belief was "AI can't replace human creativity." GenAI's "superpower" is breaking that — it mimics human creativity.

AI Hierarchy (⭐ Interview Important)

GenAI Impact Areas

  1. Customer Support — GenAI chatbots handle first-level queries, escalating complex ones to humans; ~10 people → 2-3.
  2. Content Creation — blogs, video, etc.; AI content often indistinguishable from human.
  3. Education — ChatGPT as an always-on tutor: curriculum planning, doubts, practice questions.
  4. Software Development — writes production-ready code; 5 programmers → 2-3.

Is GenAI a Successful Technology?

Compare against Internet (successful) and Blockchain/Crypto (not at full potential).

⭐ Interview Important — Criteria for a "successful" technology:
  1. Solves real-world problems? → Yes (support, education…)
  2. Useful daily? → Yes
  3. Impacts world economics? → Yes — DeepSeek R1 wiped ~$1 trillion (~80 lakh crore INR) off US tech stocks in one day.
  4. Creates new jobs? → Yes — the AI Engineer role, demand rising.
  5. Accessible? → Yes — natural language, no coding.

Conclusion: all "yes" → GenAI tracks the Internet, not a bubble like crypto.

Reasons for the Delay in GenAI Content

Doubt (real vs hype) and time — both resolved. Core problem: GenAI evolves extremely fast (new models/tools/papers daily) — hard to structure a curriculum and filter noise.

The Solution: Mental Model Around "Foundation Models"

⭐ Interview Important — Foundation Models definition:
Foundation Models are large-scale AI models trained on massive amounts of data (comparable to most of the internet's data) using huge compute (many GPUs, costing crores of rupees).

  • LLMs are the best example — backbone of GenAI today.
⭐ Interview Important: Foundation Models ⊃ LLMs; also include LMMs (Large Multimodal Models) for images, video, audio.

Video 3: What is LangChain & Why Do We Need It?

What is LangChain?

⭐ Interview Important — Definition:
"LangChain is an open-source framework for developing applications powered by an LLM."

Example App: Chat with a PDF

User uploads a PDF (e.g. an ML textbook) to read and chat with — "explain page 5 like I'm 5," "true/false questions on Linear Regression," "notes on Decision Trees."

High-Level System Flow

⭐ Interview Important — Keyword vs Semantic Search:
  • Keyword search: exact word matches → too many irrelevant pages.
  • Semantic search: matches meaning → fewer, more contextual results.

Why not send the whole book? Asking a teacher about "the whole book" vs "page 155" — targeted gets a faster, precise answer. The whole document is also computationally expensive and can give worse results.

How Semantic Search Works

⭐ Interview Important — Embeddings/Vectors: text → embeddings, vectors representing semantic meaning (Word2Vec, Doc2Vec, BERT embeddings…). Similar meanings → nearby vectors.

Low-Level Design of the RAG Pipeline

Three Big Challenges (⭐ Interview Important)

ChallengeSolved ByNotes
1. The "brain" (NLU + context-aware generation)LLMsUnsolved until the 2017 Transformer paper, then BERT/GPT — now just use an existing LLM.
2. Hosting/compute for a huge LLM (engineering + cost)LLM APIsOpenAI/Anthropic host it and expose an API — pay per use, no self-hosting.
3. Orchestrating many components/tasksLangChainComponents: S3, text splitter, embedding model, vector DB, LLM. Tasks: load, split, embed, store, retrieve, generate. Hand-coding all interactions (and swapping OpenAI → Google, AWS → GCP) is hard — LangChain solves this orchestration.

Benefits of LangChain (⭐ Interview Important)

  1. Chains — the core concept (hence the name). One component's output automatically becomes the next one's input, no manual wiring. Supports complex, parallel, conditional chains.
  2. Model-agnostic — swap LLM, embedding model, vector DB or cloud with minimal code; focus on business logic.
  3. Complete ecosystem — many document loaders, ~50 text splitters, many embedding models and vector DBs; virtually any component has a LangChain interface.
  4. Memory and state — conversation memory lets follow-ups ("also give interview questions on this algorithm" after Linear Regression) be understood in context.

What Can You Build?

  1. Conversational chatbots — most popular; first-layer support at scale (food delivery, e-commerce).
  2. AI knowledge assistants — chatbot over your own data (course bot answering doubts on the current lecture).
  3. AI Agents — "chatbots on steroids" that act (book the cheapest flight — handy for senior citizens).
  4. Workflow automation — personal, professional, company-level.
  5. Summarization & research helpers — internal "ChatGPT-like" tool for huge docs (beyond context limits) and private data.

Alternatives to LangChain

LlamaIndex (popular; CampusX courses) and Haystack. Choose by pricing and use-case fit; a comparison is planned later.

Video 4: LangChain Components — Overview

All 6 components at a conceptual level (no code); later videos go deeper into each.

⭐ Interview Important — The 6 LangChain Components: Models, Prompts, Chains, Memory, Indexes, Agents — most of LangChain's core concepts.

1. Models

⭐ Interview Important — Definition:
"Models are the core interface through which you interact with AI models" in LangChain.

Backstory

  1. Chatbots had two unsolved problems: NLU (understanding the user) and context-aware text generation. LLMs, trained on near-internet-scale text, solved both.
  2. New problem: billions of parameters → huge files (good LLMs >100GB); individuals/small companies can't afford to host them. Solved by APIs: providers (OpenAI…) host and expose an API; pay per use.
  3. Third problem: standardization — each provider has different request/response formats; two providers = two integrations, switching = rewrite.
⭐ Interview Important — Problem the Models component solves: a standard interface to any provider. OpenAI → Claude/Gemini typically changes 1-2 lines (import/class name); calling and response-parsing code stay the same.

Two Types of Models (⭐ Interview Important)

TypeInput → OutputUsed For
Language Models (LLMs)Text in → Text outChatbots, AI agents, any text generation task
Embedding ModelsText in → Vector outSemantic search (core use case)

Docs list chat-model providers (Anthropic, Mistral AI, Azure, OpenAI, Vertex AI, AWS Bedrock, Hugging Face…) with per-feature support — tool calling, structured/JSON output, local execution, multimodal input. A separate page lists embedding models (OpenAI, Mistral AI, IBM, LLaMA…).

2. Prompts

⭐ Interview Important — Definition: Prompts are the inputs provided to an LLM.
⭐ Interview Important: output is highly sensitive to the prompt — one word ("academic tone" vs "fun tone") changes it a lot. Hence Prompt Engineering and the Prompt Engineer role.

LangChain prompt styles:

  1. Dynamic & reusable — template with placeholders ("Summarize {topic} in {tone} tone") filled per request.
  2. Role-based — system prompt sets persona ("You are an experienced {profession}") + user prompt ("Tell me about {topic}"), e.g. "You are an experienced doctor. Tell me about viral fever."
  3. Few-shot — show labeled examples (support tickets: billing / technical / general inquiry), then classify a new input.

3. Chains

⭐ Interview Important: Chains give the framework its name — its most important concept. A Chain builds a pipeline; any LLM app can be shaped as one.
⭐ Interview Important — Core benefit: each step's output automatically becomes the next step's input — no manual wiring.

Example: Sequential Chain

Task: ~1000-word English text → Hindi summary under 100 words. Without Chains: call LLM-1 (translate), manually pass output to LLM-2 (summarize <100 words), handle result. With Chains: define once, call with the English text; the hand-off is automatic.

Example: Parallel Chain

Topic (e.g. "911 incident") → one combined detailed report: multiple LLMs process the same input simultaneously; a final LLM merges outputs.

Example: Conditional Chain

Agent gets customer feedback; LLM classifies it — good → reply "thank you"; bad → email the support team immediately.

Many other compositions exist; Chains do the pipeline heavy lifting, cutting wiring code drastically.

4. Indexes

⭐ Interview Important — Definition: Indexes connect your application to external knowledge sources such as PDFs, websites, and databases.
⭐ Interview Important — 4 sub-components: Document Loader, Text Splitter, Vector Store, Retriever.

ChatGPT can't answer about private data it never saw ("leave policy of my company XYZ?"). Connect the LLM to an external source (company rulebook — or a PDF, website, database) — what Indexes enable. Same RAG pipeline as Video 3: load → chunk → embed → store; at query time retrieve relevant chunks and pass them + query to the LLM.

5. Memory

⭐ Interview Important — Core problem: LLM API calls are stateless — each request is independent, no memory of earlier ones.

E.g. "Who is Narendra Modi?" → correct; then "How old is he?" in a new call → no idea who "he" is. Users would have to restate context every message. Memory adds memory to a conversation.

Types of Memory (⭐ Interview Important)

Memory TypeHow it worksTrade-off
Conversation Buffer MemoryStores the entire history; sent with every call.Long conversations → large history and cost.
Conversation Buffer Window MemoryOnly the last N interactions (e.g. 100); sliding window.Bounded cost; older context lost.
Summarizer-based MemoryRunning summary of the chat, sent instead of full text.Saves tokens/cost; loses some detail.
Custom MemorySpecialized info for advanced cases — user preferences, facts about the user.Custom design per use case.

6. Agents

⭐ Interview Important: an AI Agent is "a chatbot with superpowers" — it can also take actions, not just talk.

Chatbot vs. AI Agent (⭐ Interview Important)

Example: travel-website bot.

  • Plain chatbot: "best destination in India in summer?" → from trained knowledge ("Shimla, Manali").
  • AI Agent: "cheapest flight Delhi → Shimla on 24th January?" → hits a live flight API; "book the flight" → actually books it.
⭐ Interview Important — What an Agent has that a chatbot doesn't:
  1. Reasoning — works out what must be done to answer.
  2. Tool access — calls external tools/APIs to fetch info or act.

Worked Example: Calculator + Weather API Agent

Tools: calculator and weather API (city temperature on any date). Query: "Can you multiply today's temperature of Delhi with 3?"

⭐ Interview Important — Chain of Thought (CoT): a popular agent reasoning technique — break the query into steps and reason through each before acting.
⭐ Interview Important — Summary: an Agent is an evolved chatbot that acts, thanks to reasoning + tool access. LangChain makes building them much easier.

Two Ways to Use an Open-Source Model (⭐ Interview Important)

  1. Hugging Face Inference API — like OpenAI's API: hosted on HF servers, called remotely; free up to a limit, then paid; no local compute. LangChain: HuggingFaceEndpoint (remote LLM) + ChatHuggingFace (chat wrapper).
  2. Local download — download weights via HF, run inference locally (internet needed once). LangChain: HuggingFacePipeline.from_model_id(...) + ChatHuggingFace. Example: TinyLlama (1.1B-param fine-tune of LLaMA 2, ~500MB).
⭐ Interview Important — Disadvantages of open-source models:
  1. Hardware — larger models need a strong GPU; even TinyLlama took ~10 min per response on a weak machine (8GB RAM, low SSD) and could hang it.
  2. Complex setup — weights, tokenizers, configs, cache paths vs. just calling an API.
  3. Less refined responses — less RLHF than closed-source, so less polished.
  4. Limited multimodal — most free options are text-only; strong open multimodal models are rare.

Embedding Models

OpenAI Embeddings

  • OpenAIEmbeddings (langchain_openai), e.g. text-embedding-3-large.
  • .embed_query(text) — vector for a single text.
  • .embed_documents([text1, text2, ...]) — multiple texts → 2D list (one vector each).
  • dimensions sets vector length — default 1536 (small) / 3072 (large); can be set smaller (e.g. 32).
⭐ Interview Important — Dimension trade-off: more dimensions = more contextual meaning but higher cost (storage/comparison); fewer = cheaper, less context. OpenAI embeddings are very cheap (~$0.02 per million tokens) — output is just numbers.

Open-Source Embeddings

HuggingFaceEmbeddings (langchain_huggingface). Example: sentence-transformers/all-MiniLM-L6-v2 — ~90MB, maps sentences/paragraphs to a 384-dim dense vector; good for clustering and semantic search. Same .embed_query() / .embed_documents(). Generally somewhat less accurate than OpenAI's paid embeddings.

Worked Example: Document Similarity Search

5 short bios of Indian cricketers + a query ("Tell me about Virat Kohli") → find the most relevant document.

  • sklearn.metrics.pairwise.cosine_similarity(query_vector_2d, document_vectors_2d) — both args must be 2D (wrap the single query vector in an extra list).
  • Pair each score with its index via enumerate() before sorting, then sort by score and take the last (highest).
  • "Tell me about Virat Kohli" → Kohli doc; "Tell me about Bumrah" → top match switched correctly.
⭐ Interview Important: recomputing document embeddings each run is wasteful — real systems embed documents once and store them in a vector database (later); queries are embedded fresh per request. Comparing them is exactly RAG's retrieval step.

Video 6: Prompts — Static/Dynamic Templates, Messages & Chat History

Focus: text-based prompts only (multimodal — image/audio/video — out of scope; text is ~99% of real-world usage).

What Is a Prompt?

⭐ Interview Important — Definition: a prompt is the message/input sent to an LLM — every model.invoke() message so far was one.
⭐ Interview Important: output is extremely sensitive to wording — hence the discipline/role of Prompt Engineering.

Static vs. Dynamic Prompts

Example: a Streamlit "Research Paper Summarizer" — user pastes a prompt and clicks "Summarize."

⭐ Interview Important — Static Prompt and its problems:
A static prompt is entirely typed by the user ("Summarize the Attention Is All You Need paper in simple fashion"). Problems:
  1. Mistyped/unknown paper title → wrong/ambiguous input → hallucination or poor answer.
  2. Inconsistent phrasing ("5 lines," "math-heavy," "code-heavy") → no consistent user experience, though the app's value is summary quality/format.
⭐ Interview Important — Dynamic Prompt (the fix): a developer-designed prompt template with placeholders filled from fixed UI choices (dropdowns: paper; style — Simple / Math-Heavy / Code-Heavy; length — Short / Medium / Long). No typos; every user gets the same high-quality prompt.

Template also says: math equations only if in source, intuitive code snippets for math, relatable analogies, and "insufficient information available" instead of hallucinating.

The PromptTemplate Class

From langchain_core.prompts: template string with {placeholder}s, names listed in input_variables, filled at runtime:

from langchain_core.prompts import PromptTemplate

template = PromptTemplate(
    template=template_text,   # contains {paper_input}, {style_input}, {length_input}
    input_variables=["paper_input", "style_input", "length_input"],
)
prompt = template.invoke({
    "paper_input": paper_input,
    "style_input": style_input,
    "length_input": length_input,
})
result = model.invoke(prompt)

Keep large templates out of app code: template.save("template.json") once, load_prompt("template.json") wherever needed (reason 2 below).

Why PromptTemplate Over f-strings? (⭐ Interview Important)

ReasonWhat it gives you
1. Built-in validationvalidate_template=True checks at dev time that placeholders exactly match input_variables — missing/extra/misspelled names error immediately instead of breaking later in production.
2. ReusabilityAuthor once, save as JSON, load_prompt() anywhere — no duplicated prompt strings; single source of truth.
3. Ecosystem integrationCombines with a model into a Chain ([template, model]) — one chain.invoke({...}) replaces fill + model call. f-strings can't join a Chain. (Chains: later video.)

Messages: Why a Chatbot Needs Role-Labeled History

Console chatbot: while True → model.invoke() → print result.content; "exit" quits. Raw user string, no template (static prompt).

⭐ Interview Important — Stateless LLM: "Which is greater, 2 or 0?" → "2"; "now multiply the bigger number by 10" → "if the bigger number is x, then 10x" — prior turn never sent.

Fix 1: a chat_history list of every user message and AI reply, sent in full each turn (invoke() takes a string or a list). Follow-up → 20.

⭐ Interview Important — Remaining problem: raw strings lose who said what; long histories confuse the LLM. Fix: label each entry with its role.
⭐ Interview Important — The 3 Message Types:
  • SystemMessage — one-time top-of-conversation instruction setting persona/behavior ("You are a helpful assistant" / "You are an experienced doctor").
  • HumanMessage — from the user ("What is the capital of India?").
  • AIMessage — from the model ("The capital of India is New Delhi.").
From langchain_core.messages. Rebuilt chatbot: chat_history starts with a SystemMessage; each turn appends HumanMessage(content=user_input), then AIMessage(content=result.content). Every entry unambiguously labeled.

Recap: Two Ways to Call invoke()

ChatPromptTemplate — Dynamic Lists of Messages

⭐ Interview Important: ChatPromptTemplate is the dynamic counterpart of PromptTemplate for a list of messages where some contain placeholders. E.g. SystemMessage = "You are a helpful {domain} expert," HumanMessage = "Explain in simple terms what is {topic}."
⭐ Interview Important — Gotcha: passing pre-built SystemMessage(content="...{domain}...") / HumanMessage(content="...{topic}...") objects does not fill placeholders — their content is treated as final, so {domain}/{topic} stay literal. Called out as inconsistent/immature library behavior.

Correct approach (current docs): use (role, template_string) tuples:

from langchain_core.prompts import ChatPromptTemplate

chat_template = ChatPromptTemplate([
    ("system", "You are a helpful {domain} expert"),
    ("human", "Explain in simple terms, what is {topic}"),
])
prompt = chat_template.invoke({"domain": "cricket", "topic": "doosra"})

Both placeholders fill. ChatPromptTemplate.from_messages([...]) with the same tuples is identical — either syntax works, but tuples (not Message objects) are required for filling.

MessagesPlaceholder — Injecting a Stored Chat History

⭐ Interview Important — Definition: MessagesPlaceholder is a special slot in a ChatPromptTemplate that inserts an entire previously stored list of messages (chat history) at runtime — not a single value.

Example: support chatbot. Day 1: customer asks for a refund; the exchange (HumanMessage/AIMessage) is saved externally (DB in production; text file in demo). Day 2, new session: "Where is my refund?" — needs yesterday's conversation reloaded and combined with today's question in the same template.

from langchain_core.prompts import ChatPromptTemplate, MessagesPlaceholder

chat_template = ChatPromptTemplate([
    ("system", "You are a helpful customer support agent"),
    MessagesPlaceholder(variable_name="chat_history"),
    ("human", "{query}"),
])

# chat_history loaded from file/DB as a list of HumanMessage/AIMessage objects
prompt = chat_template.invoke({
    "chat_history": chat_history,
    "query": "Where is my refund?",
})

Resulting prompt: system message, saved turns, today's question — LLM resolves "my refund" from yesterday's context.

Prompts = input; this and the next video = processing output. Unlocks LLMs talking to other machines (databases, APIs, tools), not just humans — foundational for AI Agents.

What Is Structured Output?

⭐ Interview Important — Definition:
By default an LLM returns plain text (unstructured output). Structured output = the model returns a well-defined data format (e.g. JSON), easy to parse programmatically.

E.g. "Create a one-day travel itinerary for Paris" → a prose paragraph vs. a JSON list of {time, activity} objects you can loop over/store.

Why Structured Output? (⭐ Interview Important — 3 use cases)

Use CaseExample
Data ExtractionJob portal (Naukri.com) extracts name, last company, 10th/12th marks, college marks from resume text into a DB.
Building APIsE-commerce (Amazon) turns long reviews into key themes, pros, cons, sentiment, exposed as an API (Flask/FastAPI).
Building AI AgentsAgents act via tools (e.g. calculator) that need structured args: "Find the square root of 2" → {"operation": "sqrt", "value": 2}.
⭐ Interview Important — Core benefit: LLMs could only talk to humans (text in/out); unstructured output couldn't be wired into systems. Structured output lets an LLM talk to other machines (databases, APIs).

Two Ways to Get Structured Output

Some LLMs (e.g. OpenAI GPT) are trained to emit structured output natively; others can't.

The with_structured_output() Function

⭐ Interview Important: instead of model.invoke(...), call model.with_structured_output(schema) to get a "structured model," then .invoke(...) on it. Schema via TypedDict, Pydantic, or JSON Schema.
⭐ Interview Important — Behind the scenes: LangChain auto-generates a hidden system prompt (roughly "You are an AI assistant that extracts structured insights from text... return the response in JSON format" + field descriptions) prepended to your input. The model, trained to return JSON on request, replies in JSON; LangChain parses it into a Python dict/object.

Schema Style 1: TypedDict

⭐ Interview Important — Definition: TypedDict (Python typing) declares a dict's keys and value types for IDE type hints. Limitation: no runtime validation — assigning a str to an int field raises no error.
from typing import TypedDict

class Person(TypedDict):
    name: str
    age: int

new_person: Person = {"name": "Nitish", "age": 32}  # editor hints types; nothing enforces them at runtime

Applied to a phone review (key themes, summary, sentiment, pros/cons, reviewer name):

from typing import TypedDict, Annotated, Optional, Literal
from langchain_openai import ChatOpenAI

class Review(TypedDict):
    key_themes: Annotated[list[str], "Write down all the key themes discussed in the review in a list"]
    summary: Annotated[str, "A brief summary of the review"]
    sentiment: Annotated[Literal["pos", "neg"], "Return sentiment of the review, either negative or positive"]
    pros: Annotated[Optional[list[str]], "Write down all the pros inside a list"]
    cons: Annotated[Optional[list[str]], "Write down all the cons inside a list"]
    name: Annotated[Optional[str], "Write the name of the reviewer"]

model = ChatOpenAI()
structured_model = model.with_structured_output(Review)
result = structured_model.invoke(review_text)
print(result["summary"])       # plain dict access
print(result["sentiment"])
⭐ Interview Important — Annotated, Optional, Literal:
  • Annotated[type, "description"] adds a field description. The LLM may infer from the name (summary), but a description removes ambiguity; it becomes part of the hidden system prompt.
  • Optional[...] — field may be absent/None (review may lack cons or reviewer name) rather than forcing a fabricated value.
  • Literal["pos", "neg"] — restricts to exact values (sentiment only "pos"/"neg", never "neutral" or a full word).
⭐ Interview Important — Prompting still matters: Optional is a hint, not a rule — live, after removing cons from the review, the model still inferred a cons list. Reliable omission may need an explicit instruction ("do not include cons unless explicitly mentioned").

Schema Style 2: Pydantic

⭐ Interview Important — Definition: Pydantic is a data validation and data parsing library for Python (common with FastAPI). Unlike TypedDict it enforces declared types/constraints and errors on violation — more reliable for LLM output.
from pydantic import BaseModel

class Student(BaseModel):
    name: str = "Nitish"           # default value

new_student = {"name": 32}          # wrong type
student = Student(**new_student)    # raises: "Input should be a valid string"

Key Pydantic Features (⭐ Interview Important)

FeatureWhat it does
Default valuesname: str = "Nitish" — used if none supplied.
Optional fieldsage: Optional[int] = None — must explicitly default to None (unlike TypedDict).

from pydantic import BaseModel, Field, EmailStr
from typing import Optional

class Student(BaseModel):

    email: EmailStr

Same review task — Field(description=...) replaces Annotated:

from pydantic import BaseModel, Field
from typing import Optional, Literal

class Review(BaseModel):
    key_themes: list[str] = Field(description="Write down all the key themes discussed in the review in a list")
    summary: str = Field(description="A brief summary of the review")
    sentiment: Literal["positive", "negative"] = Field(description="Return sentiment of the review, either negative or positive")
    pros: Optional[list[str]] = Field(default=None, description="Write down all the pros inside a list")
    cons: Optional[list[str]] = Field(default=None, description="Write down all the cons inside a list")
    name: Optional[str] = Field(default=None, description="Write the name of the reviewer")

structured_model = model.with_structured_output(Review)

print(result.summary)      # dot access — it's a Pydantic object, not a dict

Access: TypedDict/JSON-schema results are dicts (result["summary"]); Pydantic results are objects (result.summary).

Schema Style 3: JSON Schema

⭐ Interview Important — When: the schema must be shared across languages (Python backend + JavaScript frontend) — JSON is language-agnostic; TypedDict/Pydantic are Python-only.

Needs: title, optional description, type ("object" for dict-shaped), properties (each field's type + description), and a required array.

{
  "title": "Student",
  "description": "Schema about students",
  "type": "object",
  "properties": {
    "name": { "type": "string" },
    "age": { "type": "integer" }
  },
  "required": ["name"]
}

Review schema in JSON Schema (same 6 fields): key_themes/pros/cons are "array" of "string" (optional ones allow "array" or "null"); sentiment uses "enum": ["positive", "negative"] instead of Literal; required = key_themes, summary, sentiment. Passed the same way:

structured_model = model.with_structured_output(json_schema)   # a Python dict holding the JSON schema
result = structured_model.invoke(review_text)
print(result["key_themes"])   # plain dict access, same as TypedDict

TypedDict: all-Python, only type hints needed (uncommon). Pydantic: need validation/defaults/coercion (guards against slightly wrong LLM types) — recommended default, as LangChain work stays in Python. JSON Schema: multi-language projects.

Important Points (⭐ Interview Important)

  • method parameter — how structured output is requested:
    ValueWhen to use it
    "json_mode"Just want JSON back (common case). Recommended for non-OpenAI JSON-capable models, e.g. Claude, Gemini.
    "function_calling"Output will be used to call a function/tool (e.g. agent → calculator). Default and recommended for OpenAI models.
  • Some models support neither — live, TinyLlama (Hugging Face) on the same code: with_structured_output errors (no JSON mode, no function calling). For these, Output Parsers (next video) are the only way.

Video 8: Output Parsers — String, JSON, Structured & Pydantic

Continues Structured Output. with_structured_output() works only with "can" models (natively structured, e.g. GPT). Output Parsers also handle "can't" models (small open-source, e.g. TinyLlama) — and "can" models too.

What Are Output Parsers?

⭐ Interview Important — Definition:
Output Parsers are classes in LangChain that help convert raw LLM responses (plain text) into structured formats like JSON, CSV, or Pydantic models. They ensure consistency, (optionally) validation, and ease of use in applications.
⭐ Interview Important — vs. with_structured_output: parsers work with both model categories; with_structured_output only with native-support models. That's why parsers still matter.

Many parsers exist (CSV, list, datetime, enum, markdown, "output-fixing" retry…); four cover most cases: StrOutputParser, JsonOutputParser, StructuredOutputParser, PydanticOutputParser.

1. StrOutputParser

⭐ Interview Important — Definition: the simplest parser — extracts just the plain string content from the response object.

Responses carry metadata (token usage, completion tokens, model name…), forcing result.content everywhere. The parser does that extraction — valuable once LLM calls are chained.

Example: Two Chained LLM Calls

(1) detailed report on a topic, (2) feed it back for a 5-line summary.

Without a parser — manual .content at each step:

template1 = PromptTemplate(template="Write a detailed report on {topic}", input_variables=["topic"])
template2 = PromptTemplate(template="Write a 5 line summary on the following text:\n{text}", input_variables=["text"])

prompt1 = template1.invoke({"topic": "black hole"})
result = model.invoke(prompt1)

prompt2 = template2.invoke({"text": result.content})   # manual .content extraction
result = model.invoke(prompt2)

print(result.content)                                   # manual .content extraction again

With StrOutputParser and a Chain — no manual extraction:

from langchain_core.output_parsers import StrOutputParser

parser = StrOutputParser()
chain = template1 | model | parser | template2 | model | parser
result = chain.invoke({"topic": "black hole"})
print(result)
⭐ Interview Important — Why: the parser sits between model and next template, stripping metadata so the report flows straight in. Without it: two chains with manual extraction between.

2. JsonOutputParser

⭐ Interview Important — Definition: forces JSON output and parses it into a Python dict. Quickest way to JSON — but no control over its internal structure.

Key mechanic: parser.get_format_instructions() returns an auto-generated instruction (e.g. "Return a JSON object") injected as a partial variable — filled at template-construction time (via a function call), not at invoke()/runtime like a regular input variable.

from langchain_core.output_parsers import JsonOutputParser
from langchain_core.prompts import PromptTemplate

parser = JsonOutputParser()

template = PromptTemplate(
    template="Give me the name, age and city of a fictional person \n{format_instruction}",
    input_variables=[],
    partial_variables={"format_instruction": parser.get_format_instructions()},
)

prompt = template.format()
result = model.invoke(prompt)
final_result = parser.parse(result.content)
print(final_result["name"])   # a plain dict

# Equivalently, as a chain (parser.parse is called automatically):
chain = template | model | parser
final_result = chain.invoke({})   # empty dict required even with zero input variables
⭐ Interview Important — Biggest flaw: can't enforce the schema (key names/nesting) — the LLM decides. Live: "5 facts about a topic" returned {"facts_about_black_holes": [...]} instead of a requested {"fact_1": ..., "fact_2": ..., "fact_3": ...}, with no way to force it.

3. StructuredOutputParser

⭐ Interview Important — Definition:
An output parser that extracts structured JSON from LLM responses based on a predefined field schema. You supply the schema up front (list of ResponseSchema objects) and the LLM follows it — schema enforcement, its key benefit over JsonOutputParser.
from langchain.output_parsers import StructuredOutputParser, ResponseSchema

schema = [
    ResponseSchema(name="fact_1", description="Fact 1 about the topic"),
    ResponseSchema(name="fact_2", description="Fact 2 about the topic"),
    ResponseSchema(name="fact_3", description="Fact 3 about the topic"),
]
parser = StructuredOutputParser.from_response_schemas(schema)

template = PromptTemplate(
    template="Give 3 facts about {topic} \n{format_instruction}",
    input_variables=["topic"],
    partial_variables={"format_instruction": parser.get_format_instructions()},
)

chain = template | model | parser
result = chain.invoke({"topic": "black hole"})
# {"fact_1": "...", "fact_2": "...", "fact_3": "..."}
⭐ Interview Important — langchain vs. langchain_core: StructuredOutputParser/ResponseSchema import from langchain.output_parsers, not langchain_core (unlike the other three). langchain is the umbrella library; langchain_core holds only the most important, most reused components — this parser didn't qualify.
⭐ Interview Important — Biggest flaw: enforces JSON shape but no data validation — an integer "age" field can still come back as "35 years", uncaught and uncoerced.

4. PydanticOutputParser

⭐ Interview Important — Definition:
A structured output parser that uses a Pydantic model (BaseModel) to enforce schema and validate data when processing LLM responses. Best of both: schema enforcement (like StructuredOutputParser) plus validation/type coercion (Pydantic).
from langchain_core.output_parsers import PydanticOutputParser
from pydantic import BaseModel, Field

class Person(BaseModel):
    name: str = Field(description="Name of the person")
    age: int = Field(gt=18, description="Age of the person")
    city: str = Field(description="Name of the city the person belongs to")

parser = PydanticOutputParser(pydantic_object=Person)

template = PromptTemplate(
    template="Generate the name, age and city of a fictional {place} person \n{format_instruction}",
    input_variables=["place"],
    partial_variables={"format_instruction": parser.get_format_instructions()},
)

chain = template | model | parser
final_result = chain.invoke({"place": "Sri Lankan"})
print(final_result)   # a validated Person object — age is guaranteed a valid int > 18

get_format_instructions() injects a JSON-schema-shaped block (fields/types/constraints) as a partial variable; parser.parse(...) (or the chain) yields a validated Person.

Video 9: Chains — Sequential, Parallel & Conditional

First of two videos on Chains (LangChain is named after them): fundamentals + three chain types. Next: Runnables — the mechanism behind chains.

What & Why

Any LLM app = several small steps; minimum three: (1) take user prompt, (2) send to LLM, (3) process/display response.

⭐ Interview Important — The problem chains solve: Without chains each step is invoked manually and individually — prompt.invoke(), pass output to model.invoke(), pass response to a parser. Fine for small apps, unmanageable as steps grow.
⭐ Interview Important — Definition: A chain connects an LLM app's small steps into a pipeline: each step's output automatically becomes the next step's input. You give input only to the first step; downstream steps fire in sequence and you get the final output.

Simple Chain

App: topic → 5 interesting facts.

from langchain_openai import ChatOpenAI
from langchain_core.prompts import PromptTemplate
from langchain_core.output_parsers import StrOutputParser
from dotenv import load_dotenv

load_dotenv()

prompt = PromptTemplate(
    template="Generate 5 interesting facts about {topic}",
    input_variables=["topic"],
)
model = ChatOpenAI()
parser = StrOutputParser()

chain = prompt | model | parser

result = chain.invoke({"topic": "cricket"})
print(result)
⭐ Interview Important — LCEL (LangChain Expression Language): the | pipe syntax that declaratively wires components (prompt | model | parser): "start at prompt, then model, then parser." Internals in the next video (Runnables).

Visualize any chain with chain.get_graph().print_ascii() — prints steps in order; handy for debugging unfamiliar chains.

1. Sequential Chain

App: topic → detailed report → fed back to the LLM → 5-point summary. Two LLM calls in sequence, fully automatic.

prompt1 = PromptTemplate(
    template="Generate a detailed report on {topic}",

)
prompt2 = PromptTemplate(
    template="Generate a 5 pointer summary from the following text \n {text}",

model = ChatOpenAI()

2. Parallel Chain

App: from a large document (e.g. text on Linear Regression), generate notes and a quiz independently and simultaneously, then merge into one document.

⭐ Interview Important — RunnableParallel: runs multiple chains in parallel. Built from a dict of name → chain; each output is collected under its name.
from langchain_openai import ChatOpenAI
from langchain_anthropic import ChatAnthropic
from langchain_core.prompts import PromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnableParallel

model1 = ChatOpenAI()
model2 = ChatAnthropic(model_name="claude-3-5-sonnet-20241022")
parser = StrOutputParser()

prompt1 = PromptTemplate(
    template="Generate short and simple notes from the following text \n {text}",
    input_variables=["text"],
)
prompt2 = PromptTemplate(
    template="Generate 5 short question answers from the following text \n {text}",
    input_variables=["text"],
)

    template="Merge the provided notes and quiz into a single document \n notes -> {notes} \n quiz -> {quiz}",

3. Conditional Chain

App: classify product feedback sentiment (positive/negative), then reply accordingly — only one reply path runs per call (unlike parallel, where both run).

Step A — Structuring the classifier's output

⭐ Interview Important — Why a plain string won't work: with StrOutputParser the LLM may return "negative" or "the sentiment is negative", inconsistently. Branching compares exactly (== "positive"), so output must be structured/constrained.

Solution: Pydantic schema with Literal["positive", "negative"] + PydanticOutputParser → always exactly one of those two words.

from langchain_core.output_parsers import PydanticOutputParser, StrOutputParser
from pydantic import BaseModel, Field
from typing import Literal

class Feedback(BaseModel):
    sentiment: Literal["positive", "negative"] = Field(
        description="Give the sentiment of the feedback"
    )

parser2 = PydanticOutputParser(pydantic_object=Feedback)

prompt1 = PromptTemplate(
    template="Classify the sentiment of the following feedback text into positive or negative \n {feedback} \n {format_instruction}",
    input_variables=["feedback"],
    partial_variables={"format_instruction": parser2.get_format_instructions()},
)

classifier_chain = prompt1 | model | parser2

Step B — Branching with RunnableBranch

⭐ Interview Important — RunnableBranch: if/elif/else between chains — (condition, chain) tuples checked in order, plus a final default chain if none match.
⭐ Interview Important — RunnableLambda: a plain Python function/lambda is not a Runnable and can't go into RunnableBranch directly; RunnableLambda wraps it into one (used here as the default chain).
from langchain_core.runnables import RunnableBranch, RunnableLambda

prompt2 = PromptTemplate(
    template="Write an appropriate response to this positive feedback \n {feedback}",
    input_variables=["feedback"],
)
prompt3 = PromptTemplate(
    template="Write an appropriate response to this negative feedback \n {feedback}",
    input_variables=["feedback"],
)

branch_chain = RunnableBranch(
    (lambda x: x.sentiment == "positive", prompt2 | model | parser),
    (lambda x: x.sentiment == "negative", prompt3 | model | parser),
    RunnableLambda(lambda x: "could not find sentiment"),
)

chain = classifier_chain | branch_chain

result = chain.invoke({"feedback": "This is a terrible smartphone"})
print(result)

Video 10: Runnables — Why They Exist & Building Them From Scratch

Part 1 of two on Runnables (what makes Chains work): why they were invented, then a simplified Runnable system built from scratch with dummy classes. Part 2: built-in Runnable subclasses.

Why Do Runnables Exist?

⭐ Interview Important — Origin, problem 1 (model fragmentation): after ChatGPT (Nov 2022) OpenAI opened its APIs; LangChain foresaw an LLM-app boom. Providers (OpenAI, Anthropic, Google, Mistral, ...) shipped differently-behaving APIs. LangChain's first win: standardized wrapper classes per provider → talk to any LLM with minimal code changes.

Second gap: the LLM call is a small part of a real app. A "chat with your PDF" app needs:

  1. Load the document (e.g. from cloud storage)
  2. Split into chunks (chapter/page/paragraph)
  3. Embed each chunk
  4. Store embeddings in a vector DB
  5. Retriever: semantic search for relevant chunk(s)
  6. Send chunk + query to the LLM
  7. Display response
⭐ Interview Important — Origin, problem 2 (missing components) → solution: LangChain broke LLM-app use cases into reusable parts with a component class each: Document Loaders, Text Splitters, Embedding Models, Vector Stores, Retrievers, Output Parsers, Memory (plus LLM/Prompt). Engineers could wire these into almost any LLM app.

Demo: a simple app (topic → prompt → LLM → display) and a full PDF/RAG app (load → split → embed → store → retrieve → prompt → LLM → display) each in a few dozen lines, purely by plugging components together.

The Chains Idea

Certain component sequences repeat in every app — most universally, build prompt → send to LLM (chatbot, PDF reader, agent, ...).

⭐ Interview Important — Birth of Chains: instead of manually calling prompt_template.format(...) then llm.predict(...), LangChain built a function taking LLM + prompt template that does both internally. Connecting components into a pipeline = a Chain; the simplest (prompt + LLM) = LLMChain.

More patterns → more chain classes, e.g. RetrievalQA (LLM + retriever → semantic search, prompt-merging, LLM call for RAG). A PDF app went ~36 → ~32 lines, but more importantly retrieval became one reusable call.

The Problem: Too Many Chains

A new chain class per use case: SimpleSequentialChain, SequentialChain, chains for SQL databases, APIs, math, and many more (docs list dozens).

⭐ Interview Important — Two disadvantages of "too many chains":
  1. Codebase bloat — huge, hard-to-maintain codebase.
  2. Steep learning curve — which of 50+ chains fits a use case? LangChain got harder to learn.

Irony: the goal was Lego-block components pluggable in any workflow; instead they hand-wrote a bespoke chain per use case.

Root Cause (⭐ Interview Important)

⭐ Interview Important: components were built independently, with no shared interface — each had a different "do your job" method:
ComponentMethod
LLM.predict(prompt)
Prompt Template.format(input_dict)
Retriever.get_relevant_documents(query)
Output Parser.parse(response)

Connecting any pair needed hand-written glue code — and that glue is each Chain class. Fix: rebuild every component on one common, standardized interface = Runnables.

What Are Runnables? (⭐ Interview Important)

⭐ Interview Important: a Runnable is a unit of work: input → process → output. Four characteristics:
  1. Single unit of work — one component, one job.
  2. Common interface — same methods everywhere: invoke() (single in → single out, most important), batch() (many inputs → many outputs), stream() (token-by-token output).
  3. Composable — any Runnables can be connected; output auto-feeds the next input.
  4. A composed workflow is itself a Runnable — R1→R2→R3 ("Workflow A") and R4→R5 ("Workflow B") can themselves be connected, recursively without limit.

chain = FakeLLMChain(llm=FakeLLM(), prompt=template)
print(chain.run({"length": "short", "topic": "India"}))
⭐ Interview Important — Why this doesn't scale: FakeLLMChain fits exactly one use case. A "generate a joke, then explain it" app needs two LLM calls — no generic .run() can handle arbitrary calls because .format() vs .predict() share no interface. Hence a new chain class per use case.

Code Demo, Part 2 — The Fix: Abstract Base Class

Every component inherits one abstract class and implements the same invoke, via Python's ABC/abstractmethod.

from abc import ABC, abstractmethod

class Runnable(ABC):
    @abstractmethod
    def invoke(self, input_data):
        pass
class FakeLLM(Runnable):
    def __init__(self):
        print("LLM created")

    def invoke(self, prompt):
        response_list = [
            "Delhi is the capital of India",
            "IPL is a cricket league",
            "AI stands for Artificial Intelligence",
        ]
        return {"response": random.choice(response_list)}

    def predict(self, prompt):
        # kept for backward compatibility with old code that still calls .predict()
        print("This method is deprecated, please use invoke instead")
        return self.invoke(prompt)


class FakePromptTemplate(Runnable):
    def __init__(self, template, input_variables):
        self.template = template
        self.input_variables = input_variables

    def invoke(self, input_dict):
        return self.template.format(**input_dict)

    def format(self, input_dict):
        # kept for backward compatibility with old code that still calls .format()
        print("This method is deprecated, please use invoke instead")
        return self.invoke(input_dict)
⭐ Interview Important: an ABC with @abstractmethod forces subclasses to implement invoke() — skipping it raises TypeError: Can't instantiate abstract class ... with abstract method invoke. That's how LangChain guarantees a shared interface. Old methods (predict, format) aren't deleted (would break users) — kept as thin wrappers around invoke() with a deprecation notice.

RunnableConnector — chaining any list of standardized components

class RunnableConnector(Runnable):
    def __init__(self, runnable_list):
        self.runnable_list = runnable_list

    def invoke(self, input_data):
        for runnable in self.runnable_list:
            input_data = runnable.invoke(input_data)
        return input_data

template = FakePromptTemplate(
    template="Write a {length} poem about {topic}",
    input_variables=["length", "topic"],
)
llm = FakeLLM()

chain = RunnableConnector([template, llm])
print(chain.invoke({"length": "long", "topic": "India"}))

A third standardized component extends the chain with zero new custom code:

class FakeStrOutputParser(Runnable):
    def invoke(self, input_data):
        return input_data["response"]

parser = FakeStrOutputParser()
chain = RunnableConnector([template, llm, parser])
print(chain.invoke({"length": "long", "topic": "India"}))
# now prints a plain string instead of a dict

Chaining chains together (principle 4)

template1 = FakePromptTemplate(
    template="Write a joke about {topic}",
    input_variables=["topic"],
)
template2 = FakePromptTemplate(
    template="Explain the following joke {response}",
    input_variables=["response"],
)
llm = FakeLLM()
parser = FakeStrOutputParser()

chain1 = RunnableConnector([template1, llm])          # topic → joke (dict)
chain2 = RunnableConnector([template2, llm, parser])  # joke → explanation (string)

final_chain = RunnableConnector([chain1, chain2])
print(final_chain.invoke({"topic": "cricket"}))

Two Categories of Runnables (⭐ Interview Important)

CategoryDefinitionExamples
Task-specific RunnablesCore components (each with a real purpose) converted into Runnables for use in pipelines.ChatOpenAI (LLM), PromptTemplate (prompts), a Retriever (semantic search)

⭐ Interview Important: the hand-built RunnableConnector (loop feeding each output to the next) is conceptually LangChain's real RunnableSequence. This video: the five most-used primitives, each with a demo.

1. RunnableSequence

⭐ Interview Important — Definition: connects two or more Runnables sequentially — each output becomes the next input. No limit on count.
from langchain_openai import ChatOpenAI
from langchain_core.prompts import PromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain.schema.runnable import RunnableSequence
from dotenv import load_dotenv

load_dotenv()

prompt = PromptTemplate(template="Write a joke about {topic}", input_variables=["topic"])
model = ChatOpenAI()
parser = StrOutputParser()

chain = RunnableSequence(prompt, model, parser)
print(chain.invoke({"topic": "AI"}))

Longer chain (generate a joke, then explain it — six Runnables):

prompt1 = PromptTemplate(template="Write a joke about {topic}", input_variables=["topic"])
prompt2 = PromptTemplate(template="Explain the following joke {text}", input_variables=["text"])

chain = RunnableSequence(prompt1, model, parser, prompt2, model, parser)
print(chain.invoke({"topic": "AI"}))
# only the FINAL step's output (the explanation) is printed — the joke itself isn't surfaced
⭐ Interview Important: a plain RunnableSequence returns only the last step's output — intermediates (the joke itself) aren't exposed. That's what RunnablePassthrough solves.

2. RunnableParallel

⭐ Interview Important — Definition: runs multiple Runnables in parallel; every branch gets the same input; result is a dictionary keyed by branch name.

Example: from one topic, a tweet (one LLM/prompt) and a LinkedIn post (another) simultaneously.

from langchain.schema.runnable import RunnableSequence, RunnableParallel

prompt1 = PromptTemplate(template="Generate a tweet about {topic}", input_variables=["topic"])
prompt2 = PromptTemplate(template="Generate a Linkedin post about {topic}", input_variables=["topic"])
model = ChatOpenAI()
parser = StrOutputParser()

parallel_chain = RunnableParallel({
    "tweet": RunnableSequence(prompt1, model, parser),
    "linkedin": RunnableSequence(prompt2, model, parser),
})

result = parallel_chain.invoke({"topic": "AI"})
print(result["tweet"])
print(result["linkedin"])

3. RunnablePassthrough

⭐ Interview Important — Definition: returns its input completely unchanged. passthrough.invoke(2) → 2; passthrough.invoke({"name": "nitish"}) → same dict.

Why useful: only the last step's output survives a sequence. To keep an earlier value (the joke, alongside its explanation), route it through a RunnablePassthrough branch inside a RunnableParallel, next to the branch that keeps processing it.

from langchain.schema.runnable import RunnableSequence, RunnableParallel, RunnablePassthrough

prompt1 = PromptTemplate(template="Write a joke about {topic}", input_variables=["topic"])
prompt2 = PromptTemplate(template="Explain the following joke {text}", input_variables=["text"])
model = ChatOpenAI()
parser = StrOutputParser()

joke_gen_chain = RunnableSequence(prompt1, model, parser)

parallel_chain = RunnableParallel({
    "joke": RunnablePassthrough(),
    "explanation": RunnableSequence(prompt2, model, parser),
})

final_chain = RunnableSequence(joke_gen_chain, parallel_chain)
result = final_chain.invoke({"topic": "cricket"})
print(result)   # {"joke": "...", "explanation": "..."}

4. RunnableLambda

⭐ Interview Important — Definition: converts any plain Python function (incl. lambda) into a Runnable, so custom logic can be plugged into a chain.

Uses: pre-processing before an LLM call (lowercasing, stripping HTML tags/punctuation/emojis, lemmatization) so dirty data doesn't hurt performance; or deterministic post-processing an LLM shouldn't be trusted with (e.g. counting words).

from langchain.schema.runnable import RunnableLambda

def word_counter(text):
    return len(text.split())

runnable_word_counter = RunnableLambda(word_counter)
print(runnable_word_counter.invoke("hi my name is nitish"))   # 5

# equivalent, more compact form (the reason it's called "Runnable-Lambda"):
runnable_word_counter = RunnableLambda(lambda x: len(x.split()))

In a chain — joke + its word count, without asking the LLM to count (LLMs are unreliable at counting):

joke_gen_chain = RunnableSequence(prompt, model, parser)

parallel_chain = RunnableParallel({
    "joke": RunnablePassthrough(),
    "word_count": RunnableLambda(lambda x: len(x.split())),
})

final_chain = RunnableSequence(joke_gen_chain, parallel_chain)
result = final_chain.invoke({"topic": "AI"})

final_result = "{} \nword count - {}".format(result["joke"], result["word_count"])
print(final_result)

Same passthrough + parallel shape as above, second branch a RunnableLambda instead of an LLM sub-chain: {"joke": RunnablePassthrough(), "word_count": RunnableLambda(...)} replaces {"joke": ..., "explanation": ...}.

5. RunnableBranch

⭐ Interview Important — Definition: LangChain's if/else for Runnables — routes down exactly one branch by condition, when downstream processing depends on upstream output (e.g. classify an email as complaint / refund request / general query, handle each differently).

Demo: detailed report on a topic; if > 500 words, summarize with another LLM call; else print as-is.

from langchain.schema.runnable import RunnableSequence, RunnableBranch, RunnablePassthrough

prompt1 = PromptTemplate(template="Write a detailed report on {topic}", input_variables=["topic"])
prompt2 = PromptTemplate(template="Summarize the following text \n {text}", input_variables=["text"])
model = ChatOpenAI()
parser = StrOutputParser()

report_gen_chain = RunnableSequence(prompt1, model, parser)

branch_chain = RunnableBranch(
    (lambda x: len(x.split()) > 500, RunnableSequence(prompt2, model, parser)),
    RunnablePassthrough(),   # default: report is short enough, print as-is
)

final_chain = RunnableSequence(report_gen_chain, branch_chain)
print(final_chain.invoke({"topic": "Russia vs Ukraine"}))
⭐ Interview Important — RunnableBranch syntax: any number of (condition, runnable) tuples checked in order (if/elif) plus one final condition-less Runnable as else/default. Each condition is a function (often a lambda) receiving the previous output.

LCEL — LangChain Expression Language

⭐ Interview Important: RunnableSequence is by far the most common pattern (inside parallel branches, passthrough branches, branch arms, everywhere), so LangChain added a shorter declarative syntax for it: the | (pipe) operator.
# these two are equivalent:
chain = RunnableSequence(prompt, model, parser)
chain = prompt | model | parser

This pipe syntax — LCEL — is a drop-in replacement wherever a RunnableSequence is used, including inside a RunnableBranch tuple.

⭐ Interview Important — current scope of LCEL: as of this video, | exists only for RunnableSequence; RunnableParallel, RunnableBranch, etc. are written explicitly (e.g. a dict for parallel). Presenter's speculation (not a confirmed roadmap): LCEL may gain syntax for others (e.g. hypothetical R1 & R2 for parallel).

What Is RAG? (⭐ Interview Important)

Plain chat LLM tools (e.g. ChatGPT) fail on:

  • Current affairs — training data has a past cutoff.
  • Personal data — e.g. your recent emails.
  • Private/internal data — e.g. your company's internal docs.
⭐ Interview Important — Definition:
RAG is a technique that combines information retrieval with language generation: a model retrieves relevant documents from an external knowledge base and then uses them as context to generate accurate, grounded responses.

The knowledge base can be anything — company DB, PDFs, personal documents — connected so the LLM can look up what it doesn't know.

⭐ Interview Important — Benefits of RAG:
  1. Up-to-date information — beyond training data.
  2. Privacy — confidential docs aren't uploaded to a third-party chat tool; they stay in your own knowledge base.
  3. No document size limit — a huge doc won't fit the context window whole; RAG chunks it and retrieves only relevant chunks per query.

The Four Core RAG Components (⭐ Interview Important)

Almost any RAG app is built from four: Document Loaders, Text Splitters, Vector Databases, Retrievers. This video: Document Loaders; the rest follow, then a full RAG app.

What Are Document Loaders? (⭐ Interview Important)

⭐ Interview Important — Definition:
Document Loaders are LangChain components used to load data from various sources into a standardized format — usually as Document objects — which can then be used for chunking, embedding, retrieval, and generation.

Sources vary (PDFs, text files, databases, cloud storage...); every loader returns the same shape, a Document with:

  • page_content — the text.
  • metadata — source, creation/modification date, author, page number, etc.
⭐ Interview Important: every loader, regardless of source, returns a list of Document objects — memorize this universal pattern.

What Is Text Splitting & Why It Matters (⭐ Interview Important)

⭐ Interview Important — Definition:
Text splitting is the process of breaking large chunks of text (articles, PDFs, HTML pages, books) into smaller, manageable pieces that an LLM can handle effectively. The code/component that does this is a Text Splitter.

Why it's essential:

  1. Context-length limits — every LLM has a max input (e.g. 50,000 tokens); a 100,000+ word document can't go in one call.
  2. Better embeddings — one vector for a huge text captures meaning poorly (too much compressed into too few numbers). Separate chunks embed far more precisely (paragraphs on CSK, RCB, MI as three chunks, not one).
  3. Better semantic search — empirically more accurate over chunked, separately-embedded docs than one giant blob.
  4. Better summarization & downstream tasks — on huge inputs LLMs drift off-topic or hallucinate; chunk-by-chunk is more reliable.
  5. Computational efficiency — smaller chunks use less memory and can be processed in parallel.

Four techniques: length-based, text-structure-based, document-structure-based, semantic-meaning-based.

1. Length-Based Text Splitting

⭐ Interview Important — Definition: simplest, fastest: pre-decide a fixed chunk size (characters or tokens) and cut a new chunk each time it's reached — no regard for words, sentences or meaning.
from langchain.text_splitter import CharacterTextSplitter

splitter = CharacterTextSplitter(
    chunk_size=100,
    chunk_overlap=0,
    separator="",   # cut purely on character count
)
chunks = splitter.split_text(text)
print(len(chunks))
print(chunks[0])

With a Document Loader (splitting loaded PDF pages):

from langchain_community.document_loaders import PyPDFLoader

loader = PyPDFLoader("dl-curriculum.pdf")
docs = loader.load()

chunks = splitter.split_documents(docs)   # note: split_documents, not split_text
print(chunks[0].page_content)             # each chunk is itself still a Document object
⭐ Interview Important — Pros/Cons: Pro: trivial, easy, very fast. Con: ignores structure, grammar and meaning — cuts mid-word/sentence/paragraph, splitting related info across disconnected chunks and hurting embedding quality. Rarely used in practice.

chunk_overlap

⭐ Interview Important — Definition: number of characters repeated at the boundary between consecutive chunks. Each chunk starts a little before the previous one ended, so information at a cut is preserved in both.
⭐ Interview Important — Trade-off & rule of thumb: more overlap → more context, but more chunks → more compute; less overlap → cheaper, more context-loss risk. RAG guideline: overlap 10–20% of chunk_size (chunk_size 100 → overlap 10–20).

2. Text-Structure-Based Splitting (RecursiveCharacterTextSplitter)

⭐ Interview Important — Definition: exploits text's hierarchy — paragraphs → sentences → words → characters. One of the most widely used LangChain splitters.

Tries separators coarsest to finest, falling back only when a piece still exceeds chunk_size:

⭐ Interview Important: after breaking at a level, it greedily re-merges adjacent pieces (without exceeding chunk_size) — so a larger chunk_size settles at paragraph-level splits, a very small one forces word/character-level splits.
from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(chunk_size=100, chunk_overlap=0)
chunks = splitter.split_text(text)
print(len(chunks))
print(chunks[0])
⭐ Interview Important: the most commonly used splitter — respects sentence/paragraph boundaries far better than length-based, so better context preservation.

3. Document-Structure-Based Splitting

⭐ Interview Important: some documents aren't paragraph/sentence text — code (organized by class/def/loops), Markdown (headings/lists). This is just RecursiveCharacterTextSplitter with a language-aware separator list.
from langchain.text_splitter import RecursiveCharacterTextSplitter, Language

python_splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.PYTHON,
    chunk_size=300,
    chunk_overlap=0,
)
chunks = python_splitter.split_text(python_code)
print(chunks[0])   # e.g. everything up through the class's constructor

Same for Markdown (split at headings) and many languages (JavaScript, Java, PHP, HTML, ...) via Language.MARKDOWN, Language.JS, etc. — LangChain ships separator presets per language/format.

md_splitter = RecursiveCharacterTextSplitter.from_language(
    language=Language.MARKDOWN,
    chunk_size=200,
    chunk_overlap=0,
)
⭐ Interview Important: tune chunk_size per document — too small cuts code mid-construct; a good size lands on structural boundaries (one chunk = a class's constructor, one = a method).

4. Semantic-Meaning-Based Splitting

Length- and structure-based both fail when one paragraph covers multiple unrelated topics (e.g. agriculture, then mid-paragraph cricket, followed by a paragraph on terrorism) — paragraph/sentence splitting still lumps agriculture + cricket into one chunk.

⭐ Interview Important — Definition: splits by meaning, not length or structure. Embeds each sentence, compares similarity of consecutive pairs with a sliding window; a sudden similarity drop = topic boundary = split point.

"Suddenly low" is set by a threshold type: percentile, standard deviation, interquartile range, or gradient. E.g. standard deviation: compute similarity (or distance) for every consecutive pair, take the std-dev of that set, break where distance exceeds N std-devs.

from langchain_experimental.text_splitter import SemanticChunker
from langchain_openai import OpenAIEmbeddings

splitter = SemanticChunker(
    OpenAIEmbeddings(),
    breakpoint_threshold_type="standard_deviation",
    breakpoint_threshold_amount=1,   # split wherever distance > 1 standard deviation
)
docs = splitter.create_documents([text])
print(len(docs))
⭐ Interview Important: SemanticChunker lives in langchain_experimental (explicitly experimental). Higher threshold (e.g. 3 std-devs) → more tolerant of context change, fewer/larger chunks; lower → more, smaller chunks. Hands-on results were inconsistent (boundaries sometimes in the wrong chunk) — promising, not yet as reliable as RecursiveCharacterTextSplitter.

Why Vector Stores? Movie Recommender Case Study

Example: IMDb-style movie site with a recommender ("liked this? you'll like these").

⭐ Interview Important — Naive approach and its flaw: keyword matching. Compare metadata (director, actor, genre, release date); enough matches = "similar."
  • False positive: My Name Is Khan and Kabhi Alvida Naa Kehna share director (Karan Johar), lead (Shah Rukh Khan), era and genre (drama) → rated highly similar, but the stories are completely different.
  • False negative: Taare Zameen Par and A Beautiful Mind are thematically very similar (a struggling central character who is brilliant in another way) but share almost no metadata → never surfaced.
⭐ Interview Important — The fix: compare plots via embeddings, not keywords. Semantically similar plots → similar movies, regardless of cast/director. Needs: (1) each movie's plot text, (2) an embedding model to turn plots into meaning vectors, (3) vector comparison (cosine similarity / angular distance) to find the closest.

Three Challenges — Solved by Vector Stores (⭐ Interview Important)

  1. Generating embeddings — possibly millions of movies each need a vector.
  2. Storage — vectors are generated once and reused; relational DBs (MySQL, Oracle) can't compute vector similarity — purpose-built storage needed.
  3. Efficient semantic search — comparing a query against all of, say, 1,000,000 vectors (linear, O(n)) is far too slow.
⭐ Interview Important: all three are exactly what a Vector Store solves.

What Is a Vector Store? (⭐ Interview Important)

⭐ Interview Important — Definition:
A vector store is a system designed to store and retrieve data represented as numerical vectors.

Four key features:

  1. Storage — vectors + metadata, in-memory (fast, non-persistent — gone on app close) or on-disk (persistent; larger/production apps).
  2. Similarity search — retrieve vectors most similar to a query vector.
  3. Indexing — data structure/method for fast search over high-dimensional vectors, avoiding linear comparison.
  4. CRUD operations — add, retrieve, update, delete.

How Indexing Works — Clustering Example

One-by-one comparison against 1,000,000 vectors is O(n), too slow. Common approach: cluster all vectors first, then search only the most relevant cluster.

Use Cases

Recommender systems, semantic search in any domain, RAG (heavy use), image/multimedia search. Any app storing/retrieving vectors does far better with a vector store than a relational DB, which isn't built for vector storage or similarity.

Vector Store vs. Vector Database (⭐ Interview Important)

Often used interchangeably online — a common confusion.

⭐ Interview Important — The distinction: a vector store is a lightweight library/service for storing vectors + similarity search. A vector database = vector store plus DB features: distributed architecture (scaling), durability (backup/restore), ACID transactions, concurrency control (simultaneous users), authentication/authorization.
⭐ Interview Important: every vector database is a vector store, not vice versa. Lightweight store: FAISS (Facebook) — prototyping/small apps. Full vector DBs: Milvus, Qdrant, Weaviate, Pinecone — production, at scale.

Vector Stores in LangChain (⭐ Interview Important)

⭐ Interview Important: LangChain foresaw embeddings/vector stores being central (esp. RAG), so it wraps essentially every major store (FAISS, Pinecone, Chroma, Qdrant, Weaviate, ...) and all wrappers share the same method signatures (from_documents/from_texts to create, add_documents/add_texts to insert, similarity_search to query, metadata filtering, etc.). Swapping stores (e.g. Chroma → Pinecone as an app scales) needs almost no other code changes.

Chroma DB

⭐ Interview Important — Definition: lightweight, open-source vector DB, friendly for local dev and small-to-medium production. Sits between a pure vector store and a full vector DB — lighter than Pinecone, more DB-like structure than FAISS.

Hierarchy: Tenant (user/org/team) → multiple Databases → multiple Collections (like a relational table) → multiple Documents (embedding vector + metadata).

What Are Retrievers? (⭐)

⭐ Definition:
A retriever is a component in LangChain that fetches relevant documents from a data source in response to a user's query.

Source = anything (vector store, API, website...); the retriever searches it and returns the most relevant docs.

⭐ Key points:
  1. LangChain has many retrievers (20-30+) for different sources/search needs.
  2. Every retriever is a Runnable — has invoke(), plugs into chains.

Two Ways to Categorize Retrievers (⭐)

Categorization axisMeaningExamples
By data sourceWhat it searchesWikipediaRetriever, Vector Store Retriever, Arxiv Retriever (research papers)
By search strategyHow it decides relevanceMMR, Multi-Query Retriever, Contextual Compression Retriever

Most useful of each covered; LangChain docs list the rest.

1. WikipediaRetriever (data-source)

⭐ Definition: Queries the Wikipedia API for content relevant to a query, returned as Document objects.
from langchain_community.retrievers import WikipediaRetriever

retriever = WikipediaRetriever(top_k_results=2, lang="en")

query = "the geopolitical history of india and pakistan from the perspective of a chinese person"
docs = retriever.invoke(query)

for doc in docs:
    print(doc.page_content)
⭐ Retriever, not loader: it doesn't load all of Wikipedia — keyword-matches the query to pick relevant articles, fetches only those. That search step makes it a retriever.

2. Vector Store Retriever (data-source)

⭐ Definition: Most common — fetches docs from a vector store by embedding similarity.
from langchain_openai import OpenAIEmbeddings
from langchain.vectorstores import Chroma

vector_store = Chroma.from_documents(docs, embedding=OpenAIEmbeddings(), collection_name="sample")
retriever = vector_store.as_retriever(search_kwargs={"k": 2})

results = retriever.invoke("What is Chroma used for?")
⭐ Why not vector_store.similarity_search()? Equivalent for plain similarity, but that's its only strategy. as_retriever() gives (1) a Runnable for chains, (2) swappable advanced strategies (MMR, multi-query, contextual compression).

3. Maximum Marginal Relevance (MMR) — search-strategy

Problem: similarity search may return near-duplicates (three "glaciers are melting" docs) instead of distinct relevant ones (deforestation, wildfires, coastal flooding).

⭐ Definition: MMR is an information retrieval algorithm that reduces redundancy in retrieved results while maintaining high relevance to the query. Picks the most relevant doc, then repeatedly the next one that is relevant and most dissimilar to those picked.
retriever = vector_store.as_retriever(
    search_type="mmr",
    search_kwargs={"k": 3, "lambda_mult": 0.5},
)
results = retriever.invoke("What is Langchain?")
⭐ lambda_mult: 0–1. 1 = plain similarity; 0 = max diversity; ~0.5 balances — tune per use case.

4. Multi-Query Retriever — search-strategy

Problem: ambiguous queries ("How can I stay healthy?" — diet, exercise, stress?) give unfocused results.

⭐ Definition: An LLM generates several reworded versions of the query; each runs through the base retriever; results are merged and de-duplicated.
from langchain.retrievers.multi_query import MultiQueryRetriever

similarity_retriever = vector_store.as_retriever(search_type="similarity", search_kwargs={"k": 5})

multiquery_retriever = MultiQueryRetriever.from_llm(
    retriever=vector_store.as_retriever(search_kwargs={"k": 5}),
    llm=ChatOpenAI(),
)

query = "How to improve energy levels and maintain balance?"
print(similarity_retriever.invoke(query))    # can drift — e.g. a stray "solar system" doc slips in
print(multiquery_retriever.invoke(query))    # stays focused on health/nutrition
⭐ Demonstrated result: mixed store (health/nutrition + solar system, Python...); query "How to improve energy levels and maintain balance?" — similarity search pulled a "solar system" doc (it mentioned "energy", "balance"); MultiQueryRetriever kept all 5 on health/nutrition, since the variants disambiguated intent.

5. Contextual Compression Retriever — search-strategy

Problem: a chunk can mix topics (splitter cut mid-paragraph), e.g. Grand Canyon + photosynthesis. A photosynthesis query matches it, but the whole chunk adds irrelevant text — worse answers, wasted context.

⭐ Definition: Compresses docs after retrieval — an LLM compressor keeps only the query-relevant parts of each.
from langchain.retrievers.contextual_compression import ContextualCompressionRetriever
from langchain.retrievers.document_compressors import LLMChainExtractor

base_retriever = vector_store.as_retriever(search_kwargs={"k": 5})
compressor = LLMChainExtractor.from_llm(ChatOpenAI())

compression_retriever = ContextualCompressionRetriever(
    base_retriever=base_retriever,
    base_compressor=compressor,
)

docs = compression_retriever.invoke("What is photosynthesis?")
for doc in docs:
    print(doc.page_content)
# each result is now a single trimmed sentence about photosynthesis —
# the unrelated Grand Canyon / basketball / cinema sentences sharing the same
# original chunk are discarded
⭐ When to use: long mixed-content docs; cutting context sent to the LLM; improving RAG accuracy.

Conceptual (first of two RAG videos): why RAG exists — via what came before — and how the pipeline works.

Why RAG? — Parametric Knowledge

⭐ Parametric knowledge: LLMs are transformers pre-trained on ~internet-scale data; their knowledge lives only in weights and biases — hence parametric; more parameters (7B → 13B → 70B...) ≈ more capable.

Accessed via prompting (prompt → interpret → generate word-by-word). Fails in three cases:

ProblemWhy it happens
1. Private dataCompany docs, personal emails, a course's videos — never in pre-training.
2. Recent / current dataKnowledge cutoff date; later events unknown. (ChatGPT handles some via separate internet search; a base/open-source model can't.)
3. HallucinationProbabilistic generation, not fact-lookup — confident fabrications (Einstein played pro football). Inherent, not rare.

Attempt 1: Fine-Tuning

⭐ Definition: Continue training a pretrained LLM on a smaller domain-specific dataset to add specialized knowledge.

Analogy: pre-training = engineering degree; fine-tuning = 2-3 month on-the-job training.

Types of Fine-Tuning

TypeHow it works
Supervised Fine-Tuning (SFT)Most common; labeled (prompt, desired output) pairs, typically 1,000–1,000,000.
Continued Pre-trainingUnsupervised — raw domain text (e.g. course transcripts), trained like pre-training on a smaller corpus.
RLHFReinforcement Learning from Human Feedback — appropriate real-world behavior.
LoRA / QLoRAParameter-efficient — freeze base weights, train a small extra set.

Supervised Fine-Tuning — 4 Steps (⭐)

  1. Collect domain data — labeled (prompt, output) pairs.
  2. Choose a method — full-parameter vs. LoRA/QLoRA.
  3. Train — few epochs (expensive).
  4. Evaluate — exact match, factuality, hallucination rate, safety.

Fine-Tuning vs the Three Problems

It can solve all three: private data → parametric; updated data → recency (per domain); "don't know → say so" examples → less hallucination.

⭐ Why it's often impractical:
  1. Expensive — even a small dataset on a huge model costs real compute.
  2. Needs expertise — ML/AI engineers, data scientists.
  3. Redo per update — every catalog change/removal means re-training; bad for fast-changing domains.

Attempt 2: In-Context Learning

⭐ Definition: LLMs (GPT-3, Claude, LLaMA...) solving a task from examples inside the prompt — no weight updates.

Example (few-shot prompting, sentiment):

Below are examples of text labeled with their sentiment. Use the examples to
determine the sentiment of the final text.

"I love this phone. It's so smooth." → Positive
"This app crashes a lot." → Negative
"The camera is amazing." → Positive
"I hate the battery life." → ?

Model answers "Negative" without retraining; works for NER, math, domain tasks too.

⭐ An emergent property: behavior that appears once a system crosses a scale threshold, undesigned. GPT-1/2 lacked it reliably; at GPT-3 scale (~175B) it emerged — named in "Language Models are Few-Shot Learners" (the GPT-3 paper).

Paper's point: per-task fine-tuning needs 10,000–1,000,000 labeled rows; humans learn from a few examples + instructions, and so could GPT-3. Later models (3.5, 4...) improved via SFT and RLHF.

From In-Context Learning to RAG

⭐ Key upgrade: instead of generic examples, inject the actual context for this query into the prompt. That is RAG.

Example: 2-hour Linear Regression lecture; doubt on Gradient Descent (min 5–25) → send only that ~20-min transcript with the question.

⭐ Definition:
RAG (Retrieval-Augmented Generation) is a way to make a language model smarter by giving it extra information at the time you ask your question.
You are a helpful assistant. Answer the question only from the provided context.
If the context is insufficient, just say "I don't know."

Context: {retrieved transcript segment}
Question: {student's question}

How RAG Works: The 4-Stage Pipeline (⭐)

Information Retrieval (classic CS) + Text Generation (LLMs), in four stages:

Stage 1 — Indexing

⭐ Definition: Preparing the knowledge base for efficient query-time search (detailed in the last four videos). Sub-steps:
  1. Document ingestion — loaders (PyPDFLoader, YouTube loader, WebBaseLoader...) from server, Google Drive, S3...
  2. Text chunking — semantic chunks (e.g. RecursiveCharacterTextSplitter); needed for context limits and good semantic search.
  3. Generate embeddings — chunk → dense vector (OpenAI, sentence-transformers...).
  4. Store in a vector store — vector + chunk text + metadata (FAISS, Chroma, Pinecone, Weaviate, Milvus, Qdrant...) — this is the external knowledge base.

Stage 2 — Retrieval

⭐ Definition: Real-time lookup of the most relevant pieces of the index — "which 3-5 chunks help most?"

A retriever:

  1. Embeds the query with the same model as indexing (same space/dimensions).
  2. Finds closest vectors — similarity or advanced (MMR, compression...).
  3. Ranks them (cosine similarity or re-ranking).
  4. Returns top chunks' text = the context.

Stage 3 — Augmentation

⭐ Interview: Query + context merged into one prompt — where parametric knowledge gets "augmented".

Stage 4 — Generation

⭐ Interview: The LLM uses generation + in-context learning to answer grounded in the injected context.

How RAG Solves the Three Problems (⭐)

ProblemHow RAG solves it
Private dataKnowledge base is built from your data.
Recent / current dataAdd docs (embed + store) — no retraining.
HallucinationPrompt: answer only from context, else "I don't know".

RAG vs. Fine-Tuning (⭐)

⭐ Interview: RAG is cheaper and simpler — no training; updates = new docs in the vector store. Fine-tuning still suits changing behavior/style; for private, changing or grounding-sensitive knowledge, RAG is the default.

Problem Statement

Plan of Action (⭐ maps onto the 4-stage RAG architecture)

  1. Indexing — fetch transcript → split into chunks → embed → store in vector store.
  2. Retrieval — retriever embeds the query and semantically searches for the most relevant chunks.
  3. Augmentation — merge retrieved chunks + query into one prompt.
  4. Generation — send prompt to LLM, return response.

Each stage is built manually first, then wired into one LangChain chain so a single invoke() runs everything.

Step 1a — Fetching the Transcript

⭐ Interview: Uses the youtube-transcript-api package directly against YouTube's transcript API instead of LangChain's YoutubeLoader (buggy/inconsistent across videos) — more reliable.

except TranscriptsDisabled:

⭐ Interview: The API returns a list of dicts, one per subtitle line: text, start timestamp, duration (time on screen); join into one string. No English captions (e.g. Hindi) → languages=["hi"] (or whatever exists).

from langchain.text_splitter import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)
chunks = splitter.create_documents([transcript])
# e.g. a ~2-hour podcast transcript → 168 chunks

Step 1c — Embeddings + Vector Store

from langchain_openai import OpenAIEmbeddings
from langchain_community.vectorstores import FAISS

embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
vector_store = FAISS.from_documents(chunks, embeddings)
# each chunk is now assigned an ID and embedded into the vector store

Indexing done — this is the knowledge base.

Step 2 — Retrieval

retriever = vector_store.as_retriever(search_type="similarity", search_kwargs={"k": 4})

results = retriever.invoke("What is deepmind?")
# returns the 4 chunks the retriever judges most relevant to this query
⭐ Retriever contract: input = query string, output = list of Document objects — held when tested on the transcript.

Step 3 — Augmentation

from langchain_openai import ChatOpenAI
from langchain_core.prompts import PromptTemplate

llm = ChatOpenAI(model="gpt-4o-mini")

prompt = PromptTemplate(
    template="""
      You are a helpful assistant.
      Answer ONLY from the provided transcript context.
      If the context is insufficient, just say you don't know.

      {context}
      Question: {question}
    """,
    input_variables=["context", "question"],
)

question = "Is the topic of nuclear fusion discussed in this video? If yes then what was discussed?"
retrieved_docs = retriever.invoke(question)

Retriever returns a list of Documents but the prompt template needs a string — join their page_content manually:

context_text = "\n\n".join(doc.page_content for doc in retrieved_docs)
final_prompt = prompt.invoke({"context": context_text, "question": question})

Step 4 — Generation

answer = llm.invoke(final_prompt)
print(answer.content)
# e.g. "Yes, the topic of nuclear fusion is discussed in the video. ..."

All four stages work, but each was called separately (retriever, then prompt, then LLM). Next: wire into one chain so one invoke() runs it all.

Building the Full Chain

⭐ Chain structure: two chains. prompt | llm | parser needs context and question: question passes through; context = question → retriever → docs formatted to a string. Preparing both in parallel = RunnableParallel + RunnablePassthrough + RunnableLambda (Runnable Primitives video).
from langchain_core.runnables import RunnableParallel, RunnablePassthrough, RunnableLambda
from langchain_core.output_parsers import StrOutputParser

def format_docs(retrieved_docs):
    return "\n\n".join(doc.page_content for doc in retrieved_docs)

parallel_chain = RunnableParallel({
    "context": retriever | RunnableLambda(format_docs),
    "question": RunnablePassthrough(),
})

parallel_chain.invoke("Who is Demis?")
# {"context": "...", "question": "Who is Demis?"}
parser = StrOutputParser()
main_chain = parallel_chain | prompt | llm | parser

print(main_chain.invoke("Can you summarize the video?"))
# one call now runs retrieval, augmentation and generation automatically

Why Tools Exist — LLMs Can Think and Speak, But Not Act

⭐ Interview: LLMs have two core capabilities: reasoning and language generation only — no live weather, reliable complex math, APIs, tweeting, running code or DB queries.

What Is a Tool? (⭐)

⭐ Definition:

⭐ Interview Important — Agent definition: An AI agent is an LLM-powered system that can autonomously think, decide, and take actions using external tools and APIs to achieve a goal. Tools are as foundational as the LLM — hence covered first.

Custom Tools — Method 1: @tool Decorator

Needed for: your own app's API (e.g. a travel agent creating bookings), app-specific business logic, your own DB/product.

⭐ Interview Important — 3-step recipe:
  1. Write the function's logic (plain Python function).
  2. Add type hints for every input and the return value.
  3. Decorate with @tool.
Docstring (step 1) and type hints (step 2) are optional but highly recommended — they tell the LLM what the tool does and expects.
from langchain_core.tools import tool

@tool
def multiply(a: int, b: int) -> int:
    """Multiply two numbers"""
    return a * b

result = multiply.invoke({"a": 3, "b": 5})
print(result)  # 15

print(multiply.name)          # "multiply"
print(multiply.description)   # "Multiply two numbers"
print(multiply.args)          # {'a': {'title': 'A', 'type': 'integer'}, 'b': {...}}
⭐ Interview: Every tool object (built-in like DuckDuckGoSearchRun, or custom) has .name, .description, .args.

Custom Tools — Method 2: StructuredTool + Pydantic

⭐ Definition: Stricter: input follows an explicit (usually Pydantic) schema, not inferred type hints.
from langchain.tools import StructuredTool
from pydantic import BaseModel, Field

class MultiplyInput(BaseModel):
    a: int = Field(required=True, description="The first number to add")
    b: int = Field(required=True, description="The second number to add")

def multiply_func(a: int, b: int) -> int:
    return a * b

multiply_tool = StructuredTool.from_function(
    func=multiply_func,
    name="multiply",
    description="Multiply two numbers",
    args_schema=MultiplyInput,
)

result = multiply_tool.invoke({"a": 3, "b": 3})
⭐ Interview: schema, name, description declared explicitly in from_function. Preferred for production; @tool suffices for ~80-90% of cases.

Custom Tools — Method 3: Subclassing BaseTool

⭐ Interview: BaseTool is the abstract base of every tool (core interface); @tool and StructuredTool build on it. Subclassing = maximum control.
from langchain.tools import BaseTool
from typing import Type
from pydantic import BaseModel, Field

class MultiplyInput(BaseModel):
    a: int = Field(required=True, description="The first number to add")
    b: int = Field(required=True, description="The second number to add")

class MultiplyTool(BaseTool):
    name: str = "multiply"
    description: str = "Multiply two numbers"
    args_schema: Type[BaseModel] = MultiplyInput

    def _run(self, a: int, b: int) -> int:
        return a * b

multiply_tool = MultiplyTool()
result = multiply_tool.invoke({"a": 3, "b": 3})
⭐ Interview: Method must be named _run (required by BaseTool). Only this approach supports an async version of a tool (for concurrency) — @tool and StructuredTool don't.

Video 19: Tool Calling — Binding, Calling & Executing Tools

How an LLM and tools connect and how the LLM invokes one — foundation for agents.

Recap

LLMs can reason and generate language but can't act (APIs, reliable math, DBs); tools are functions packaged so an LLM can request them.

1. Tool Binding

⭐ Definition: Registering one or more tools with an LLM so it knows: (1) which tools exist, (2) what each does (description), (3) what input schema each expects.
from langchain_core.tools import tool
from langchain_openai import ChatOpenAI

@tool
def multiply(a: int, b: int) -> int:
    """Given 2 numbers a and b this tool returns their product"""
    return a * b

llm = ChatOpenAI()
llm_with_tools = llm.bind_tools([multiply])   # pass a list — can bind multiple tools
⭐ Interview: Not every LLM supports tool binding — check LangChain docs for which chat models support tool calling.

2. Tool Calling

⭐ Definition: During a conversation the LLM decides it needs a specific tool and generates structured output naming the tool plus the arguments to call it with.
llm_with_tools.invoke("Hi, how are you?")
# a normal AIMessage with actual text content — no tool needed

response = llm_with_tools.invoke("can you multiply 3 with 10")
print(response.content)     # "" — empty!
print(response.tool_calls)  # [{'name': 'multiply', 'args': {'a': 3, 'b': 10}, 'id': '...', 'type': 'tool_call'}]
⭐ Interview: tool needed → empty .content + a .tool_calls list (may hold several), each with name, suggested args, unique call id, type: "tool_call".
⭐ Common misconception: the LLM does not run the tool — it only suggests name + args; the programmer/LangChain executes. Intentional: free execution is risky (wrong/harmful actions).

3. Tool Execution

⭐ Definition: The programmer runs the suggested tool with the exact arguments the LLM proposed.
# Option A: pass just the args dict — get the raw return value
result = multiply.invoke(response.tool_calls[0]["args"])   # 30

# Option B: pass the entire tool_call dict — get a ToolMessage back
tool_message = multiply.invoke(response.tool_calls[0])
print(tool_message)
# ToolMessage(content='30', name='multiply', tool_call_id='...')
⭐ ToolMessage: 4th message type (after SystemMessage, HumanMessage, AIMessage), from invoking a tool with the full tool-call dict; sent back to the LLM so the answer uses the real result.

Putting It Together: The Full Cycle

A running message history grounds the final answer in the tool's actual output:

from langchain_core.messages import HumanMessage

query = HumanMessage("can you multiply 3 with 10")
messages = [query]

ai_message = llm_with_tools.invoke(messages)
messages.append(ai_message)          # [Human, AI(tool_calls=[...])]

tool_result = multiply.invoke(ai_message.tool_calls[0])
messages.append(tool_result)         # [Human, AI, Tool]

final = llm_with_tools.invoke(messages)
print(final.content)   # "The product of 3 and 10 is 30."

Full Example: Real-Time Currency Conversion

An LLM can't reliably convert currencies — rates fluctuate and its knowledge is stale. Two tools fix this:

import requests
from langchain_core.tools import tool

@tool
def get_conversion_factor(base_currency: str, target_currency: str) -> float:
    """This function fetches the currency conversion factor between a given base currency and a target currency"""
    url = f"https://v6.exchangerate-api.com/v6/YOUR_API_KEY/pair/{base_currency}/{target_currency}"
    response = requests.get(url)
    return response.json()

@tool
def convert(base_currency_value: int, conversion_rate: float) -> float:
    """Given a currency conversion rate, this function calculates the target currency value from a given base currency value"""
    return base_currency_value * conversion_rate
llm_with_tools = llm.bind_tools([get_conversion_factor, convert])

messages = [HumanMessage(
    "What is the conversion factor between USD and INR, "
    "and based on that can you convert 10 USD to INR?"
)]
ai_message = llm_with_tools.invoke(messages)
messages.append(ai_message)

The Problem: Parallel Tool Calls With a Hidden Dependency

⭐ What went wrong: the LLM emitted both calls at once; convert needs conversion_rate, unknown until the first tool runs, so it hallucinated a plausible rate from stale training data (e.g. 73.73, an old USD→INR rate) — silently breaking the sequence.

The Fix: InjectedToolArg

⭐ Definition: Marking an argument InjectedToolArg tells the LLM "don't fill this in — the developer supplies it after running earlier tools." The LLM omits it from the tool call; the program injects the real value.
from langchain_core.tools import InjectedToolArg
from typing import Annotated

@tool
def convert(base_currency_value: int, conversion_rate: Annotated[float, InjectedToolArg]) -> float:
    """Given a currency conversion rate, this function calculates the target currency value from a given base currency value"""
    return base_currency_value * conversion_rate

Now ai_message.tool_calls has convert with only base_currency_value — conversion_rate is filled by the program:

import json

for tool_call in ai_message.tool_calls:
    if tool_call["name"] == "get_conversion_factor":
        tool_message_1 = get_conversion_factor.invoke(tool_call)
        conversion_rate = json.loads(tool_message_1.content)["conversion_rate"]
        messages.append(tool_message_1)

    if tool_call["name"] == "convert":
        # inject the real rate before executing this tool
        tool_call["args"]["conversion_rate"] = conversion_rate
        tool_message_2 = convert.invoke(tool_call)
        messages.append(tool_message_2)

final_response = llm_with_tools.invoke(messages)
print(final_response.content)
# "The conversion factor between USD and INR is X. Converting 10 USD to INR yields Y."
⭐ Interview: A raw API response is JSON, not a dict — parse tool_message.content with json.loads(...) before accessing "conversion_rate".

Pattern generalizes to any number of dependent tools: loop over tool_calls, execute in correct order, append each ToolMessage to messages, one final LLM call with full history.

Is This an AI Agent? (⭐)

⭐ No — why: an agent's defining trait is autonomy (breaks down and works through the problem itself). Here the programmer wrote the loop, order and injection — hardcoded. A true agent would reason: "rate unknown → call get_conversion_factor → have rate → call convert" with no human pre-wiring.

Why AI Agents? — Goa Trip Example

Delhi → Goa by hand: onward/return train or flight (price/availability), hotel (price, reviews, breakfast), attractions + itinerary, local transport (scooter rental), payments — tedious, multi-site, hard for less tech-savvy (e.g. older) users.

Value: many-step web tasks become one conversation, in any domain (support, education, travel...).

What Is an AI Agent, Technically? (⭐)

⭐ Definition:
An AI agent is an intelligent system that receives a high-level goal from a user and autonomously plans, decides, and executes a sequence of actions using external tools, APIs, and knowledge sources — all while maintaining context, reasoning over multiple steps, adapting to new information, and optimizing for the intended outcome.
⭐ Composition: agent = LLM (reasoning engine, decides) + Tools (act: APIs, DBs, web search). LLM alone can't act; tools alone can't judge when to fire.

Characteristics of an AI Agent (⭐)

  1. Goal-driven — you give the what, not the how.
  2. Plans and breaks down problems — goal → steps, executed one at a time.
  3. Tool-aware — knows its tools and when to use each.
  4. Maintains context — remembers what's done and what remains.
  5. Adaptive — replans when things change (API fails, new info).

What Is ReAct? (⭐)

⭐ Definition: ReAct ("Reasoning + Acting") is a design pattern for AI agents that lets a language model interleave internal reasoning with external actions in a structured, multi-step process — not single-turn Q → A.
  • Thought — what does it still need?
  • Action — pick a tool + input.
  • Observation — the tool's result.
⭐ Why useful: multi-step and tool-needing tasks (search, DB, APIs); transparent, auditable trace, not a black box. From the 2022 paper "ReAct: Synergizing Reasoning and Acting in Language Models."

Agent vs. AgentExecutor (⭐)

⭐ Interview: Agent = "thinker": from query + trace, produces the next Thought then an Action (tool + input) or a final answer. AgentExecutor = "doer": runs the loop — sends query + trace to the Agent, executes the chosen tool, records the Observation, updates the trace, repeats.

Building the Agent — create_react_agent

agent = create_react_agent(llm=llm, tools=[search_tool], prompt=prompt)

From an llm and a ReAct prompt (which must list the tools), returns an Agent object: given query + "agent scratchpad", it outputs a Thought then an Action or final answer.

Building the Orchestrator — AgentExecutor

agent_executor = AgentExecutor(agent=agent, tools=[search_tool], verbose=True)

Runs the Thought/Action/Observation loop and executes the chosen tools.

The Full ReAct Loop, Step by Step

⭐ Two object types: tool chosen → AgentAction (tool, tool_input, log). Done → AgentFinish (return_values with the answer, log).

Worked Example: "What is the capital of France and its population?"

  1. Iteration 1: Thought "find the capital first" → search "capital of France" → "Paris."
  2. Iteration 2: Thought "need Paris's population" → search "population of Paris" → "2.1 million."
  3. Iteration 3: Thought "I now know the final answer." → AgentFinish: "Paris is the capital of France and has a population of 2.1 million."
⭐ Interview: every iteration re-sends the whole growing scratchpad with the query — a multi-turn LLM exchange behind one question; that's the agent's "memory".

Tool Calling With Ollama

⭐ Definition: Gives an LLM external Python functions ("tools") for what it can't do (DB queries, live weather, today's news) — working around its cutoff and isolation.
⭐ Note: only models with tool-calling capability (per their Ollama model page) can reliably do it.

The Full Tool-Calling Workflow

import ollama, json

def check_inventory(product_name: str) -> dict:
    """Looks up a product in the inventory database."""
    ...  # returns stock + base price

def calculate_loyalty_discount(base_price: float, years_as_customer: int) -> float:
    """Calculates a final price after a loyalty discount (5%/year, capped at 30%)."""
    ...

tools_schema = [
    {"type": "function", "function": {
        "name": "check_inventory",
        "description": "Checks stock and price for a product",
        "parameters": {"type": "object", "properties": {
            "product_name": {"type": "string", "description": "Name of the product"}
        }, "required": ["product_name"]},
    }},
    {"type": "function", "function": {
        "name": "calculate_loyalty_discount",
        "description": "Calculates final price after loyalty discount",
        "parameters": {"type": "object", "properties": {
            "base_price": {"type": "integer", "description": "..."},
            "years_as_customer": {"type": "integer", "description": "..."},
        }, "required": ["base_price", "years_as_customer"]},
    }},
]

messages = [{"role": "user", "content": "I have been a customer for 5 years. What will be the final price of the laptop?"}]
response = ollama.chat(model="qwen3:8b", messages=messages, tools=tools_schema)
messages.append(response.message)

function_map = {"check_inventory": check_inventory, "calculate_loyalty_discount": calculate_loyalty_discount}

for tool_call in response.message.tool_calls:
    fn = function_map[tool_call.function.name]
    result = fn(**tool_call.function.arguments)
    messages.append({"role": "tool", "content": str(result)})

final = ollama.chat(model="qwen3:8b", messages=messages)
print(final.message.content)
⭐ Why chat(), not generate(): the tools parameter exists only on chat (history-based); generate() is single-turn.
⭐ Demonstrated result: the model itself ran check_inventory before calculate_loyalty_discount (no discount on out-of-stock items) — its reasoning, not hardcoded.
