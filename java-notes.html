Video 1: Introduction to Java: Why Java Exists

Why Java when C/C++ existed? It fixed three problems: Java is Portable, Simple, and Secure.

The Era Before Java (1980s–1990s)

C/C++ dominated: fast, relatively simple (English-like), low-level (close to hardware, few abstraction layers; you do what Python does internally).

Compiler & Machine Code

Computers understand only binary = machine code; a compiler (software) translates source into it. Evolution: machine code (raw 0/1) → Assembly (MOV, hardware-tied) → C/C++ (English-like).

Problem 1 with C/C++: Portability

C/C++ compile to one platform's machine code; other platforms need a recompile (platform-dependent).

What is a Platform?

⭐ Interview Important: Platform = Processor + Operating System (Intel x86 + Windows, ARM + macOS).

Why Same Source → Different Binaries?

1. Operating System → different system libraries

Printing, file I/O, memory allocation go through the OS: cout/printf call OS system libraries (precompiled methods) linked into the binary, and Windows/macOS expose different methods (hypothetical WriteToConsole vs WriteThere).

2. Processor → different ISA

A CPU = billions to trillions of transistors (on 1 / off 0). Intel and ARM lay out transistors, circuits, pins differently, so even "add two numbers" needs different binary. The ISA defines how add, load, store, jump are expressed.

⭐ Interview Important: ISA = Instruction Set Architecture, the processor's "grammar"; x86 and ARM need different machine code.
Platform componentWhat differsEffect on binary
Operating SystemSystem libraries / calls (console, files, memory)Different OS-level code linked in
ProcessorISA: instruction "grammar"Different machine instructions

All pre-Java languages compiled to machine code, so all were platform-dependent.

Problem 2: Simplicity

Complex C++ features: pointers, multiple inheritance, manual memory management (esp. deallocation).

Problem 3: Security

C++ was less secure, urgent once code traveled over the internet.

⭐ Interview Important: Why Java was created: portability, simplicity, security problems of C/C++.

Solution 1: Portable, via Bytecode + JVM

Analogy: C/C++ = learn Mandarin for China, Spanish for Spain; Java = one language plus a local translator.

  • javac compiles to bytecode (intermediate, not machine code): Hello.java → Hello.class, identical on every platform.
  • The JVM (Java Virtual Machine), per-platform software, translates bytecode step by step into that platform's instructions.
⭐ Interview Important: JVM platform-independent? No. Bytecode is; the JVM isn't (must know its OS libraries and ISA). One JVM per platform, then any bytecode runs anywhere.
⭐ WORA = Write Once, Run Anywhere: compile once, run wherever a JVM exists.

Why portability mattered

  • Embedded devices (set-top boxes, TVs, later smart devices): build once for any JVM device.
  • Internet: servers differ in platform; no recompiling per server.
  • Speed stopped being decisive: fast CPUs favored a general-purpose language. Java: slower than C++, much faster than Python.

Solution 2: Simple

Removed pointers, multiple inheritance (classes), manual deallocation (automatic; later).

Solution 3: Secure, via the JVM Sandbox

Servlets (backend): server Java acting like an API (fetch data, write DB). Applets (frontend): code sent over the internet to run in the browser (forms, calculators, server output); Java predates JavaScript.
Risk: a clicked link runs an applet that grabs permissions, steals data, or crashes the system. Fix: the JVM runs bytecode restricted, denying harmful permissions: the Sandbox Model.

⭐ Interview Important: The JVM alone solves portability and security; simplicity is language design.
  • Applets are obsolete. Speaker unsure (JDK 10 or 11); actually deprecated in JDK 9, plugin/appletviewer removed in JDK 11, API later marked for removal.
  • JavaScript took Java's name for popularity only; unrelated.

Could C/C++ Be Made Platform-Independent?

Yes, in theory (intermediate code + per-platform VM), but C++ is meant to stay close to hardware and fast. Microsoft did it with C# (Java alternative): intermediate language run by .NET. Later languages (C#, Python) use the same idea; Java popularized platform independence.

⭐ Quick Revision
• Why Java? → C/C++ portability, simplicity, security problems.
• Platform? → Processor + OS.
• Different binaries? → OS system libraries + ISA.
• ISA? → Processor's "grammar" (add/load/store/jump).
• Bytecode? → Platform-independent .class from javac.
• JVM platform-independent? → No; bytecode is.
• WORA? → Write Once, Run Anywhere.
• Security? → JVM sandbox.
• Removed from C++? → Pointers, multiple inheritance, manual deallocation.

Separate JREs are gone: Oracle stopped shipping one from JDK 11; install the JDK.

Compiler vs Interpreter

Both translate code (not always to machine code: javac outputs bytecode); they differ in how much at once.

Compiled (C/C++): source → machine code. Interpreted (Python): an interpreter in between. Neither is strictly better.

⭐ Interview Important: Java is both: compiled (javac → bytecode) and interpreted + JIT-compiled (JVM → machine code at runtime).

Inside the JVM: Interpreter + JIT Compiler

Why only an interpreter at first (1990s)?

Java already pays an extra step for portability; a second full compile would slow startup further on slow CPUs, limited RAM, slow disks. An interpreter starts running immediately.

Modern JVM: hybrid model

A highly optimized JIT (Just-In-Time) compiler was added alongside, not replacing, the interpreter (upfront compile still starts slower).

  • Hot code (frequent) → JIT compiles to native code, no re-interpreting.
  • Cold code → interpreter, line by line.
  • Hot code is found at runtime by profiling (counting method/loop runs); the speaker called it "reading the bytecode".
⭐ Interview Important: JIT = Just-In-Time compiler in the JVM: compiles hot bytecode to native code during execution; the interpreter handles the rest. Fast startup + fast execution.

Java vs C++ speed: C++ is slightly faster (no extra stage); with modern hardware + JIT the gap is negligible, the price of portability, simplicity, security.

⭐ Interview Important: JVM responsibilities
1. Bytecode → machine code (interpreter + JIT).
2. Security (sandbox): bytecode never runs directly on the system; the JVM (itself software) blocks unauthorized access (deleting files, viruses, trojans).
3. Garbage collection (later).

Class Libraries (what the JRE adds)

Your code is business logic; printing, file reading, etc. are prewritten class libraries (like C/C++ printf/cout via #include <iostream>; Java uses import). Without them the JVM can't even print, so the JRE is the minimum to run.

What the JDK adds

Compiler (javac): source → bytecode. Debugger: step line by line, inspect values. Javadoc: docs; plus other tools. Then write in any editor (Notepad for tiny programs; VS Code/IntelliJ for real ones), compile, run.

Video 3: Variables, Data Types, Keywords & Comments

Variables

  • Working values must be stored in memory (RAM). A variable is a named container (memory location) holding a value, internally binary. Stack/heap come later.
  • Name descriptively (firstNumber, secondNumber), not x, y.

Identifier & Literal

  • Identifier: the name (firstNumber); variable, method, class names are identifiers.
  • Literal: the actual value in code (10, 'a', false). These terms are language-agnostic.

Syntax of a Variable

⭐ Interview Important: Java is statically typed: types are declared in code and checked at compile time (Python decides at runtime).

Black-box model: treat boilerplate (public class Demo, public static void main(String[] args)) as a black box; focus on code inside main.

Data Types

⭐ Interview Important: 8 primitive types: byte, short, int, long, float, double, char, boolean.

1. Integer Types

Differ only in width, hence range; a value fitting a smaller type fits all larger ones.

Binary basics

Decimal = base 10 (place values 1, 10, 100…); binary = base 2 (20=1, 21=2, 22=4, 23=8…). 2 = 10, 3 = 11, 4 = 100, 10 = 1010 (8 + 2). Unused high bits are 0.

n bits → 2n combinations; unsigned max 2n − 1 (3 bits → 7 = 111; 8 → 255). Java integers are signed, splitting combinations between negatives and non-negatives.

⭐ Interview Important: signed n-bit range = −2n−1 to 2n−1 − 1. Byte: −128 to 127 (0 takes a non-negative slot). All numeric primitives are signed; char is unsigned 16-bit (0 to 65,535).

3. Character Type: char

  • One character in single quotes: char alphabet = 'a'; (quotes distinguish it from an identifier).
  • Stored as a mapped integer ('A' = 65, 'a' = 97); the data type decides display: char shows 'A', int shows 65.
  • ASCII (C/C++): English letters, digits, symbols, codes 0–127 (7 bits, stored in 8); nothing for Hindi क/ग, Chinese, Greek, Tamil…
  • Java uses Unicode (characters of every language), so char is 16 bits.
⭐ Interview Important: Java char = 16 bits, Unicode; C/C++ char = 8 bits, ASCII.

4. Boolean Type: boolean

⭐ Interview Important: only true/false (boolean b = false;). C/C++ treat non-zero as true; in Java boolean b = 0; / = 1; is a compile error and an int can't be a condition.

Video 4: How Negative & Floating-Point Numbers Are Stored

Positive integers are plain binary. Here: negative integers (2's complement), floats (IEEE 754), and why some decimals come back slightly wrong.

The Hidden Problem with Floats

float f = 0.7f;
System.out.println(f);          // 0.7
System.out.printf("%.20f%n", f); // 0.69999998807907100000   ← not 0.7!

float g = 8.125f;
System.out.printf("%.20f%n", g); // 8.12500000000000000000   ← exact

%.20f prints 20 decimal places. println hides the error: Float.toString prints the shortest decimal mapping back to the same float ("0.7"; video: Java "rounds it off"), but memory holds 0.699999988079071044921875. 8.125 is exact, 0.7 isn't (why).

Decimal → Binary (integer part)

Divide by 2 repeatedly; read remainders bottom to top.

42 ÷ 2 = 21  r 0
21 ÷ 2 = 10  r 1
10 ÷ 2 =  5  r 0
 5 ÷ 2 =  2  r 1
 2 ÷ 2 =  1  r 0
 1 → 1              read upward → 101010 → padded to 8 bits: 00101010  (32 + 8 + 2)

Left zero-padding to type width never changes the value.

Negative Integers: 2's Complement

byte b = -42;: (1) binary of +42; (2) 1's complement: invert all bits; (3) 2's complement: add 1. That is stored.

Reading it back (System.out.println(b))

  • MSB 1 → negative; invert (00101001) + 1 (00101010) = 42 → −42.
  • Shortcut: MSB weighs −128: −128 + 64 + 16 + 4 + 2 = −42.
  • Correction: not the compiler at print time; -42 is encoded at compile time, but printing is runtime (JVM + Integer.toString).

MSB & LSB

MSB (Most Significant Bit): leftmost, most weight (like thousands in 2321). LSB: rightmost, worth 1. In signed integers the MSB is the sign bit: 0 → positive/zero, 1 → negative.

⭐ Interview Important: why no positive byte has MSB 1: max +127 = 01111111; 10000000 would be 128, out of range. Inversion gives negatives MSB 1 (+1 flips it back only for zero). 10000000 = −128.

Why 2's Complement, Not 1's?

1's complement has two zeros; adding 1 removes one.

⭐ Interview Important: 2's complement advantages
• One zero (1's has +0 00000000, −0 11111111); the video's reason.
• (Not in video) Freed pattern = one extra negative: range −128 to +127.
• (Not in video) Same adder for add and subtract (a − b = a + (−b)).
• -x == ~x + 1, e.g. ~42 + 1 = -42.

Not in video: Math.abs(Integer.MIN_VALUE) = -2147483648 (+2,147,483,648 overflows int). Classic trick.

Floating-Point Numbers: IEEE 754 Layout

float/double use IEEE 754: three fields.

Storing a Float: 4 Steps (8.125f)

  1. To binary. 8 = 1000; fraction: multiply by 2, take integer digits, read top to bottom: 
    0.125 × 2 = 0.25  → 0
0.25  × 2 = 0.5   → 0
0.5   × 2 = 1.0   → 1   (fraction is now 0 → stop)
0.125 = .001   →   8.125 = 1000.001₂
  2. Normalize to 1.x × 2exp: 1.000001 × 23 (video once writes "1.0001", but its mantissa 000001 is right).
  3. Add bias: 3 + 127 = 130 = 10000010.
  4. Store: sign 0, exponent 10000010, mantissa = bits after "1." padded to 23. Leading 1 not stored (the "implicit/hidden bit").

Decode formula

value = (−1)sign × (1 + mantissa) × 2(exponent − bias)
  • (−1)0 = 1 positive, (−1)1 = −1 negative; 1 + restores the hidden 1; − bias undoes step 3.
  • Mantissa weights 2−1, 2−2…; for 8.125 only bit 6: 2−6 = 0.015625. 1.015625 × 2130−127 = 8.125, exact.

Why 0.7f Is Not Exact

0.7 × 2 = 1.4 → 1
0.4 × 2 = 0.8 → 0
0.8 × 2 = 1.6 → 1
0.6 × 2 = 1.2 → 1
0.2 × 2 = 0.4 → 0   ← 0.4 again: the cycle 0.4 → 0.8 → 0.6 → 0.2 repeats forever
0.4 × 2 = 0.8 → 0
...
0.7 = 0.1 0110 0110 0110 …₂   (never terminates)

Normalized: 1.0110 0110 0110… × 2−1; exponent −1 + 127 = 126 = 01111110 (bias stores negative exponents positive); the infinite pattern is cut off at 23 bits.

Result: the nearest float, not 0.7 (0.69999998…). Precisely, IEEE 754 rounds to nearest; for 0.7 the next bit is 0, so same as truncation.

⭐ Interview Important: exact decimals are only sums of powers of ½ fitting the mantissa (0.5, 0.25, 0.125, 8.125 ✓). 0.1, 0.2, 0.7 repeat: approximate in float and double. 0.1 + 0.2 → 0.30000000000000004; == 0.3 is false.
→ Compare with a tolerance (Math.abs(a - b) < 1e-9), never ==. Money: BigDecimal.

Not in video: use new BigDecimal("0.7"); new BigDecimal(0.7) keeps the error (0.69999999999999995559…).

The Bias

  • A fixed bias makes the stored exponent unsigned: simpler hardware, floats compare almost like integers.
  • bias = 2(k−1) − 1 (k exponent bits): float k = 8 → 127; double k = 11 → 1023. 127 is mid-range of 0–255 (127 vs 128: hardware detail, skipped).
  • Correction: stored 0 and 255 are reserved (0: zero, subnormals; 255: Infinity, NaN), so normal exponents are −126 to +127, not −127.

double in Memory

64 bits: 1 sign + 11 exponent + 52 mantissa, bias 1023. Smaller error, but 0.7 is still inexact.
Not in video: floats have −0.0: 0.0 == -0.0 true, Double.valueOf(0.0).equals(-0.0) false, 1 / -0.0 = -Infinity.

⭐ Quick Revision
• Negatives? → 2's complement (invert |x|, add 1); −42 = 11010110. Sign = MSB 1.
• Why 2's? → One zero, extra negative (−128..127), same adder.
• Math.abs(Integer.MIN_VALUE)? → Still negative.
• Layout? → float 1+8+23, bias 127; double 1+11+52, bias 1023.
• Decode? → (−1)S × (1 + M) × 2(E − bias); leading 1 implicit (free bit).
• Bias? → Unsigned exponents; 2k−1 − 1.
• printf("%.20f", 0.7f) → 0.6999… (mantissa cut off).
• 0.1 + 0.2 == 0.3? → false; tolerance or BigDecimal (String).

1. Implicit (Widening) Conversion

⭐ Interview Important: the destination must be wider, so every value fits and Java converts silently.
byte b = 24;
int i;
i = b;                   // OK: byte (8-bit, −128..127) always fits in int (32-bit)
System.out.println(i);   // 24

char c = 'a';
int x = c;               // OK: char (16-bit) → int (32-bit)
System.out.println(x);   // 97, the Unicode value of 'a'

char is stored as its Unicode number, so it widens to int; the type only affects printing.

  • Not in video: int/long → float, long → double are implicit but can lose precision: (float) 16777217 → 1.6777216E7 (range fits).
  • Not in video: byte b = 24; compiles as a compile-time constant that fits; so does final int k = 10; byte bb = k;. Non-final int needs a cast.

2. Explicit (Narrowing) Conversion: Casting

int i = 300;
byte b = i;            // ✗ compile error: "incompatible types: possible lossy conversion from int to byte"
byte b = (byte) i;     // ✓ cast: "I know data may be lost, do it anyway"
System.out.println(b); // 44

(targetType) value marks narrowing as intentional; also long → int, double → float.

Why 300 becomes 44

⭐ Interview Important: int → byte shortcut: 300 % 256 = 44 (modulo; 256 = 28). Correction: kept bits are signed, so if the remainder is 128–255, subtract 256: (byte) 200 = −56 (11001000).

3. Truncating Conversion (float/double → integer)

float f = 15.678f;
int i = f;          // ✗ error, even though float and int are both 32 bits

  • Cast required even at equal 32-bit width (no fraction in int).
  • Truncates toward zero: (int) 15.678f = 15, (int) -15.9 = −15; round with Math.round(15.678f) = 16.
  • Not in video: out-of-range clamps ((int) 1e20f = Integer.MAX_VALUE); NaN → 0.

boolean: No Conversion At All

int i = (int) bool;  // ✗ still an error, even with a cast
⭐ Interview Important: boolean converts to/from nothing, even with a cast (unlike C/C++, 0 isn't false).

Automatic Type Promotion (in expressions)

byte a = 50, b = 40, c = 100;
int i = a * b / c;   // 50*40 = 2000 (outside byte range!) → /100 = 20 → fits in int ✓

Arithmetic promotes byte/short/char to int, so intermediates like 2000 don't overflow.

The classic surprise

byte b = 50;
b = b * 2;            // ✗ error: possible lossy conversion from int to byte
                      //   b is promoted to int, so b * 2 is an int (100), and int → byte needs a cast
b = (byte) (b * 2);   // ✓ 100
b = (byte) b * 2;     // ✗ still an error: the cast applies only to b, then * 2 makes it an int again
  • Parentheses needed: cast binds tighter than *.
  • Not in video: compound assignment hides a cast (b *= 2; compiles) and can overflow silently: b = 100; b += 100 → −56.

Type Promotion Rules

  1. byte, short, char → int (even byte + byte).
  2. Any long → long.
  3. Any float → float (wider range than long).
  4. Any double → double.

Result = widest type, minimum int: double > float > long > int.

Not in video: so i / c is integer division before meeting the float; 1 / 2 * 2.0 = 0.0.

5. Shift Operators: << >> >>>

Left shift <<

⭐ Interview Important: shifts happen only on int/long: byte/short/char are promoted to int, shifted on 32 bits, and a byte cast truncates to the low 8. b = b << 1; fails; use b = (byte)(b << 1);.

byte b = 1; shifted left 7 times = 10000000 = −128. Once more:

As a byte, shifting "stops" at 0; int i = b << 1; shows the real −256, then −512, −1024…. Widening copies the sign bit into upper bits, preserving value.

How far can you shift? (distance mod 32)

1 << 30   // 1073741824      (the 1 is at bit 30, just below the sign bit)
1 << 31   // -2147483648     = Integer.MIN_VALUE (the 1 is now the sign bit)
1 << 32   // 1   ← not 0!   (32 % 32 = 0, so it's a shift by 0)
1 << 33   // 2               (33 % 32 = 1)
⭐ Interview Important: shift distance is masked: int uses n % 32 (0–31; LSB to MSB takes ≤ 31 shifts). Correction: long uses n % 64, not 32: 1L << 32 = 4294967296, 1L << 64 = 1.

Correction: Integer.MIN_VALUE isn't "negative infinity" but the smallest int (−2,147,483,648), often a "−∞" placeholder; only float/double have -Infinity.

Right shifts: >> (signed) vs >>> (zero-fill)

  • x >> n: new MSBs copy the sign bit; ≈ x / 2n (8 → 4 → 2 → 1; −128 → −64 → −32).
  • x >>> n: always fills 0 ("dumb shift"); negatives become large positives. For unsigned data: pixels, hashes.
⭐ Correction: >>> on a byte does NOT give +64: the byte −128 is promoted to int (1111…10000000), zero enters at bit 31 (2147483584), and the cast keeps 11000000 = −64, same as >> (verified). >>> is "unsigned" only on full int/long.

Right shifts on byte/short look right after a cast (low 8 bits still match); left shifts expose truncation. Mod-32/64 applies to right shifts too.

Flow of Control

Flow of control = execution order, sequential by default. Three kinds change it:

KindWhat it doesStatements

IterationRepeats a blockloops (next video)

1. if and if-else

int i = 9;
if (i % 2 == 0) {            // condition MUST evaluate to a boolean
    System.out.println("i is even");
} else {                     // runs only when the condition is false
    System.out.println("i is odd");
}
  • Condition must be boolean; may combine operators (if (i > 5 && i < 10)).
  • if: run or skip. if-else: exactly one runs. Two separate ifs are independent (demo printed both "i is 5" and "i is not 5").
  • Even check: i % 2 == 0. Braces optional for one statement, but always use them. Style (not in video): if (b == true) → if (b).

2. Nested if

if (i > 5) {
    if (i < 10) { … }   // inner if
    else { … }          // belongs to the inner if
} else { … }            // belongs to the outer if
  • An else pairs with the nearest unmatched if; each if may lack an else.
  • No depth limit; keep ≤ 2 levels, flatten with &&.
  • Trace (i = 8): i > 5, i < 10 true, i == 7 false; outer elses skipped since their ifs were true.
⭐ Interview Important: dangling else (not in video) 
int x = 12;
if (x > 5)
    if (x < 10) System.out.println("5-10");
else System.out.println("dangling else ran");   // prints! The indentation lies
Without braces, the else binds to the inner if (x < 10). Always use braces.

3. if-else-if Ladder

int age = 50;
if (age > 80)       System.out.println("You are very old");
else if (age > 60)  System.out.println("You are old");
else if (age > 40)  System.out.println("You are becoming old");   // ← this runs
else if (age > 20)  System.out.println("You are young");          // never checked
else                System.out.println("You are a child");        // final fallback
  • More than two choices: checked top to bottom; the first true runs, then control leaves the ladder. Final else optional.
  • As separate ifs, age 50 would print "becoming old" (> 40) and "young" (> 20). Order most to least specific.

4. switch Statement

int i = 3;
switch (i) {                 // compares i against each case label
    case 1:
        System.out.println("i is 1");
        break;
    case 2:
        System.out.println("i is 2");
        break;
    case 3:
        System.out.println("i is 3");
        break;
    default:                 // like the final else: nothing matched
        System.out.println("i is greater than 3");
        break;
}

break and fall-through

  • break exits. Without it, execution falls through into the next case without checking its label, until a break or the end (demo, no breaks, i = 1: "i is 1", "i is 2", "i is 3", default).
  • Intentional, for shared code; commonest (not in video): case 1: case 2: case 3: System.out.println("small"); break;.

switch rules and limitations

  • Selector: byte, short, char, int (+ wrappers), enum, String (JDK 7+). Not long, float, double, boolean (switch (i > 4) fails; long: "selector type long is not allowed").
  • No duplicate labels (compile error); a ladder allows repeats (second unreachable). Labels must be compile-time constants (not in video).
  • JDK 14+: arrow labels case 1 -> … (no fall-through), switch expressions (later). Switches can be nested; avoid deep nesting.

Why switch Is Faster: Jump Tables

The compiler emits a jump table, not a comparison chain:

BytecodeWhenHow it worksCost
tableswitchDense values (1, 2, 3)Table low..high, indexed by i − low; out of range → default.O(1)
lookupswitchSparse values (1, 1000, 100000)Sorted keys + targets, searched (typically binary search).O(log n)

Sparse values would make a huge mostly-empty tableswitch (100,000 slots). Both beat the ladder's O(n) with many cases. Checked with javap -c:

switch(i) { case 1: … case 2: … case 3: … default: … }
  → tableswitch  { // 1 to 3
        1: 28   2: 31   3: 34   default: 37 }

switch(i) { case 1: … case 1000: … case 100000: … default: … }
  → lookupswitch { // 3
        1: 36   1000: 39   100000: 42   default: 45 }
  • Correction: default is a separate target, not a table slot.
  • Correction: choice is a javac cost heuristic (size vs search time); a dense 2-case switch became lookupswitch.
  • For few cases the difference is negligible (JIT may optimize either); pick switch for clarity.
  • Not in video: String switch uses hashCode(), then equals().

Video 8: Loops (Iteration) & Jump Statements

A loop repeats a block while a condition is true; each pass = an iteration. Loops: while, do-while, for; jumps: break, continue.

Why: ten println calls (or println(i); i++; ×10) don't scale.

1. while Loop

int i = 1;
while (i <= 10) {           // condition must be a boolean, checked BEFORE every iteration
    System.out.println(i);
    i++;                    // update. Forget it and the loop never ends
}                           // prints 1..10, then the condition fails at i = 11
// Reverse: start i = 10, use while (i >= 1), and i--
  • Braces optional for one statement (then only it loops); always use them.
  • Condition never false → infinite loop.

Trap: increment inside the condition

int i = 1;
while (i++ <= 10) System.out.print(i + " ");   // prints 2 3 … 11 (!)
int i = 0;
while (i++ < 10)  System.out.print(i + " ");   // prints 1 2 … 10 ✓

Postfix i++ compares the old value, increments before the body (body sees new value). Fix: start one lower, use < (see Video 6).

2. do-while Loop

int i = 11;
do {
    System.out.println(i);   // runs once and prints 11, even though 11 <= 10 is false
    i++;
} while (i <= 10);           // ← semicolon required here
⭐ Interview Important: while vs do-while while = entry-controlled (0+ runs); do-while = exit-controlled (1+ runs). Classic do-while: a menu (Play / Load saved game / Exit) — show once, repeat until Exit.

3. for Loop

for (int i = 1; i <= 10; i++) {      // (init; condition; update)
    System.out.println(i);
}
for (int i = 10; i >= 1; i--) { … }  // reverse
  • for (int i …) scopes i to the loop (later use: "cannot find symbol"); declare before if needed after.
  • All parts optional, semicolons required: for (;;) = infinite.
  • Comma-separated variables: for (int i = 1, j = 1; i <= 10 && j <= 5; i++, j += 2).
    • Same type, each updated its own way (i++, j += 2, k *= 2).
    • No comma in the condition; use && / ||.
    • && stops when either fails; || when both fail.
  • Condition = any boolean, e.g. for (…; flag == true; …), flag cleared in an if.
  • for-each: with arrays/strings.

Infinite Loops & Empty Bodies

while (true) { … }           for (;;) { … }          for (int i = 1; i < 10; ) { … }   // no update
int i = 5;  while (i < 10) { }   // empty body: i never changes, so it never ends

Traps (not in video):

  • Stray semicolon: while (i < 3); — empty body, hangs (verified).
  • Code after while (true) { } without break → "unreachable statement". while (i < 10) { } compiles (i not constant).

Why Loop Counters Are int

  • Convention: int (or long). byte/short promote to int anyway (Video 5) and take a 32-bit JVM slot — no saving.
  • Not in video: for (byte b = 0; b < 200; b++) never ends (wraps 127 → −128; verified b = 44 after 300 iterations).

Nested Loops

for (int i = 1; i <= 5; i++) {        // outer: which ROW
    for (int j = 1; j <= i; j++) {    // inner: how many stars in this row (depends on i)
        System.out.print("* ");       // print() stays on the same line
    }
    System.out.println();             // new line after each row
}
*
* *
* * *
* * * *
* * * * *
  • Inner loop runs fully for every outer iteration.
  • println adds a newline, print doesn't; bare System.out.println() = new line.
  • Pattern problems: outer = rows, inner bound often depends on i.

Jump Statements: break & continue

break example: primality test

int p = 9;
int i;                              // declared outside so it can be used after the loop (scope)
for (i = 2; i < p; i++) {
    if (p % i == 0) {               // found a divisor
        System.out.println("The number is not prime");
        break;                      // no need to check further divisors
    }
}
if (i == p) System.out.println("The number is prime");   // the loop finished without a break
  • i == p after loop → no divisor. p = 9 breaks at i = 3; p = 7 runs through.
  • break exits dynamically, without changing the condition.
  • Faster: divisors up to √p (i * i <= p). Prints nothing for p ≤ 1.

continue example: odd numbers

for (int i = 1; i <= 10; i++) {
    if (i % 2 == 0) continue;   // even: skip the print and move to the next i
    System.out.println(i);      // prints 1 3 5 7 9
}

break and continue in nested loops

  • Affect only the innermost loop: if (j >= 5) break; in the inner star loop caps rows at 5; all 10 rows still print (triangle flattens).
  • Not in video: break in a switch inside a loop exits only the switch.

Labels: break/continue an Outer Loop

outer:
for (int i = 1; i <= 10; i++) {
    inner:
    for (int j = 1; j <= i; j++) {
        System.out.print("* ");
        if (j >= 5) break outer;     // exits BOTH loops: output stops after the 5th row
    }
    System.out.println();
}
  • labelName: before a loop, then break labelName; / continue labelName;.
  • continue outer; skips rest of inner and outer body (verified: if (y == 2) continue outer; → 11 21 31).
  • Labelled blocks: first: { second: { … break first; } }; break works, continue doesn't ("not a loop label"). Rare.
  • No goto (reserved, unused; Video 3); labels replace it.

• while vs do-while? → 0+ vs 1+ runs; menus.
• for order? → init once; condition → body → update. for(;;) infinite.
• Multiple for variables? → Comma in init/update; &&/|| in condition.
• Scope of i? → Loop only.
• Why int counters? → No saving; byte wraps forever.

• break vs continue? → Exit vs next iteration; innermost unless labelled.

Random Access

arr[2] jumps straight to index 2 (no walking 0 → 1 → 2): random access, O(1) for any index. Why needs where arrays live.

Primitive vs Non-Primitive Storage

  • Primitive (int x = 4;): holds the value; locals on the stack.
  • Non-primitive (int[] arr = new int[5];): array on the heap; arr on the stack is a reference variable holding its address (the arrow).
  • Rule of thumb: new → heap. Stack/heap: own video later.
  • Precision (not in video): "primitives on stack" holds only for locals; object fields and array elements are on the heap (the ints in new int[5] too).

The Address Formula

address of arr[i] = base address + (element size × i)
• Base address: array start, stored in arr. • Element size: from the type (int 4, long/double 8). • i: the index.
Needs contiguous, same-sized elements. Also why indexes start at 0 (offset 0).

Precision (not in video): arrays start with a header (metadata + length, ~16 bytes on HotSpot): ref + headerOffset + size × i, still O(1). Java hides real addresses; numbers here are a mental model.

Why ArrayIndexOutOfBoundsException Exists

arr[100] on size 5 would compute 100 + 4 × 100 = 500 and read possibly foreign memory. Java checks bounds first:

// conceptually, on every array access:
if (index < 0 || index >= arr.length) {
    throw new ArrayIndexOutOfBoundsException(index);
}
// only now: address = base + size * index
  • Correction: video writes index > length; must be >= (last valid = length − 1).
  • Makes Java memory safe (C/C++: undefined behaviour). Done at runtime by the JVM; the JIT often removes it when provably in range (for (i = 0; i < arr.length; i++)).

  • Each points to a separate int[4] row on the heap.
  • arr[i][j]: formula twice (row reference, then element).

Correction: the video's example says arr[1] → 200, but its final drawing has rows at 200/300/400 (row 1 = 300); diagram follows the drawing. Method: row lookup, then column lookup.

Why Functions?

Copy-pasting "add and print" in five places = repeated code. A function is a named block written once, called when needed — code reusability.

  • Functions until OOP, methods after; in Java all live in a class, so strictly all are methods.
  • Like maths f(x): input → processing → output.

Syntax

public class Demo {

Scope of a Variable

  • Local scope: declared in { } (function, if, loop, any block) → visible only there, destroyed at block end.

  • An if-block variable is gone after the block; a new j afterwards is fine.

Recursion

⭐ Definition: Recursion = function calling itself on a smaller input. Needs ① a base case (stops; else infinite calls) and ② a recursive call toward it (n − 1, n − 2, …).

Example: print 1 to n recursively

static void printNum(int n) {
    if (n == 0) return;          // base case: stop
    printNum(n - 1);             // recursive call on a smaller problem
    System.out.println(n);       // runs on the way BACK
}
printNum(5);                     // 1 2 3 4 5
  • Down: printNum(5) → 4 → 3 → 2 → 1 → 0 (base case returns).
  • Up: each call resumes and prints its n → 1 2 3 4 5 (chaining with one function). Analogy: walk downstairs to the floor, print while climbing back.
  • Print before the call → 5 4 3 2 1 (first exercise).
  • A loop does this too; recursion pays off for self-similar problems: trees, divide and conquer, backtracking, DSA.
⭐ Interview Important: No base case → StackOverflowError
Video: runs forever. Correction: infinite recursion crashes — each call adds a frame to a finite stack → java.lang.StackOverflowError (Error, not Exception). Very deep recursion (n = 100000) can overflow even with a base case — one reason to prefer iteration.

Example: n-th Fibonacci (two recursive calls)

1, 1, 2, 3, 5, 8, 13, …: fib(n) = fib(n−1) + fib(n−2), translated directly:

static int fib(int n) {
    if (n == 0 || n == 1) return 1;   // base cases (video's indexing: fib(0)=1, fib(1)=1)
    int x = fib(n - 1);
    int y = fib(n - 2);
    return x + y;
}
fib(4);   // 5      fib(5);   // 8
  • Correction: video's base case "n is 0 and n is 1" must be OR (||); && never triggers → StackOverflowError.
  • Standard: fib(0) = 0, fib(1) = 1 (0, 1, 1, 2, …); video's is shifted by one. Clarify in interviews.
  • Recursive leap of faith: don't trace every level; assume fib(n−1), fib(n−2) are correct, write the combination + base case.
⭐ Interview Important: Why naive recursive Fibonacci is slow (not in video)
Subproblems recomputed (fib(2) twice for n = 4, exploding with n): O(2ⁿ) time (~1.6ⁿ), O(n) stack. Fix: memoization (cache fib(k) in an array) → O(n); or two-variable loop: O(n) time, O(1) space. Entry point to dynamic programming.

The this Keyword

Use 1: field vs same-named parameter

  • Same-named parameter shadows the field: plain name = parameter, this.name = field.
  • Different names (name = n;) make this optional, but same names + this.x = x is the standard convention.

Use 2: calling another constructor, this(…)

Constructor chaining: delegate to another constructor in the class; assignment logic written once.

class Student {
    String name; int age; int rollNo; String college;

    Student()                                   { this("Unknown");                          System.out.println("1st"); }
    Student(String name)                        { this(name, 0);                            System.out.println("2nd"); }
    Student(String name, int age)               { this(name, age, 0);                       System.out.println("3rd"); }
    Student(String name, int age, int rollNo)   { this(name, age, rollNo, "Unknown");       System.out.println("4th"); }
    Student(String name, int age, int rollNo, String college) {      // the only place fields are assigned
        this.name = name; this.age = age; this.rollNo = rollNo; this.college = college;
        System.out.println("5th");
    }

  • "Unknown" instead of null avoids later NullPointerException.

• First statement only (even a println above it = error).
• Only in constructors.
• Not in video: not with super(…) (both must be first); cycles → "recursive constructor invocation".
• Not in video: no this in static context (e.g. main) — no current object.

Call by Value vs Call by Reference

Experiment 1: primitives, where the change is lost

static void add10(int x, int y) { x = x + 10; y = y + 10; }

int x = 4, y = 5;
System.out.println(x + " " + y);   // 4 5
add10(x, y);
System.out.println(x + " " + y);   // 4 5   ← unchanged!

Experiment 2: an object, where the change is visible

class Random {
    int x, y;
    Random(int x, int y) { this.x = x; this.y = y; }
}
static void add10(Random r) { r.x = r.x + 10; r.y = r.y + 10; }

Random r1 = new Random(4, 5);
System.out.println(r1.x + " " + r1.y);   // 4 5
add10(r1);
System.out.println(r1.x + " " + r1.y);   // 14 15   ← changed!
⭐ Interview Important: "Is Java call by value or call by reference?"
Java is strictly call (pass) by value, always, for primitives and objects alike. No call by reference (C++ has int&). For objects the copied value is the reference, so methods can modify contents — it only feels like by-reference. "Value for primitives, reference for objects" is wrong.
⭐ The proof: reassigning a parameter doesn't affect the caller (not in video) static void reset(Random r) { r = new Random(0, 0); }; reset(r1); → r1.x still 4. Likewise swap(Random a, Random b) can't swap the caller's variables.
  • Parameters and return types can be non-primitive: static Random add10(Random r) { …; return r; }.
  • Parameter references are locals (r dies on return; object lives via r1). Unreachable objects → garbage collection.

Copying Objects

Random r3 = r1;               // NO new object: r3 and r1 point to the SAME object

System.out.println(r1.x);     // 14  (same object)
System.out.println(r2.x);     // 4   (separate object)

  • r3 = r1: r1 == r3 true; r1 == r2 false despite equal fields.
⭐ Correction: what "shallow copy" and "deep copy" really mean
Video: r3 = r1 "shallow", new Random(r1) "deep". Standard:
• r3 = r1 = reference copy (alias), no object copied.
• Shallow: new object, fields copied as is — reference fields share inner objects.
• Deep: new object plus recursive copies of referenced objects.

    }

// deep:    copy.marks[0] = 99 leaves the original untouched

The Problem static Solves

One-college app: every Student has college = "IIT Guwahati". As a normal field, 1,000 students = 1,000 identical copies: wasted memory (4-byte reference each), error-prone. It belongs to the class.

Static Variables (Class Variables)

class Student {
    String name; int age; int rollNo;     // instance variables: one copy PER OBJECT
    static String college;                // class variable: ONE copy, shared by all objects
}

Student.college = "IIT Guwahati";         // preferred: ClassName.staticVar
Student s1 = new Student(), s2 = new Student(), s3 = new Student();
s3.college = "IIT Kharagpur";             // legal (with a warning): changes it for EVERYONE
System.out.println(s1.college);           // IIT Kharagpur
  • Access via ClassName.var; s1.college compiles with warning "static field should be accessed in a static way".
  • Instance variable = one per object; class (static) variable = one per class.
  • Correction ("statics aren't on the heap"): class metadata (method code etc.) is in Metaspace, but since Java 8 static values live on the heap in the java.lang.Class object (pre-8: PermGen). Model unchanged: one shared copy.
  • Pitfall: assigning a static in a constructor (this.college = college, warning) overwrites it for every existing object on each new.

Static Methods

class Student {
    static void markAttendance() { … }
}
Student.markAttendance();     // call with the class name. No object needed.
s1.markAttendance();          // also compiles (with a warning). It's the same shared method.
⭐ Rules for static methods
① Directly calls only static methods. ② Directly accesses only static variables. ③ No this (or super).
Why: it runs with no object (Student.markAttendance()); name or instance print() — whose? No current object.
  • Precision: rule is about direct access; via an explicit reference it can: static void f() { Student s = new Student(); s.print(); s.name = "X"; } (what main always does).
  • Reverse is fine: instance methods can use static members. Methods are never stored in objects — objects hold only instance fields.
  • Not in video: static methods can't be overridden (same-signature subclass method hides it). Trap: Student s = null; s.markAttendance(); does not NPE — only the reference type is used.

Static Block

class Student {
    static String college;
    static int grade;
    static {                         // runs ONCE, when the class is initialised, before any object
        college = "IIT Guwahati";
        grade = 8;
    }
}
  • Constructor initialises instance vars; static block initialises static vars (or assign directly: static String college = "IIT Guwahati";).
  • Runs once per class, before any object/constructor — precisely, when the class is initialised on first use (first new, static call or static field access), not necessarily at start. Multiple blocks run in textual order.

The final Keyword

final variable = constant: assigned once, never changed.

Correction: declare-then-assign isn't a Java "optimisation"/exception as the video says — the rule is "assigned exactly once" (definite assignment) before use.

Video 16: OOP Pillars I: Encapsulation (Access Modifiers, Getters/Setters, Packages) & Inheritance (Types, Diamond Problem, super)

4 pillars: Encapsulation, Inheritance, Abstraction, Polymorphism — each mimics real-world objects. Here: the first two.

Encapsulation

Analogy: a medicine capsule — ingredients sealed in one wrapper.

⭐ Definition: Encapsulation
① Data and behaviour bundled in one unit (class): fields + methods.
② No unrestricted data access: private fields, access only via controlled public methods that validate (data hiding).

Why ②: BankAccount. A plain balance allows ba.balance = 100000;. Real balances change only via validated deposit/withdraw (real currency? enough funds?).

class BankAccount {
    private double balance;                  // hidden: ba.balance won't compile outside this class

    public void deposit(double amount) {
        if (amount <= 0) throw new IllegalArgumentException("Invalid amount");   // validation lives here
        balance += amount;
    }
    public void withdraw(double amount) {
        if (amount > balance) throw new IllegalArgumentException("Insufficient balance");
        balance -= amount;
    }
    public double getBalance() { return balance; }  // read-only view. There's deliberately NO setBalance()
}

BankAccount ba = new BankAccount();
ba.deposit(500);  ba.withdraw(300);
System.out.println(ba.getBalance());   // 200.0
// ba.balance = 100000;                // ✘ "The field BankAccount.balance is not visible"

Correction: the video's "amount ≥ balance" check is wrong; valid is amount <= balance (reject amount > balance).

Getters and setters

class Student {
    private String name; private int age; private int rollNo; private String college;

    public String getName()              { return name; }
    public void   setName(String name)   { this.name = name; }
    public String getCollege()           { return college; }
    public void   setCollege(String college) {
        // validation: the college must be real (e.g. look it up via an API) before accepting it
        this.college = college;
    }
}
  • Why not public? The method is a checkpoint: add rules later (age ≤ 120, roll number in range, name needs surname) without changing callers.
  • Getter only = read-only (like balance); neither = internal. Naming: getX() / setX(value); booleans isX().

Inheritance

IS-A: a Car is a Vehicle, a Bike is a Vehicle, an EngineeringStudent is a Student (not reverse). Write start() once in Vehicle; all inherit it.

class Vehicle {
    void start() { System.out.println("Vehicle starting"); }
}
class Car extends Vehicle {                 // extends = inherits from
    void setGear() { System.out.println("Gear set"); }   // Car-specific: not every vehicle has gears
}
Car c = new Car();
c.start();     // inherited from Vehicle
c.setGear();   // its own
  • Terms: parent / superclass / base; child / subclass / derived.
  • Child calls its own + parent's non-private methods; parent can't call child-only ones: new Student().attendLab() → "The method attendLab() is undefined for the type Student".
  • private members aren't accessible in the child (protected/public/default-in-package are). Constructors aren't inherited.
  • Same-signature child start() wins: the video says "shadowing", correct term is overriding; shadowing/hiding is for same-named fields.
  • Benefits: ① code reuse (no duplicate start() in Car, Bike, Truck); ② enables polymorphism.
  • Not in video: all classes implicitly extend java.lang.Object (source of toString(), equals(), hashCode()).

Types of Inheritance

class Student              { public void markAttendance() { … } }
class EngineeringStudent    extends Student            { void attendLab() { … } }     // single
class CSEEngineeringStudent extends EngineeringStudent { void attendCSELab() { … } }  // multilevel: has all 3 methods
class MedicalStudent        extends Student            { void attendLab() { … } }     // hierarchical: 2 children of Student

Multilevel: bottom class gets every non-private member up the chain. Not in video: hybrid (a mix) allowed only without multiple class inheritance.

Why not multiple inheritance? The Diamond Problem

  • Correction: not "at runtime" — prevented at compile time (extends takes one class). Also risks two copies of A's state.
  • Solution: interfaces — implements many. Conflicting default methods → class must override and resolve (e.g. B.super.show()).

The super Keyword

this = current object; super = its parent-class part. Uses:

class Student {
    String name; int age; int rollNo; int x = 4;
    Student() { }
    Student(String name, int age, int rollNo) { this.name = name; this.age = age; this.rollNo = rollNo; }
    void print() { System.out.println(name + " " + age + " " + rollNo); }
}
class EngineeringStudent extends Student {
    String college; int x = 5;                      // this x hides the parent's x

    EngineeringStudent(String name, int age, int rollNo, String college) {
        super(name, age, rollNo);                   // ③ call the parent constructor: MUST be the first line
        this.college = college;
    }
    void print() {
        super.print();                              // ② call the parent's method (it prints name, age, rollNo)
        System.out.println(college);
        System.out.println(x + " " + super.x);      // ① parent's variable: 5 4
    }
}
new EngineeringStudent("Aditya", 28, 1001, "IIT Guwahati").print();   // Aditya 28 1001 / IIT Guwahati / 5 4
  • ① super.field: parent's same-named field (optional without a clash).
  • ② super.method(): reuse parent logic then extend (standard when overriding).
  • ③ super(args): parent constructor sets its own fields; no repeated this.name = name.
⭐ Interview Important: constructors and super()
• super(…) must be the first statement (like this(…)) — can't have both.
• Omitted → compiler inserts super(); (parent no-arg). Hence Student() { }: EngineeringStudent(String college) implicitly calls it; parent with only a parameterized constructor → "Implicit super constructor Student() is undefined".
• Order: parent first. new CSEEngineeringStudent(): Object → Student → EngineeringStudent → CSEEngineeringStudent.
• super, like this, not in static context.

Video 17: OOP Pillars II: Abstraction (Abstract Classes, Interfaces) & Polymorphism (Overloading vs Overriding)

Abstraction

⭐ Definition: Abstraction is the process of focusing on what something does while ignoring how it does it.
  • A car = drive, brake, accelerate + colour, type, price, not 30,000 parts and combustion; an ATM = deposit, withdraw, check balance.
  • Otherwise every driver must be an engineer, engineer a physicist, physicist a mathematician; each layer uses the one below without its internals.
  • OOP simulates how humans perceive reality (teacher teaches, button is clicked), not reality (cells, organs).
  • ① Model only what's necessary; ② users needn't know the implementation (steering, pedals, gearbox = interface).

Two levels of abstraction in Java

LevelIdeaHow Java does it
Low-levelHide implementationConcrete classes: c.brake() without reading its code
High-levelSeparate the what from the howAbstract classes and interfaces (on inheritance)

Concrete-only problem: FuelCar fc, ElectricCar ec are tightly coupled to one implementation each; every new car needs a new type. Goal: one Car c for any car, c.drive() running the actual object's version — enabled by inheritance (parent ref → child object), formalised by abstract classes/interfaces.

Abstract Classes

abstract class Car {                         // has ≥1 abstract method → the class MUST be abstract
    void start() { System.out.println("Car started"); }   // concrete: shared by all cars
    abstract void accelerate();              // declared only (no body): children MUST define it
    abstract void brake();
}
class FuelCar extends Car {
    @Override void accelerate() { System.out.println("Fuel car is accelerating"); }
    @Override void brake()      { System.out.println("Fuel car is stopping"); }
}
class ElectricCar extends Car {
    @Override void accelerate() { System.out.println("Electric car is accelerating"); }
    @Override void brake()      { System.out.println("Electric car is stopping (regenerative)"); }
}

Car car = new ElectricCar();   // or new FuelCar(). Car itself can't be instantiated
car.start();                   // Car started (inherited)
car.accelerate();              // Electric car is accelerating
// new Car();                  // ✘ "Cannot instantiate the type Car"
  • Abstract method: declared, no body (ends ;); without abstract → "This method requires a body instead of a semicolon".
  • One abstract method → class must be abstract; can't be instantiated (new Car().accelerate() would have no body).
  • Concrete subclass implements every abstract method ("The type FuelCar must implement the inherited abstract method…") or is abstract itself.
  • @Override: optional, best practice — compiler errors on a mistyped signature (else a silent new method).
  • Not in video: may have fields, constructors (via child's super(…)), concrete methods, even zero abstract methods (to block instantiation). abstract + final contradict.

Polymorphism

Poly + morph: one thing, many forms.

① Compile-time (static) polymorphism = method overloading

Same object, same command, parameter changes reaction: "run" = 2 km/h, 5 km/h if a dog chases.

Autoboxing & Unboxing

int x = 10;
Integer y = x;          // AUTOBOXING (primitive → wrapper). The compiler writes:  Integer y = Integer.valueOf(x);
                        //   (in old Java: new Integer(x))
Integer a = 20;         // autoboxing a literal
int b = a;              // UNBOXING (wrapper → primitive). The compiler writes:  int b = a.intValue();
System.out.println(y);  // prints 10 (println(Object) calls toString; for an Integer it gives the value)

Correction: println(y) uses println(Object) → y.toString(), not unboxing (same output).

Happens automatically in:

  1. Assignments: Integer y = x;, int b = a;
  2. Method calls: Integer → printInteger(int x) unboxes; int → Integer param boxes.
  3. Arithmetic: Integer a = 10, b = 20; int sum = a + b; = a.intValue() + b.intValue() = 30.
⭐ Unboxing null → NullPointerException: Integer x = null; int y = x; compiles, then x.intValue() on null throws. Same in x + 1 or an int param. Common production bug with collections/maps.

== vs equals()

int p = 10000, q = 10000;

Integer a = 200, b = 200;

System.out.println(a.intValue() == b.intValue()); // true (compare the values)
System.out.println(a.equals(b));               // true   (equals compares the values)
  • == compares what variables hold: primitive = value; reference = address ("same object?").

  • Not in video: one primitive side → unbox, numeric: Integer a = 200; int c = 200; a == c → true.

The Integer Cache: why 100 == 100 is true but 200 == 200 is false

Integer x = 100, y = 100;   System.out.println(x == y);   // true
Integer a = 200, b = 200;   System.out.println(a == b);   // false
  • Precision: not compiler-dependent — the spec guarantees −128…127 on autoboxing; outside is unspecified (usually uncached). Raise the bound with -XX:AutoBoxCacheMax.
  • Not in video: Byte/Short/Long −128…127, Character 0…127, Boolean TRUE/FALSE; Float/Double uncached.
⭐ Rule: never compare wrapper objects with ==. Use .equals(). Small-value tests pass; production values over 127 fail.

Video 19: Nested Classes: Static Nested, Inner, Local & Anonymous

Nested class = class inside an outer class. Four kinds: static nested, inner (non-static member), local, anonymous. Officially: static nested vs inner (member, local, anonymous).

Why Nest a Class?

  1. Logical grouping: a helper meaningful only inside its outer; tidy package.
  2. Access: uses outer's private members directly (and vice versa).
  3. Hiding: can be private (top-level can't).

1. Static Nested Class

class Outer {
    private static int x = 4;
    int y;                                         // instance (non-static) field

    static class Inner {                           // static nested class
        void fun() {
            System.out.println(x);                 // ✔ static member of Outer (even private)
            // System.out.println(y);              // ✘ "Cannot make a static reference to the non-static field y"
        }
        void show(Outer o) { System.out.println(o.y); }  // ✔ via an explicit Outer reference
    }
}

Outer.Inner inner = new Outer.Inner();             // no Outer object needed. Its full name is Outer.Inner
inner.fun();
  • Belongs to class Outer, not an object — new Outer.Inner() needs no Outer.
  • Named Outer.Inner (like Outer.x); compiled Outer$Inner.class.
  • Directly accesses only outer's static members (private too); instance members need an explicit Outer reference (param or constructor-stored).
  • Otherwise normal: fields, methods, constructors, static members, any modifiers, extends/implements.

Correction: not "one shared inner object" — static isn't singleton; create any number, each independent of any Outer object.

Use case: a private helper class

class BankAccount {
    public double computeInterest(double principal) {
        return InterestCalculator.calculateYearly(principal, 0.09);
    }
    private static class InterestCalculator {             // hidden from everyone outside BankAccount
        static double calculateYearly(double p, double rate)  { return p * rate; }
        static double calculateMonthly(double p, double rate) { return p * rate / 12; }
    }
}

Uses: helpers, Builder pattern (new Pizza.Builder().size(…).build()), request/response DTOs (Spring Boot), nested classes needing statics. Most common kind.

2. Inner Class (non-static member class)

class Outer {
    int x = 10;
    class Inner {                                  // no "static"
        int x = 20;                                // shadows Outer's x
        void fun() {
            System.out.println(x);                 // 20 (Inner's own)
            System.out.println(Outer.this.x);      // 10 (the outer instance's x)
        }
    }
}

Outer outer = new Outer();
Outer.Inner inner = outer.new Inner();             // needs an Outer object: outer.new Inner()
// Outer.Inner inner = new Outer().new Inner();    // one-liner, if you don't need the Outer reference
inner.fun();
  • Needs an Outer object: outer.new Inner() (into that outer, create its Inner).
  • Carries a compiler-added hidden outer reference (Outer.this) → accesses all outer members incl. private; plain x = Outer.this.x.
  • A separate heap object, not inside the outer — just points to it.
  • Same-named inner field shadows; use Outer.this.x.

Correction: inner objects exist only via outer.new Inner(); an outer may have zero, one or many.

⭐ Static members inside an inner class
Before Java 16: ✘ except constants (static final int K = 5;) — ambiguous: per class, or per outer object (as the inner class is)? Use a static nested class instead.
Since Java 16 (JEP 395, with records): allowed, per class — hence no IDE error in the video.
⭐ Prefer static nested unless you need the outer instance (not in video): Outer.this keeps the outer alive while the inner is reachable — a long-lived listener blocking GC is a classic memory leak (Android). No outer instance use → make it static.

3. Local Class

Declared in a block (method, constructor, if, loop, switch, static block); exists only there. Rare in production.

class Outer {
    private int x = 4;
    void greet() {
        int y = 5;                                  // a local variable of greet()
        class Local {                               // local class: visible only inside greet()
            void sayHello() {
                System.out.println(x);              // ✔ outer members (instance/static, private too)
                System.out.println(y);              // ✔ only because y is effectively final
            }
        }
        Local local = new Local();
        local.sayHello();
        // y++;                                     // ✘ would break it: "Local variable y defined in an
                                                    //    enclosing scope must be final or effectively final"
    }
}
  • Inner-class access rules; in a static method only outer statics.
  • Not in video: no access modifiers, not static. Java 16+: local records, enums, interfaces.
⭐ The "effectively final" rule, and why it exists
Local/anonymous classes use enclosing locals only if final or effectively final (never modified after initial assignment).
Why: the local is on the stack and dies when greet() returns; the Local object is on the heap and may outlive it (returned as Object). So the value is copied into a hidden field (capture by value) — with y++, old or new value? Java forbids changes.
Same for lambdas. (Pre-Java 8: explicit final; "effectively final" since Java 8.)

Escape route: return type can't be Local (invisible outside) but can be Object: Object greet() { …; return new Local(); }.

Nameless class declared and instantiated in one expression, for a one-off override.

class Person {

  • No constructors (no name). Not in video: ① parent constructor args new Person("x") { … }; ② instance initializer { … }.
  • Inner-class access rules; effectively final applies in methods. Compiled Demo$1.class.
  • Repeated use → named class. One-method interfaces → lambdas: Runnable r = () -> System.out.println("run");.

Input Level 2: InputStreamReader + BufferedReader

import java.io.*;

    InputStreamReader isr = new InputStreamReader(System.in);   // bytes → characters

    int age = Integer.parseInt(br.readLine());   // only Strings come back, so parse manually

  • Chain: InputStreamReader(InputStream in), BufferedReader(Reader in) — the isr is a Reader.

Video 21: Immutable Classes & Defensive Copying

⭐ Definition: Immutable = state can't change after construction: fields keep constructor values forever, no subclass can alter behaviour. JDK: String, wrappers (Integer…), LocalDate, BigInteger.

Normal class (getters + setters) is mutable: s1.setName("Rohit"); a subclass (class CSEStudent extends Student) can override behaviour.

Rules for an Immutable Class

  1. Class final: no overriding or added mutable state.
  2. Fields private final: hidden, assigned once.
  3. Set only in the constructor; no setters (getters fine).
  4. Mutable-object fields: defensive copies in ① constructor and ② getters, never sharing the internal object.
final class Student {                          // rule 1
    private final int age;                     // rule 2
    private final String name;
    Student(int age, String name) { this.age = age; this.name = name; }   // rule 3
    public int getAge()     { return age; }
    public String getName() { return name; }
}
// class CSEStudent extends Student {}         // ✘ "cannot subclass the final class Student"

Fully immutable: int getter returns a value copy; String is immutable.

The Hole: a Mutable Reference Field

class College {                                // an ordinary MUTABLE class
    String name, address;
    College(String name, String address) { this.name = name; this.address = address; }
}

final class Student {
    private final int age; private final String name;
    private final College college;
    Student(int age, String name, College college) { …; this.college = college; }   // stores the caller's reference
    public College getCollege() { return college; }                                  // hands out the internal reference
}

College c = new College("IIT Guwahati", "Assam");
Student s1 = new Student(28, "Aditya", c);
s1.getCollege().name = "IIT Bombay";           // no setter used, yet…
System.out.println(s1.getCollege().name);      // IIT Bombay  ← the "immutable" Student changed!
c.name = "XYZ";                                // the caller's own reference can change it too
  • final College college freezes which object, not its contents (Video 15 trap).
  • Getter leaks the internal reference (receiver can modify the same heap object); constructor leaks in reverse (caller keeps c).

Terms: the video's "shallow copy" here is really reference sharing/aliasing — no copy at all (Video 14 copy-types table).

Fix A: Make the Referenced Class Immutable Too

Immutable College (final, private final fields, no setters) → sharing is harmless, like String fields. Primitive fields are always safe: getters return value copies.

Correction: not "because primitives are on the stack" — primitive fields are inside the heap object; safe because passed/returned by value, so no outside handle to the field.

Fix B: Defensive Copies (when you can't change College)

final class Student {
    private final int age;
    private final String name;
    private final College college;

    Student(int age, String name, College college) {
        this.age = age;
        this.name = name;
        this.college = new College(college.name, college.address);        // copy IN
    }
    public College getCollege() {
        return new College(college.name, college.address);                // copy OUT
    }
}

s1.getCollege().name = "IIT Bombay";          // modifies a throwaway copy
System.out.println(s1.getCollege().name);     // IIT Guwahati ✔ unchanged
  • Constructor copy guards against later caller changes to c; getter copy against the receiver. Need both.
  • If the copied class holds mutable references, one level isn't enough — recursive deep copy.
⭐ Collections and arrays need defensive copies too (not in video)
private final List<String> subjects; → this.subjects = List.copyOf(subjects); (Java 10+, unmodifiable); getter returns it or Collections.unmodifiableList(...).
private final int[] marks; → marks.clone() in constructor and getter.
"Change" = return a new instance (withName(String n) { return new Student(age, n, college); }), like String.toUpperCase().

Why Immutability Matters

  • Free thread safety: shared without locks or races.
  • Safe HashMap keys / HashSet elements: hashCode never changes. (Not in video.)
  • Cacheable/shareable: String pool, Integer cache rely on it. Valid once = valid forever.
  • Not in video: Java 16+ record gives final class, private final fields, constructor, accessors — but only shallowly immutable; copy mutable components in its constructor.
⭐ Quick Revision
• Immutable class? → State fixed after construction (String, Integer, LocalDate).
• How? → Final class, private final fields set in constructor, no setters, defensive copies in constructor and getters.
• Why final class? → No overriding / added mutable state.
• final reference field = immutable? → No; contents can change.
• Defensive copy? → Copy mutable objects in and out; never share the internal instance.

equals(Object obj): are two objects equal?

Default: return this == obj; (reference check) — identical-data Students give false. Override to compare values:

@Override
public boolean equals(Object obj) {                  // the parameter MUST be Object, or it's an overload, not an override
    if (this == obj) return true;                    // same reference → equal (cheap shortcut first)
    if (obj == null) return false;                   // avoids NullPointerException
    if (getClass() != obj.getClass()) return false;  // avoids ClassCastException (e.g. an Integer passed in)
    Student s = (Student) obj;                       // now the cast is safe
    return age == s.age && Objects.equals(name, s.name);   // compare fields (null-safe for objects)
}
⭐ Correction: never compare String fields with == inside equals: the video's this.name == s.name worked only because both used literal "Aditya" (pooled). Input names (new String("Aditya"), Scanner…) fail. Use name.equals(s.name) or null-safe Objects.equals(name, s.name).
  • equals(Student s) + @Override → "must override or implement a supertype method"; must be equals(Object).

  • An int used by HashMap, HashSet, Hashtable to pick a bucket; same input, same hash. Correction: not "hexadecimal" — hex only in toString().
⭐ The equals–hashCode contract
Equal objects MUST have equal hash codes; equal hashes needn't mean equal objects (collisions).
Defaults satisfy it. Override equals → override hashCode, else "equal" Students hash differently: HashSet duplicates, HashMap.get() misses.
@Override
public int hashCode() {

    result = 31 * result + age;                              // mix in each field used by equals

The Problem Before Enums (pre-Java 5)

Payment is SUCCESS, FAILED or PENDING; without enums, int constants:

What an Interface Is

  • Abstraction via abstract classes or interfaces (Video 17). Interface = what, not how.
  • Class = blueprint of an object; interface = blueprint of behaviour / contract: implement all abstract methods or be abstract.
  • Not instantiable, but usable as a reference type.
interface Car { void drive(); }                  // implicitly: public abstract void drive();

Car c = new Thar();                              // interface reference → concrete object

⭐ Why public? Interface methods are implicitly public and overriding can't reduce visibility; omitting it → "Cannot reduce the visibility of the inherited method from Car".

The Diamond Problem, and Why Interfaces Avoid It

interface A { void fun(); }
interface B extends A { }
interface C extends A { }
class D implements B, C {
    @Override public void fun() { System.out.println("D"); }   // one implementation, no ambiguity
}

Java 8 Brought the Diamond Back (with Defaults)

interface B { default void fun() { System.out.println("B"); } }
interface C { default void fun() { System.out.println("C"); } }

class D implements B, C {
    // without this override: "Duplicate default methods named fun with the parameters () and ()
    //                          are inherited from the types C and B"
    @Override
    public void fun() {
        B.super.fun();          // pick B's version explicitly: InterfaceName.super.method()
        C.super.fun();          // …or C's, or both, or your own code
    }
}
new D().fun();                  // B  C

Implementing only B inherits B's default; conflict only when two same-signature defaults meet.

⭐ Resolution Priority Rules

1Class wins over any interface default.
2More specific interface wins (B extends A, both default fun() → B). (Not in video.)

⭐ String Is Immutable

Problem of Immutability: Concatenation in a Loop

  • Each iteration makes a new object, garbage piles up, and all previous chars are copied → O(n²).
  • Fix: mutable StringBuilder (unsynchronized, faster) / StringBuffer (synchronized) editing one buffer (next video).
  • Precision: a single a + b + c is optimised (StringBuilder pre-9; invokedynamic/StringConcatFactory 9+), but not across loop iterations.

Why byte[]? Compact Strings (Java 9, JEP 254)

  • char = 2 bytes (UTF-16) for all scripts (Hindi क, Chinese…), yet most strings are Latin and fit 1 byte: "Java" as char[] = 8 bytes.
  • Java 9+: all chars fit one byte → LATIN1 (coder 0): [74, 97, 118, 97] = 4 bytes (50% saving). Else UTF16 (coder 1): "कग" → 4 bytes. coder tells methods how to read value.

Corrections:
• ASCII is 0–127; 0–255 is Latin-1 (ISO-8859-1) (ASCII + é, ñ) — hence LATIN1.
• Encoding is per whole string: one क in "Hello क" makes every char 2 bytes.
• UTF16 mode reads two bytes per char (video: "two characters").
• Non-BMP chars (😀) need a surrogate pair (2 chars, 4 bytes): "😀".length() is 2.

The Cached hash

// String.hashCode(): s[0]*31^(n-1) + s[1]*31^(n-2) + … + s[n-1]
int h = hash;
if (h == 0 && …) { h = compute(); hash = h; }   // computed once, on first call
return h;
  • Computed on first hashCode(), then reused → fast map keys. Safe only because of immutability.
  • Precision: String overrides Object's hashCode() with this content formula; equal strings → equal hashes.
⭐ Three optimisations, all from immutability: ① pool ② compact strings (byte[] + coder) ③ hash caching.

Video 27: Generics (Part 1): Type Safety, Up/Down-casting, Generic Classes & Methods, Bounded Types

Type Safety

  • A type = set of values + allowed operations.
  • Java is statically, strongly typed: int x = 10.2; ✘, int y = s; (String) ✘. Type safety catches mistakes before runtime.

Upcasting & Downcasting

// primitives (recap): widening is automatic, narrowing needs a cast
long l = x;               // int → long ✔
int  i = (int) bigLong;   // long → int needs an explicit cast

// references
Animal a = new Dog();     // UPCASTING: child → parent, implicit, always safe
a.eat();                  // ✔ only Animal's methods are visible through 'a'
// a.bark();              // ✘ compile error: bark() isn't in Animal
Object obj = "Hello";     // String → Object, implicit

String s = obj;           // ✘ compile error: "Type mismatch: cannot convert from Object to String"
String s = (String) obj;  // DOWNCASTING: parent → child, needs an explicit cast

Object o2 = 10;           // autoboxed Integer
String bad = (String) o2; // compiles, but at RUNTIME: ClassCastException
  • Upcast (specific → general): always valid, no cast; callable methods follow the reference type.
  • Downcast: needs (Type); JVM checks at runtime → ClassCastException. Guard with instanceof (Video 22).
  • Why isn't (String) o2 caught? Compiler sees only declared types, not values (could come from input/file/API).
  • Unrelated casts ((String) someInteger) are compile errors ("Cannot cast from Integer to String"): siblings under Object.
⭐ Compile-time errors beat runtime errors (caught in the IDE, never reach production). Generics move type errors from runtime (ClassCastException) to compile time.

The Problem Generics Solve

class Box { private int value; … }         // works only for int
// → IntBox, StringBox, DoubleBox… one class per type: duplicated code

    private Object value;
    Box(Object value) { this.value = value; }
    public Object getValue() { return value; }
    public void setValue(Object value) { this.value = value; }
}
Box b1 = new Box(10);  Box b2 = new Box("Hello");  Box b3 = new Box(true);   // all compile
// b1.getValue() + 5;                      // ✘ "The operator + is undefined for the argument type Object"

String  s = (String)  b1.getValue();       // compiles… ClassCastException at runtime!
  1. Type info lost ("some Object").
  2. Wrong types accepted.
  3. Cast on every read.
  4. Errors at runtime.

Arrays Are Covariant, Which Makes Them Unsafe

Dog[] dogs = new Dog[10];

  • Generics: invariant, safe, compile-time error. Arrays: covariant, unsafe, runtime error → prefer List<T> in APIs.

Problem: printAnimals(List<Animal> a) can't take List<Dog>/List<Cat>. Solution: wildcards.

Wildcards (?)

1. Unbounded List<?>: some unknown type

2. Upper-Bounded List<? extends Animal>: Animal or SUBtype (covariant)

static void fun(List<? extends Animal> values) {

Erased Object get() vs String get() differ in bytecode, so the compiler (not "JVM") adds a synthetic bridge Object get() delegating to String get(): Parent<String> p = new Child(); p.get() → "Hello".

⭐ Two classic "why" questions
Why erasure? Java 5 had millions of raw-type classes; erasure kept bytecode and JVM unchanged (migration compatibility).
Why no List<int>? T erases to Object/bound and int isn't an Object; use Integer + autoboxing. (Not because "int is on the stack" — primitive fields live in heap objects.)

The Problem: Looping Over Any Collection

How It Works Inside

class ArrayList<T> implements Iterable<T> {           // really: via List → Collection → Iterable
    private Object[] arr;  private int size;

    @Override public Iterator<T> iterator() {
        return new Itr();                                // a NEW iterator object on every call
    }
    private class Itr implements Iterator<T> {           // inner class: can read arr and size directly
        private int pos = 0;                             // the cursor lives HERE, not in the list
        public boolean hasNext() { return pos < size; }
        public T next() { return (T) arr[pos++]; }       // return the current element, then move the cursor
    }
}

class LinkedList<T> implements Iterable<T> {
    private static class Node<T> { T data; Node<T> next; }
    private Node<T> head;
    public Iterator<T> iterator() {
        return new Iterator<T>() {
            private Node<T> current = head;
            public boolean hasNext() { return current != null; }
            public T next() { T d = current.data; current = current.next; return d; }   // O(1) per step
        };
    }
}
  • Iterator is an inner class (Video 19), reading the list's private arr/size/head directly.
  • LinkedList iteration: O(n) total vs O(n²) with get(i). Hash iterators go bucket by bucket; tree iterators in-order.
  • next() at end → NoSuchElementException; guard with hasNext(). (Not in video.)

Writing Your Own Iterable

class NameContainer implements Iterable<String> {
    private String[] names; private int size;
    NameContainer(String[] names) { this.names = names; this.size = names.length; }

    @Override public Iterator<String> iterator() {
        return new Iterator<>() {                       // anonymous class: used once, no named class needed
            private int pos = 0;
            @Override public boolean hasNext() { return pos < size; }

⭐ ConcurrentModificationException (Fail-Fast)

List<Integer> list = new ArrayList<>(List.of(1, 2, 3, 4, 5));
Iterator<Integer> it = list.iterator();
while (it.hasNext()) {
    int value = it.next();
    if (value == 3) list.remove(value);   // ✘ modifies the list BEHIND the iterator's back
    System.out.println(value);            // prints 1 2 3, then the next next() → ConcurrentModificationException
}
  • Structural change not via the iterator during iteration → iterator fails fast.
  • Mechanism (not in video): modCount vs iterator's expectedModCount, checked in next(). Happens single-threaded too; best-effort only (removing the second-to-last element slips through as hasNext() returns false).
  • Fixes: it.remove(), list.removeIf(v -> v == 3), or iterate a copy. for-each fails the same way.
  • Fail-safe (not in video): CopyOnWriteArrayList (snapshot), ConcurrentHashMap (weakly consistent) don't throw.
⭐ Hidden trap: list.remove(value) with int value = 3 picks remove(int index) over remove(Object o), deleting index 3 (value 4). By value: list.remove(Integer.valueOf(3)).

⭐ Why Separate Iterable and Iterator?

  1. SRP: the collection stores; another object traverses.
  2. Independent traversals. A cursor inside the list means one cursor per list:
    • A second loop sees hasNext() == false → manual reset().
    • Nested loops (pairs 10-10 … 30-30) break: inner advances outer, giving only "10 20, 10 30".
    • Each iterator() returns a new cursor → any number of simultaneous traversals.

⭐ Java Has No Separate "Set" Data Structure

A set = a map using only keys. HashSet is built on a HashMap, each element a key mapped to one shared dummy value:

public class HashSet<E> … {
    private transient HashMap<E, Object> map = new HashMap<>();
    private static final Object PRESENT = new Object();       // ONE dummy object shared by all keys

    public boolean add(E e)          { return map.put(e, PRESENT) == null; }  // null → it was new → true
    public boolean contains(Object o){ return map.containsKey(o); }
    public boolean remove(Object o)  { return map.remove(o) == PRESENT; }

HashMap Internals

The Idea, Step by Step

  1. Direct addressing: 5 at table[5]; O(1) but array as big as the largest key (10,000? a billion?).
  2. Modulo: index = key % n ∈ 0…n-1. Non-numbers: hashCode() → int → index.
  3. Collision: 4 % 4 = 8 % 4 = 0.
  4. Chaining: bucket holds a linked list (removal relinks, no shifting).
  5. Map entries: Node<K,V>; only the key is hashed. get(k) recomputes index, walks bucket.

The Real HashMap.Node

static class Node<K,V> implements Map.Entry<K,V> {
    final int hash;      // cached: never recompute hashCode during lookups or resizes
    final K key;
    V value;
    Node<K,V> next;      // the next node IN THE SAME BUCKET (collision chain)
}
⭐ Why compare the hash AND call equals? (Video 22 contract)
Check: p.hash == hash && (p.key == key || key.equals(p.key)).
• hashCode picks the bucket, O(1).
• Equal objects must share a hash, but equal hashes ≠ equal objects ("Aditya"/"Rohit" could collide) — equals decides.
• Cheap int compare first skips most equals calls.
• equals without hashCode → equal keys in different buckets: Set "duplicates", get null. Never mutate a key after insert (entry lost).
  • Duplicate key → value replaced (node kept); put returns the old value, null if new. (Video's early "won't be stored" is self-corrected.)
  • Table size is a power of two (16, 32…); index = (n - 1) & hash = non-negative hash % n, faster. Hash spread first: h ^ (h >>> 16).
  • Java 8+: new nodes at chain tail (Java 7: head).

Chaining vs Open Addressing

  • Separate chaining (HashMap): colliders share the bucket (list/tree).
  • Open addressing: entries in the array; collision → probe. Linear probing i+1, i+2… (Rohit wanted slot 1, taken → 2). Lookups probe the same; clusters form. (Not in video: IdentityHashMap and ThreadLocal's map use it.)

⭐ Load Factor & Rehashing

  • Load factor = entries / buckets; default 0.75.
  • Capacity 16 → threshold 12; 13th entry (++size > threshold; video: "stay below 12") → doubles to 32, entries redistributed.
  • Keeps chains short (~O(1)); else 100 entries in 5 buckets → O(n) lists.
  • Java 8: resize reuses cached hash (no hashCode()); each node stays at i or moves to i + oldCapacity by one bit.
  • Known size → new HashMap<>(expected / 0.75f + 1).

Treeification (Java 8+)

  • Chain hits 8 (TREEIFY_THRESHOLD) → red-black tree: O(n) → O(log n). Guards against bad hashes and collision attacks.
  • Only if capacity ≥ 64 (MIN_TREEIFY_CAPACITY); else resize.
  • Correction: untreeify at 6 (UNTREEIFY_THRESHOLD), not 8 — avoids flip-flopping.
  • Not always trees: nodes ~2× bigger; tiny buckets faster as lists.

    return this.name.compareTo(other.name);    // 2nd priority: String's own compareTo
}

⭐ Dangers of Returning Zero

  • 0 means the same element, not "similar".
  • TreeSet/TreeMap detect duplicates via compareTo, not equals: a different student comparing 0 is silently dropped (TreeMap put overwrites) — data loss.
  • Why not equals? Trees need left/right; 10.equals(20) = false doesn't place 20.
  • HashSet/HashMap (Video 33) use hashCode + equals, never compareTo.

⭐ Rule: compareTo consistent with equals — a.compareTo(b) == 0 ⇔ a.equals(b); use the same fields.
Lecture says "symmetric"; Javadoc: "consistent with equals", strongly recommended, not enforced. JDK exception: new BigDecimal("1.0") vs "1.00" — compareTo == 0, equals == false; TreeSet keeps 1, HashSet 2 (JDK 23).

Video 37: Comparator, Behaviour Passing, Functional Interfaces & Lambda Expressions

The Core Problem: Behaviour Is a "Second-Class Citizen"

  • OOP: everything revolves around objects — characteristics (variables) + behaviour (methods).
  • To run logic: write class X, put it in m1(), X x = new X();, call x.m1(). Behaviour is always boxed in an object — painful when you only need the behaviour.
  • Goal: behaviour passing — a function as an argument, m1(doSomething). Pre-Java 8 arguments were only variables: primitives (int, float, char…) or references (e.g. Student s1, whose methods m1 calls).
  • Java 8 (2014) added functional interfaces + lambdas — partial shift to functional programming. Lecture: OOP fits ~90–98% of cases; otherwise objects-for-everything is verbose.

Analogy: A Recipe for a Chef

Chef has cook(…); my pasta recipe is a behaviour. Java makes me create Person p1 = new Person(), put the recipe in it as a method, call cook(p1), and the chef calls p1.recipe() — an absurd middle-man.

Why: Sorting Students Many Ways

  • Student: String name, int rollNo, int marks; sort a List<Student>.
  • Comparable (Video 36), compareTo returning this.marks - s1.marks, fixes one ordering forever.
  • College app: teacher by marks, admin office by name, others by roll number.

The Comparator Interface: Logic Outside the Class

public interface Comparator<T> {      // java.util
    int compare(T o1, T o2);
}
  • Student stays lightweight; comparison lives in separate external objects, as many as needed.
  • Sign rule as in Video 36: negative → o1 first, positive → o2 first, 0 → equal.
  • Not "only one method": one abstract method + default/static helpers (reversed(), thenComparing(), comparing()…) + re-declared boolean equals(Object) (doesn't count, from Object, Video 24).

Functional Interfaces

Definition: exactly one abstract method; any number of default/static methods. Spec: SAM ("single abstract method") type. (Video 24.)
  • Comparable<T>: int compareTo(T o); Comparator<T>: int compare(T o1, T o2).
  • Lambdas are built on top of these — functional programming starts here: sometimes functions matter more than objects.

Lambda Expressions

General form: (parameters) -> expression; -> reads "maps to".

compare's params s1, s2, body s1.marks - s2.marks:

Collections.sort(list, (s1, s2) -> s1.marks - s2.marks);   // 85, 89, 93, 98

No class, object, @Override, name or return; sorts by marks.

Target Typing

  1. sort's 2nd param → Comparator.
  2. List<Student> → Comparator<Student>.
  3. One abstract method compare(Student, Student) → lambda is its body.
  4. s1, s2 are Students; the expression is the int result.

Target typing: the lambda's type is inferred from its context.

Anticipated: "Why must it be functional?"

With f1() and f2() abstract, () -> … is ambiguous. One abstract method is what makes lambdas possible. (Verified: "incompatible types: Two2 is not a functional interface".)

Lambda Syntax Variants

Examples target small interfaces (Adder, Square, Greeter), added here so they compile; built-in functional interfaces next lecture.

@FunctionalInterface interface Adder   { int add(int a, int b); }
@FunctionalInterface interface Square  { int apply(int x); }
@FunctionalInterface interface Greeter { void greet(); }

Adder   sum  = (a, b) -> a + b;                          // 1. multiple parameters
Square  sq   = x -> x * x;                               // 2. single parameter: () optional
Greeter g    = () -> System.out.println("hello");        // 3. no parameters: () required
Adder   sum2 = (a, b) -> {                               // 4. multi-line (block) body
    int s = a + b;
    return s;
};

sum.add(2, 3);    // 5
sq.apply(7);      // 49
g.greet();        // hello
FormSyntaxRules
Multiple parameters(a, b) -> a + bParens required; = int sum(int a, int b) { return a + b; }; types from target.
Single parameterx -> x * xParens optional.
No parameters() -> System.out.println("hello")() required; returns nothing → fits void.
Multi-line (block)(a, b) -> { int s = a + b; return s; }Braces + return (if a value) compulsory.
  • Single-expression: no return, no braces.
  • Explicit types (Student s1, Student s2) -> … or var (11+) — all-or-nothing.
Avoid long lambdas: they pay off for small logic; long complex logic belongs in a proper class (named Comparator) — OOP wins there.

Your Own Functional Interface & @FunctionalInterface

interface Demo {
    void m1();                // exactly one abstract method

One abstract method already is functional; annotation optional, but a later second abstract method is rejected ("Unexpected @FunctionalInterface annotation … multiple non-overriding abstract methods"), protecting existing lambdas.

⭐ Corrections & worth knowing
• Lambda ≠ anonymous class: invokedynamic, no Demo$1.class (verified; runtime name like Demo$$Lambda/0x…). this = enclosing object (anonymous class: itself).
• Captured locals must be effectively final (not in lecture); same for anonymous classes (pre-8: explicit final).
• No target, no type: var f = x -> x * x;, Object o = () -> {}; fail ("cannot infer type for local variable").
• Still use Integer.compare (subtraction overflows, Video 36). Idiomatic: list.sort(Comparator.comparingInt(s -> s.marks)) + .reversed()/.thenComparing(…); Collections.sort(list, cmp) delegates to list.sort(cmp).
• "Java is pure OOP": no — primitives aren't objects.
• Strategy pattern: interchangeable comparison logic; a lambda is the lightest strategy.
