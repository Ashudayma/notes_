Lecture 01

Introduction to Low-Level Design

Source: "Introduction To System Design" · 24 min · Code Army (Aditya)

The problem this lecture sets up

Most people learn DSA (searching, sorting, graphs, heaps) and can solve isolated LeetCode-style problems, but freeze when asked "build me a real app like Zomato / Ola / Uber." The gap isn't algorithmic — it's not knowing how to structure a whole application: what the objects are, how they relate, and how the app stays clean as it grows. That structuring skill is LLD.

Core idea: DSA vs LLD

DSA solves isolated, well-defined problems: "search an element in an array" → linear/binary search. "Sort an array" → quicksort/merge sort. Each is a self-contained problem with a self-contained algorithmic solution.

LLD is what happens when you take one or more DSA solutions and wrap a complete, structured application around them — deciding the objects, their relationships, and how everything plugs together so the algorithm actually becomes a working product.

"If DSA is the brain of an application, LLD is the skeleton."

Walkthrough: the QuickRide story

Two friends, Anurag (strong DSA, zero LLD) and Maurya (strong DSA and LLD), both join a ride-hailing startup "QuickRide" (an Ola/Uber-style app) and are separately asked: "figure out how to build this."

Anurag's approach (DSA-first, no LLD)
Sub-problem he sawHis solution
Get user from source → destinationModel the city as a graph (intersections = nodes, roads = edges), run Dijkstra's algorithm for shortest path.
Assign nearest available rider to a userPut nearby riders into a min-heap / priority queue keyed by distance from the user; pop the closest one.
Why the manager rejected this Both sub-solutions are algorithmically correct, but Anurag jumped straight to algorithms without ever defining: (1) what the entities/objects in the app are (User, Rider, Location, Notification, Payment…) and how they relate, (2) data security — e.g. once a ride ends, the rider shouldn't see the user's phone number and vice versa, (3) how to plug in Notifications and a Payment Gateway, (4) how the app scales to millions of users. Algorithms alone don't answer any of this.
Maurya's approach (LLD-first, then DSA)
StepWhat he does
1Identify entities/objects first: User, Rider, Location, Notification, Payment, etc.
2Define relationships between those objects (User ↔ Rider, Rider ↔ Location, …).
3Think through data security and privacy boundaries between objects.
4Design so the structure holds up under millions of users (scalability of the architecture, not just the algorithm).
5Only now does he bring in DSA — the same Dijkstra / min-heap ideas Anurag used — and plugs them into this already-solid skeleton.
Why this matters / why not skip straight to algorithms The algorithm was never the missing piece — both friends could write Dijkstra. What separated them was that Maurya built the skeleton (LLD) before writing any algorithm, so the algorithm had a proper place to live. Building LLD-first is why his design survives new requirements (payments, notifications, privacy rules) without a rewrite.

The Three Pillars of LLD

Whenever you design at the LLD level, you are optimizing for these three things:

  1. Scalability — can the application sustain a growing number of users, and how easily can a new feature be added/scaled, without the design falling apart?
  2. Maintainability — adding a new feature should not break old, unrelated features. Code should be easily debuggable (bugs are easy to isolate and find) and should introduce the minimum possible new bugs when extended. (0% bugs is unrealistic — the real goal is minimum bugs.)
  3. Reusability — code/modules should be "plug and play": you should be able to lift a piece out of one app and drop it into a different app with minimal changes.
Reusability in practice Notifications and Payment Gateway modules are application-independent — the same module plugs into QuickRide, Zomato, Swiggy, etc. Even the "assign nearest rider" algorithm is really a generic nearest-match mapping algorithm: Zomato/Swiggy use the same idea to match a delivery partner to a restaurant/order, Amazon and Blinkit use it for delivery assignment. The entities change, the matching logic doesn't. The opposite of this — logic fused so tightly to one specific app that it can't be lifted out — is called tightly coupled code, and it's exactly what LLD tries to avoid.

LLD vs HLD (a common confusion)

What each actually focuses on
Focuses onTypical interview activity
HLD (High-Level Design)Tech stack (e.g. Java/Spring Boot), database choice (SQL vs NoSQL vs hybrid), server scaling under bulk traffic, cost optimization (scale servers up/down to control real infra spend)Drawing system-architecture boxes/diagrams — almost no code is written

Edge cases / things worth double-checking

  • Dijkstra caveat: the video uses Dijkstra for shortest-path routing as a simplification. It only works correctly with non-negative edge weights (fine if edges are distances/times, which are never negative) — worth remembering if a variant of this question adds negative weights or requires re-routing around live traffic, where A* or other approaches are more appropriate.
  • "Everything is an object" is a simplification. The video says you can generally treat almost anything as an object in OOP — true in principle, but over-modeling (turning every noun into its own class) adds needless complexity. Later lectures on OOP pillars and SOLID refine when something deserves to be its own class/object — treat this first-pass identification as a rough draft, not a final model.
  • The privacy example (hiding phone numbers between rider/user after a ride ends) is a good recurring interview probe: whenever you design an entity relationship, ask "what should NOT be visible across this relationship, and when does that change?"

One-line takeaway

Remember this DSA = the brain (isolated problem-solving). LLD = the skeleton (the structure that holds the whole application together, built before the algorithms are dropped in). HLD = the architecture around the whole system (tech stack, DBs, servers, cost) — a different zoom level entirely, not a replacement for either.

OOPs: History, Abstraction & Encapsulation

Source: "OOPs Real-World Examples | OOPs Pillars" · 54 min · Code Army

Why OOP exists (history, compressed)

EraWhat it gaveWhat it still lacked
Machine language (0s/1s, direct to CPU)Direct CPU executionExtremely error-prone, tedious, not scalable at all
Assembly language (mnemonics, e.g. MOV A, 61H)English-like keywords, more people could programStill tightly coupled to hardware; no real loops/methods as we know them; still error-prone, not scalable
Procedural programming (e.g. C)Functions, loops, if/else & switch blocks — everything except OOP itselfNo real-world modeling, no data security, poor scalability/reusability for complex/enterprise programs
Object-Oriented ProgrammingModels real-world entities directly as objects—

What OOP adds over procedural programming

  1. Real-world modeling — code should mirror how the real world works: real objects interacting with each other.
  2. Data security — covered under Encapsulation below.
  3. High scalability & reusability — adding new entities/instances shouldn't mean duplicating variable/method sets by hand.

An object = Characteristics (state/data — unique identifying attributes) + Behavior (methods/functions it performs). A class is the blueprint used to create objects of that shape.

Procedural vs OOP — the Car/Owner example

Model: a Car (brand, model, isEngineOn) with behaviors (start, stop, shiftGear), and an Owner who owns and drives the car.

Procedural version — problems Car's characteristics become loose variables (brand, model, isEngineOn); its behaviors become standalone functions. To represent "Owner drives Car," you must write a free function drive(brand, model) that takes the car's data as parameters and calls start(), shiftGear(), accelerate() manually in sequence. Consequences: every new car needs a hand-duplicated set of variables (brand2, model2…); every new owner needs new variables and possibly new driving functions; the relationship "Owner owns/drives Car" is not visible anywhere in the code — it's just a pile of functions calling each other. Low scalability, low reusability, no real-world mapping.
OOP version — fix class Car { brand, model, isEngineOn, start(), stop(), shiftGear() } and class Owner { name, car, drive() } where Owner holds a Car object directly. drive() needs no parameters — it already has the car object and simply calls car.start(), car.shiftGear(), etc. Creating a new car/owner is just instantiating a new object from the same class — no manual variable duplication. The relationship (Owner → has-a → Car) is now explicit in the code structure itself.

Ideology of OOP (one-line rule)

Any OOP codebase is nothing more than a set of objects interacting with each other — either by calling one another's methods, or by being passed to one another as parameters. Nothing else is happening underneath.

The Four Pillars of OOP

Abstraction, Encapsulation, Inheritance, Polymorphism. This lecture covers the first two; Inheritance & Polymorphism are covered in the next lecture.

Pillar 1: Abstraction

Definition Abstraction hides unnecessary implementation details from a client (client = whatever object/user is interacting with this object) and exposes only what is necessary to use it.

Real-world analogies: driving a car needs only the interface (steering, pedals, gear stick) — not engine/gearbox internals. A TV remote is the interface to a TV whose internal circuitry/broadcast handling stays hidden. A laptop screen is the interface to its internal hardware. Even a high-level programming language (C++, Java, Kotlin) is an abstraction: keywords like if/for are English-like interfaces over what the compiler ultimately turns into machine code — you don't need to know that translation to use the keyword.

Abstraction — C++ implementation pattern

  • Define an abstract class (here, Car) containing only virtual method declarations (no implementation) — this is the interface/contract.
  • A concrete child class (here, SportsCar) inherits from it and provides the actual implementation (brand, model, isEngineOn, currentSpeed, currentGear as state; startEngine(), shiftGear(), accelerate(), brake(), stopEngine() as behavior).
  • An abstract class cannot be instantiated directly in C++ — a concrete subclass is required, then instantiated via Car* myCar = new SportsCar(...) (parent-type pointer to a child-type object).
  • Caller only ever calls the interface methods (myCar->startEngine(), myCar->shiftGear()…) without knowing how each is implemented internally.
Correction — pure virtual syntax matters The lecture writes the interface methods as plain virtual void startEngine();. In real C++, that alone does not make the class abstract or block instantiation — a class only becomes abstract (non-instantiable) when its virtual methods are declared pure virtual, i.e. virtual void startEngine() = 0;. Without the = 0, Car could technically be instantiated directly (and calling an undefined virtual method would only fail at link time, not compile time). If implementing this for interview/practice, always use = 0 for the interface methods to correctly enforce "must be overridden by a subclass."
Note C++ has no dedicated interface keyword (unlike Java/C#). An abstract class made entirely of pure-virtual methods with no data members is the C++ equivalent of an "interface."

Pillar 2: Encapsulation

Definition — two parts 1) Bundle an object's characteristics (data) and behavior (methods) together inside one unit (the class) — e.g. all of Car's fields and methods live inside one class Car.
2) Provide data security: some characteristics must not be directly readable/writable from outside the object at all.

Concrete example: a car's odometer/current speed should never be settable directly from outside — you can only change speed indirectly by calling accelerate() / brake(). This is enforced with C++ access modifiers: public (freely accessible, no security concern), private (not accessible from outside the class at all), protected (accessible to child classes only — covered properly in the Inheritance lecture).

Getters & Setters

Once a field is made private (e.g. currentSpeed, tyre), external code can no longer touch it directly. Controlled access is given back via public methods:

  • Getter: int getCurrentSpeed() { return this->currentSpeed; } — read-only exposure. (e.g. currentSpeed is given a getter but deliberately no setter — it should only ever change via accelerate()/brake().)
  • Setter: void setTyre(string tyre) { this->tyre = tyre; } — write access, but funneled through a method.
Why use getters/setters instead of just making the field public Even when both a getter and a setter exist for a field, routing writes through a setter method (instead of a public field) gives you a control point to add validation before the mutation happens — e.g. a setTyre(brand) can check the string is non-empty/valid, or that that tyre brand actually exists, before committing the change. A public field can never enforce this.

Abstraction vs Encapsulation — the actual distinction

ConcernIf violated
AbstractionData/implementation hiding for simplicity — client doesn't need to know internalsNo real harm if the hidden detail is seen anyway (e.g. popping the car's hood and inspecting the engine doesn't break anything)
EncapsulationData security — some state must never be directly accessible/settable from outsideReal harm/invalid state if violated (e.g. directly setting currentSpeed = 500 from outside produces a nonsensical/unsafe object state)
Worth flagging The lecture's "hiding vs security" split between Abstraction and Encapsulation is a simplified teaching heuristic, useful for interviews and for telling the two apart quickly. In broader OOP literature the two concepts overlap quite a bit (encapsulation is sometimes defined as including abstraction), so don't treat this as a rigid formal law — treat it as the practical rule of thumb this course uses consistently, which is what matters for applying it in LLD interviews.

Inheritance & Polymorphism

Source: "Inheritance & Polymorphism in OOPs" · 44 min · Code Army

Pillar 3: Inheritance

Real-world objects often show a parent–child relationship. Example: Car is generic; ManualCar and ElectricCar are both "a kind of" car — so Car is the parent, both are children.

  • Common to every car (belongs in the parent Car): brand, model, isEngineOn, currentSpeed; startEngine(), stopEngine(), accelerate(), brake().
  • Specific to ManualCar: currentGear; shiftGear().
  • Specific to ElectricCar: batteryPercentage; chargeBattery().

C++ syntax: class ManualCar : public Car { ... }. The child only needs to define what's specific to it — everything defined in Car is directly usable on a ManualCar/ElectricCar object without redefinition.

Access modifiers under inheritance

Why public inheritance is used ~99% of the time Protected/private inheritance strip visibility further down the hierarchy (e.g. a class inheriting from ManualCar could lose access to what ManualCar privately inherited from Car). This works against the whole point of inheritance — that a child should expose and build on everything the parent exposes. In real LLD/interview code, inheritance is used publicly almost exclusively; protected/private inheritance are rare, deliberate exceptions.

Pillar 4: Polymorphism

"Poly" = many, "morphism" = forms → one behavior, many forms. Two distinct real-world scenarios map to two distinct programming mechanisms:

Real-world scenarioProgramming termMechanism
Different subtypes of the same parent respond differently to the same call (Duck / Human / Tiger all "run" differently)Dynamic PolymorphismMethod Overriding
The same object/method responds differently depending on input/situation (a human runs differently with vs. without danger present)Static PolymorphismMethod Overloading

Dynamic Polymorphism (Method Overriding)

Declare the method as an (abstract/virtual) interface method in the parent Car — e.g. accelerate(), brake() — and let each child define its own version:

  • ManualCar.accelerate() → currentSpeed += 20
  • ElectricCar.accelerate() → checks battery isn't empty, drains battery, currentSpeed += 15

Rule for overriding: the method signature must match exactly between parent and child — same name, same return type, same number and type of parameters.

Correction (same issue as Lecture 2) For accelerate()/brake() in Car to actually behave as a true abstract/must-override contract in C++, they need to be declared pure virtual: virtual void accelerate() = 0;, not just virtual void accelerate();. Plain virtual without = 0 and without a body is a linker error only if called and never overridden — it does not force every subclass to override it, and does not make Car non-instantiable.

Static Polymorphism (Method Overloading)

Same class, same method name, different parameter lists: accelerate() (defaults to +20 speed) and accelerate(int speed) (accelerates by the given amount).

Rule for overloading: name and return type stay the same; the number and/or type of arguments must differ.

Overloading vs. Overriding — what must match

Full worked example: all 4 pillars in one hierarchy

Car (parent) — protected fields (brand, model, isEngineOn, currentSpeed) = Encapsulation; common methods startEngine()/stopEngine() defined here, accelerate()/accelerate(int)/brake() left virtual = Abstraction. ManualCar & ElectricCar extend Car = Inheritance. Each overrides accelerate()/brake() differently (dynamic) while also providing an overloaded accelerate(int speed) (static) = Polymorphism. One hierarchy, all four pillars simultaneously.

UML Diagrams: Class & Sequence Diagrams

Source: "UML Diagrams | Class & Sequence Diagrams" · 1h12m · Code Army

Why UML

UML diagrams are just a diagrammatic way to express an application's design instead of long descriptive paragraphs — what components/objects exist, and how they connect/interact.

Types of UML diagrams

CategoryAlso calledShows
Structural (7 types)Static diagramsThe application's static structure — what components exist and how they're connected
Behavioral (7 types)Dynamic diagramsHow components interact/communicate at runtime (message passing, method calls)
Why only 2 of the 14 matter The other 12 are highly use-case-specific and rarely appear in LLD interviews or day-to-day LLD work. Two cover almost everything needed: Class Diagram (structural — used in ~99% of LLD interviews, drawn before writing code) and Sequence Diagram (behavioral — not always asked, but clarifies specific flows extremely well when it is).

Class Diagram — representing a class

A class is drawn as a rectangle split into 3 parts: class name (top), attributes with their type (middle), methods with return type (bottom). Access modifiers are prefixed: + public, # protected, - private. An abstract class is labeled «abstract» above its name.

Class associations — 2 broad categories

  1. Class-level association — just one kind: Inheritance. Always an "is-a" relationship (ManualCar is a Car). Drawn as a line with a closed/hollow triangular arrowhead pointing to the parent.
  2. Object-level association — always a "has-a" relationship, 3 sub-types by strength. All three are coded identically in C++ (class B stores a reference/pointer to class A, initialized in B's constructor) — they differ only in real-world semantic strength, which is a design judgment call, not a syntax difference.
The 3 object-association strengths
TypeNotationMeaningExample
Simple Association (weakest)open arrowTwo objects just reference each other; no ownership/containment impliedArjun has-a / lives-in House
Aggregation (medium)hollow diamond, at the "container" endA container object holds several part-objects, but each part can exist independently of the containerRoom has Sofa, Bed, Chair (each could exist without that room)
Composition (strongest)filled/solid diamond, at the "whole" endThe whole is made of parts that cannot exist independently — destroying the whole destroys the partsChair is composed of Wheels, Seat, Armrest
Worth adding (standard UML nuance beyond the lecture's heuristic) The lecture's test for aggregation vs. composition is "can the part exist independently in real life?" — a good practical heuristic. The fuller UML definition adds: in composition the part's lifecycle is bound to the whole (created/destroyed with it) and it belongs to only one whole at a time; in aggregation the part can outlive the whole and can even be shared across multiple containers. Both framings agree in practice for typical LLD interview examples.
Why this is genuinely subjective sometimes Example from the lecture: is a Zomato/Swiggy Menu aggregated to or composed with its Restaurant? If you believe a menu can't meaningfully exist without its restaurant → composition. If you think of it as more loosely attached → aggregation. Both are defensible; there is no single correct answer, it depends on how you're modeling the rest of the system. Interviewers care more about whether you can justify the choice than which one you pick.
Counterintuitive but important In real LLD work, composition is used more often than inheritance. Composition is also the more flexible tool — it doesn't lock two classes into a rigid is-a hierarchy the way inheritance does.

Sequence Diagram — purpose

Shows how objects communicate over time for one specific use case/flow — not the whole application. A real application has many use cases, so it has many sequence diagrams (one per flow), never a single sequence diagram for the entire app.

Sequence Diagram — components

  • Object: drawn as a plain labeled box (no attributes/methods — that's the class diagram's job).
  • Lifeline: a vertical dashed line showing when an object exists within the flow (can start partway through, if the object is created mid-flow).
  • Activation bar: a solid bar on the lifeline showing when the object is actively able to send/receive messages. Outside its activation bar, an object can't send or receive.
  • Synchronous message: solid line + closed arrowhead; sender waits for a response before doing anything else. Response is drawn as a dashed line back.
  • Asynchronous message: solid line + open arrowhead; sender does not wait — can fire further messages within the same activation bar.
  • Create message: spawns a new object's lifeline mid-diagram.
  • Destroy message: ends an existing object's lifeline at that point (marked with an X in standard UML).
  • Lost message: a message sent that never reaches any object (ends in a filled dot in mid-air) — e.g. sent to an object whose activation bar had already ended.
  • Found message: a message received from an unspecified/unknown source (starts from a filled dot).
  • Control fragments (borrowed straight from programming): alt = if/else branch, opt = if-only branch, loop = iteration. Rarely used in interviews since you usually diagram the "happy path" only.

How to draw a sequence diagram (procedure)

  1. Write out the use case/flow in plain words first.
  2. Identify every object involved in that flow.
  3. Draw each object with its lifeline, add activation bars where it's active, and draw the messages between them in order.

Flow: User sends withdraw(amount, accountNumber) to ATM → ATM creates a new Transaction object → Transaction synchronously asks Account to checkAmount() → Account returns true → Transaction returns true to ATM and is then destroyed (its job is done) → ATM tells CashDispenser to withdrawCash() → CashDispenser returns the cash → ATM hands it to the User. PIN validation etc. is treated as a separate use case, not part of this diagram — each sequence diagram covers exactly one flow.

Lecture 05

SOLID Design Principles — Part 1 (S, O, L)

Source: "SOLID Design Principles | Complete Guide with Code Examples" · 1h7m · Code Army

Why design principles are needed

OOP pillars let you build classes/objects, but a real project has thousands of classes. Without agreed rules for structuring them, the codebase becomes tightly coupled and messy (analogy: a wall with electrical, internet and plumbing wiring all bundled together — a fault in one becomes very hard to isolate and fix). Concretely this shows up as three problems: poor maintainability (new features require touching a lot of code and risk breaking old features), poor readability (new engineers take long to understand tightly coupled code), and excess time spent debugging. SOLID = 5 design principles published by Robert C. Martin in 2000 to address exactly this.

SOLID = Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion. This lecture covers S, O, L; the next covers I, D.

S — Single Responsibility Principle (SRP)

Definition A class should have only one reason to change — i.e. it should do only one thing / handle only one responsibility.
Common misconception, corrected SRP does not mean "one method per class." A class can have as many methods (and helper methods) as it needs — the rule is that all of them must serve the same single responsibility. Real-world analogy used: a TV remote should only control the TV; cramming fridge and AC controls into the same remote is what SRP forbids, not having multiple buttons.

Violation example: a ShoppingCart class with calculateTotalPrice(), printInvoice(), and saveToDB() all in one class — it now has 3 separate reasons to change (pricing logic, invoice format, DB persistence), so a change to any one risks touching/breaking a class doing unrelated work.

After the split: ShoppingCart only calculates total price; CartInvoicePrinter (holds a reference to the cart) only prints invoices; CartDBStorage (also holds a reference to the cart) only persists to a database. Changing invoice formatting now only touches CartInvoicePrinter; changing DB logic only touches CartDBStorage.

O — Open/Closed Principle (OCP)

Definition A class should be open for extension, but closed for modification. Adding a new feature should not require editing the code of an already-existing, already-working class.
Violation example Given a DBStorage class with saveToDB(), adding Mongo and file support by directly adding saveToMongoDB() and saveToFile() methods inside that same class violates OCP — you modified an existing, already-shipped class just to add a new feature.

Fix: introduce an abstraction and use inheritance + polymorphism (method overriding) — the same interface/abstract-class mechanism from the OOP lectures. Each new persistence mechanism becomes its own new subclass; no existing class is ever touched again.

Adding Cassandra support later = add one new CassandraPersistence subclass overriding save(). SQLPersistence, MongoPersistence, and every other existing class stay untouched.

A caveat stated directly in the lecture OCP is a strict/idealistic rule — it's rarely followed with 100% purity in real production code. Treat it as "follow as closely as practical," not as an absolute law that can never be bent.

L — Liskov Substitution Principle (LSP)

Definition Subclasses must be substitutable for their base class: anywhere client code holds/uses a base-class reference, swapping in a subclass object instead must work correctly with zero changes to the client. Practically: a child class should only ever extend the parent's capabilities, never narrow/restrict them.

Violation example: Account (abstract: deposit(), withdraw()) → SavingsAccount, CurrentAccount implement both fine. But FixedDepositAccount cannot really support withdraw() (money is locked in) — forced to override it, it can only throw an exception. A client that loops over a list of Accounts calling withdraw() on each (never knowing some are FixedDepositAccount) crashes unexpectedly. The child narrowed the parent's contract instead of extending it — that's the LSP break.

Bad fix (and why it's bad) Adding an if (account is FixedDepositAccount) skip withdraw() check inside the client fixes the crash, but now the client is tightly coupled to every concrete account type — it has to be edited again every time a new account type with different capabilities is introduced. This "fixes" LSP by breaking OCP instead. Type-checking in client code to work around a subclass's limitations is a signal the hierarchy itself is wrong, not a real fix.

Correct fix: split the single Account abstraction into two, based on actual capability, so no subclass is ever forced to reject a method it inherits.

WithdrawableAccount extends DepositOnlyAccount and adds withdraw(). FixedDepositAccount now only extends DepositOnlyAccount — it was never forced to have a withdraw() method it can't honor. The client now keeps two separate lists (withdrawable accounts, deposit-only accounts) and only ever calls the method each interface actually guarantees — no runtime type-checks, no unexpected exceptions.

Worth adding: the deeper technical reason this matters Formally, LSP (per Barbara Liskov's original definition) also requires behavioral subtyping, not just matching method signatures: an override must not strengthen preconditions, weaken postconditions, or throw new exception types the base method's contract never promised. That's precisely why FixedDepositAccount.withdraw() throwing a brand-new exception is a violation at a technical level too — client code written against Account's contract has no reason to expect or catch that exception.

General lesson from LSP

When a subclass can't honestly implement one of its parent's methods, the fix is almost always to reshape the abstraction (split the interface by actual capability) — not to patch calling code with type-checks or make the method throw. Type-checks in client code against concrete subclasses is a recurring smell across SRP/OCP/LSP alike.
Lecture 06

SOLID Design Principles — Part 2 (LSP rules, Interface Segregation, Dependency Inversion)

Source: "SOLID Design Principles | part 2" · 1h17m · Code Army

Why revisit LSP

LSP (Lecture 5) looks simple — "a subclass must be substitutable for its parent" — but it's the SOLID rule most often broken unintentionally, because it's easy to miss. This lecture gives concrete, checkable guidelines split into 3 groups: Signature Rule, Property Rule, Method Rule.

Vocabulary used throughout: "broader" = a parent/ancestor class; "narrower" = a child/descendant class.

1. Signature Rule (3 sub-rules)

Sub-ruleRuleWhy
Method Argument RuleAn overriding method's parameter type must be the same as the parent's, or broader (contravariant) — never narrower.The compiler itself enforces this for a true override (mismatched params in C++ don't count as an override at all — you get a compile error like "does not override a base class member"). Not really breakable in practice.
Return Type RuleAn overriding method's return type must be the same, or narrower (covariant) — never broader. This is called covariance.A client holding a parent-typed reference only expects the parent type (or narrower) back. If a child returned something broader than the parent's declared return type, the client's reference couldn't hold it.
Exception RuleAn overriding method may throw the same exception type or a narrower (subclass) exception — never a broader/unrelated exception type.The client's catch block is written against the parent's contract (e.g. catching LogicError). A child throwing an unrelated exception (e.g. RuntimeError, which isn't a subtype of LogicError) sails past that catch block uncaught and crashes the program.
Concrete failure demonstrated in the lecture Parent's method throws LogicError (or a subclass like OutOfRangeError) — client catches LogicError. If a child overrides the method to throw RuntimeError instead (a sibling/unrelated exception branch, not a subclass of LogicError), the client's catch(LogicError&) never matches it → uncaught exception, program terminates.

2. Property Rule (2 sub-rules)

Sub-ruleMeaningExample
Class InvariantA rule that must always hold true for a class (documented as a comment, enforced by you in code — not a language construct). Extra fact worth remembering An immutable class (C++ final class) can't be inherited; an immutable method (C++ final method) can't be overridden. If a parent marks something immutable, a subclass making it mutable (were that even possible) would also violate the History Constraint — the rule isn't just about values, it covers "this should never change" guarantees generally.

3. Method Rule (2 sub-rules)

Sub-ruleRuleExample
Precondition (must hold before a method runs)A child may weaken (relax) the parent's precondition, but never strengthen (narrow) it.Parent: createPassword() requires length ≥ 8. Child requiring ≥ 6 is fine (weaker — accepts everything the parent accepted, plus more). Child requiring ≥ 10 is not fine (stronger — would reject a length-8 password the client, per the parent's contract, believed was always valid).

An ElectricCar override that also increases charge is fine (extra guarantee, strengthened) — but an override that stops decreasing speed would weaken the postcondition and is a safety-breaking LSP violation.

LSP: the 3 concrete tells of a violation

A child class fails to be substitutable for its parent when its override does any of: (1) throws an exception the parent's contract never promised, (2) leaves the method empty/no-op instead of properly implementing it, or (3) returns a hardcoded/meaningless value just to satisfy the compiler. Spotting any of these three in an override is a reliable signal of an LSP break — and per Lecture 5, the fix is almost always to reshape the interface (split by capability), not to patch the override or the caller.

I — Interface Segregation Principle (ISP)

Definition Many client-specific interfaces are better than one general-purpose interface. A class should never be forced to implement/override a method it has no real use for.

Violation example: abstract Shape with area() works fine for Square/Rectangle. Adding volume() directly to Shape (to support a new Cube subclass) forces every 2D shape to also override volume() — even though it's meaningless for them, leaving them to throw an error or return garbage just to compile.

Square and Rectangle only ever need to know about area(); Cube gets both area() and volume() from its own interface. No class overrides a method it can't meaningfully implement.

D — Dependency Inversion Principle (DIP)

Definition High-level modules should not depend on low-level modules — both should depend on an abstraction. High-level module = anything dealing with business logic. Low-level module = anything that talks directly to a system resource (a database, the file system, an external API).

Violation example: a UserService (high-level) directly holds MySQLDatabase and MongoDatabase objects and has separate methods storeUserToSQL(), storeUserToMongo() — tightly coupling business logic to specific storage tech. Swapping Mongo for Cassandra means editing UserService itself — breaking OCP as a direct side-effect of the DIP violation.

UserService now only calls db.save() — it never knows or cares which concrete database is behind db. The concrete object is supplied from outside (through the constructor) and resolved at runtime via polymorphism — this pattern of "handing in" a dependency rather than constructing it internally is called Dependency Injection. Adding Cassandra later = one new subclass; UserService is never touched again.

One-line rule worth memorizing "If Open/Closed Principle is the target, Dependency Inversion Principle is the solution." Introducing the abstraction layer between high- and low-level modules is usually exactly what makes OCP achievable in the first place.
Real-world analogy given A CEO (high-level) never talks directly to individual developers/QAs (low-level) — a Manager (the abstraction) sits in between in both directions. The CEO doesn't need to know who the current developers are; swapping team members doesn't require changing how the CEO operates.

Reconciling SOLID with "OOP models the real world"

Apparent contradiction, resolved If OOP is about mapping real-world objects, and real objects (like a human/User) do many things at once, how can SRP demand "one responsibility per class"? Resolution: a real-world object shows different behavior depending on context — the same person behaves differently at work vs. at home. Similarly, the same conceptual object (e.g. a User) only exposes the behaviors relevant to one specific application: a User in an Ola/Uber-style app can book/cancel a ride; the same conceptual User in a Zomato/Swiggy-style app can order/cancel food — not both at once, in the same class. SRP scopes "one responsibility" to what's relevant within a given application's context, not a claim that a real-world entity only ever does one thing in general.
Final caveat — SOLID are principles, not laws These are guidelines, not hard constraints. Real production code sometimes has to consciously bend a SOLID principle to serve the actual business logic — this is a genuine trade-off, comparable to the time-vs-space trade-off in DSA (you don't always reach for a hash map just because it saves time, if space is the real constraint). The goal is to follow SOLID as closely as practical, not dogmatically at all costs.

Build Google Docs — Document Editor LLD

Source: "Build Google Docs | A Real-World LLD Project | Document Editor LLD" · 45 min · Code Army

Problem statement

Design a document editor (Google Docs–style): a document holds an ordered sequence of elements — right now just text and image, but the design must be scalable to new element types later (tables, videos, fonts, bold/italic, new line, tab space…) without a rewrite. In a real interview you're not expected to implement every feature — explain the architecture for a couple of features and make sure it's extensible for the rest.

Design methodology: Top-Down vs. Bottom-Up

ApproachWhat it does
Top-downDesign the top-most/main object of the application first, then create smaller objects and dependencies inside it.
Bottom-upDesign the smallest objects and their dependencies first, then compose them into progressively bigger objects.
Which to use Most developers default to bottom-up in LLD interviews (and it's used for this problem) — a few specific question types are better suited to top-down, which becomes clearer with practice on more problems. Neither is universally "correct"; pick per problem.

Bad design (starting point, deliberately naive)

One DocumentEditor class holding a single vector<string> of "elements" (text stored as-is, images stored as a file path string), with addText(), addImage(), renderDocument(), and saveToFile() all inside it.

The hacky smell inside renderDocument() Since text and images are both stored as plain strings in one list, telling them apart at render time requires a **type-sniffing hack**: check if the string's length > 4 and ends in .png/.jpg → treat it as an image path, else treat it as text. This is a concrete anti-pattern worth recognizing: inferring an object's type from string content instead of using real polymorphism is exactly the kind of thing OOP/SOLID is meant to eliminate.

Violates: SRP (one class has ≥3 reasons to change: add-logic, render-logic, save-logic) and OCP (supporting a new element type like Table means editing this class's renderDocument() directly). LSP/ISP/DIP don't even apply — there's only one class, no hierarchy at all.

Better design: extract 3 hierarchies

  • DocumentElement (abstract, one method render()): each concrete type (TextElement, ImageElement, and later NewLineElement, TabSpaceElement, BoldElement…) knows how to render itself. Adding a new element type = one new subclass, zero changes to existing code → OCP satisfied.
  • Document: holds the ordered list of DocumentElements (a 1–to–many composition). Its render() doesn't know how to render any specific element — it just loops the list and calls element.render() on each, delegating the actual work. This is the same generic-mapping/polymorphism idea from earlier lectures.
  • Persistence (abstract, one method save()): FileStorage, DBStorage (extensible to more later) — identical DIP/OCP pattern as the persistence hierarchies in Lectures 5–6.
  • DocumentEditor: the client-facing class. Holds a Document and a Persistence reference (has-a, both injected via constructor). Every one of its public methods (addText, addImage, renderDocument, saveDocument) just delegates to the object that actually knows how to do the work.
Verified against all 5 SOLID principles SRP: each class has one job (Document = hold/manage elements, Persistence = storage, DocumentEditor = talk to the client and delegate). OCP: new element types or storage types are new subclasses, no existing class is edited. LSP: any DocumentElement subclass can sit in Document's list and get its render() called uniformly — fully substitutable. ISP: both abstract interfaces (DocumentElement, Persistence) have exactly one method each — no subclass is ever forced to implement something irrelevant to it. DIP: the high-level modules (Document, DocumentEditor) never talk directly to a low-level module (a specific storage mechanism) — they go through the abstract Persistence/DocumentElement layer.

A legitimate counter-question (and why it's genuinely debatable)

Even though DocumentEditor delegates all real work, it still needs to know that render() exists on Document and save() exists on Persistence — i.e. it has knowledge of more than one reason things could change elsewhere in the system, even if it isn't directly responsible for doing that work itself.

Instructor's own verdict on this This is genuinely a judgment call, not a clear pass/fail. If your reasoning is "this class only ever delegates, it never implements the logic itself," you can defend it as SRP-compliant. If an interviewer disagrees, that's a legitimate discussion, not you being "wrong." There is no single perfect LLD design — the goal is a design you can justify, not one that satisfies every principle with zero tension.

Further refinement: extracting DocumentRenderer

Pushing the SRP question further: pull rendering entirely out of Document into its own DocumentRenderer class (has-a Document). Document is reduced to a pure "model" class doing only CRUD on its element list (addElement, and now also getElements() so DocumentRenderer can fetch the list). A Client class is introduced to own and coordinate Document, DocumentEditor, DocumentRenderer, and Persistence together.

Principle of Least Knowledge (Law of Demeter) — a related but separate principle

Definition (not part of SOLID — a distinct design principle) "Talk only to your immediate friends." A class should only call methods on objects it directly holds/knows about — never reach through one object to call a method on its internal object ("a friend of a friend").
Where the refined design still breaks it DocumentRenderer.render() first calls document.getElements() (fine — Document is its direct friend), then loops the returned list and calls .render() on each DocumentElement (not fine — DocumentRenderer has no direct has-a relationship with DocumentElement; it only got access to it indirectly through Document). This is "talking to a friend of a friend," and it makes DocumentRenderer indirectly coupled to DocumentElement's interface.
The unresolved tension — and why that's the honest answer Fixing this Law-of-Demeter violation by moving render() logic back inside Document re-creates the earlier SRP tension (Document now does both element-management and rendering again). This is presented deliberately as an open trade-off, not resolved further — there is no configuration of this design that satisfies every principle at once with zero tension. Which trade-off to accept is something you'd negotiate with an interviewer or team, not something to treat as a single objectively "correct" answer.

Takeaway for approaching any LLD build question

Start from a deliberately bad/naive design, identify exactly which SOLID principle(s) it breaks and why, then refactor incrementally — extracting one hierarchy/responsibility at a time — re-checking against all 5 principles after each change. Expect genuine, defensible trade-offs near the end (not every principle can be maximized simultaneously); the skill being tested is reasoned justification, not reciting a single "correct" final diagram.

Strategy Design Pattern

Source: "Strategy Design Pattern Explained with Real-World Example" · 32 min · Code Army · First lecture of the Design Patterns section

What design patterns are

A design pattern is a proven, reusable solution to a recurring design problem — there are 23 official (GoF) patterns, but they all express the same core idea in different forms: identify the part of your application that changes frequently (the dynamic part) and extract it away from the part that stays fixed (the static part), into its own class(es). This keeps future changes localized to the dynamic part only.

Setup: simulating robots

A Robot base class needs walk(), talk(), and an abstract project() (how the robot visually looks — always overridden per robot type). CompanionRobot and WorkerRobot subclass it and only override project(). Looks fine initially.

Why the inheritance-only design collapses

StepNew requirement"Fix" attemptedNew problem created
1SparrowRobot, CrowRobot can flyAdd a fly() override in each new subclassIdentical fly() code duplicated across every flying robot — violates DRY (Don't Repeat Yourself)
2—Move fly() up into the base Robot class to de-duplicateNow every robot can fly, including ones that never should — incorrect behavior
3—Deepen the hierarchy: Robot → Flyable / NonFlyable → concrete robotsWorks, until…
4JetRobot flies via jet, not wingsOverride fly() again inside FlyableSame DRY violation recurs one level down once multiple jet-based robots exist
5—Split further: Flyable → FlyWithWings / FlyWithJetNow add robots that also vary independently in walking and talking ability…
6Robots that can't walk, can't talk, in every combination with flying abilityAdd Walkable/NonWalkable, Talkable/NonTalkable branches tooCombinatorial explosion: a new subclass is needed for every independent combination of walk/talk/fly behavior
The real failure mode This tree only branches on flying. Cross it with independent Walkable/NonWalkable and Talkable/NonTalkable variation (which the lecture does next) and the number of subclasses needed multiplies combinatorially — a new leaf class for every combination of behaviors, even though each behavior varies independently of the others.
One-liner from the lecture "The solution to inheritance is not more inheritance."

Strategy Pattern — definition

Define a family of algorithms, put each one into its own class, so that they can be swapped at runtime. ("Algorithm" here just means any self-contained behavior/method — walking, talking, flying all qualify.)

Applying it: extract the varying behaviors

What varies per robot: walk, talk, fly. What's fixed relative to a robot's own identity: project() (though see below — even this can be extracted). Pull each varying behavior out into its own abstract "Strategy" interface, with independent concrete implementations:

  • Walkable (walk()) → NormalWalk, NoWalk
  • Talkable (talk()) → NormalTalk, NoTalk
  • Flyable (fly()) → NormalFly, NoFly, FlyWithJet, … (freely extensible)

Robot's walk()/talk()/fly() methods do nothing themselves — each just delegates: walk() { walkBehavior.walk(); }, and so on. The instructor calls this a "dumb object": all real behavior lives in the injected strategy objects, resolved dynamically via polymorphism based on whatever was passed into the constructor.

Why this actually fixes the explosion A new robot is just: pick any existing (or new) Walkable + Talkable + Flyable combination and inject them at construction — no new subclass needed for a new combination of behaviors, only for a genuinely new individual behavior. A brand-new flying style (e.g. FlyWithJet) is one new class; Robot's own code is never touched — full OCP compliance.
One-line philosophy "Favor composition over inheritance." Composition solves exactly the combinatorial/duplication problem that deep inheritance hierarchies create.

Anticipated question: "aren't CompanionRobot/WorkerRobot still inheritance?"

Yes — and it can be removed too. Extract project() itself into its own Projectable strategy interface (with concrete implementations per look), inject it the same way as the other three. Robot then needs zero subclasses at all — every robot is just a new Robot(walkBehavior, talkBehavior, flyBehavior, projectBehavior) with a chosen combination of strategies. This shows the pattern can be pushed to fully eliminate inheritance from the design if desired.

Standard UML shape of Strategy Pattern (reusable template)

This Client/Strategy/ConcreteStrategy shape recurs across many design patterns — worth recognizing on sight:

Client = whatever object uses the algorithm (here, Robot). Strategy = the abstract family (here, Walkable/Talkable/Flyable). ConcreteStrategy = each interchangeable implementation. The client's own method just calls strategy.run() — which concrete strategy actually runs is decided purely by what was injected.

Real-world examples (beyond robots)

ContextClient methodStrategies
Payment systempayNow()UPIPayment, CardPayment, NetBankingPayment
Sorting utilitysort()QuickSort (normal / randomized variants), MergeSort (normal / in-place variants), InsertionSort

Why this pattern matters most

Strategy is one of the most frequently used patterns in real LLD interviews — almost any non-trivial application design ends up using it somewhere, any time a piece of behavior needs to vary independently and be swapped at runtime without touching the classes that use it.

Factory Design Pattern

Source: "Factory Design Pattern | Simple, Factory Method & Abstract Factory" · 32 min · Code Army

Why Factory exists (relation to Strategy)

Strategy Pattern (Lecture 8) assumed the strategy objects (NormalTalk, FlyWithJet, etc.) already existed somewhere and just called their methods — it never addressed where the new keyword actually gets used. Every application eventually has to construct objects somewhere. Factory Pattern's job: separate object-creation logic from business logic, so the two don't get tangled in the same class — mixing "what an object is used for" with "how/when it gets built" makes code harder to read and reason about.

The goal (same decoupling instinct as everything else in LLD) A client shouldn't need to know how an object is constructed. It just asks a factory for the object it needs, and the factory hands one back. This is the same "keep the client dumb about internals" instinct behind DIP, Strategy, and most SOLID principles.

Three kinds of Factory

KindIs it an official (GoF) design pattern?What it does
Simple FactoryNo — it's a design idiom, not a catalogued patternOne factory class with an if/else (or switch) chain that picks which concrete class to instantiate, based on a type parameter
Factory MethodYesThe factory itself becomes an abstract class/interface; each concrete factory subclass decides which concrete product class to build
Abstract FactoryYes (extends Factory Method)A factory (abstract, with multiple creation methods) produces a whole family of related products, not just one

Simple Factory — burger shop example

Burger (abstract, prepare()) → BasicBurger, StandardBurger, PremiumBurger. A BurgerFactory class has one method createBurger(type: string) that if/else-matches the string ("basic"/"standard"/"premium") and returns the matching concrete Burger.

Why this isn't a "real" pattern — and the OCP problem it still has Adding a fourth burger type means editing BurgerFactory.createBurger()'s if/else chain directly — the exact same "modify existing working code to add a feature" problem OCP forbids. Simple Factory only solves the separation problem (creation logic is out of business logic); it does not solve the extensibility problem. That's exactly what Factory Method fixes.
Definition "A factory class that decides which concrete class to instantiate."

Factory Method — making the factory itself polymorphic

Extend the example: two franchises, SingBurger (makes normal burgers) and KingBurger (makes wheat-based burgers) — add BasicWheatBurger/StandardWheatBurger/PremiumWheatBurger alongside the normal trio. Now BurgerFactory itself becomes abstract with one abstract method createBurger(type); SingBurgerFactory and KingBurgerFactory each override it to build their own family of concrete burgers.

Client: BurgerFactory* factory = new KingBurgerFactory(); factory->createBurger("basic") → a BasicWheatBurger. A brand-new franchise with a brand-new burger family = one new BurgerFactory subclass; no existing factory's code is ever edited — OCP restored.

Definition "Define an interface for creating an object, but let subclasses decide which class to instantiate."

Abstract Factory — producing families of related products

Extend once more: SingBurger and KingBurger now each also sell GarlicBread (BasicGarlicBread/CheeseGarlicBread, and their wheat equivalents). The abstract factory now declares two creation methods — createBurger(type) and createGarlicBread(type) — and each concrete factory overrides both, consistently producing its own family (SingBurger → normal burger + normal garlic bread; KingBurger → wheat burger + wheat garlic bread).

Definition "Provides an interface for creating families of related objects without specifying their concrete classes."
Factory Method vs. Abstract Factory — the one thing that differs Factory Method: one product type per factory hierarchy. Abstract Factory: multiple related product types produced together, consistently, by the same concrete factory. Abstract Factory is Factory Method extended to more than one product family.

Real-world example: Notification System

NotificationSystem (abstract) → SMSNotification, PushNotification, EmailNotification. A factory takes a type string ("sms"/"push"/"email") and returns the matching concrete notification object.

Strategy vs. Factory — how to decide which one applies (important, recurring confusion)

The exact same Notification System could also be modeled with Strategy Pattern (treat SMS/Push/Email as interchangeable strategies injected into NotificationSystem via composition). Both are valid — they just carry different intent, and multiple design patterns can legitimately solve the same problem.

The decision heuristic given Ask: do I need to vary an algorithm/behavior at runtime, assuming the object already exists somewhere? → Strategy. Do I need to separate the object-creation logic itself from business logic — i.e. the object is not assumed to be pre-built, and deciding how to construct it is the actual problem? → Factory.
There is no single correct answer Which pattern "better fits" a given problem is often a genuinely subjective call, and reasonable engineers can disagree. What actually matters in an interview is being able to articulate why you chose one over the other, and being aware the alternative exists — not landing on one uniquely "correct" diagram.

Singleton Design Pattern

Source: "Singleton Design Pattern | Thread-Safe, Lazy & Eager Initialization + Real Use Cases" · 32 min · Code Army

Definition

A Singleton is a class that can have only one instance ever. Any further attempt to create an instance returns the same existing one instead of a new one.

Background: what new actually does

Two memory regions: stack (primitive/non-heap locals) and heap (objects of custom classes). A* a = new A(); does, in order: (1) reserve space on the heap sized to class A, (2) call A's constructor to initialize it (every class has one — the compiler supplies a default constructor if you don't write one), (3) store the heap address in the stack-allocated pointer a. Nothing stops you from repeating this line to get a second, independent object — that's the exact behavior Singleton needs to block.

Building it step by step

  1. Make the constructor private — blocks any external code from calling new Singleton() directly.
  2. Add a public static method, conventionally getInstance(), that returns the instance. It must be static because a normal (non-static) method needs an object to be called on — but no object can exist yet before the first call.
  3. Add a private static pointer (e.g. instance), initialized to nullptr. getInstance() checks: if instance == nullptr, create the one-and-only object and store it; otherwise just return the existing one.

C++ specific: a static member must be defined outside the class body (Singleton* Singleton::instance = nullptr;) — Java allows inline initialization instead.

Making it thread-safe

The naive version above is not thread-safe: two threads can both evaluate instance == nullptr as true simultaneously (before either has created the object) and both proceed to construct their own instance — defeating the entire point of Singleton.

ApproachHow it worksTrade-off
Lock the whole methodAcquire a mutex lock at the very start of getInstance(), for every callCorrect, but locking is expensive — paying that cost on every call (even the millionth call, long after the instance already exists) is wasteful
Double-Checked Locking (DCL)Check instance == nullptr without a lock first; only acquire the lock if it's still null; then check == nullptr again inside the lock before actually constructingSkips locking entirely once the instance exists (the common case) — but needs both checks: the first check alone still lets two threads both enter the locked region back-to-back and double-construct
Technical correction — DCL has a known deeper pitfall in C++ Classic Double-Checked Locking as taught here is a well-known real-world pitfall: without proper memory ordering, the compiler or CPU can reorder instructions so a second thread observes a non-null pointer to an object whose constructor hasn't actually finished running yet (this is the historically documented "DCLP" problem, discussed by Meyers & Alexandrescu). Fixing it properly needs an atomic pointer with acquire/release memory ordering (C++11 std::atomic), not a plain raw pointer.
The simpler, standard-guaranteed modern alternative Since C++11, a function-local static variable is guaranteed by the language standard to be initialized exactly once, in a thread-safe way, with no manual locking needed at all (the so-called "Meyer's Singleton"): static Singleton& getInstance() { static Singleton instance; return instance; }. In real C++ LLD/interview contexts, this is generally preferred over hand-written double-checked locking.

Eager Initialization (the no-locking alternative)

Instead of lazily creating the instance on first getInstance() call, construct it immediately when the static member is declared — Singleton* Singleton::instance = new Singleton(); — so it exists before main() even runs. getInstance() then just returns instance directly, no null-check, no lock, ever.

BenefitCost
Eager initSimplest possible code; inherently thread-safe with zero locking overheadMemory/resources are spent immediately even if the singleton is never actually used in that particular run
When to use eager vs. lazy+DCL Eager initialization is fine only when the singleton object is lightweight. If constructing it is expensive (heavy memory/resource allocation — e.g. a large connection pool), eager init risks wasting that cost on every application startup even when unused; lazy initialization (with correct thread-safety) is the better fit there.

Real-world use cases

Use caseWhy Singleton fits
Logging systemIf every service fetched its own logger object independently, log lines from different services would interleave unpredictably across many objects that all do the same job. One shared logger instance = one consistent, ordered log output.
Database connectionEstablishing a DB connection is expensive. Creating a fresh connection object per request wastes massive memory/resources; a single shared connection (or connection manager) avoids that.
Configuration managerAPI keys and other app-wide config must be a single source of truth. If every service held its own copy, one service could silently drift out of sync by mutating its own copy.

When NOT to use Singleton

  • When you already know you need multiple independent instances by design — e.g. each player object in a game must have its own separate state/session, never a shared one.
  • Singleton adds real thread-safety complexity (locking, DCL correctness) and makes unit testing harder (shared global state between tests, harder to mock/reset). Don't reach for it unless the single-shared-instance benefit is clear and needed.

Build Zomato/Swiggy — Food Delivery App LLD

Interview process this lecture models (reusable for any "build X" question)

  1. Gather requirements — split into functional (product/business logic: what entities exist, how they interact) and non-functional (scalability, concurrency, etc. — not directly business logic).
  2. Narrow the scope aggressively via counter-questions. No one expects a fully working Zomato in an hour; the interviewer is evaluating your flow, your UML, your use of OOP/SOLID/patterns, and whether you can produce working (if simplified) code — not full delivery-app coverage.
  3. Discuss the "happy flow" in plain words with the interviewer before touching UML, to confirm you're both aligned.
  4. Only then build the UML diagram (catches structural issues cheaply, before code) followed by working code.
Treat the interviewer as a collaborator, not a judge LLD questions are subjective and conversational by nature — there's constant back-and-forth ("true and fro"). Ask questions, propose a direction, let them redirect you. Silently building in your head and presenting a finished answer is the wrong mode for this format.

Scoping decisions made via counter-questions (what's IN vs OUT)

Happy flow agreed on: User → searches restaurants by location → opens one → sees its menu → adds items to cart → checks out (delivery or pickup, now or scheduled) → pays → gets notified.

Building bottom-up (smallest objects first)

Bottom-up: build small objects and their relationships first, then compose upward into bigger objects — the approach used for most LLD interview questions (vs. top-down, which suits a narrower set of question types and comes with practice).

Composition vs. aggregation vs. association — each call justified, each subjective

RelationshipChosen asReasoning given

Why Manager classes are Singletons AND a single point of contact

A manager (e.g. RestaurantManager) must be a Singleton — if multiple instances existed, each would maintain its own separate list of restaurants, fragmenting state that should be shared app-wide. It's also deliberately made the only way anything else talks to Restaurant objects (no other class holds/queries restaurants directly) — the same "single point of contact / don't let outside code reach through you" instinct as Principle of Least Knowledge (Lecture 7) and DIP's abstraction layer.

Refining OrderFactory's parameters (a live Principle-of-Least-Knowledge fix)

First pass: createOrder() took everything — User, Cart, Restaurant, MenuItems, PaymentStrategy, OrderType — and reached into User to pull the cart, then into the cart to pull restaurant/items/total.

Why that's wrong This forces OrderFactory to know User has a Cart, and that a Cart has a Restaurant and items — a Principle-of-Least-Knowledge violation (reaching through an object to its internals, "talking to a friend of a friend," same failure mode flagged in the Document Editor lecture).
The fix actually used Let the caller (the orchestrator, which already legitimately knows how to pull restaurant/items/total out of a cart for its own checkout logic) pre-extract those values and pass them directly: createOrder(user, restaurant, items, total, paymentStrategy, orderType). OrderFactory now only needs to know how to assemble an Order from parts handed to it — it stays a "dumb object," with zero knowledge of User/Cart internals.

The Tomato orchestrator — a deliberate, named trade-off

Tomato is the single class the client (front-end) talks to; it delegates every real operation to the right manager/factory/strategy (searchRestaurant() → RestaurantManager, addToCart() → Cart, checkoutNow() → OrderFactory, payForOrder() → PaymentStrategy, then NotificationService).

Explicitly acknowledged cost Tomato itself breaks SRP (many reasons it could need to change, since it touches every subsystem) and the Principle of Least Knowledge (it must know about nearly every object in the system to route requests). This is accepted on purpose to give the client one clean single point of contact, rather than exposing the entire object mesh directly — the same "no design perfectly satisfies every principle at once" conclusion reached in the Document Editor lecture.
Real-world alternative (out of scope here, but worth knowing) Modern frameworks (Spring Boot, Django) avoid a single orchestrator "God object" by splitting a Controller/API layer (routes requests, e.g. /searchRestaurant?location=Delhi) from a separate Service layer per concern (business logic) — a more decentralized alternative not built here because API/routing design is its own separate concern from the class-diagram-level LLD this exercise focuses on.

Further extensions discussed (not built, but noted as natural next steps)

  • Combine Factory + Strategy: introduce a PaymentStrategyFactory so deciding which payment strategy (UPI/credit card/net banking) to use isn't hardcoded in client code — the client should only need to say what it wants paid, not pick the strategy class itself.
  • Turn NotificationService into its own Strategy hierarchy: PushNotification, EmailNotification, WhatsAppNotification, etc., each overriding a common notifyUser() method — instead of one hardcoded notification implementation.

Observer Design Pattern

Source: "Observer Design Pattern Explained | Real-Life Use Case + Code Example" · 28 min · Code Army

The problem

Two objects: one's internal state changes over time, and one or many others need to know exactly when it changes (and what the new value is) — e.g. a YouTube channel uploading a video, and every subscriber wanting to know immediately.

Polling vs. Pushing

ApproachHow it worksProblem
Polling (rejected)The interested object repeatedly asks the source "has your value changed yet?"Wasteful and impractical — you don't know how often to ask, so you'd have to ask constantly (every second? millisecond?) getting "no" almost every time.
Pushing (Observer Pattern)The source itself takes responsibility for telling interested objects the moment its state changes— this is the whole pattern.

Naming convention used from here on: the "I" prefix

A pure abstract class (C++) / interface (Java) — every method virtual/abstract, acting purely as a contract between a client and whichever concrete class implements it — gets named with a leading I (e.g. IObservable, IObserver). This is just a naming convention (C++ has no separate interface keyword), used from here on in the course to make "is this abstract or concrete?" obvious at a glance.

Structure: Observable and Observer

The object being watched = Observable (a.k.a. Subject) — something that can be observed. The objects watching it = Observers. Relationship is one-to-many: one Observable, many Observers.

  • IObservable (abstract): add(observer) (subscribe), remove(observer) (unsubscribe), notify() (loop over all registered observers and call each one's update()).
  • IObserver (abstract): update() — called by the observable whenever it changes; the observer's job is to refresh its own state in response.
A deliberately atypical design choice, called out explicitly Usually a relationship should be drawn between two abstract types, not two concrete ones. Here, ConcreteObserver is deliberately given a reference to ConcreteObservable (the concrete class), not IObservable. Why: when update() runs, the observer needs to actually pull the new value (e.g. call a getValue()-style method) — and that data-fetching method is specific to the concrete observable, not part of the generic IObservable contract. Holding the concrete reference lets update() reach the concrete-specific getter directly.
Worth knowing: this is the "pull" variant — there's also a "push" variant This lecture implements the classic pull model: notify() calls update() with no arguments, and the observer reaches back into the observable to fetch what it needs. The equally common push variant instead passes the changed data directly as a parameter — update(newValue) — which avoids the observer needing to hold a concrete reference to the observable at all (it can hold the abstract IObservable type, or no reference whatsoever). Push is simpler when observers only need the one piece of data that changed; pull is better when the observer might need to query the observable for more/other state on demand.

Standard definition

"Define a one-to-many relationship between objects so that when one object changes state, all of its dependents are notified and updated automatically."

Worked example: YouTube channel & subscribers

IChannel (abstract): subscribe(), unsubscribe(), notifySubscribers(). ISubscriber (abstract): update(). ConcreteChannel holds the subscriber list and adds two business-specific methods: uploadVideo(title) (stores the new video, then internally calls notifySubscribers()) and getVideoData() (returns info about the latest video). ConcreteSubscriber holds a reference to the concrete channel; its update() calls channel.getVideoData() to pull the new video's info.

Flow: varun and tarun both call channel.subscribe(self) → both added to the subscriber list. channel.uploadVideo("Observer Pattern Tutorial") → internally calls notifySubscribers() → loops the list calling update() on each → both varun and tarun print a notification, each pulling the video title via channel.getVideoData(). After varun calls unsubscribe(), the next uploadVideo() only notifies tarun.

Acknowledged SRP violation — and why it's kept anyway

The violation ConcreteChannel does two distinct jobs: (1) the generic Observer-pattern mechanics (subscribe/unsubscribe/notifySubscribers), and (2) channel-specific business logic (uploadVideo, getVideoData). Two reasons to change → SRP violation.
Why it's accepted as a deliberate trade-off The Observer-mechanics half of this class is never going to change — subscribe/unsubscribe/notify logic is generic and stable. Only the business-logic half changes over time. Since one half is genuinely static and the other genuinely dynamic, combining them causes little real harm in practice, and standard reference UML diagrams for Observer Pattern found elsewhere make the same simplification. Splitting them further is possible (keep pure Observer mechanics in IChannel's concrete base, business logic in a separate subclass) but adds complexity for no real payoff here — simplicity wins this particular trade-off.

Real-world use cases

  • Notification services — a notification source informs every registered listener the moment something new exists.
  • News feed / social media — a new post from an account is pushed out to every follower/friend watching that account.
  • Event handling (a well-known programming paradigm) — an event is triggered, and every registered listener/handler for that event type is invoked; front-end "event listeners" are a direct real-world instance of Observer Pattern under the hood.

Decorator Pattern

Source: "Decorator Pattern Explained | Real-world use case + Code" · 29 min · Code Army

The problem

Attach additional responsibilities/behavior to an object dynamically, at runtime — and be able to stack an arbitrary number of enhancements, in any combination and order, without an explosion of subclasses.

Why plain inheritance + polymorphism isn't enough

You can already pick between behaviors at runtime via a base-class pointer: Base* b = new Base() vs. Base* b = new Child() determines which overridden method runs. But this only lets you choose one fixed variant at construction time — it doesn't let you layer multiple independent enhancements on top of each other and combine them arbitrarily.

Class explosion: the Mario game example

A Mario character gains power-ups over time: Height-up, Gun ability, Star ability, (later) Fly ability — and critically, these can apply in any combination and any order (unlike the real game, this design wants Gun-without-Height-up to be valid too). Modeling this with inheritance means a new subclass for every combination: MarioWithHeightUp, MarioWithGun, MarioWithHeightUpAndGun, MarioWithGunAndHeightUp(?), and every time a new power-up is added, the number of required combination-subclasses multiplies further.

Same root cause as the Strategy Pattern lecture This is the identical failure mode as the flying-robot class explosion in Lecture 8 (independent behavior axes crossed combinatorially). The two patterns solve related-but-different shapes of that problem: Strategy swaps out one behavior at a time via composition (pick one Walkable + one Talkable + one Flyable). Decorator instead lets you stack an open-ended number of layered enhancements on the same object, recursively, which Strategy's one-slot-per-behavior model doesn't support.

The Decorator solution

Wrap the object in a decorator object. Calling a method on the outer decorator calls the same method on the wrapped object first, then enhances the result before returning it to the caller. Decorators can be stacked arbitrarily deep — each new decorator wraps the previous one.

The defining dual relationship: is-a AND has-a, together

A Decorator both extends ("is-a") the same abstract base type as the object it wraps, and holds a reference to ("has-a") an instance of that same abstract base type. Is-a exists so the decorator can be used anywhere the base type is expected — including being passed into another decorator's constructor, which is exactly what allows unlimited stacking. Has-a exists so the decorator can delegate to (and then enhance) whatever it's wrapping.

Building a character: new StarPowerDecorator(new GunPowerDecorator(new HeightUpDecorator(new MarioCharacter()))). Calling getAbilities() on this recursively unwinds inward — StarPower calls GunPower's getAbilities(), which calls HeightUp's, which calls the base MarioCharacter's — then each layer appends its own bit on the way back out: "Mario" → "Mario with Height-up" → "Mario with Height-up with Gun" → "Mario with Height-up with Gun with Star Power". Any subset and any order of decorators is achievable with zero new subclasses beyond one per genuinely new power-up — no combinatorial explosion.

It's recursion, just spread across classes Each decorator's method calling the wrapped object's same method, then appending to the result, is structurally identical to a recursive function unwinding a call stack — it's just implemented as a chain of object delegation instead of a single function calling itself.

Standard definition

"Attaches additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality."

Real-world use cases

  • Text editor formatting (ties directly back to the Document Editor build in Lecture 7, which didn't use this pattern at the time): a base Text component wrapped by BoldDecorator, then ItalicsDecorator, then UnderlineDecorator/FontDecorator — each formatting option layered independently and in any combination.
  • Form validation pipeline: a base form wrapped by an EmailValidationDecorator, then an XSSCheckDecorator, then a SQLInjectionCheckDecorator — each validation/security layer added independently, stackable in any combination, without editing a monolithic validation method.

Build a Notification Engine (Observer + Strategy + Decorator + Singleton)

Source: "Build Your Own Notification Engine | System Design" · 42 min · Code Army

Requirements

  • Plug-and-play: integrate into any application with minimal code changes to that application's architecture.
  • Highly extendable channels: support SMS, email, popup now; adding e.g. WhatsApp later should need minimal changes (SOLID-compliant).
  • The notification itself must be dynamically extendable: able to add headers, footers, signatures, timestamps, etc. on the fly.
  • Store all notifications sent (history) and log them.

This lecture is a synthesis exercise: it reuses four previously-covered patterns together — Decorator (building the notification), Observer (delivering it to whoever cares), Strategy (how each channel actually sends it), and Singleton (the coordinating service).

Layer 1: building the notification (Decorator Pattern)

Satisfies "the notification must be dynamically extendable." INotification (abstract, getContent()) ← SimpleNotification (wraps a plain text string). NotificationDecorator (abstract, is-a + has-a INotification — the same dual relationship from Lecture 13) ← TimeStampDecorator, SignatureDecorator, each prepending/appending to whatever the wrapped notification's getContent() returns.

Layer 2: delivering it (Observer Pattern) + sending it (Strategy Pattern)

IObservable (add/remove/notify) ← NotificationObservable: holds the observer list and a reference to the current INotification, with getNotification()/setNotification() — setNotification() internally triggers notifyObservers(). IObserver (update()) ← two concrete observers: Logger (pulls the notification content and logs it) and NotificationEngine (an observer that is itself a Strategy-pattern client).

A twist on classic Strategy: one-to-MANY, not one-to-one Ordinarily a Strategy client holds exactly one active strategy (has-a). Here, NotificationEngine must send the same notification out through every channel the user wants simultaneously (email and SMS and popup, not a choice of one) — so it holds a list of INotificationStrategy and loops over all of them on update(), calling sendNotification() on each.

The bridge: NotificationService (Singleton)

NotificationService connects notification-building to notification-delivery: sendNotification(notification) pushes the notification onto its history list (for storage), then calls observable.setNotification(notification), which triggers the whole Observer cascade. Made a Singleton for the same reason as the manager classes in Lecture 11 (Zomato) — a second instance would fragment the notification history into two disconnected lists.

Refactor: making it genuinely plug-and-play

First pass required the client to manually build the observable, then manually wire every observer to it (observable.addObserver(logger), observable.addObserver(engine)) — violating the "plug and play, client shouldn't need to know internals" requirement.

The fix: self-registering observers via a default constructor Give Logger and NotificationEngine a default (no-argument) constructor that internally calls NotificationService.getInstance().getObservable() to fetch the shared observable, then immediately calls observable.addObserver(this) to register itself. Creating new Logger() or new NotificationEngine() now auto-wires it into the system — the client never touches an Observable or calls addObserver at all. Client code shrinks to: create observers, add strategies to the engine, build/decorate a notification, call service.sendNotification(notification).

Command Design Pattern

Source: "Command Design Pattern | Real-world use case + Code" · 29 min · Code Army

The problem

A source (invoker) needs to trigger an action on a receiver. Calling the receiver's method directly works, but ties the source to that receiver's specific interface. Turning the request itself into an object — a Command — sitting between them lets the source and receiver stay loosely coupled: the source just tells the command "go do something," without knowing what or on whom.

Smart Home Remote — the naive design and why it breaks OCP

A Remote class directly holding a Light object and hardcoding pressLightButton() { light.on(); } works — until you want that same button to control a Fan tomorrow, or a newly-added Heater. Changing what a button does means reopening and editing Remote's code directly — a direct Open/Closed Principle violation.

The Command Pattern fix

ICommand (abstract, execute()) ← concrete commands (LightCommand, FanCommand), each holding a reference to one specific concrete receiver and calling the right method on it. RemoteControl holds only a reference (or list, for multiple buttons) to ICommand — it calls execute() and has zero knowledge of what actually happens. Reassigning a button to control something else = call setCommand(index, newCommand); RemoteControl's own code is never touched.

Adding Undo (toggling behavior)

ICommand gets a second method, undo(), alongside execute() — each concrete command implements both (LightCommand.execute() turns the light on, undo() turns it off). RemoteControl tracks a parallel boolean array (pressed) per button: on pressButton(index), if not yet pressed → call execute() and flip to pressed; if already pressed → call undo() and flip back — giving each button real on/off toggle behavior.

Doubt 1: why does the CONCRETE command hold the receiver, not the abstract ICommand?

It's about intent. The abstract ICommand only promises "I can execute, and I can undo whatever I executed" — it deliberately doesn't know what. Only a concrete command (LightCommand) knows which specific receiver (Light) and which specific action (on()/off()) that means. So the has-a relationship with a receiver always belongs at the concrete level, never the abstract one.

Doubt 2: why does LightCommand hold a concrete Light, not a generic Appliance interface?

Tempting alternative, rejected You could imagine one Appliance interface (on()/off()) that Light, Fan, AC, etc. all implement, and a single generic Command holding an Appliance reference — avoiding a concrete command class per appliance type.
Why it's rejected: it breaks LSP Not every real appliance genuinely reduces to just on/off. An AC has timers and temperature settings; a fridge or heater has an entirely different feature set. Forcing every appliance into one common on()/off()-shaped interface is exactly the kind of over-generalized abstraction Liskov Substitution warns against (Lecture 5/6) — some "appliance" subclasses would be unable to honestly fulfill that shared contract. The pattern deliberately accepts one concrete command class per receiver type instead, trading a bit of extra coupling for a model that's actually correct.

Standard definition

"Encapsulates a request as an object, thereby letting you parameterize clients with different requests, queue or log requests, and support undoable operations."

Real-world use cases

  • Undo/redo in editors (text editors, Photoshop): every user action becomes a Command object capable of both execute() and undo(); pressing Ctrl+Z typically pops the most recent command off an internally-maintained stack and calls its undo().
  • Keyboard shortcuts: a key is bound to a Command object (e.g. "increase brightness"), not hardcoded directly to a specific device call — so the same key can be dynamically rebound to a different command later, exactly like the remote's buttons.
When to reach for this pattern Any time a feature needs an undo/redo capability, or a button/trigger needs to be dynamically reassignable to a different action without touching the invoker's code — think Command Pattern.

Adapter Design Pattern

Source: "Adapter Design Pattern | Real-world use case + Code" · 21 min · Code Army

Real-world analogy

A travel plug adapter lets an Indian charger plug into a US socket; a USB-C↔USB-B adapter lets an incompatible cable and port connect. Same idea in code: two interfaces/classes that can't talk to each other directly get a third object between them that translates.

The problem

Your existing application code needs a third-party library/vendor class (a payment gateway, a data provider, etc.) whose interface is completely different from what your code expects. Calling the third-party library directly from many places tightly couples your codebase to it — switching vendors later means editing your existing code everywhere it's called. Puzzle-piece analogy: existing code and the third-party library are two puzzle pieces that don't fit together; the Adapter is a third piece shaped to connect both.

Worked example: IReport client expects JSON, library only provides XML

Client expects IReport (abstract, getJsonData(rawData)). A third-party XMLDataProvider class already exists and returns getXMLData(rawData) instead. XMLDataProviderAdapter: is-a IReport (inherits/overrides getJsonData()) and has-a XMLDataProvider reference (the "adaptee"). Inside getJsonData(): call the adaptee's getXMLData(), convert the result from XML to JSON, return it.

Client only ever holds an IReport reference and calls getJsonData() — it never knows an XML-based third-party library is involved at all.

Standard vocabulary and UML

Target = the interface the client expects. Adaptee = the existing, incompatible class being wrapped. Adapter = is-a Target + has-a Adaptee.

Standard definition

"Converts the interface of a class into another interface clients expect. Adapter lets classes work together that couldn't otherwise, because of incompatible interfaces."

Two variants: Object Adapter vs. Class Adapter

Object Adapter (shown above): Adapter is-a Target via inheritance, has-a Adaptee via composition. Class Adapter: Adapter inherits from both Target and Adaptee simultaneously (multiple inheritance) — functionally equivalent, just structured differently.

Why Object Adapter is preferred in practice Same "favor composition over inheritance" reasoning that's recurred throughout the course. Additionally: Java doesn't support multiple inheritance of classes at all, and even in C++ (which does), multiple inheritance is generally avoided in real applications for the same coupling/fragility reasons inheritance is minimized everywhere else in LLD.

Adapter vs. Decorator — don't confuse the shapes

Both patterns superficially look alike (a wrapper class with is-a + has-a toward some interface), but the intent differs completely. Decorator (Lecture 13) wraps an object of the same interface to add extra behavior while preserving that interface exactly. Adapter wraps an object of a different, incompatible interface specifically to translate/convert it into the interface the client actually expects. Decorator enhances; Adapter translates.

Real-world use cases

  • Integrating any third-party vendor/library with an interface that doesn't match what your codebase expects — the canonical use case, shown above.
  • Working with legacy code: an old codebase (e.g. written against a much older language version) has outdated or duplicated method shapes you can't change (it isn't your code to edit) but still must call from a modern application. An adapter sits between the modern app and the legacy methods, exposing a clean modern-shaped interface while internally calling the legacy methods.

Facade Design Pattern

Source: "Facade Design Pattern | Real-world use case + Code" · 18 min · Code Army

The problem

A complex subsystem of many interdependent classes (A depends on B and C, B depends on D, etc.) together perform one overall job. A client that wants that job done shouldn't have to know or call into every class in that web.

The Facade solution

Introduce one new class — the Facade — that internally talks to the whole complex subsystem, and exposes just one (or a few) simple method(s) to the client, e.g. getWorkDone(). The client calls only that; it has no idea which classes were involved or how.

Two benefits (1) Simplifies what the client has to do — one call instead of orchestrating a whole subsystem. (2) Decouples the client from the subsystem entirely — new classes or interactions can be added inside the subsystem later with zero impact on the client, since it never depended on any of that directly.

Worked example: computer boot-up

PowerSupply, CoolingSystem, CPU, Memory, HardDrive, BIOS (needs both CPU and Memory to boot), OperatingSystem — a genuinely complex, interdependent subsystem. ComputerFacade holds references to all of them and exposes one method, startComputer(), which internally calls each subsystem class's method in the right order. The client just calls computerFacade.startComputer().

Standard definition

"Provides a simplified, unified interface to a set of complex subsystems. It hides the complexity of the system and exposes only what is necessary to the user."

Deep dive: Principle of Least Knowledge (Law of Demeter), the full rule set

First introduced briefly in Lecture 7 (Document Editor); here covered as 4 concrete, checkable rules. A class's method may only call methods on:

#Allowed targetExample
1The object itselfA's own method can call A's other methods (m1() calling m2())
2An object passed in as a parameter to the current methodm3(B b) may call methods on b
3An object the current method creates itselfm4() { D* d = new D(); d->m4(); }
4An object the class directly has-a (a component field)If A has-a B, any method of A may call B's methods
What's explicitly forbidden If A has-a B, and B has-a C, A must never reach through B to call a method on C directly (a.b.c.someMethod()-style chaining). If A genuinely needs something from C, that need must be exposed as a method on B itself, with B internally talking to C — the same "talk only to your immediate friends" rule from Lecture 7's Document Editor renderer issue, now given its full four-part form.
Why this rule exists Fewer inter-class dependencies = looser coupling. If every class can freely reach into every other class's components, the whole point of a loosely-coupled design collapses — this is the exact same underlying goal Facade itself serves.

Facade vs. Adapter — distinguish by INTENT, not by UML shape

These two patterns often look structurally similar (a wrapper class sitting between a client and something else) and are commonly confused. Decide by asking what problem is actually being solved:

PatternIntent
FacadeHides/simplifies the complexity of a subsystem for a client.
Adapter (Lecture 16)Makes two completely different, otherwise-incompatible interfaces able to interact.

In a real design, sometimes both readings seem plausible for the same wrapper class — the deciding factor is always which problem you were actually trying to solve when you introduced it.

Real-world use cases

  • Game engines (e.g. Unity): one "Start Game"/"Load Game" call hides a genuinely complex subsystem underneath — loading game assets, memory management (only nearby map regions load, not the whole world at once), physics engine initialization, and more.
  • Payment gateway: a client calls one makePayment() method; internally it hides balance checks, PIN validation, fraud-detection checks, and notification dispatch.

Build Spotify — Music Player App (Strategy + Singleton + Adapter + Factory + Facade)

Source: "Build Spotify, Music Player App | System Design" · 1h15m · Code Army

Requirements

  • Play/pause songs.
  • Create playlists, add songs to a playlist, play an entire playlist — in sequential, random, or custom queue order — extensible to new playback algorithms later.
  • Support multiple, extensible output devices: Bluetooth speaker, wired speaker, headphones, with room for more later.

Five design patterns compose to build this: Strategy (playback order), Singleton (every manager), Adapter (wrapping each third-party output-device API), Factory (creating adapters), Facade (simplifying the whole subsystem for the app's entry point).

Subsystem 1: Output devices (Adapter + Factory)

Each real speaker/headphone brand exposes its own incompatible third-party API (e.g. BluetoothSpeakerAPI.playSoundViaBluetooth(data)). IAudioOutputDevice (abstract, playAudio(song)) ← BluetoothSpeakerAdapter, WiredSpeakerAdapter, HeadphonesAdapter, each wrapping its corresponding third-party API instance and translating the call. AudioEngine holds the current song and calls device.playAudio(song)/handles pause() — it only ever talks to the abstract IAudioOutputDevice, never a concrete adapter. DeviceFactory creates the right adapter (pre-wired to the right third-party API) based on a DeviceType enum; DeviceManager (Singleton) calls the factory, stores the result as currentOutputDevice, and exposes connect(type)/getDevice().

Subsystem 2: Playlists (with an efficiency-driven data structure choice) + playback order (Strategy)

Song (title, artist, path) and Playlist (name, list of songs, addSong()) are plain models. Song can exist independently of any playlist → simple association, not composition.

Why PlaylistManager stores a Map, not a List A naive vector<Playlist> works, but looking up a specific playlist by name would be an O(n) scan across potentially huge numbers of playlists. Storing Map<string, Playlist> (name → playlist) makes lookup O(1). A deliberate data-structure choice driven by the DSA layer underneath the LLD, not just an arbitrary pick.

PlayingStrategy (abstract): setPlaylist(), next(), hasNext(), previous(), hasPrevious() ← SequentialPlayingStrategy (index +1/-1), RandomPlayingStrategy (picks + removes from a remaining-songs pool, pushes onto a history stack so "previous" is possible), CustomQueueStrategy (user enqueues songs directly; falls back to sequential once the queue empties, in this implementation). PlayingStrategyManager (Singleton) holds all three and returns the requested one via a StrategyType enum.

A deliberate ISP trade-off: addToNext() Only CustomQueueStrategy genuinely needs an addToNext(song) method. Declaring it as a pure-abstract method on PlayingStrategy would force Sequential and Random to override something meaningless to them — a straight Interface Segregation violation (Lecture 6). The fix used here: give addToNext() a concrete, empty default body in the abstract class instead of declaring it pure-abstract. Subclasses that don't need it simply never override it (a harmless no-op); CustomQueueStrategy overrides it meaningfully. A small, explicit, named trade-off — not a strict-ISP design, but a deliberate one.

Tying it together: MusicPlayerFacade + the top-level MusicPlayerApp

MusicPlayerFacade (Singleton) holds the AudioEngine, current Playlist, and current PlayingStrategy, exposing: connectDevice(), setStrategy(), loadPlaylist() (fetches the playlist once, hands it to the strategy, so later calls don't need the name repeated), playSong(), pauseSong(), playAllTracks() (loop while strategy.hasNext(), pulling each song and handing it to AudioEngine), playNextTrack(), playPreviousTrack(), enqueueNext().

Honest exception, not an oversight MusicPlayerApp routes almost everything through MusicPlayerFacade, except song/playlist creation (createSongInLibrary, createPlaylist, addSongToPlaylist), which call PlaylistManager directly. Consistent with the course's recurring point: LLD trade-offs are subjective, and a design can name and accept a small, deliberate exception rather than force every single interaction through one facade for its own sake.

Generalizes beyond music The same skeleton (device abstraction via Adapter, playback-order via Strategy, creation via Factory, managers as Singletons, one Facade tying it together) applies to a movie player, video player, or any "play a sequence of items across pluggable output channels" application — not just Spotify.

Composite Design Pattern (File System)

Source: "Composite Design Pattern | Build File System (UML & Code)" · 38 min · Code Army

A shift in kind: "foundational" vs. "specialized" patterns

Strategy, Factory, Singleton, Observer, Decorator, Adapter, Facade, Command (Lectures 8–17) are foundational — generic enough to plug into almost any LLD problem. Starting with Composite, the remaining patterns are more specialized: each solves one recognizable shape of problem. Not less important — just narrower in when they apply. Recognizing the shape is the actual skill.

The shape Composite solves: tree-structured, part-whole data

Directly maps to tree data structures from DSA: some nodes are leaf nodes (no children — an end point), others are non-leaf / composite nodes (can contain further children, recursively). Classic example: a file system — a Folder can contain more folders and files; a File is always a leaf.

Why the naive (non-pattern) approach breaks down

Naive attemptProblem
Separate File and Folder classes, Folder holds two separate lists (a files list + a folders list)Loses the actual insertion order — listing would print all files, then all folders, not the true interleaved order they were added in.
Fix: one common list of pointers to preserve orderNow every operation (ls, openAll) needs an if/else checking the runtime type of each element (File vs. Folder) to decide what to do — and this type-check has to be duplicated in every new command added later (e.g. cd, which is only valid on folders).

The Composite Pattern fix

Give leaf and composite a single common interface, and have client code call that interface uniformly, never checking "is this a leaf or a composite?" Each concrete type (File vs. Folder) implements the shared methods according to its own nature — a leaf's implementation is trivial/terminal, a composite's implementation typically loops its children and recurses.

FileSystemItem (abstract): ls(), openAll(), getSize(), getName(), cd(target), isFolder(). File (leaf): ls()/openAll() just print its own name; getSize() returns its own stored size; cd() returns null (not applicable to a leaf). Folder (composite): has-a list of FileSystemItem ("children"); ls() lists immediate children's names; openAll() recursively calls openAll() on every child; getSize() recursively sums every child's getSize(); cd(target) searches children for a matching folder by name.

Calling root.openAll() on the whole tree: Folder.openAll() prints its own name, then loops its children calling openAll() on each — a File child terminates the recursion by just printing its name; a Folder child recurses further. The caller never branches on type — it's the same recursive-descent idea as traversing any tree in DSA, just expressed as polymorphic dispatch instead of an explicit type switch.

Technical nuance: this is the "safe" variant of Composite, not the "transparent" one

GoF's original Composite pattern actually comes in two flavors. Transparent: child-management methods (add/remove) are declared on the shared Component interface itself, so even leaves technically have them (typically no-op or throwing) — maximum uniformity, at the cost of leaf classes exposing meaningless operations. Safe (what's built here): add() exists only on Folder, not on the shared interface at all — File never has to pretend to support child management. Safe avoids ISP violations (Lecture 6/18) at the cost of the client needing to know it's holding a Folder specifically before calling add() on it.

Standard definition

"Composes objects into tree-like structures representing part-whole hierarchies. It lets clients treat individual objects and compositions of objects uniformly."

Composite vs. Decorator — same is-a + has-a shape, different intent

Both patterns give a class the same "is-a the shared interface, has-a the shared interface" signature. Decorator (Lecture 13) wraps exactly one object to layer extra behavior onto it dynamically. Composite structures a genuine tree (a composite holds many children, of mixed leaf/composite types) so that a whole hierarchy can be treated uniformly by client code. Same shape on a UML diagram, solving entirely different problems — decide by what you're actually modeling, not by the diagram alone.

Real-world use cases

Any nested dropdown/menu system: File → Save As → PDF/Text/… — each expandable menu item is a composite (more items inside), each final selectable action (e.g. "Save As PDF") is a leaf. Same recursive part-whole shape as a file system.
How to spot when to reach for it Any LLD problem where the underlying data is genuinely tree-shaped, with some nodes that terminate (leaves) and some that can recursively contain more nodes (composites) — that shape alone should make Composite Pattern come to mind directly.

Template Method Pattern

Source: Code Army LLD playlist · "Template Method Pattern"

Why this pattern is "specialized," not core

Strategy, Factory, Singleton, Observer, Decorator, Command, Adapter, Facade, Composite are foundational — broadly reusable across almost any LLD problem. Template Method belongs to the same second tier as Composite: it targets one specific shape of problem, but where that shape appears, it solves it completely and exactly — a fixed multi-step process where the order of steps must never change, but the internal implementation of each step legitimately differs per case.

Motivating example: training different ML models

A data scientist trains multiple model types — neural network, decision tree, random forest, SVM, etc. Every single one of them, regardless of algorithm, must follow the exact same pipeline of steps, in the exact same order:

  1. Load data — from a path (CSV, images, database…)
  2. Preprocess data — train/test split, normalization, etc.
  3. Train model
  4. Evaluate results
  5. Save model

The implementation of each step is algorithm-specific (a neural net loads/trains completely differently from a decision tree), but the order can never change — you can never train before preprocessing, or evaluate before training.

The naive risk without this pattern

Without an enforced skeleton, each new model class (e.g. a developer adding NeuralNetworkTrainer) is trusted to manually call load → preprocess → train → evaluate → save in the correct order, by convention alone. Nothing stops a developer from accidentally calling train() before preprocess(). The fix: hand every subclass a pre-built, non-overridable template that calls the steps in the right order for them — the order can no longer be gotten wrong, because it's no longer the subclass's responsibility.

The pattern: one final "template method" that calls abstract steps in order

An abstract base class, e.g. ModelTrainer, declares each pipeline step (load(path), preprocess(), train(), evaluate(), save()) as abstract/virtual — subclasses are free to implement each however they need. But ModelTrainer also defines one additional method — the template method, e.g. trainPipeline() — and this one is fully defined, not abstract, in the base class:

trainPipeline() body: call load(path), then preprocess(), then train(), then evaluate(), then save() — in that fixed sequence. This method is marked final (Java) / non-virtual with no override intended (C++) so no subclass can ever override the order itself — subclasses may only override the individual steps, each of which the client never calls directly.

Any subclass (NeuralNetworkModel, DecisionTreeModel, future SVMModel…) implements the five steps in whatever order it defines them in the source file — that authoring order is irrelevant, because only trainPipeline() decides call order at runtime. A Client class holds a reference typed as the abstract ModelTrainer (it doesn't know or care which concrete subclass it holds) and calls only trainPipeline(). The client is fully decoupled from which concrete model is plugged in — the execution order is guaranteed identical regardless.

Steps common to every subclass (e.g. "always load from a file," "always save to the same format") can instead be given a real, shared implementation directly in the base class — subclasses then only override the steps that genuinely vary (commonly just train() and evaluate()), while still being free to override a "common" step too if a specific case needs to (standard OOP overriding/shadowing: the most-derived override always wins).

Standard UML diagram

Sequence at runtime Client.run() calls trainer.templateMethod() → which internally calls step1(), then step2(), then step3() — in that fixed order, regardless of whether trainer actually points to a ConcreteClassA or ConcreteClassB instance. The client only ever sees one call; the guaranteed order lives entirely inside the base class.

Applied back to the ML example

ModelTrainer (abstract) defines trainPipeline() as the template method, and gives real shared implementations for load(), preprocess(), and save() directly (common defaults), leaving train() and evaluate() abstract. NeuralNetworkTrainer overrides train(), evaluate(), and (for illustration) also overrides save() to prove the standard OOP rule that a subclass override always shadows the parent's default. DecisionTreeTrainer overrides only train() and evaluate(), keeping the parent's default load()/preprocess()/save(). Both are driven identically: construct the trainer, call trainPipeline() — the console output always shows load → preprocess → train → evaluate → save in that order for both models, even though the underlying training/evaluation logic differs completely.

Standard definition

"Defines the skeleton of an algorithm in a method, deferring some steps to subclasses. Template Method lets subclasses redefine certain steps of an algorithm without changing the algorithm's structure." The algorithm's structure (its step order) never changes — only how each step is carried out changes, per subclass.

Real-world use cases

Money-transfer / payment processing: any transaction (UPI, credit card, debit card) follows the fixed pipeline validate funds → debit source account → credit destination account → validate the transaction completed → close/finalize the transaction. That order can never be reordered (you cannot credit before debiting, or finalize before validating), but exactly how validation or debiting works legitimately differs between UPI and a card network. Any time an LLD problem has a fixed, order-sensitive multi-step process where individual step implementations vary by case, that's the direct signal to reach for Template Method.

Proxy Design Pattern

Source: Code Army LLD playlist · "Proxy Design Pattern"

Core idea: a stand-in object sits between client and resource

A user wants to send a request to a resource and get a reply. Instead of letting the user talk to the resource directly, a new object — the proxy — is placed in between. The user sends the request to the proxy; the proxy (optionally validating/transforming it) forwards it to the real resource; the resource replies to the proxy; the proxy relays that reply back to the user. The user never knows — and never needs to know — whether it's talking to the proxy or the real resource directly, because the proxy exposes the exact same interface as the resource.

Why introduce an extra object instead of just editing the resource class? Three recurring reasons, each becoming one "flavor" of proxy: (1) the resource is expensive to construct/load and shouldn't be created until actually needed — Virtual Proxy; (2) the resource is sensitive/restricted and only authorized users should reach it — Protection Proxy; (3) the resource lives on a different server, reachable only over a network call, and the client shouldn't have to know that — Remote Proxy. Sometimes another reason applies too: you may not even have write-access to the resource's class (a third-party library) — a proxy lets you add behavior around it without touching its source.

All three types share one UML shape

Every variant below is built from the exact same relationship pair: the proxy is-a shared interface/abstract-class (so it's substitutable anywhere the real resource is expected), and the proxy has-a reference to the real resource (so it can forward calls to it once needed). Only the intent behind what the proxy does before forwarding differs between the three types.

Type 1 — Virtual Proxy (lazy loading an expensive resource)

Example: an ImageDisplay class whose constructor is expensive — it loads the image from disk, runs compression, applies filters, all before the object is even displayed. If a client creates an ImageDisplay object but never calls display(), that expensive work was wasted memory and time for nothing.

Fix: extract a shared interface IDisplay (with a display() method) that both ImageDisplay and a new ImageProxy implement. ImageProxy holds a reference to ImageDisplay, initialized to null in its own (cheap) constructor — the expensive object is not created yet. Only inside ImageProxy.display(), on the first call, does it check if its reference is null and, if so, construct the real ImageDisplay right there, then delegate the call to it. Every client is handed an ImageProxy (typed as IDisplay), never the real class directly.

Lazy loading = deliberate trade-off The first display() call is now slightly slower (it pays the construction cost at that moment), but memory/resources for objects that are never actually used are never wasted. You accept a small latency cost on first use to avoid a much larger, unconditional resource cost.

Type 2 — Protection Proxy (authorization gate)

Example: an IDocumentReader interface with unlockPdf(file, password), implemented by RealDocumentReader. Unlocking a PDF is a premium-only feature. A DocumentProxy is-a IDocumentReader and has-a RealDocumentReader reference, but also has-a reference to the current User (with an isPremium flag). Inside DocumentProxy.unlockPdf(), it first checks user.isPremium; only if true does it delegate to realDocumentReader.unlockPdf() — otherwise it throws/returns an "only for premium users" response, without ever touching the real object.

Structurally identical to Virtual Proxy (same is-a/has-a pair) — the only difference is intent: Virtual Proxy protects an expensive resource from unnecessary construction; Protection Proxy protects a restricted resource from unauthorized access.

Type 3 — Remote Proxy (hiding a network call)

Example: a real DataService (behind an IDataService interface) that actually lives on a separate server and must be reached over the network. A DataServiceProxy is-a IDataService and has-a DataService reference. Inside fetchData(), it checks if a connection to the remote DataService already exists; if not, it establishes the connection first (passing IP/credentials as needed), then calls the real fetchData() over that connection and relays the result back. The client only ever sees fetchData() on a local-looking object — it never has to know a network hop happened underneath.

Whether the connection is established eagerly (in the proxy's constructor) or lazily (on first method call, exactly like Virtual Proxy) is an implementation choice — lazy connection-establishment makes Remote Proxy a strict superset of the Virtual Proxy idea applied specifically to network resources.

Standard UML diagram (identical shape for all three types)

What varies between the three types The shape above never changes. Only what ProxySubject.operation() does before/instead of delegating to realSubject.operation() changes: lazily construct it first (Virtual), check authorization first (Protection), or establish a remote connection first (Remote) — and a real system can freely combine more than one of these in a single proxy (e.g. authenticate and make a remote call).

Standard definition

"The Proxy pattern provides a surrogate or placeholder for another object to control access to it." The client always talks to the surrogate; the surrogate decides what happens before (or instead of) forwarding to the real object.

Real-world use cases

Login/premium-gated features (Protection Proxy) — any feature reachable only if a user is logged in or on a paid tier. Microservice architectures (Remote Proxy) — e.g. a CartService on one server never calls a UserService on another server directly; it calls a local UserServiceProxy, which itself makes the actual network call to the real UserService — this is effectively what frameworks like Spring Boot/Django generate under the hood for inter-service calls.

Chain of Responsibility Pattern (ATM Cash Dispenser)

Source: Code Army LLD playlist · "Chain of Responsibility Design Pattern"

Core idea: a request travels down a chain of handler objects

A client sends a request not to one object, but to a chain of objects: R1 holds a reference to R2, which holds a reference to R3, and so on. The request goes to R1 first; R1 checks whether it can fulfill the request itself. If yes, it responds directly. If not, it forwards the request to R2, which does the same check, forwarding to R3 if needed — and so on down the chain, with results eventually flowing back up to the original caller.

Superficially resembles a linked list — but isn't one Just like Composite Pattern (Lecture 19) evokes a tree, Chain of Responsibility evokes a linked list — but the resemblance is only structural. A linked-list node stores data, and every node is an instance of the same class. A Chain-of-Responsibility handler's job is to process a request (or delegate it), and each handler in the chain is typically a different concrete class implementing a shared interface — e.g. a ₹1000-note handler and a ₹500-note handler are different classes, not different instances of one node class. Same "chain of linked objects" shape, entirely different intent and structure underneath.

Motivating example: ATM cash dispensing

An ATM has separate handlers for each note denomination — a ₹1000 handler, ₹500 handler, ₹100 handler, etc. — each tracking how many notes of its own denomination it currently holds. Money isn't stored as one lump sum; it's compartmentalized by denomination, and a withdrawal should dispense the largest denominations first.

When a client requests, say, ₹6000: the request reaches the ₹1000 handler first. It checks how many ₹1000 notes it can supply toward this request. If it has 5 notes (₹5000) and the request is ₹6000, it dispenses all 5 notes and forwards the remaining ₹1000 to the next handler (₹500). That handler dispenses 2×₹500 notes, fully satisfying the remainder, and returns success back up the chain. The client ends up with ₹6000 total, without ever knowing how many handlers were involved.

What if a requested amount can't be exactly fulfilled (e.g. ₹150 with only ₹1000/₹500/₹100 handlers)? Two valid design choices, decided by the use case: either dispense the closest fulfillable amount and report the shortfall, or fail the entire transaction outright rather than partially fulfill it. Neither is "more correct" — it depends on what the system is for.

Why the "next handler" link belongs on the shared interface, not hardcoded per class

A naive design might hardcode, inside the ₹1000 handler class itself, a reference of concrete type "₹500 handler." This tightly couples every handler class to its specific successor — if a denomination is discontinued or reordered (e.g. ₹500 notes get demonetized and ₹1000 must now point directly to ₹100), the handler classes themselves need code changes.

Fix: put the "next" reference on the shared abstract MoneyHandler class itself, typed as a reference to that same abstract class (not to any concrete subclass) — call it nextHandler, with a setNextHandler(handler) method to wire it. Concrete subclasses (₹1000, ₹500, ₹100…) know nothing about which concrete class comes next — the chain's actual order is assembled entirely from client code at setup time, so it can be reconfigured (add/remove/reorder denominations) without touching any handler class. This is a direct application of the Open/Closed Principle (Lecture 5) — adding a new ₹50 handler later means writing one new subclass and rewiring pointers, never editing an existing handler.

Standard UML diagram

Reading the self-reference Handler having a field of its own type is exactly what makes this a chain: at runtime, nextHandler is populated with a concrete instance (a ConcreteHandlerB, say), but the field's declared type stays the shared abstract Handler — so a handler never needs to know the concrete type of its successor, only that it also exposes handleRequest().

Applied to cash dispensing

Each concrete handler (ThousandHandler, FiveHundredHandler, etc.) stores its own numberOfNotes count. Its handleRequest(amount): compute notesNeeded = amount / denomination; if notesNeeded > numberOfNotes, dispense all available notes and set the remaining amount to amount - (numberOfNotes × denomination); otherwise dispense exactly notesNeeded notes and remaining amount becomes 0. If remaining amount > 0 and nextHandler != null, forward the remainder via nextHandler.handleRequest(remaining); if remaining > 0 and there's no next handler (the smallest denomination configured), throw/report insufficient funds. The client only ever calls handleRequest() on the first handler in the chain — every subsequent hop happens invisibly inside the chain itself.

Why not just one class with if/else branches per denomination?

A single class handling all denominations via cascading if/else if blocks would work functionally, but violates two SOLID principles at once: Open/Closed (Lecture 5) — adding a new denomination means editing that one shared method's branching logic directly, risking regressions in existing branches; and Single Responsibility (Lecture 5) — if the physical validation rules for one denomination change (e.g. new ₹500 notes have a different security pattern to verify), a monolithic handler forces you to touch code shared by every other denomination too. Splitting into one class per denomination means a change to how ₹100 notes are validated touches only HundredHandler — nothing else in the chain is at risk.

Standard definition

"Allows an object to pass a request along a chain of potential handlers until one of them handles it." Each handler independently decides: handle it now, or pass it to the next handler in the chain.

Real-world use cases

Logger systems: INFO, DEBUG, and ERROR log handlers form a chain ordered by severity level — a log request is checked against each handler's level in sequence. Leave-request approval systems (a common interview question, given here as homework): an employee's leave request is approved by a Team Lead if ≤2 days, else escalated to a Manager if ≤5 days, else escalated further to a Director, else rejected — each approver is a handler that either resolves the request or forwards it up the hierarchy. Any problem shaped like "try handler A, if it can't fully resolve this, try handler B, then C…" is a direct signal for Chain of Responsibility.

Build a Payment Gateway System

Source: Code Army LLD playlist · "Payment Gateway System LLD"

Scope: a plug-and-play gateway, not a bank's internals

Two very different systems both get called "payment architecture": (1) a payment gateway that any app (Amazon, Zomato, Uber…) integrates so a user can pay — this is what this lecture builds; (2) the internal architecture of a bank/wallet itself (how Paytm or GPay actually moves money between accounts) — explicitly out of scope, treated as an external system this design merely calls into.

Requirements

  • Support multiple providers (Paytm, Razorpay, …) and let new gateways be added easily — a direct Open/Closed Principle (Lecture 5) requirement.
  • Enforce one standard payment flow with required validations: every payment must go validate → initiate → confirm, in that exact order, regardless of which provider handles it — this is a direct signal for Template Method Pattern (Lecture 20).
  • Error handling and a retry mechanism: a failed payment (server issue, insufficient funds, network blip) should be retried a bounded number of times before being reported as failed.

What "gateway" means at the LLD level

In HLD, "API Gateway" means something different. At the LLD level, a gateway is simply the layer inside your own application through which every outbound call (HTTP call to some external server) passes — the rest of the application never talks to the outside world directly, only to the gateway. So "Paytm gateway" and "Razorpay gateway" are the internal classes in this application responsible for making outbound calls to Paytm's/Razorpay's actual banking systems — not the external banking systems themselves.

Bottom-up UML construction

PaymentRequest — a plain model/DTO class: sender, receiver, amount, currency (currency is included deliberately, to future-proof for international gateways like PayPal handling multiple currencies).

IBankingSystem (abstract/interface) — one method, processPayment(amount): bool. Concrete PaytmBankingSystem and RazorpayBankingSystem implement it. This hierarchy is treated as a black box (an already-existing third-party system) — its internals (actual money movement) are a separate LLD problem entirely.

Why the gateway can't hold a direct field reference to IBankingSystem IBankingSystem's concrete implementations don't actually live in this application's codebase — they live on a remote server, reached only over the network. A class can't declare a field of a type that isn't compiled into its own application (that would be a compiler error). The conceptual fix: assume a Remote Proxy (Lecture 21) sits transparently in between — the gateway holds what looks like a normal reference, but it's actually a local stand-in that performs the real HTTP call underneath. This proxy layer is assumed, not drawn, to keep the diagram focused.

PaymentGateway (abstract, the Template Method class) — declares the template method processPayment(request), fully defined, calling three abstract steps in fixed order: validate(request) → initiate(request) → confirm(request). Concrete PaytmGateway and RazorpayGateway each override all three steps in their own way, and each holds a pure composition (filled-diamond) reference to its own banking-system proxy — composition, not plain association, because a gateway's banking-system link cannot outlive the gateway itself; the two are that tightly bound.

Standard UML diagram

Why retries can't live on the client, and can't live inside PaymentGateway either

Putting retry logic in the client (whatever calls the gateway) couples the client to provider-specific retry counts (Paytm might need 3 retries, Razorpay 5) — any retry-policy change forces a client-code change, and the client shouldn't need to know this detail exists. Putting it inside PaymentGateway/its subclasses is also wrong: retrying is a distinct responsibility from actually performing a payment (Single Responsibility Principle, Lecture 5) — the concrete gateways' only job should be talking to their banking system correctly, not managing failure-recovery policy.

The fix: a real Proxy Design Pattern application (Protection Proxy, not Remote)

A PaymentGatewayProxy is introduced: it is-a PaymentGateway (so it overrides processPayment) and has-a reference to the real gateway (PaytmGateway or RazorpayGateway) it wraps. Its overridden processPayment() wraps the real gateway's processPayment() in a retry loop (with its own configurable retry count), and its validate/initiate/confirm simply delegate straight through to the real gateway, unchanged.

Why this is Protection Proxy, not Virtual or Remote Of the three Proxy variants (Lecture 21): not Virtual (nothing here is being lazily constructed to save an expensive allocation) and not the visible Remote proxy (that's the separately-assumed layer talking to the actual external banking system). This proxy adds a guard/policy (the retry mechanism) in front of a call before letting it reach the real object — structurally identical to how a Protection Proxy gates access, just gating "how many attempts" instead of "is this user authorized."

Assembling the full call chain: Factory, Service, Controller

GatewayType (enum): PAYTM, RAZORPAY. GatewayFactory (Singleton): createGateway(type) builds the real concrete gateway (PaytmGateway or RazorpayGateway) but always returns it wrapped inside a PaymentGatewayProxy — callers can never reach a real gateway directly, only through the proxy, so retries and any future cross-cutting policy are guaranteed to apply. PaymentService (Singleton): holds the current PaymentGateway (always the proxy, though typed abstractly), exposes setGateway(gateway) and processPayment(request) which simply delegates to the held gateway. PaymentController (Singleton): the single entry point any external application integrates against — handlePayment(type, request) asks the factory for a gateway of the requested type, hands it to the service via setGateway(), then calls the service's processPayment() and returns the boolean result up to the caller.
Why split Controller and Service instead of one class? Standard layering discipline: the controller's only job is being the stable entry point and redirecting; the service's job is owning the actual business logic (which gateway, which request, wiring it all together). Any plug-and-play application (Amazon, Zomato, …) integrating this system only ever needs to know about the controller.

End-to-end call flow

One request, traced top to bottom Client → PaymentController.handlePayment(PAYTM, request) → controller asks GatewayFactory.getInstance().createGateway(PAYTM) → factory builds a PaytmGateway, wraps it in a PaymentGatewayProxy, returns the proxy → controller calls PaymentService.getInstance().setGateway(proxy), then .processPayment(request) → service calls proxy.processPayment(request) → proxy retry-loops calling the real PaytmGateway.processPayment(request) → which runs validate → initiate → confirm in fixed order (Template Method) → initiate delegates to PaytmBankingSystem.processPayment(amount) (the assumed remote-proxy hop) → result (true/false) flows back up through every layer to the original client.

Real-world simulation detail

The sample code simulates realistic failure rates (e.g. Paytm succeeding ~20% of the time, Razorpay ~90%) using a random check inside each banking system's processPayment(), purely to demonstrate the retry proxy actually kicking in across multiple attempts before either succeeding or exhausting its retry budget and throwing.

Homework / suggested extensions

(1) Make the retry mechanism itself pluggable/scalable — support both linear retry (what was built: fixed attempts, one after another) and exponential backoff retry (increasing delay between attempts) as swappable strategies. (2) Extend the flow to support recurring/subscription payments (e.g. a monthly YouTube Premium or Netflix charge), not just one-off sender-to-receiver transfers — and consider how Template Method could structure a recurring flow alongside the existing one-off flow.

Build a Discount Coupon Engine

Source: Code Army LLD playlist · "Design a Discount Coupon Application"

Scope: a plug-and-play coupon engine for any checkout

Almost every checkout (Zepto, Blinkit, Amazon, Swiggy, Zomato) lets you apply coupons before paying — some from a bank ("10% off with ABC card"), some from the platform itself ("60% off up to ₹120"). This lecture builds a generic coupon/discount engine that could be dropped into any of those apps, like the Notification Engine (Lecture 14) and Payment Gateway (Lecture 23). The lecturer mentions this exact question was asked to a friend in a real LLD interview.

Functional requirements

  • Add new coupons at runtime — the set of coupons must be extensible (Open/Closed, Lecture 5).
  • Support both cart-level discounts (apply to the whole cart total) and product-level discounts (e.g. 5% off only on Electronics).
  • Coupon types: Seasonal offer, Loyalty discount, Bank discount (plus a Bulk-purchase coupon added later) — and more must be addable.
  • Discount strategies: Flat (₹20 off), Percentage (20% off), Percentage with cap (60% off up to ₹120 — on a ₹1,000 or ₹2,000 order you still get only ₹120 off). New strategies must be addable too.
  • Coupons can or cannot be stacked on top of other coupons (e.g. platform coupon + bank coupon together, vs. "this bank offer can't be combined with anything else").
  • Thread safety: millions of concurrent users; if only 4 units of a coupon exist, only the first 4 users should get it — needs a locking mechanism (std::mutex in C++; synchronized blocks or CAS/AtomicInteger in Java).

Non-functional requirements (scalable, plug-and-play, extensible) are assumed as always.

Happy flow (deliberately tiny)

User browses products → adds them to a cart → (this system starts here) applies one or more coupons, some stackable and some standalone → a final payable total is produced. Browsing and paying belong to the host app, so there's no User class, and Product is kept generic. The design imagines an inventory app like Zepto (products with categories). To plug it into the Zomato clone from Lecture 11, swap Product for its menu/food item — a suggested exercise.

Bottom-up UML: Product → CartItem → Cart

Product — model class: name, category, price.

CartItem — a product plus its quantity (three earphones show as one line "Earphones × 3", not three rows). getItemTotal() = product.price × quantity.

Cart — items: list<CartItem>, isLoyaltyMember, paymentBank, originalTotal (sum of items, never changes) and currentTotal (called "final total" in the UML — what's left after discounts, i.e. what the user pays). Methods: addProduct(product, qty = 1) and applyDiscount(amount), plus getters/setters.

Why addProduct(product, qty) and not addProduct(CartItem)? CartItem is the Cart's internal bookkeeping — nobody outside should even know it exists; callers only know about Product. So addProduct builds the CartItem itself, pushes it into items, and adds its total to both originalTotal and currentTotal. That's also why Cart–CartItem is drawn as composition (filled diamond): a CartItem can't exist without its Cart. CartItem–Product is aggregation (hollow diamond): a Product exists fine without any cart.
Stand-ins for the host app's User isLoyaltyMember (think Swiggy One / Zomato Gold, e.g. free delivery) and paymentBank really belong on a User/payment context. They sit on Cart only because this design has no User class; in a real integration the cart would fetch them from the user.

Cart.applyDiscount(d): currentTotal -= d, clamped so it never goes below 0.

"But the if/else in the manager breaks Open/Closed!" Yes — a new strategy means a new branch here. Objects have to be created somewhere, and that creation needs a branch. It also calls Builder "structural" — Builder is actually a creational pattern.) Since getStrategy only creates objects, it's really a Factory; "manager" vs "factory" is just naming.

Stacking coupons: Decorator vs Chain of Responsibility

"Some coupons stack, some don't" fits two patterns. Decorator (Lecture 13): wrap the price in coupon after coupon. Chain of Responsibility (Lecture 22): link coupons in a chain; each applies its discount if it can, then passes the cart on — and a non-combinable coupon simply ends the chain. Both work; the lecture picks CoR. In an interview, naming both options and justifying your pick scores points.

The Coupon base class — CoR + Template Method (Lecture 20)

  • next: Coupon (self-reference, like a linked list's next) + setNext(c) / getNext().
  • isApplicable(cart)* — abstract; each coupon decides (right bank? right category? above threshold?).
  • getDiscount(cart)* — abstract; each coupon picks the base amount and asks its strategy to calculate().
  • isCombinable() — defaults to true; a coupon overrides it to return false if nothing may follow it.
  • name() — for console output only.
  • applyDiscount(cart) — the concrete template method that fixes the order of those steps.
applyDiscount(cart), as the code does it 1. If isApplicable(cart): d = getDiscount(cart); cart.applyDiscount(d); log it. Then if !isCombinable() → stop the chain (return).
2. If next != null → next.applyDiscount(cart) (recursive hop down the chain).
An inapplicable coupon is simply skipped; the cart still moves on to the next coupon.
Clarifying the UML walkthrough During the UML walkthrough, the lecture describes a while (current != null) loop that checks the next coupon's isCombinable. The code is simpler, and it's what counts: each coupon checks its own isCombinable() after applying, and recursion (not a loop) moves to next. The loop explanation is just linked-list traversal (temp = temp.next); the recursive version walks the chain the same way.

Gaps worth raising in an interview

  • Order-dependence. The same coupons in a different order give a different total (percent-before-flat ≠ flat-before-percent), and the bank coupon's minSpend check runs on the already-discounted total. Real systems use explicit priorities or a rule such as "all percentage coupons compute on the original total."
  • isCombinable = false only blocks coupons after it. Coupons earlier in the chain have already applied, so "this bank offer can't be combined with anything" isn't truly enforced. Fixes: evaluate exclusive coupons first, or compute "best exclusive coupon" vs "best stack" and pick the better one.
  • The "only 4 users" requirement isn't implemented. The mutex only protects the chain structure. Limited-quantity coupons need a per-coupon remainingUses counter decremented atomically (std::atomic/CAS, or a lock around check-and-decrement), ideally reserved at checkout and released if payment fails. Across multiple servers this has to live in shared storage (a DB row lock or a Redis DECR), not an in-process mutex.
  • One global mutex around applyAll makes every user's checkout wait for everyone else's. Carts are per-user, so applying coupons only needs a consistent read of the chain; a read-write lock or an immutable chain snapshot scales far better.
  • Money as double causes rounding errors (₹3,504.75…); production code uses integer paise or a decimal type.
  • Raw pointers from getStrategy and the coupon chain are never freed in the demo; unique_ptr ownership would match the composition arrows.
  • Missing but realistic: coupon codes the user picks (instead of auto-applying everything), expiry dates, per-user usage limits, and removing a coupon.

Interview takeaway

You're rarely asked for full working code in a one-hour LLD round. What's expected is a clean UML, clear relationships (composition vs aggregation vs association), justified pattern choices, and one or two classes coded out. Get the UML right and the code follows.
Lecture 25

Bridge Design Pattern

Source: Code Army LLD playlist · "Bridge Design Pattern"

The problem: class explosion from two independent dimensions

Build cars. Every car can drive(). Cars come in several types (Sedan, Hatchback, SUV) and several engines (Petrol, Diesel, Electric), and any type can take any engine. Doing this with inheritance alone means one subclass per pair: SedanPetrol, SedanDiesel, SedanElectric, HatchbackPetrol… → m × n classes (3 × 3 = 9). Add a CNG engine and you need 3 more; add a new car type and you need 4 more.

Correction: it grows multiplicatively, not "exponentially" The lecture says the class count grows "exponentially." With two dimensions it's m × n: adding one engine adds m classes, a linear step. It gets truly out of hand when you add a third dimension (e.g. transmission: m × n × k), and each new dimension multiplies the count again.

This is called class explosion: many classes to implement one feature, where every small change (a new engine) creates even more classes. The system gets hard to understand, the same code gets duplicated across siblings (breaking DRY), and SOLID principles start to crack.

The idea: split one concept into two hierarchies and link them

Bridge says: take the concept and break it into two parts.

  • High-level part = the Abstraction — how the thing looks/behaves from the outside. For cars: the car type (Sedan, SUV).
  • Low-level part = the Implementation — how it actually works inside. For cars: the engine (Petrol, Diesel, Electric).

Each part gets its own inheritance hierarchy, and the high-level side has-a reference to the low-level side. That has-a link is the "bridge" between the two hierarchies.

Don't confuse Bridge's "abstraction/implementation" with the OOP meaning In OOP, "abstraction" usually means an abstract class and "implementation" a concrete class. Here both hierarchies have an abstract base (Car and Engine), yet Car is called the abstraction and Engine the implementation. In Bridge, the words mean outside view vs inside mechanism. The lecturer prefers "high-level / low-level layer" to avoid the clash; use "abstraction / implementation" in interviews, since that's the standard vocabulary.

Car example UML

A client calls car.drive(); inside, drive() calls engine.start() and then does its own car-type-specific work. Car doesn't know which engine it holds, and Engine has no reference back to the car, so it doesn't know whether it sits in a Sedan or an SUV. Pass any engine to any car type → every combination is available with only m + n classes (2 car types + 3 engines = 5 classes instead of 6; 3 + 3 = 6 instead of 9). A new engine or a new car type is one new class, with no changes on the other side.

Standard UML

ConcreteAbstraction.execute() calls imp.implement(). The lecture calls the concrete high-level classes "Concrete Abstraction"; in the GoF book they're named Refined Abstraction — worth knowing if an interviewer uses that term.

Standard definition

"Bridge decouples an abstraction from its implementation so that the two can vary independently." Abstraction = the high-level layer (Car); implementation = the low-level layer (Engine).

Code walkthrough (C++)

Implementation hierarchy: abstract Engine with pure virtual start(). PetrolEngine prints "starting with ignition", DieselEngine its own message, ElectricEngine "powering up silently." (Console output stands in for a real start-up procedure.)
Abstraction hierarchy: abstract Car holding an Engine* (passed in through the constructor) and pure virtual drive(). Sedan::drive() calls engine->start(), then prints "driving a sedan on the highway"; SUV::drive() does the same with its own message.
main: create Petrol, Diesel and Electric engines; build Sedan(petrol), SUV(electric), SUV(diesel); call drive() on each. Output pairs every engine's start message with its car's drive message: Petrol+Sedan, Electric+SUV, Diesel+SUV.

Bridge vs Strategy — the UML is almost identical, so what's different?

Redraw the car example as Strategy (Lecture 8): Engine is a strategy, Petrol/Diesel are algorithms, and Car is the client that has-a strategy. Lecture 8's robot example (Companion/Worker robots with NoFly/FlyWithWings/FlyWithJet behaviours) had exactly this shape. The structure is the same; the difference is intent.

Why the car example is Bridge, not Strategy Once you've built a petrol SUV, you don't pull its engine out and drop in a diesel one — a lot of the car is petrol-specific. The point was to be able to build any type/engine pair and to add new types and engines freely, not to switch engines on a live object. That's Bridge's intent. Patterns overlap because they share one goal — turning tightly coupled code into loosely coupled code — so when two look the same, ask what each is for. A nuance the lecture skips Bridge doesn't forbid changing the implementor at runtime (GoF notes that's possible), so "fixed vs swappable" is a tendency, not a hard rule. Another useful signal: in a textbook Bridge, the implementor offers low-level primitives and the abstraction combines several of them into higher-level operations (e.g. Window.drawBorder() built from imp.drawLine() calls). In the car example, drive() just calls start(), which is exactly why it looks so much like Strategy.

Real-world use cases

Remote controls & TVs (hardware): the remote is the abstraction (high-level), the TV/device is the implementation (low-level). New remotes (standard, touch-screen, one with a Netflix button) and new TVs (LCD, LED, OLED) of the same brand can be added independently, and any remote can pair with any TV — e.g. the premium touch remote with the OLED, the standard remote with the LCD.
GUI widgets across operating systems (software): widgets (TextBox, Dropdown, RadioButton) are the abstraction — what the control is and how you use it; the OS layer (Windows, macOS, Linux) is the implementation — how it's actually drawn (fonts, native look). Add a widget or an OS without touching the other side, and any widget renders on any OS. This is the classic GoF Bridge example.
Other common fits: a notification type (alert, reminder) × a delivery channel (email, SMS, push), or a shape × a rendering backend.

When to reach for Bridge

If you catch yourself naming classes as <Dimension1><Dimension2> (SedanPetrol, WindowsTextBox), there are two independent axes of variation. Pull one axis out into its own hierarchy, have the other hold a reference to it, and m × n becomes m + n.
Lecture 26

Build Zepto (Quick Commerce / Inventory Management)

Source: Code Army LLD playlist · "Design Zepto / Blinkit — 10-minute delivery LLD"

What makes 10-minute delivery different

Zomato-style food delivery (Lecture 11) has one restaurant per order. Quick commerce (Zepto, Blinkit) keeps stock in many small dark stores — warehouses close to users that only fulfil online orders. Your nearest dark store may not have everything in your cart, so the order is split: one delivery partner picks up part of it from store A, another picks up the rest from store B (that's why the app sometimes shows "arriving in 10 min" and "arriving in 13 min" for one order). Managing all that stock is inventory management, so this design doubles as the answer to any "design an inventory management system" interview question.

Functional requirements

  • Manage inventory: add/remove items (products across categories — food, electronics, daily essentials).
  • Replenishment strategies: refill when stock falls below a threshold, or on a weekly schedule (a truck comes every week) — and new strategies must be addable.
  • Multiple inventory store types (e.g. a DB-backed store), extensible later.
  • A user sees items from all dark stores near them (within 5 km).
  • If one dark store can't fulfil the order, split it across several dark stores, each part delivered by its own delivery partner.

Payments are deliberately left out — the Payment Gateway from Lecture 23 could be plugged in, but it would scatter the requirements.

Happy flow: user opens app → sees nearby items → adds some to cart → places order → order assigned to one or more delivery partners → delivered to the user's location.

Bottom-up UML

Product (model / POJO) — sku, name, price. SKU (Stock Keeping Unit) is the inventory world's unique product ID — the code printed on every item in a store like Vishal Mega Mart.

ProductFactory — createProduct(sku), so code doesn't sprinkle new Product(...) everywhere. In the demo it hardcodes a small catalog (1001 Apple ₹20, 1002 Banana ₹10, 1003 Chocolate ₹50, 2001 T-shirt ₹500, 2002 Jeans ₹1000; anything else becomes a ₹100 "Item"). In reality it would load the product from the database.

InventoryStore (abstract) — only declares what can be done: addProduct(product, qty), removeProduct(sku, qty), checkStock(sku), listAvailableProducts(). How the data is stored is left to subclasses.

DbInventoryStore — the concrete store. Instead of a vector<Product> (every stock check would scan up to thousands of items, and stock changes constantly with orders and replenishment), it keeps two maps keyed by SKU:

  • stock: map<sku, quantity> — how many units are available.
  • products: map<sku, Product> — the Product object itself, so the factory isn't called again.
DbInventoryStore operations addProduct: if the SKU is new, store the Product in products; then add qty to stock[sku].
removeProduct: remaining = stock[sku] - qty; if remaining > 0 update it, otherwise erase the SKU from stock.
checkStock: stock[sku], or 0 if absent.
listAvailableProducts: every SKU with quantity > 0 that also exists in products.
Correction: std::map isn't O(1) The lecture says maps give O(1) lookup. std::map is a balanced tree, so lookups are O(log n); std::unordered_map (Java's HashMap) gives O(1) on average. Either is far better than scanning a list, which is the real point.
"It's called DbInventoryStore but uses maps?" LLD rounds focus on class structure, not SQL. To actually persist, reuse the idea from the SOLID lectures (Lectures 5–6): an abstract Persistence with save(), subclassed by SqlPersistence/MongoPersistence. DbInventoryStore holds a Persistence reference and calls persistence.save() after updating its maps.

InventoryManager — holds an InventoryStore; methods addStock(sku, qty), removeStock(sku, qty), checkStock(sku), getAvailableProducts(). The dark store talks to this manager, never to the store directly.

Isn't the manager just repeating the store's methods (DRY)? No. The manager delegates: it knows what needs doing, the store knows how. It also does work that isn't the store's job — addStock(sku, qty) first asks ProductFactory for the Product, then calls store.addProduct(product, qty). Validations before touching stock also belong here. The store stays a "dumb" data holder, and the dark store stays loosely coupled to how inventory is managed.
Why InventoryManager is NOT a Singleton Managers have usually been Singletons in this course, but here each dark store needs its own inventory manager — 50 dark stores means 50 managers. A Singleton would make every store share one inventory. (One shared manager could be a valid design too, but then every call must carry which store it's for.) Always be able to say why something is or isn't a Singleton.

ReplenishStrategy (Strategy Pattern, Lecture 8) — replenish(manager, itemsToReplenish: map<sku, qty>).

  • ThresholdReplenishStrategy(threshold) — for each SKU, manager.checkStock(sku); if below the threshold, manager.addStock(sku, qtyToAdd).
  • WeeklyReplenishStrategy — in the demo it just prints; a real one would run on a weekly schedule and top everything up.

DarkStore — name, coordinates x, y, an InventoryManager and a ReplenishStrategy.

  • distanceTo(ux, uy) — distance formula from the store's coordinates to the user's.
  • runReplenishment(items) — strategy.replenish(inventoryManager, items); the store hands over its own manager.
  • Delegate methods (addStock, removeStock, checkStock, getAllProducts) that just forward to its inventory manager.
Why DarkStore repeats the inventory methods too Otherwise callers would write darkStore.getInventoryManager().checkStock(sku), reaching through a stranger. That breaks the Principle of Least Knowledge (Law of Demeter): talk only to your immediate friends. Callers talk to the dark store, the dark store talks to its manager, and the manager talks to the store.

DarkStore–InventoryManager is composition: the dark store's constructor creates its own manager (with a new DbInventoryStore()), and the manager can't exist without it.

A trade-off the code admits Hardcoding new DbInventoryStore() inside DarkStore is tight coupling. The code's comment suggests the fix: an InventoryStoreFactory taking an enum (DB, FILE, …). It was skipped because only one store type exists today, which is an acceptable call as long as you say it out loud.

Where's the Bridge? (InventoryManager ↔ InventoryStore)

The lecture points out that InventoryManager (high level: what to do) holding an InventoryStore (low level: how it's stored) is shaped like the Bridge pattern (Lecture 25): new store types can be added without touching the manager, and later there could be several kinds of manager. It's a "modified" Bridge, since the abstraction side has only one class for now — a reminder that textbook UMLs get bent to fit real use cases.

A more precise way to say it in an interview With a single manager class, this is really Dependency Inversion (Lecture 6) — the manager depends on an abstract store — and InventoryStore is essentially the Repository pattern (an abstract data-access interface with swappable backends). It only becomes a true Bridge once the manager side also grows its own hierarchy.

Nearby stores, users and orders

User (prototype) — name, coordinates ux, uy, and a Cart (composition: created with the user). Cart — items: vector<pair<Product, qty>>; addItem(sku, qty) gets the Product from the factory; getTotal() sums price × qty; getItems(). DeliveryPartner (prototype) — just a name. These stay tiny on purpose: the system being designed is the inventory, not riders or users.

DarkStoreManager (Singleton — one for the whole app) — holds all dark stores; registerDarkStore(ds); getNearbyDarkStores(ux, uy, maxDistance): call distanceTo on each store, keep those within maxDistance (5 km), sort by distance, and return the list nearest-first. DarkStoreManager–DarkStore is left as plain association (you could argue for aggregation if stores outlive the manager, e.g. regional managers).

Order (model) — orderId (from a static nextId++, as in Zomato), user, items: vector<pair<Product, qty>>, partners: vector<DeliveryPartner> (a list, because a split order has several partners), totalAmount.

OrderManager (Singleton) — keeps all orders; placeOrder(user, cart); getAllOrders(). The cart is passed separately instead of pulling it out of the user — again the Principle of Least Knowledge, as in Lecture 11. DarkStoreManager is reached via getInstance() rather than passed in.

Zepto (orchestrator, like Tomato in Lecture 11) — the single entry point: initialize() seeds dark stores, showAllItems(user) lists every product from stores within 5 km.

placeOrder — the splitting algorithm

Step by step 1. nearby = DarkStoreManager.getInstance().getNearbyDarkStores(user.x, user.y, 5); if empty → "no dark store near you."
2. requested = cart.getItems().
3. Fast path: check whether the nearest store has every item in the required quantity (checkStock(sku) ≥ qty for all). If yes → removeStock for each item, copy items into the order, total = cart.getTotal(), assign one partner, done.
4. Split path: build remaining: map<sku, qty>. For each nearby store, nearest first (stop early once remaining is empty):
  • for each (sku, needed) in remaining: avail = store.checkStock(sku); skip if 0; taken = min(avail, needed); store.removeStock(sku, taken); add (product, taken) to the order; if needed > taken reduce remaining[sku], else put the SKU in toErase; mark assigned = true.
  • after the inner loop, erase every SKU in toErase from remaining (erasing while iterating the same map would break the loop — hence the separate list).
  • if assigned → add a new delivery partner for this store.
5. Anything still in remaining → report "could not fulfil," but still deliver the rest.
6. Recompute the total from the items actually in the order (it may differ from the cart total), print the summary, and store the order.

Gaps worth raising in an interview

  • Greedy nearest-first isn't minimal. Only the nearest store is checked for a full fulfilment. If store 2 alone had everything, the algorithm would still split across stores 1 and 2. Better: first look for any nearby store that can fulfil everything, then fall back to splitting. (Minimising partners exactly is a set-cover problem, so real systems use heuristics.)
  • Race conditions on stock. checkStock then removeStock isn't atomic, so two users can both be promised the last banana. It needs a per-store lock or an atomic "reserve" operation, plus releasing the reservation if the order fails. The static nextId++ for order IDs isn't thread-safe either.
  • Straight-line distance. distanceTo uses Euclidean distance on x/y. Real apps use latitude/longitude (the haversine formula) and, for a 10-minute promise, estimated travel time by road, not distance.
  • ProductFactory is really a catalog lookup. Calling it for every addStock/addItem creates duplicate Product objects for the same SKU; a product catalog/repository returning a shared instance fits better.
  • Replenishment is never triggered automatically; a scheduler (weekly) or a hook after removeStock (threshold) would call runReplenishment.
