Lecture 1: Introduction to Low-Level Design ▶ Watch

Source: "Introduction To System Design" · 24 min · Code Army (Aditya)

DSA vs LLD

  • DSA solves isolated, well-defined problems (search → linear/binary search; sort → quick/merge sort).
  • LLD wraps a complete, structured application around those solutions: which objects exist, how they relate, how everything plugs together — i.e. how to build "Zomato / Ola / Uber," not just solve a LeetCode problem.
"If DSA is the brain of an application, LLD is the skeleton."

Example: ride-hailing app (QuickRide, Ola/Uber-style)

DSA-first approach (no LLD)
Sub-problemSolution
Route user source → destinationCity as graph (intersections = nodes, roads = edges) + Dijkstra for shortest path.
Assign nearest available riderMin-heap / priority queue of nearby riders keyed by distance; pop the closest.
Why DSA-first fails: algorithmically correct, but never defines (1) the entities (User, Rider, Location, Notification, Payment…) and their relationships, (2) data security — e.g. after a ride ends, rider and user shouldn't see each other's phone numbers, (3) how Notifications and Payment Gateway plug in, (4) scaling to millions of users.
LLD-first approach (then DSA)
StepWhat
1Identify entities: User, Rider, Location, Notification, Payment, etc.
2Define relationships (User ↔ Rider, Rider ↔ Location, …).
3Define data-security/privacy boundaries between objects.
4Design for scale (scalability of the architecture, not just the algorithm).
5Only now plug the same DSA (Dijkstra / min-heap) into the skeleton.
Key point: the algorithm is never the missing piece. Building the skeleton first gives the algorithm a place to live, so the design absorbs new requirements (payments, notifications, privacy rules) without a rewrite.

The Three Pillars of LLD

  1. Scalability — sustains growing users; new features can be added/scaled without the design falling apart.
  2. Maintainability — new features don't break unrelated old ones; code is easily debuggable; extensions introduce minimum new bugs (0% is unrealistic).
  3. Reusability — "plug and play": lift a module into another app with minimal changes.
Reusability in practice: Notifications and Payment Gateway are application-independent (same module in QuickRide, Zomato, Swiggy). "Assign nearest rider" is a generic nearest-match mapping algorithm — reused by Zomato/Swiggy (delivery partner ↔ order), Amazon, Blinkit. Entities change, matching logic doesn't. The opposite — logic fused to one app — is tightly coupled code, which LLD avoids.

LLD vs HLD

What each actually focuses on
Focuses onTypical interview activity
HLD (High-Level Design)Tech stack (e.g. Java/Spring Boot), DB choice (SQL / NoSQL / hybrid), server scaling under bulk traffic, cost optimization (scale servers up/down)System-architecture diagrams — almost no code
LLD (Low-Level Design)Code structure — classes, objects, relationships (class diagrams)Designing classes/interfaces, sometimes real code
DSATool LLD uses for one isolated problem inside that structureWriting/optimizing an algorithm

Not competing approaches — different zoom levels of the same system.

Caveats

  • Dijkstra requires non-negative edge weights (fine for distance/time). With negative weights or live-traffic re-routing, consider A* or other approaches.
  • "Everything is an object" is a simplification: over-modeling (every noun → class) adds needless complexity. Treat first-pass entity identification as a rough draft; OOP/SOLID refine it.
  • Interview probe: for every entity relationship, ask "what should NOT be visible across this relationship, and when does that change?" (e.g. phone numbers after ride ends).

One-line takeaway

Remember this:
DSA = brain (isolated problem-solving). LLD = skeleton (structure built before algorithms are dropped in). HLD = architecture around the system (tech stack, DBs, servers, cost) — a different zoom level, not a replacement.

Lecture 2: OOPs: History, Abstraction & Encapsulation ▶ Watch

Source: "OOPs Real-World Examples | OOPs Pillars" · 54 min · Code Army

Why OOP exists

EraWhat it gaveWhat it still lacked
Machine language (0s/1s)Direct CPU executionExtremely error-prone, tedious, not scalable
Assembly (mnemonics, e.g. MOV A, 61H)English-like keywordsTightly coupled to hardware; no real loops/methods; error-prone, not scalable
Procedural (e.g. C)Functions, loops, if/else, switchNo real-world modeling, no data security, poor scalability/reusability for enterprise code
Object-Oriented ProgrammingModels real-world entities directly as objects—

What OOP adds over procedural

  1. Real-world modeling — code mirrors real objects interacting.
  2. Data security — via Encapsulation.
  3. Scalability & reusability — new instances don't require hand-duplicating variables/methods.

Object = Characteristics (state/data) + Behavior (methods). Class = blueprint for objects.

Procedural vs OOP — Car/Owner example

Car (brand, model, isEngineOn; start, stop, shiftGear) and an Owner who owns/drives it.

Procedural — problems: car state = loose variables, behaviors = free functions; "drive" becomes drive(brand, model) calling start(), shiftGear(), accelerate() manually. Each new car/owner needs hand-duplicated variables (brand2, model2…); the Owner–Car relationship is invisible in code. Low scalability/reusability, no real-world mapping.
OOP — fix: class Car { brand, model, isEngineOn, start(), stop(), shiftGear() }, class Owner { name, car, drive() }. drive() takes no params — it calls car.start(), car.shiftGear(). New car/owner = new instance. Relationship (Owner has-a Car) is explicit in structure.

Ideology of OOP

An OOP codebase is just a set of objects interacting — by calling each other's methods or being passed as parameters.

The Four Pillars of OOP

Abstraction, Encapsulation (this lecture), Inheritance, Polymorphism (Lecture 3).

Pillar 1: Abstraction

Definition:
Abstraction hides unnecessary implementation details from a client (whatever object/user interacts with it) and exposes only what is necessary.

Analogies: car controls (steering, pedals, gears) vs engine internals; TV remote vs circuitry; laptop screen vs hardware; high-level languages (if/for) over machine code.

Abstraction — C++ pattern

  • Abstract class Car with only virtual method declarations = the interface/contract.
  • Concrete subclass SportsCar inherits and implements (state: brand, model, isEngineOn, currentSpeed, currentGear; behavior: startEngine(), shiftGear(), accelerate(), brake(), stopEngine()).
  • Abstract class can't be instantiated; use Car* myCar = new SportsCar(...) (parent-type pointer to child object).
  • Caller only uses interface methods (myCar->startEngine()…) without knowing internals.
Correction — pure virtual syntax: the lecture writes virtual void startEngine();. That does not make the class abstract — only pure virtual virtual void startEngine() = 0; does. Without = 0, Car is instantiable and an undefined virtual fails only at link time. Always use = 0 to enforce "must override."
Note: C++ has no interface keyword (unlike Java/C#); an abstract class of only pure-virtual methods and no data members is the C++ equivalent.

Pillar 2: Encapsulation

Definition — two parts:
1) Bundle data and methods together in one unit (the class).
2) Data security: some state must not be directly readable/writable from outside.

E.g. odometer/currentSpeed must change only via accelerate()/brake(). Enforced by access modifiers: public (accessible anywhere), private (class only), protected (class + children).

Getters & Setters

  • Getter: int getCurrentSpeed() { return this->currentSpeed; } — read-only. currentSpeed deliberately has no setter.
  • Setter: void setTyre(string tyre) { this->tyre = tyre; } — write access funneled through a method.
Why setters over public fields: a setter is a control point for validation before mutation (e.g. setTyre checks non-empty / brand exists). A public field can't enforce this.

Abstraction vs Encapsulation

ConcernIf violated
AbstractionImplementation hiding for simplicity — client doesn't need internalsNo real harm (opening the hood breaks nothing)
EncapsulationData security — state must not be directly set from outsideInvalid/unsafe state (e.g. currentSpeed = 500)
Caveat: "hiding vs security" is a practical heuristic for interviews; in broader OOP literature the two overlap (encapsulation sometimes defined to include abstraction). Not a rigid formal law.

Pillar 3: Inheritance

Parent–child (is-a) relationship: ManualCar and ElectricCar are kinds of Car.

  • Parent Car (common): brand, model, isEngineOn, currentSpeed; startEngine(), stopEngine(), accelerate(), brake().
  • ManualCar: currentGear; shiftGear().
  • ElectricCar: batteryPercentage; chargeBattery().

C++: class ManualCar : public Car { ... }. Child defines only what's specific; parent members are usable directly.

Access modifiers under inheritance

Public inheritance ~99% of the time: protected/private inheritance strip visibility further down the hierarchy (a grandchild may lose access to what ManualCar privately inherited from Car), defeating the purpose of inheritance. Rare, deliberate exceptions only.

Pillar 4: Polymorphism

One behavior, many forms.

Dynamic Polymorphism (Method Overriding)

Parent Car declares virtual accelerate(), brake(); each child implements:

  • ManualCar.accelerate() → currentSpeed += 20
  • ElectricCar.accelerate() → check battery not empty, drain battery, currentSpeed += 15

Rule: signature must match exactly — name, return type, parameter count and types.

Correction (same as Lecture 2): use pure virtual virtual void accelerate() = 0;. Plain virtual without body doesn't force overriding or make Car non-instantiable — it's only a linker error if called and never overridden.

Static Polymorphism (Method Overloading)

Same class, same name, different parameter lists: accelerate() (+20) and accelerate(int speed) (+speed). Rule: the number and/or type of arguments must differ.

Overloading vs. Overriding — what must match
NameReturn typeParametersClass relationship
Overloading (static)samesamemust differ (count/type)same class
Overriding (dynamic)samesamemust be identicalparent → child

All 4 pillars in one hierarchy

Car: protected fields (brand, model, isEngineOn, currentSpeed) = Encapsulation; startEngine()/stopEngine() defined, accelerate()/accelerate(int)/brake() virtual = Abstraction. ManualCar & ElectricCar extend Car = Inheritance. Each overrides accelerate()/brake() (dynamic) and overloads accelerate(int speed) (static) = Polymorphism.

UML diagram types

UML = diagrammatic expression of an application's design: which components exist and how they interact.

CategoryAlso calledShows
Structural (7 types)Static diagramsStatic structure — components and connections
Behavioral (7 types)Dynamic diagramsRuntime interaction (message passing, method calls)
Only 2 of 14 matter for LLD: Class Diagram (structural — ~99% of LLD interviews, drawn before code) and Sequence Diagram (behavioral — not always asked, clarifies specific flows). The other 12 are use-case-specific.

Class Diagram — representing a class

Rectangle in 3 parts: name, attributes (with type), methods (with return type). Prefixes: + public, # protected, - private. Abstract class labeled «abstract».

Class associations — 2 categories

  1. Class-level: only Inheritance — "is-a". Line with hollow triangular arrowhead pointing to parent.
  2. Object-level: "has-a", 3 sub-types by strength. All coded identically in C++ (B holds a reference/pointer to A, set in B's constructor) — they differ only in semantic strength, a design judgment, not syntax.
The 3 object-association strengths

Aggregation (medium)hollow diamond, at container endContainer holds parts that can exist independentlyRoom has Sofa, Bed, Chair
Composition (strongest)filled diamond, at whole endParts cannot exist independently — destroying whole destroys partsChair is composed of Wheels, Seat, Armrest

Aggregation vs composition — nuances:
  • Standard UML: in composition the part's lifecycle is bound to the whole (created/destroyed with it) and belongs to only one whole; in aggregation the part can outlive the whole and be shared across containers. Agrees with the "can it exist independently?" heuristic in practice.
  • Often subjective: Zomato Menu ↔ Restaurant — composition if a menu can't exist without its restaurant, aggregation if loosely attached. No single correct answer; interviewers care about the justification.
  • Composition is used more often than inheritance in real LLD — more flexible, no rigid is-a lock-in.

Sequence Diagram — purpose

Shows how objects communicate over time for one specific use case/flow. An app has many sequence diagrams (one per flow), never one for the whole app.

Sequence Diagram — components

  • Object: plain labeled box (no attributes/methods).
  • Lifeline: vertical dashed line — when the object exists in the flow (can start mid-flow if created then).
  • Activation bar: solid bar on lifeline — when the object can send/receive messages; outside it, it can't.
  • Synchronous message: solid line + closed arrowhead; sender waits. Response = dashed line back.
  • Asynchronous message: solid line + open arrowhead; sender does not wait, can fire more messages in the same activation bar.
  • Create message: spawns a new lifeline mid-diagram.
  • Destroy message: ends a lifeline (marked X).
  • Lost message: never reaches an object (ends in filled dot) — e.g. target's activation already ended.
  • Found message: from unknown source (starts at filled dot).
  • Control fragments: alt = if/else, opt = if-only, loop = iteration. Rare in interviews (happy path only).

Procedure

  1. Write the use case in plain words.
  2. Identify every object involved.
  3. Draw objects + lifelines, activation bars, then messages in order.

ATM creates a Transaction → it synchronously calls Account.checkAmount() → returns true to ATM and is destroyed → ATM calls CashDispenser.withdrawCash() → cash to User. PIN validation is a separate use case/diagram.

Lecture 5: SOLID Design Principles — Part 1 (S, O, L) ▶ Watch

Source: "SOLID Design Principles | Complete Guide with Code Examples" · 1h7m · Code Army

Why design principles

With thousands of classes and no structuring rules, code becomes tightly coupled (like electrical, internet and plumbing wires bundled in one wall), causing: poor maintainability (features touch lots of code, break old ones), poor readability, excess debugging time. SOLID = 5 principles by Robert C. Martin, 2000.

SOLID = Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion. (I, D in next lecture.)

S — Single Responsibility Principle (SRP)

Definition:
A class should have only one reason to change — one responsibility.
Misconception: SRP is not "one method per class" — any number of methods is fine if all serve the same responsibility (a TV remote has many buttons, but shouldn't control the fridge/AC).

Violation: ShoppingCart with calculateTotalPrice(), printInvoice(), saveToDB() → 3 reasons to change (pricing, invoice format, persistence).

Fix: ShoppingCart only prices; CartInvoicePrinter and CartDBStorage each hold a cart reference and do one job. Invoice/DB changes touch only their own class.

O — Open/Closed Principle (OCP)

Definition:
A class should be open for extension, but closed for modification — new features must not require editing existing, working classes.

Violation: adding saveToMongoDB() and saveToFile() inside the existing DBStorage class (modifies shipped code). Fix: abstraction + inheritance + overriding — each persistence mechanism is a new subclass.

Adding Cassandra = new CassandraPersistence overriding save(); existing classes untouched.

Caveat: OCP is idealistic — rarely followed with 100% purity in production. Follow as closely as practical.

L — Liskov Substitution Principle (LSP)

Definition:
Subclasses must be substitutable for their base class: replacing a base-class reference with a subclass object must work with zero client changes. A child should only extend the parent's capabilities, never narrow them.

Violation: abstract Account (deposit(), withdraw()) → SavingsAccount, CurrentAccount fine; FixedDepositAccount can't withdraw, so its withdraw() throws. A client looping over Accounts calling withdraw() crashes — the child narrowed the contract.

Bad fix: if (account is FixedDepositAccount) skip withdraw() in the client → client becomes tightly coupled to concrete types and must change for every new type — fixes LSP by breaking OCP. Type-checks in client code signal a wrong hierarchy.

Correct fix: split the abstraction by actual capability so no subclass must reject an inherited method.

WithdrawableAccount extends DepositOnlyAccount adding withdraw(); FixedDepositAccount extends only DepositOnlyAccount. Client keeps two lists (withdrawable, deposit-only) and calls only guaranteed methods — no type-checks, no surprise exceptions.

Formal LSP (Barbara Liskov) — behavioral subtyping: beyond matching signatures, an override must not strengthen preconditions, weaken postconditions, or throw new exception types the base contract never promised. Hence FixedDepositAccount.withdraw() throwing is a technical violation too.

General lesson from LSP

If a subclass can't honestly implement a parent method, reshape the abstraction (split by capability) — don't patch callers with type-checks or make the method throw. Client type-checks against concrete subclasses are a recurring smell across SRP/OCP/LSP.

Lecture 6: SOLID Design Principles — Part 2 (LSP rules, Interface Segregation, Dependency Inversion) ▶ Watch

Source: "SOLID Design Principles | part 2" · 1h17m · Code Army

LSP: checkable rules

LSP is the most commonly broken SOLID rule (unintentionally). Rules fall in 3 groups: Signature, Property, Method. Terms: "broader" = ancestor type; "narrower" = descendant type.

1. Signature Rule (3 sub-rules)

Sub-ruleRuleWhy
Method Argument RuleOverride's parameter type: same or broader (contravariant), never narrower.Compiler-enforced for true overrides (C++: mismatched params → "does not override a base class member" error). Practically unbreakable.
Return Type RuleOverride's return type: same or narrower — covariance. Never broader.A parent-typed client reference can't hold a broader return value.
Exception RuleOverride may throw the same or a narrower (subclass) exception — never broader/unrelated.Client's catch is written against the parent's contract; an unrelated exception escapes it.
Concrete failure:
Parent throws LogicError (or subclass OutOfRangeError); client has catch(LogicError&). Child throws RuntimeError (sibling branch) → not caught → uncaught exception, program terminates.

2. Property Rule (2 sub-rules)

Sub-ruleMeaningExample
Class InvariantA condition that must always hold for the class (documented + enforced in code, not a language construct). Child must preserve or tighten it.Account: "balance never negative." CheatAccount allowing negative balance → not substitutable.
History ConstraintAn established behavior/state guarantee that a subclass must never change.Account: "withdrawal always allowed." FixedDepositAccount throwing on withdraw() breaks it (Lecture 5's LSP violation).
Extra fact:
C++ final class can't be inherited; final method can't be overridden. A subclass making a parent's immutable thing mutable (if possible) would also violate the History Constraint — it covers any "must never change" guarantee, not just values.

3. Method Rule (2 sub-rules)

Sub-ruleRuleExample
Precondition (holds before method runs)Child may weaken, never strengthen.Parent createPassword() needs length ≥ 8. Child ≥ 6: OK (accepts a superset). Child ≥ 10: violation (rejects length-8 input the client believed valid).
Postcondition (holds after method runs)Child may strengthen, never weaken.Parent brake() guarantees speed decreases. ElectricCar also recharging: OK (extra guarantee). Not decreasing speed: violation.

LSP: the 3 concrete tells of a violation

An override that (1) throws an exception the parent never promised, (2) is empty/no-op, or (3) returns a hardcoded/meaningless value just to compile → LSP break. Fix: reshape the interface (split by capability), not patch the override or caller.

I — Interface Segregation Principle (ISP)

Definition:
Many client-specific interfaces are better than one general-purpose interface. A class should never be forced to implement a method it has no use for.

Violation: abstract Shape with area(); adding volume() for Cube forces Square/Rectangle to override a meaningless method (throw or return garbage).

D — Dependency Inversion Principle (DIP)

Definition:
High-level modules should not depend on low-level modules — both should depend on an abstraction. High-level = business logic. Low-level = talks directly to a system resource (DB, file system, external API).

Violation: UserService holds concrete MySQLDatabase/MongoDatabase with storeUserToSQL()/storeUserToMongo(). Swapping to Cassandra means editing UserService → also breaks OCP.

UserService calls only db.save(); the concrete DB is passed in via constructor (Dependency Injection) and resolved at runtime by polymorphism. Adding Cassandra = one new subclass; UserService untouched.

Rule to memorize:
"If OCP is the target, DIP is the solution." The abstraction layer between high- and low-level modules is what makes OCP achievable.
Analogy: CEO (high-level) ↔ Manager (abstraction) ↔ developers/QA (low-level); swapping team members doesn't change how the CEO operates.

SOLID vs. "OOP models the real world"

Apparent contradiction resolved:
Real objects do many things, yet SRP demands one responsibility. Resolution: behavior is context-dependent; a class models only the behavior relevant to one application. A User in an Uber-style app books/cancels rides; in a Zomato-style app orders/cancels food — not both in one class.
SOLID are principles, not laws:
Production code sometimes consciously bends a principle for business needs — a trade-off like time-vs-space in DSA. Follow SOLID as closely as practical, not dogmatically.

Lecture 7: Build Google Docs — Document Editor LLD ▶ Watch

Source: "Build Google Docs | A Real-World LLD Project | Document Editor LLD" · 45 min · Code Army

Problem statement

Document editor holding an ordered sequence of elements (now text, image); must scale to new types (table, video, bold/italic, new line, tab…) without rewrite. In interviews: design a couple of features, keep the architecture extensible for the rest.

Design methodology: Top-Down vs. Bottom-Up

ApproachWhat it does
Top-downDesign the main/top-level object first, then its smaller objects and dependencies.
Bottom-upDesign the smallest objects first, then compose them into bigger ones.
Which to use:
Bottom-up is the common default in LLD interviews (used here); some problems suit top-down. Pick per problem.

Bad design (naive starting point)

One DocumentEditor with a vector<string> of elements (text as-is, images as file paths) plus addText(), addImage(), renderDocument(), saveToFile().

Anti-pattern in renderDocument():
Type-sniffing: if length > 4 and ends in .png/.jpg → image, else text. Inferring type from string content instead of using polymorphism.

Violates: SRP (≥3 reasons to change: add, render, save) and OCP (new element type, e.g. Table, means editing renderDocument()). LSP/ISP/DIP don't apply — no hierarchy.

Better design: extract 3 hierarchies

  • DocumentElement (abstract, render()): each subclass (TextElement, ImageElement, later NewLineElement, TabSpaceElement, BoldElement…) renders itself. New type = new subclass → OCP.
  • Document: ordered list of DocumentElements (1-to-many composition); render() loops and delegates to element.render().
  • Persistence (abstract, save()): FileStorage, DBStorage, … — same DIP/OCP pattern as Lectures 5–6.
  • DocumentEditor: client-facing; has-a Document + Persistence (constructor-injected); every public method just delegates.
SOLID check:
SRP: Document = manage elements, Persistence = storage, DocumentEditor = client interface + delegation. OCP: new element/storage types = new subclasses. LSP: any DocumentElement works uniformly in the list. ISP: both interfaces have exactly one method. DIP: high-level Document/DocumentEditor depend on abstractions Persistence/DocumentElement, not concrete storage.

Counter-question: is DocumentEditor really SRP?

Debatable — a judgment call:
DocumentEditor delegates all work but still knows about render() on Document and save() on Persistence (aware of multiple reasons to change). Defensible as SRP-compliant since it only delegates. There is no single perfect LLD design — aim for a design you can justify.

Further refinement: extracting DocumentRenderer

Move rendering out of Document into DocumentRenderer (has-a Document). Document becomes a pure model doing CRUD (addElement, getElements()). A Client class coordinates Document, DocumentEditor, DocumentRenderer, Persistence.

Principle of Least Knowledge (Law of Demeter)

Definition (not part of SOLID):
"Talk only to your immediate friends." Call methods only on objects you directly hold — never reach through one object to call methods on its internals ("friend of a friend").
Violation in the refined design + unresolved trade-off:
DocumentRenderer calls document.getElements() (OK, direct friend) then .render() on each DocumentElement (violation — no direct has-a; indirect coupling to DocumentElement's interface). Fixing it by moving rendering back into Document re-creates the SRP tension. Deliberately left as an open trade-off to negotiate with interviewer/team — no configuration satisfies every principle.

Takeaway for any LLD build question

Start naive → identify which SOLID principles break and why → refactor one hierarchy/responsibility at a time → re-check all 5 after each step. Expect defensible trade-offs at the end; the skill tested is reasoned justification, not one "correct" diagram.

Lecture 8: Strategy Design Pattern ▶ Watch

Source: "Strategy Design Pattern Explained with Real-World Example" · 32 min · Code Army · First lecture of the Design Patterns section

What design patterns are

Proven, reusable solutions to recurring design problems; 23 GoF patterns. Common core idea: separate the frequently-changing (dynamic) part from the fixed (static) part into its own class(es), so changes stay localized.

Setup: simulating robots

Robot base: walk(), talk(), abstract project() (appearance). CompanionRobot, WorkerRobot override only project().

Why the inheritance-only design collapses

"The solution to inheritance is not more inheritance."

Strategy Pattern — definition

Define a family of algorithms, put each into its own class, and make them swappable at runtime. ("Algorithm" = any self-contained behavior: walk, talk, fly.)

Applying it: extract the varying behaviors

Varying: walk, talk, fly → each becomes an abstract strategy interface with concrete implementations:

  • Walkable (walk()) → NormalWalk, NoWalk
  • Talkable (talk()) → NormalTalk, NoTalk
  • Flyable (fly()) → NormalFly, NoFly, FlyWithJet, … (freely extensible)

Robot is a "dumb object": walk() { walkBehavior.walk(); } etc. — pure delegation to constructor-injected strategies, resolved via polymorphism.

Why this fixes the explosion:
New robot = any combination of Walkable + Talkable + Flyable injected at construction; new subclass only for a genuinely new behavior (e.g. FlyWithJet). Robot never changes → OCP.
"Favor composition over inheritance."

"Aren't CompanionRobot/WorkerRobot still inheritance?"

Yes — extract project() into a Projectable strategy too. Then Robot needs zero subclasses: new Robot(walkBehavior, talkBehavior, flyBehavior, projectBehavior).

Standard UML shape of Strategy Pattern

This Client/Strategy/ConcreteStrategy shape recurs across many patterns:

Client = uses the algorithm (Robot); Strategy = abstract family (Walkable/Talkable/Flyable); ConcreteStrategy = interchangeable implementation. Client calls strategy.run(); the injected object decides what runs.

Real-world examples

ContextClient methodStrategies

Sorting utilitysort()QuickSort (normal / randomized), MergeSort (normal / in-place), InsertionSort

One of the most-used patterns in LLD interviews: applies whenever a behavior must vary independently and be swapped at runtime without touching its users.

Lecture 9: Factory Design Pattern ▶ Watch

Source: "Factory Design Pattern | Simple, Factory Method & Abstract Factory" · 32 min · Code Army

Why Factory exists

Strategy assumed strategy objects already exist; it never addressed where new is called. Factory separates object-creation logic from business logic.

Goal:
The client doesn't know how an object is constructed — it asks a factory and gets one back. Same decoupling instinct as DIP/Strategy.

Three kinds of Factory

KindOfficial (GoF) pattern?What it does
Simple FactoryNo — a design idiomOne factory class with if/else (switch) picking the concrete class from a type parameter
Factory MethodYesFactory is abstract; each concrete factory subclass decides which concrete product to build
Abstract FactoryYes (extends Factory Method)Abstract factory with multiple creation methods producing a family of related products

Simple Factory — burger shop example

Burger (abstract, prepare()) → BasicBurger, StandardBurger, PremiumBurger. BurgerFactory.createBurger(type: string) matches "basic"/"standard"/"premium".

Definition: "A factory class that decides which concrete class to instantiate."
OCP problem: a new burger type means editing createBurger()'s if/else. Solves separation, not extensibility — Factory Method fixes that.

Factory Method — polymorphic factory

Two franchises: SingBurger (normal burgers) and KingBurger (wheat: BasicWheatBurger/StandardWheatBurger/PremiumWheatBurger). BurgerFactory becomes abstract with createBurger(type); SingBurgerFactory, KingBurgerFactory override it.

Client: BurgerFactory* factory = new KingBurgerFactory(); factory->createBurger("basic") → BasicWheatBurger. New franchise = new BurgerFactory subclass; no existing factory edited → OCP.

Definition:
"Define an interface for creating an object, but let subclasses decide which class to instantiate."

Abstract Factory — families of related products

Both franchises also sell GarlicBread (BasicGarlicBread/CheeseGarlicBread + wheat versions). Abstract factory declares createBurger(type) and createGarlicBread(type); each concrete factory produces a consistent family (Sing → normal; King → wheat).

Definition: "Provides an interface for creating families of related objects without specifying their concrete classes."
Factory Method vs. Abstract Factory: Factory Method = one product type per factory hierarchy; Abstract Factory = multiple related product types created consistently by the same concrete factory (Factory Method extended to product families).

Real-world example: Notification System

NotificationSystem (abstract) → SMSNotification, PushNotification, EmailNotification; factory maps "sms"/"push"/"email" to the concrete object.

Strategy vs. Factory — which applies?

The same Notification System could be modeled with Strategy (SMS/Push/Email injected via composition). Both valid; different intent.

Decision heuristic:
Need to vary behavior at runtime on an object that already exists? → Strategy. Need to separate object-creation logic from business logic (how to construct is the problem)? → Factory. Often subjective — in interviews, articulate why you chose one and acknowledge the alternative.

Lecture 10: Singleton Design Pattern ▶ Watch

Source: "Singleton Design Pattern | Thread-Safe, Lazy & Eager Initialization + Real Use Cases" · 32 min · Code Army

Definition

A class that can have only one instance; further creation attempts return the same instance.

Background: what new does

Stack holds locals/primitives; heap holds custom-class objects. A* a = new A();: (1) allocate heap space for A, (2) call constructor (compiler supplies a default if none), (3) store address in stack pointer a. Repeating it yields another object — what Singleton must block.

Building it step by step

  1. private constructor — blocks external new Singleton().
  2. public static getInstance() — must be static since no object exists before the first call.
  3. private static pointer instance = nullptr; getInstance() creates the object if null, else returns the existing one.

C++: static member must be defined outside the class (Singleton* Singleton::instance = nullptr;); Java allows inline initialization.

Making it thread-safe

Naive version is not thread-safe: two threads can both see instance == nullptr and each construct an instance.

ApproachHow it worksTrade-off
Lock the whole methodAcquire a mutex at the start of every getInstance() callCorrect, but pays lock cost on every call even after the instance exists
Double-Checked Locking (DCL)Check null without lock; if null, lock, then check null again before constructingNo locking once instance exists. Both checks needed: with only the outer check, two threads can enter the lock back-to-back and double-construct
Technical correction — DCL pitfall in C++:
Without proper memory ordering, compiler/CPU reordering can let another thread see a non-null pointer to a not-yet-constructed object (the documented "DCLP" problem, Meyers & Alexandrescu). Proper fix: C++11 std::atomic pointer with acquire/release ordering, not a raw pointer.
Preferred modern alternative (Meyers' Singleton):
Since C++11, a function-local static is guaranteed initialized exactly once, thread-safely, with no manual locking: static Singleton& getInstance() { static Singleton instance; return instance; }. Generally preferred over hand-written DCL.

Eager Initialization (no locking)

Construct at static definition — Singleton* Singleton::instance = new Singleton(); — before main() runs. getInstance() just returns it: no null-check, no lock.

BenefitCost
Eager initSimplest; inherently thread-safe, zero locking overheadResources spent at startup even if the singleton is never used
Eager vs. lazy:
Eager only for lightweight singletons. For expensive construction (e.g. large connection pool), use lazy init with correct thread-safety.

Real-world use cases

Use caseWhy Singleton fits
Logging systemPer-service loggers interleave output unpredictably; one shared logger = consistent, ordered log.
Database connectionConnections are expensive; a connection per request wastes resources. One shared connection/manager avoids it.
Configuration managerAPI keys/config need a single source of truth; per-service copies can drift out of sync.

When NOT to use Singleton

  • When you need multiple independent instances by design (e.g. each game player has its own state).
  • It adds thread-safety complexity and makes unit testing harder (shared global state, hard to mock/reset). Use only when a single shared instance is clearly needed.

Lecture 12: Observer Design Pattern ▶ Watch

Source: "Observer Design Pattern Explained | Real-Life Use Case + Code Example" · 28 min · Code Army

The problem

One object's state changes; one or many others must know when (and the new value) — e.g. a YouTube channel uploads, subscribers are told.

Polling vs. Pushing

ApproachHow it worksProblem
Polling (rejected)Interested object repeatedly asks "changed yet?"Wasteful; unknown frequency, almost always "no".
Pushing (Observer Pattern)Source notifies interested objects the moment state changes— this is the whole pattern.

Naming convention: the "I" prefix

Pure abstract class (C++) / interface (Java) — all methods abstract, a pure contract — is prefixed I (IObservable, IObserver). Convention only (C++ has no interface keyword); used from here on.

Structure: Observable and Observer

Observable (a.k.a. Subject) is watched; Observers watch. One-to-many.

  • IObservable: add(observer), remove(observer), notify() (loop observers, call update()).
  • IObserver: update() — refresh own state on change.
Atypical choice — concrete-to-concrete reference: normally relate abstract types, but ConcreteObserver holds ConcreteObservable (not IObservable) because update() must pull data via a concrete-specific getter (e.g. getValue()) not in the IObservable contract.
Pull vs. push variant: this is pull (update() with no args; observer queries the observable). Push passes data: update(newValue) — observer needs only IObservable or no reference. Push: simpler when only the changed value is needed. Pull: better when the observer may query more state on demand.

Standard definition

"Define a one-to-many relationship between objects so that when one object changes state, all of its dependents are notified and updated automatically."

Example: YouTube channel & subscribers

IChannel: subscribe(), unsubscribe(), notifySubscribers(). ISubscriber: update(). ConcreteChannel holds subscribers + uploadVideo(title) (stores, then calls notifySubscribers()) and getVideoData(). ConcreteSubscriber holds the concrete channel; update() pulls via channel.getVideoData().

Flow: varun, tarun subscribe → uploadVideo(...) → notifySubscribers() → each update() pulls the title. After varun unsubscribes, only tarun is notified.

Acknowledged SRP violation — kept on purpose

Violation: ConcreteChannel does (1) Observer mechanics (subscribe/unsubscribe/notify) and (2) business logic (uploadVideo, getVideoData) → two reasons to change.
Why accepted: Observer mechanics are generic and never change; only business logic does. Little practical harm, and standard reference UMLs make the same simplification. Splitting (mechanics in a concrete base, business logic in a subclass) adds complexity for no payoff.

Real-world use cases

  • Notification services — source informs all registered listeners.
  • News feed / social media — new post pushed to all followers.
  • Event handling — event triggers all registered handlers; front-end event listeners are Observer under the hood.

Lecture 13: Decorator Pattern ▶ Watch

Source: "Decorator Pattern Explained | Real-world use case + Code" · 29 min · Code Army

The problem

Attach responsibilities to an object dynamically, at runtime, stacking any number of enhancements in any combination/order, without subclass explosion.

Why inheritance + polymorphism isn't enough

Base* b = new Child() picks one fixed variant at construction; it can't layer multiple independent enhancements.

Class explosion: Mario example

Power-ups (Height-up, Gun, Star, later Fly) apply in any combination and order. Inheritance needs a subclass per combination (MarioWithHeightUp, MarioWithGun, MarioWithHeightUpAndGun, ...), multiplying with each new power-up.

Strategy vs. Decorator (same root cause as Lecture 8's robot explosion — independent axes crossed combinatorially): Strategy swaps one behavior per slot via composition (one Walkable + one Talkable + one Flyable). Decorator stacks an open-ended number of layers recursively on one object.

The Decorator solution

Wrap the object in a decorator: its method calls the wrapped object's same method, then enhances the result. Decorators stack arbitrarily deep.

Defining dual relationship: is-a AND has-a

A Decorator extends (is-a) the abstract base type and holds (has-a) an instance of it. Is-a: usable anywhere the base is expected, including as input to another decorator → unlimited stacking. Has-a: delegate to, then enhance, the wrapped object.

new StarPowerDecorator(new GunPowerDecorator(new HeightUpDecorator(new MarioCharacter()))): getAbilities() recurses inward to MarioCharacter, then each layer appends on the way out: "Mario" → "Mario with Height-up" → "Mario with Height-up with Gun" → "Mario with Height-up with Gun with Star Power". Any subset/order with only one class per power-up — no combinatorial explosion.

It's recursion across classes: each layer calls the wrapped method then appends — a call stack unwinding via object delegation.

Standard definition

"Attaches additional responsibilities to an object dynamically. Decorators provide a flexible alternative to subclassing for extending functionality."

Real-world use cases

  • Text editor formatting (Lecture 7 editor didn't use it): Text wrapped by BoldDecorator, ItalicsDecorator, UnderlineDecorator/FontDecorator in any combination.
  • Form validation pipeline: form wrapped by EmailValidationDecorator, XSSCheckDecorator, SQLInjectionCheckDecorator — stackable, no monolithic validation method.

Lecture 15: Command Design Pattern ▶ Watch

Source: "Command Design Pattern | Real-world use case + Code" · 29 min · Code Army

The problem

An invoker triggers an action on a receiver. Direct calls couple the invoker to the receiver's interface; wrapping the request as a Command object keeps them loosely coupled — invoker just says "execute".

Naive Smart Home Remote breaks OCP

Remote holding a Light with pressLightButton() { light.on(); } must be edited to control a Fan or new Heater — OCP violation.

The Command fix

ICommand (execute()) ← LightCommand, FanCommand, each holding its concrete receiver. RemoteControl holds a list of ICommand and just calls execute(). Rebinding a button = setCommand(index, newCommand); RemoteControl is never edited.

Adding Undo (toggle)

ICommand adds undo() (e.g. LightCommand: on/off). RemoteControl keeps a parallel pressed boolean array: pressButton(index) calls execute() if not pressed, else undo(), and flips the flag.

Doubt 1: why does the CONCRETE command hold the receiver?

Intent: ICommand only promises "execute / undo what I executed". Only the concrete command knows which receiver (Light) and action (on()/off()), so the receiver has-a lives at the concrete level.

Doubt 2: why concrete Light, not a generic Appliance interface?

Rejected alternative: one Appliance interface (on()/off()) + a single generic Command — fewer command classes.
Why rejected — breaks LSP: appliances don't all reduce to on/off (AC: timers, temperature; fridge/heater: different features). Forcing a common contract is the over-generalization LSP warns against (Lecture 5/6). Accept one concrete command per receiver type: slightly more coupling, correct model.

Standard definition

"Encapsulates a request as an object, thereby letting you parameterize clients with different requests, queue or log requests, and support undoable operations."

Real-world use cases

  • Undo/redo in editors (text editors, Photoshop): each action is a Command with execute()/undo(); Ctrl+Z pops the latest command off a stack and calls undo().
  • Keyboard shortcuts: key bound to a Command (e.g. "increase brightness"), dynamically rebindable — like the remote's buttons.
When to use: undo/redo needed, or a trigger must be reassignable to different actions without touching the invoker.

Lecture 16: Adapter Design Pattern ▶ Watch

Source: "Adapter Design Pattern | Real-world use case + Code" · 21 min · Code Army

Problem & analogy

Analogy: travel plug adapter / USB-C↔USB-B adapter — a third object translates between two incompatible interfaces.

Client code needs a third-party/vendor class (payment gateway, data provider) whose interface differs from what it expects. Calling it directly from many places tightly couples the codebase to the vendor — switching vendors means editing every call site.

Example: client expects JSON, library returns XML

  • IReport (abstract): getJsonData(rawData). Existing third-party XMLDataProvider: getXMLData(rawData).
  • XMLDataProviderAdapter: is-a IReport, has-a XMLDataProvider (adaptee). getJsonData() calls getXMLData(), converts XML→JSON, returns it.

Client holds only an IReport reference — unaware of the XML library.

Vocabulary and UML

Target = interface the client expects. Adaptee = existing incompatible class. Adapter = is-a Target + has-a Adaptee.

Standard definition

"Converts the interface of a class into another interface clients expect. Adapter lets classes work together that couldn't otherwise, because of incompatible interfaces."

Object Adapter vs. Class Adapter

  • Object Adapter (above): is-a Target via inheritance, has-a Adaptee via composition.
  • Class Adapter: inherits from both Target and Adaptee (multiple inheritance) — functionally equivalent.
Object Adapter is preferred: favor composition over inheritance; Java has no multiple class inheritance; in C++ multiple inheritance is avoided for coupling/fragility reasons.

Adapter vs. Decorator

Same wrapper shape (is-a + has-a), different intent. Decorator (L13) wraps the same interface to add behavior. Adapter wraps a different, incompatible interface to translate it. Decorator enhances; Adapter translates.

Real-world use cases

  • Third-party vendor/library integration with a mismatched interface (canonical case).
  • Legacy code: outdated/duplicated method shapes you can't modify; adapter exposes a modern interface and internally calls the legacy methods.

Lecture 17: Facade Design Pattern ▶ Watch

Source: "Facade Design Pattern | Real-world use case + Code" · 18 min · Code Army

Problem & solution

A subsystem of many interdependent classes (A→B,C; B→D…) jointly performs one job. A Facade class talks to the whole subsystem and exposes one/few simple methods (e.g. getWorkDone()) to the client.

Two benefits:
(1) Simplifies the client — one call instead of orchestrating the subsystem. (2) Decouples client from subsystem — internal classes/interactions can change with zero client impact.

Example: computer boot-up

Subsystem: PowerSupply, CoolingSystem, CPU, Memory, HardDrive, BIOS (needs CPU + Memory), OperatingSystem. ComputerFacade holds all and exposes startComputer(), calling each in the correct order.

Standard definition

"Provides a simplified, unified interface to a set of complex subsystems. It hides the complexity of the system and exposes only what is necessary to the user."

Principle of Least Knowledge (Law of Demeter) — full rules

(Introduced in L7.) A method may only call methods on:

#Allowed targetExample
1The object itselfm1() calling m2() of the same A
2A parameter of the current methodm3(B b) may call methods on b
3An object the method createsm4() { D* d = new D(); d->m4(); }
4A direct component (has-a field)If A has-a B, A may call B's methods
Forbidden: if A has-a B has-a C, A must never call C through B (a.b.c.someMethod()). Expose the need as a method on B that talks to C ("talk only to immediate friends"). Why: fewer inter-class dependencies = looser coupling — the same goal Facade serves.

Facade vs. Adapter — decide by intent, not UML shape

PatternIntent
FacadeHides/simplifies a subsystem's complexity.
Adapter (L16)Makes two incompatible interfaces interact.

If a wrapper seems to fit both, classify by the problem it was introduced to solve.

Real-world use cases

  • Game engines (Unity): "Start/Load Game" hides asset loading, memory management (load only nearby map regions), physics init, etc.
  • Payment gateway: makePayment() hides balance check, PIN validation, fraud detection, notifications.

Lecture 19: Composite Design Pattern (File System) ▶ Watch

Source: "Composite Design Pattern | Build File System (UML & Code)" · 38 min · Code Army

Foundational vs. specialized patterns

Foundational (L8–17): Strategy, Factory, Singleton, Observer, Decorator, Adapter, Facade, Command — apply to almost any LLD problem. From Composite on, patterns are specialized: each solves one recognizable problem shape. The skill is recognizing the shape.

Shape: tree-structured, part-whole data

Leaf nodes (no children) and composite nodes (contain children, recursively). Example: file system — Folder contains folders/files; File is always a leaf.

Why the naive approach breaks

Naive attemptProblem
Separate File/Folder classes; Folder holds a files list + a folders listLoses insertion order (prints all files, then all folders).
One common list of pointersEvery operation (ls, openAll) needs runtime type if/else (File vs. Folder), duplicated in every new command (e.g. cd, folders only).

The Composite fix

Leaf and composite share one common interface; clients call it uniformly, never checking type. Leaf implementations are terminal; composite implementations loop children and recurse.
  • FileSystemItem (abstract): ls(), openAll(), getSize(), getName(), cd(target), isFolder().
  • File (leaf): ls()/openAll() print own name; getSize() returns own size; cd() returns null.
  • Folder (composite): has-a list of FileSystemItem; ls() lists immediate children; openAll() recurses on children; getSize() sums children recursively; cd(target) finds child folder by name.

root.openAll(): a folder prints its name then calls openAll() on each child; File terminates recursion. The caller never branches on type — tree recursion via polymorphic dispatch instead of a type switch.

"Safe" vs. "transparent" Composite

GoF has two flavors. Transparent: add/remove declared on Component, so leaves have them too (no-op/throw) — max uniformity, but leaves expose meaningless ops. Safe (used here): add() only on Folder — avoids ISP violation, but the client must know it holds a Folder before calling add().

Standard definition

"Composes objects into tree-like structures representing part-whole hierarchies. It lets clients treat individual objects and compositions of objects uniformly."

Composite vs. Decorator

Same "is-a + has-a the shared interface" UML shape. Decorator (L13) wraps exactly one object to add behavior. Composite holds many children (mixed leaf/composite) to form a tree treated uniformly. Decide by what you're modeling.

Real-world use cases / when to use

Nested menus: File → Save As → PDF/Text/… — expandable items are composites, final actions (e.g. "Save As PDF") are leaves. Signal: any tree-shaped data with terminating leaves and recursively-containing composites → Composite.

Lecture 20: Template Method Pattern ▶ Watch

Source: Code Army LLD playlist · "Template Method Pattern"

Specialized pattern: the shape it solves

Like Composite, a specialized pattern: a fixed multi-step process where the step order must never change, but each step's implementation varies per case.

Example: training ML models

Neural net, decision tree, random forest, SVM… all follow the same pipeline in the same order:

  1. Load data — from a path (CSV, images, database…)
  2. Preprocess data — train/test split, normalization, etc.
  3. Train model
  4. Evaluate results
  5. Save model

Step implementations are algorithm-specific; the order is invariant (never train before preprocessing).

Naive risk: each subclass is trusted by convention to call load → preprocess → train → evaluate → save in order; nothing prevents train() before preprocess(). Fix: a pre-built, non-overridable template method in the base class owns the order.

The pattern

  • Abstract ModelTrainer declares steps load(path), preprocess(), train(), evaluate(), save() as abstract/virtual.
  • It also defines the template method trainPipeline(), which calls the steps in fixed order.
trainPipeline() is final (Java) / non-virtual (C++) — no subclass can override the order; subclasses override only individual steps, which the client never calls directly.
  • Order of method definitions in a subclass's source is irrelevant; only trainPipeline() decides runtime order.
  • Client holds a ModelTrainer reference and calls only trainPipeline() — decoupled from the concrete model; execution order guaranteed identical.
  • Steps common to all subclasses can get a shared default implementation in the base class; subclasses override only what varies (often train()/evaluate()), but may still override a default (most-derived override wins).

Standard UML diagram

Runtime sequence: Client.run() → trainer.templateMethod() → step1(), step2(), step3() in fixed order, whether trainer is ConcreteClassA or B. Client sees one call; ordering lives in the base class.

Applied to the ML example

ModelTrainer: template method trainPipeline(); shared defaults for load(), preprocess(), save(); train()/evaluate() abstract. NeuralNetworkTrainer overrides train(), evaluate() and save() (override shadows default). DecisionTreeTrainer overrides only train()/evaluate(). Both run via trainPipeline(); output order is always load → preprocess → train → evaluate → save.

Standard definition

"Defines the skeleton of an algorithm in a method, deferring some steps to subclasses. Template Method lets subclasses redefine certain steps of an algorithm without changing the algorithm's structure." Structure (step order) fixed; step implementation varies per subclass.

Real-world use cases

Payment processing (UPI, credit, debit): validate funds → debit source → credit destination → validate completion → finalize. Order is fixed (can't credit before debit); how validation/debit works differs per method. Signal: fixed, order-sensitive multi-step process with per-case step implementations → Template Method.

Lecture 21: Proxy Design Pattern ▶ Watch

Source: Code Army LLD playlist · "Proxy Design Pattern"

Core idea: a stand-in between client and resource

Client → proxy → real resource, reply relayed back. The proxy exposes the same interface as the resource, so the client can't tell (and needn't know) which one it's talking to. The proxy may validate/transform before forwarding.

Why a proxy instead of editing the resource class?
  • Resource is expensive to construct → create only when needed: Virtual Proxy.
  • Resource is restricted → only authorized users reach it: Protection Proxy.
  • Resource lives on a different server → hide the network call: Remote Proxy.
  • Also: you may lack write access to the class (third-party lib) — a proxy adds behavior without touching its source.

One UML shape for all three types

Proxy is-a shared interface (substitutable for the real resource) and has-a reference to the real resource (to forward calls). Only the intent of the pre-forwarding logic differs.

Type 1 — Virtual Proxy (lazy loading)

Example: ImageDisplay's constructor is expensive (load from disk, compress, filter); wasted if display() is never called.

  • Shared interface IDisplay with display(); implemented by ImageDisplay and ImageProxy.
  • ImageProxy holds an ImageDisplay reference initialized to null (cheap constructor).
  • On first display(): if null, construct the real object, then delegate. Clients only ever get an ImageProxy typed as IDisplay.
Lazy loading trade-off: first call pays the construction latency, but objects never used never consume memory/resources.

Type 2 — Protection Proxy (authorization gate)

Example: IDocumentReader.unlockPdf(file, password), implemented by RealDocumentReader; premium-only. DocumentProxy is-a IDocumentReader, has-a RealDocumentReader and has-a User (isPremium). unlockPdf() checks user.isPremium; delegates if true, else throws/returns "premium only" without touching the real object.

Structurally identical to Virtual Proxy; differs only in intent: Virtual guards an expensive resource from unnecessary construction, Protection guards a restricted resource from unauthorized access.

Type 3 — Remote Proxy (hiding a network call)

Example: real DataService (behind IDataService) on a separate server. DataServiceProxy.fetchData(): if no connection exists, establish it (IP/credentials), call the remote fetchData(), relay the result. Client sees a local-looking object.

Connection can be established eagerly (constructor) or lazily (first call) — lazy makes Remote Proxy the Virtual Proxy idea applied to network resources.

Standard UML diagram (identical shape for all three types)

What varies: only what ProxySubject.operation() does before/instead of delegating — lazy-construct (Virtual), check authorization (Protection), establish remote connection (Remote). One proxy can combine several (e.g. authenticate and remote call).

Standard definition

"The Proxy pattern provides a surrogate or placeholder for another object to control access to it." The surrogate decides what happens before (or instead of) forwarding.

Real-world use cases

  • Protection: login/premium-gated features.
  • Remote: microservices — CartService calls a local UserServiceProxy which makes the network call to the real UserService; effectively what Spring Boot/Django generate for inter-service calls.

Lecture 22: Chain of Responsibility Pattern (ATM Cash Dispenser) ▶ Watch

Source: Code Army LLD playlist · "Chain of Responsibility Design Pattern"

Core idea: a request travels down a chain of handlers

Request goes to R1 (which references R2, which references R3…). Each handler either fulfills it or forwards it to the next; results flow back up to the caller.

Looks like a linked list, but isn't: a list node stores data and all nodes are the same class. A CoR handler processes or delegates a request, and handlers are typically different concrete classes behind a shared interface (₹1000 handler ≠ ₹500 handler). (Just as Composite (L19) only evokes a tree.)

Example: ATM cash dispensing

One handler per denomination (₹1000, ₹500, ₹100…), each tracking its own note count; dispense largest first. Request ₹6000, ₹1000 handler has 5 notes → dispenses ₹5000, forwards remaining ₹1000 → ₹500 handler dispenses 2 notes → success returns up. Client doesn't know how many handlers were involved.

Amount not exactly fulfillable (e.g. ₹150 with ₹1000/₹500/₹100): either dispense the closest amount and report the shortfall, or fail the whole transaction. A use-case decision.

"Next" link belongs on the shared abstract class

Hardcoding a concrete "₹500 handler" reference inside the ₹1000 class couples each handler to its successor; reordering/removing a denomination (e.g. ₹500 demonetized) needs handler code changes.

Fix: abstract MoneyHandler holds nextHandler typed as MoneyHandler, wired via setNextHandler(handler). Concrete handlers don't know their successor; the client assembles the order at setup, so denominations can be added/removed/reordered without touching any handler. OCP (L5): a new ₹50 handler = one new subclass + rewiring.

Standard UML diagram

Self-reference: nextHandler is declared as abstract Handler but holds a concrete instance at runtime, so a handler only knows its successor exposes handleRequest().

Applied to cash dispensing

Each concrete handler (ThousandHandler, FiveHundredHandler…) stores numberOfNotes. handleRequest(amount):
  • notesNeeded = amount / denomination.
  • If notesNeeded > numberOfNotes: dispense all, remaining = amount - numberOfNotes × denomination; else dispense notesNeeded, remaining = 0.
  • If remaining > 0 and nextHandler != null → nextHandler.handleRequest(remaining); if remaining > 0 and no next → throw/report insufficient funds.
Client only calls handleRequest() on the first handler.

Why not one class with if/else per denomination?

Works, but violates OCP (new denomination = edit shared branching, regression risk) and SRP (a validation-rule change for one note, e.g. new ₹500 security pattern, touches code shared by all). One class per denomination isolates changes (only HundredHandler changes for ₹100).

Standard definition

"Allows an object to pass a request along a chain of potential handlers until one of them handles it." Each handler decides: handle now or pass on.

Real-world use cases

  • Logger: INFO / DEBUG / ERROR handlers chained by severity.
  • Leave approval (common interview question): Team Lead if ≤2 days → Manager if ≤5 → Director → else rejected.
  • Signal: "try A; if it can't fully resolve, try B, then C…"

Lecture 23: Build a Payment Gateway System ▶ Watch

Source: Code Army LLD playlist · "Payment Gateway System LLD"

Scope: plug-and-play gateway, not bank internals

In scope: a payment gateway any app (Amazon, Zomato, Uber) integrates. Out of scope: a bank/wallet's internal money movement (Paytm, GPay) — treated as an external system.

Requirements

  • Multiple providers (Paytm, Razorpay…), easy to add new ones → OCP (L5).
  • Fixed flow for every provider: validate → initiate → confirm → Template Method (L20).
  • Error handling + bounded retry on failure (server issue, insufficient funds, network blip).

"Gateway" at the LLD level

Not the HLD "API Gateway". At LLD, a gateway is the layer in your app through which all outbound calls to external servers pass. "Paytm gateway" = the internal class that calls Paytm's banking system, not the external system itself.

Bottom-up UML construction

  • PaymentRequest (DTO): sender, receiver, amount, currency (future-proofs for multi-currency gateways like PayPal).
  • IBankingSystem: processPayment(amount): bool; implemented by PaytmBankingSystem, RazorpayBankingSystem. Black box (third-party); its internals are a separate LLD problem.
  • PaymentGateway (abstract, Template Method): concrete processPayment(request) calls abstract validate → initiate → confirm. PaytmGateway/RazorpayGateway override all three and hold a composition (filled diamond) reference to their banking-system proxy — the link can't outlive the gateway.
Why the gateway can't hold a direct IBankingSystem field: the implementations live on a remote server, not in this codebase, so a field of that type wouldn't compile. Assume a Remote Proxy (L21) in between: a local stand-in doing the HTTP call. Assumed, not drawn.

Standard UML diagram

Where retries go: not client, not PaymentGateway

  • Client: couples it to provider-specific retry counts (Paytm 3, Razorpay 5); every policy change touches client code.
  • PaymentGateway/subclasses: violates SRP (L5) — retrying is distinct from performing the payment.

Fix: PaymentGatewayProxy (Protection Proxy)

PaymentGatewayProxy is-a PaymentGateway and has-a real gateway. Its processPayment() wraps the real one in a retry loop (configurable count); validate/initiate/confirm delegate unchanged.

Why Protection, not Virtual/Remote: nothing is lazily constructed (not Virtual); the Remote proxy is the separate assumed banking layer. This adds a guard/policy before reaching the real object — gating "how many attempts" instead of "is the user authorized".

Factory, Service, Controller

  • GatewayType enum: PAYTM, RAZORPAY.
  • GatewayFactory (Singleton): createGateway(type) builds the concrete gateway but always returns it wrapped in a PaymentGatewayProxy — callers can't bypass retries/future cross-cutting policy.
  • PaymentService (Singleton): holds current PaymentGateway (the proxy); setGateway(gateway), processPayment(request) delegates.
  • PaymentController (Singleton): sole entry point; handlePayment(type, request) → factory → service.setGateway() → service.processPayment() → returns bool.
Why split Controller and Service? Layering: controller = stable entry point/redirect; service = business logic and wiring. Integrating apps only know the controller.

End-to-end call flow

Client → PaymentController.handlePayment(PAYTM, request) → GatewayFactory.getInstance().createGateway(PAYTM) builds PaytmGateway, wraps in PaymentGatewayProxy → PaymentService.getInstance().setGateway(proxy), .processPayment(request) → proxy.processPayment(request) retry-loops PaytmGateway.processPayment(request) → validate → initiate → confirm (Template Method) → initiate calls PaytmBankingSystem.processPayment(amount) (remote-proxy hop) → true/false back up every layer.

Simulation detail

Demo banking systems succeed randomly (Paytm ~20%, Razorpay ~90%) to show the retry proxy retrying until success or exhausting its budget and throwing.

Extensions (homework)

  • Pluggable retry strategies: linear (built) vs exponential backoff.
  • Recurring/subscription payments (YouTube Premium, Netflix) alongside one-off transfers — consider a Template Method flow for it.

Scope: plug-and-play coupon engine for any checkout

Generic coupon/discount engine for checkouts (Zepto, Amazon, Swiggy…) — bank coupons ("10% off with ABC card") and platform coupons ("60% off up to ₹120"). Same plug-and-play style as Notification Engine (L14) and Payment Gateway (L23). Asked in a real LLD interview.

Functional requirements

Lecture 25: Bridge Design Pattern ▶ Watch

Source: Code Army LLD playlist · "Bridge Design Pattern"

Problem: class explosion from two independent dimensions

Cars drive(); types (Sedan, Hatchback, SUV) × engines (Petrol, Diesel, Electric), any combination. Inheritance alone needs one subclass per pair (SedanPetrol, SedanDiesel…) → m × n classes (3 × 3 = 9); +CNG engine = 3 more, +new type = 4 more.

Class explosion: every small change spawns more classes; hard to understand, duplicated code across siblings (breaks DRY), SOLID cracks.

Correction: multiplicative, not "exponential". Two dimensions = m × n (adding one engine adds m classes, linear). Each extra dimension multiplies again (transmission: m × n × k).

Idea: split one concept into two linked hierarchies

  • Abstraction (high-level) — outside view/behavior: car type.
  • Implementation (low-level) — inside mechanism: engine.

Each gets its own hierarchy; the abstraction has-a implementation reference — that link is the "bridge".

Not the OOP meaning: both Car and Engine are abstract, yet Car is "abstraction" and Engine "implementation". In Bridge the words mean outside view vs inside mechanism. Use "abstraction / implementation" in interviews (standard vocabulary).

Car example UML

car.drive() calls engine.start() then does type-specific work. Car doesn't know which engine it holds; Engine has no back-reference. Any engine with any type → m + n classes (3 + 3 = 6 instead of 9). New engine or type = one class, no changes on the other side.

Standard UML

ConcreteAbstraction.execute() calls imp.implement(). GoF name for concrete high-level classes: Refined Abstraction.

Standard definition

"Bridge decouples an abstraction from its implementation so that the two can vary independently." Abstraction = high-level layer (Car); implementation = low-level layer (Engine).

Code walkthrough (C++)

  • Implementation: abstract Engine, pure virtual start(); PetrolEngine ("starting with ignition"), DieselEngine, ElectricEngine ("powering up silently").
  • Abstraction: abstract Car with Engine* (constructor-injected), pure virtual drive(). Sedan::drive() = engine->start() + "driving a sedan on the highway"; SUV::drive() likewise.
  • main: Sedan(petrol), SUV(electric), SUV(diesel); drive() each → engine start message paired with car message.

Bridge vs Strategy — same UML, different intent

As Strategy (L8): Engine = strategy, Petrol/Diesel = algorithms, Car = client (cf. L8's robots with NoFly/FlyWithWings/FlyWithJet). Structure identical; intent differs.

Same shape, different reason for existing

Why the car example is Bridge: you don't swap a live SUV's petrol engine for diesel; the goal is to build any pair and add types/engines freely. When patterns look alike, ask what each is for — they share the goal of loose coupling.
Nuance: Bridge doesn't forbid runtime implementor changes (GoF), so fixed-vs-swappable is a tendency. Another signal: in textbook Bridge the implementor offers low-level primitives that the abstraction combines (Window.drawBorder() from imp.drawLine() calls); the car's drive() just calls start(), hence the Strategy look-alike.

Real-world use cases

  • Remotes × TVs: remote (standard, touch, Netflix-button) = abstraction; TV (LCD, LED, OLED) = implementation; any pairs with any.
  • GUI widgets × OS (classic GoF): TextBox/Dropdown/RadioButton = abstraction; Windows/macOS/Linux rendering = implementation.
  • Notification type (alert, reminder) × channel (email, SMS, push); shape × rendering backend.

When to reach for Bridge

Class names like <Dimension1><Dimension2> (SedanPetrol, WindowsTextBox) signal two independent axes. Extract one axis into its own hierarchy referenced by the other: m × n → m + n.

Lecture 26: Build Zepto (Quick Commerce / Inventory Management) ▶ Watch

Source: Code Army LLD playlist · "Design Zepto / Blinkit — 10-minute delivery LLD"

Quick commerce vs food delivery

Unlike Zomato (Lecture 11; one restaurant per order), Zepto/Blinkit keep stock in many nearby dark stores (online-only warehouses). If the nearest store lacks some items, the order is split across stores, each part with its own delivery partner. This is effectively the answer to "design an inventory management system".

Functional requirements

  • Manage inventory: add/remove products across categories.
  • Replenishment strategies: threshold-based or weekly; new ones must be addable.
  • Multiple inventory store types (e.g. DB-backed), extensible.
  • User sees items from all dark stores within 5 km.
  • If one store can't fulfil, split across several dark stores, one delivery partner per part.

Payments out of scope (Lecture 23's gateway could plug in). Happy flow: open app → see nearby items → add to cart → place order → assign one or more partners → deliver.

Bottom-up UML

  • Product (POJO) — sku, name, price. SKU (Stock Keeping Unit) = unique product ID in inventory systems.
  • ProductFactory — createProduct(sku), avoids scattered new Product(...). Demo hardcodes a catalog (1001 Apple ₹20, 1002 Banana ₹10, 1003 Chocolate ₹50, 2001 T-shirt ₹500, 2002 Jeans ₹1000; else ₹100 "Item"); real one loads from DB.
  • InventoryStore (abstract) — declares what: addProduct(product, qty), removeProduct(sku, qty), checkStock(sku), listAvailableProducts(); how is left to subclasses.
  • DbInventoryStore — instead of a vector<Product> (linear scan on every check of frequently-changing stock), two maps keyed by SKU: stock: map<sku, quantity> and products: map<sku, Product> (avoids re-calling the factory).
DbInventoryStore operations:
addProduct: if the SKU is new, store the Product in products; then add qty to stock[sku].
removeProduct: remaining = stock[sku] - qty; if remaining > 0 update it, otherwise erase the SKU from stock.
checkStock: stock[sku], or 0 if absent.
listAvailableProducts: every SKU with quantity > 0 that also exists in products.
Correction: std::map isn't O(1):
std::map is a balanced tree → O(log n); std::unordered_map / Java HashMap → O(1) average. Either beats a list scan.
"DbInventoryStore" but uses maps?
LLD focuses on class structure, not SQL. To persist: abstract Persistence with save() (SqlPersistence/MongoPersistence, as in Lectures 5–6); DbInventoryStore holds a Persistence and calls save() after updating its maps.

InventoryManager — holds an InventoryStore; addStock(sku, qty), removeStock(sku, qty), checkStock(sku), getAvailableProducts(). Dark store talks only to the manager.

Manager vs store — not a DRY violation:
The manager delegates: knows what; store knows how. It also does non-store work: addStock gets the Product from ProductFactory then calls store.addProduct(product, qty); validations live here. Store stays a "dumb" data holder; dark store stays loosely coupled.
Why InventoryManager is NOT a Singleton:
Each dark store needs its own manager (50 stores → 50 managers); a Singleton would share one inventory. (A single shared manager is possible, but every call must then carry the store.) Always be able to justify why something is/isn't a Singleton.

ReplenishStrategy (Strategy, Lecture 8) — replenish(manager, itemsToReplenish: map<sku, qty>).

  • ThresholdReplenishStrategy(threshold) — per SKU, if manager.checkStock(sku) < threshold → manager.addStock(sku, qtyToAdd).
  • WeeklyReplenishStrategy — demo only prints; real one runs on a weekly schedule.

DarkStore — name, x, y, an InventoryManager, a ReplenishStrategy.

  • distanceTo(ux, uy) — distance formula to the user.
  • runReplenishment(items) — strategy.replenish(inventoryManager, items).
  • Delegate methods (addStock, removeStock, checkStock, getAllProducts) forwarding to the manager.
Why DarkStore repeats the inventory methods:
Avoids darkStore.getInventoryManager().checkStock(sku) — violates the Principle of Least Knowledge (Law of Demeter): talk only to immediate friends. Caller → dark store → manager → store.

DarkStore–InventoryManager is composition: the dark store's constructor creates its manager (with new DbInventoryStore()).

Trade-off:
Hardcoding new DbInventoryStore() in DarkStore is tight coupling. Fix: InventoryStoreFactory taking an enum (DB, FILE, …). Skipped since only one store type exists — acceptable if stated.

Where's the Bridge? (InventoryManager ↔ InventoryStore)

Manager (high level: what) holding an abstract store (low level: how) is a "modified" Bridge (Lecture 25): new store types need no manager changes, and manager types could grow later. The abstraction side has only one class for now.

More precise interview framing:
With one manager class it's really Dependency Inversion (Lecture 6), and InventoryStore is essentially the Repository pattern (abstract data access, swappable backends). It becomes a true Bridge only once the manager side has its own hierarchy.

Nearby stores, users and orders

  • User — name, ux, uy, Cart (composition). Cart — items: vector<pair<Product, qty>>; addItem(sku, qty) (via factory), getTotal() (Σ price × qty), getItems(). DeliveryPartner — name. Kept minimal: the focus is inventory.
  • DarkStoreManager (Singleton) — holds all stores; registerDarkStore(ds); getNearbyDarkStores(ux, uy, maxDistance): filter by distanceTo ≤ maxDistance (5 km), sort by distance, nearest first. Plain association to DarkStore (aggregation arguable if stores outlive the manager).
  • Order — orderId (static nextId++), user, items: vector<pair<Product, qty>>, partners: vector<DeliveryPartner> (list: split orders have several), totalAmount.
  • OrderManager (Singleton) — placeOrder(user, cart), getAllOrders(). Cart passed separately (Least Knowledge); DarkStoreManager reached via getInstance().
  • Zepto (orchestrator, like Tomato) — initialize() seeds stores; showAllItems(user) lists products from stores within 5 km.

placeOrder — the splitting algorithm

Step by step:
1. nearby = DarkStoreManager.getInstance().getNearbyDarkStores(user.x, user.y, 5); if empty → "no dark store near you."
2. requested = cart.getItems().
3. Fast path: check whether the nearest store has every item in the required quantity (checkStock(sku) ≥ qty for all). If yes → removeStock for each item, copy items into the order, total = cart.getTotal(), assign one partner, done.
4. Split path: build remaining: map<sku, qty>. For each nearby store, nearest first (stop early once remaining is empty):
  • for each (sku, needed) in remaining: avail = store.checkStock(sku); skip if 0; taken = min(avail, needed); store.removeStock(sku, taken); add (product, taken) to the order; if needed > taken reduce remaining[sku], else put the SKU in toErase; mark assigned = true.
  • after the inner loop, erase every SKU in toErase from remaining (erasing while iterating the same map would break the loop — hence the separate list).
  • if assigned → add a new delivery partner for this store.
5. Anything still in remaining → report "could not fulfil," but still deliver the rest.
6. Recompute the total from the items actually in the order (it may differ from the cart total), print the summary, and store the order.

Gaps worth raising in an interview

  • Greedy nearest-first isn't minimal. Only the nearest store is checked for full fulfilment; if store 2 alone could fulfil, it still splits. Better: first find any nearby store that fulfils all, then split. (Exact partner minimisation = set cover → heuristics.)
  • Race conditions on stock. checkStock + removeStock isn't atomic → two users promised the last banana. Need a per-store lock or atomic "reserve" (released if the order fails). Static nextId++ isn't thread-safe either.
  • Straight-line distance. Euclidean on x/y; real apps use lat/long (haversine) and, for a 10-min promise, road travel time.
  • ProductFactory is really a catalog lookup. Calling it per addStock/addItem duplicates Product objects per SKU; a catalog/repository returning a shared instance fits better.
  • Replenishment never auto-triggers; needs a scheduler (weekly) or a hook after removeStock (threshold) calling runReplenishment.

Lecture 27: Build Tinder (Dating App LLD) ▶ Watch

Why it's asked

Dating/matrimonial apps test algorithms beyond class structure: recording swipes, detecting a match, computing a match score. Many small objects (profile, preference, interest, location, message, chat room), simple interactions.

Functional requirements

  • Swipe left/right on a profile.
  • Profile: name, age, gender, bio, photos, interests.
  • Preferences: genders, age range, max distance, desired interests.
  • On a match, the two users get a chat room.
  • See profiles nearby (e.g. 5 km), via pluggable strategies (e.g. one that hides blocked users).
  • Notify on new match / new message.
  • Matching combines several factors (basic compatibility, interests, location) into a score.

NFRs: scalable, loosely coupled. Happy flow: profile set up → shown nearby profiles → swipe → mutual RIGHT = match → both notified, chat room opens → messages trigger notifications.

Top-down instead of bottom-up

Start with the big object (User) and discover the small objects it needs while filling it in.

When top-down:
Bottom-up tends to miss small classes (Interest, Gender, Location) and turns everything into strings ("location = 'lat,long'"). Writing User first exposes them. Rule of thumb: many small objects → top-down; otherwise (most questions) bottom-up works. Neither is wrong.

Notifications — a tweaked Observer (Lecture 12)

NotificationService — the observable; Singleton.

  • observers: map<userId, NotificationObserver> instead of a list.
  • registerObserver(userId, observer); removeObserver(userId) (ID suffices, map is keyed by it).
  • notifyUser(userId, msg) — new: targeted notification (a match concerns only two users, so no broadcast).
  • notifyAll(msg) — classic broadcast.

NotificationObserver (abstract) — update(message); UserNotificationObserver prints it. Abstract so loggers/event publishers can observe later.

Two deliberate deviations from textbook Observer:
(1) No abstract + concrete observable: add/remove/notify written directly in NotificationService — only one notification service will ever exist. (2) User's constructor creates its UserNotificationObserver and registers it with NotificationService.getInstance() (as in Lecture 18) — hardcoded type, acceptable since it won't change.

User and its small objects

User — id, profile: UserProfile, preference: Preference, swipeHistory: map<userId, SwipeAction>, notificationObserver.

  • swipe(targetUserId, action) — records into history.
  • hasLiked(id) (present and RIGHT), hasDisliked(id) (present and LEFT), hasInteractedWith(id) (present).
  • displayProfile() → profile.display().
  • UserProfile — name, age, gender: Gender, bio, photos: vector<string> (URLs; images in S3), interests: vector<Interest>, location: Location, display(), add/remove interest.
  • Gender (enum) — MALE, FEMALE, NON_BINARY, OTHER. Interest — name, category. SwipeAction (enum) — LEFT, RIGHT (the map is the history; each entry is a swipe).
  • Location — latitude, longitude, distanceInKm(other) using the haversine formula (great-circle distance); keeps lat/long + distance logic together.
  • Preference — what the user wants in others: interestedIn: vector<Gender>, minAge, maxAge, maxDistance, interests: vector<string>; isInterestedInGender(g), isAgeInRange(age) (minAge ≤ age ≤ maxAge), isDistanceAcceptable(d).
Composition, and least knowledge:
UserProfile, Preference can't exist without User → composition; User's destructor deletes profile, preference, observer and unregisters from NotificationService. Use user.displayProfile(), not user.getProfile().display() (Least Knowledge).

Nearby users — LocationService + Strategy (Lecture 8)

  • LocationStrategy (abstract) — findNearbyUsers(location, maxDistance, allUsers). BasicLocationStrategy: keep users with distanceInKm ≤ maxDistance.
  • LocationService (Singleton) — holds a strategy, setStrategy(s), findNearbyUsers(...) delegates. New strategies (skip blocked users, extra validations) plug in without changes.

Match scoring — a chain of matchers

A plain Strategy would score on one factor only; real apps combine basic compatibility + interest overlap + proximity into one score ("90% match").

Matcher (abstract) — calculateMatchScore(user1, user2) : double (takes Users, needs their details). Three subclasses, each hard-linked to the next:

LocationBasedMatcher → InterestBasedMatcher → BasicMatcher:
BasicMatcher — the gatekeeper. Returns 0.0 immediately if either user isn't interested in the other's gender, if either's age is outside the other's range, or if the distance is outside either's max distance. If all pass → 0.5 (an arbitrary "you're at least 50% compatible" baseline).
InterestBasedMatcher — creates a BasicMatcher, gets base. If base == 0 → return 0 (no point continuing). Otherwise count shared interest names between the two profiles; maxInterests = max(size1, size2); bonus = 0.5 × shared / maxInterests (0 if maxInterests is 0). Returns base + bonus.
LocationBasedMatcher — creates an InterestBasedMatcher, gets base; 0 → return 0. Otherwise proximity bonus = 0.2 × (1 − distance / maxDistance) (0 if maxDistance is 0): distance 0 gives the full 0.2, and it shrinks as distance grows. Returns base + proximity.

Calling the outermost matcher runs the chain recursively (Location → Interest → Basic, scores flow back up); you can also start lower. MatcherType (BASIC, INTEREST, LOCATION) + MatcherFactory.createMatcher(type) returns the entry point (default BasicMatcher).

Corrections on scoring:
It adds, not averages: 0.5 + up to 0.5 + up to 0.2 → max 1.2, not 1.0. Normalise (÷ 1.2) or re-weight for a real percentage.
Preference.interests is never used — the bonus compares the two profile interest lists.
Is it really Chain of Responsibility?
Lecture calls it a "tweaked" CoR, not Decorator. But classic CoR (Lecture 22): request passes until one handler handles it, next handler injected. Here every link runs and adds to the wrapped result, and the next link is created with new inside the method → closer to a hardcoded Decorator/pipeline (only the early return 0 is CoR-like). Cleaner: inject the inner matcher (new LocationMatcher(new InterestMatcher(new BasicMatcher()))) so the factory composes any order, or sum weighted scores from a list of scorers.

Chat

  • Message — senderId, content, timestamp (time_t / Java Instant/LocalDateTime), getFormattedTime().
  • ChatRoom — id, participantIds: vector<string> (list, so group chat is possible later), messages: vector<Message> (one-to-many); addMessage(senderId, content), hasParticipant(id), getMessages(), displayChat().

DatingApp — orchestrator (Singleton)

Holds users, chatRooms, a matcher.

  • createUser(id), getUserById(id), setMatcher(m).
  • findNearbyUsers(userId, maxDistance = 5) — ask LocationService for users in range; exclude self; skip users already interacted with; keep only score > 0 (passes basic criteria). Location service returns all nearby; filtering happens here.
  • swipe(userId, targetId, action) — null-check both, user.swipe(targetId, action); if action == RIGHT and target.hasLiked(userId) → match: create ChatRoom with ID userId + "_" + targetId, store it, notifyUser both.
  • getChatRoom(id1, id2) — room or null.
  • sendMessage(senderId, receiverId, content) — no room → error; else addMessage + notifyUser(receiverId, "New message from …").
  • displayUser(id), displayChatRoom(id1, id2) — console output.

Lecture 28: Builder Design Pattern (Simple, Director & Step Builder) ▶ Watch

Source: Code Army LLD playlist · "Builder Design Pattern — simple builder, builder with director, step builder"

The problem: building a complex object

new Target(t1, t2, t3, …) gets messy with many fields, several optional. Unlike Singleton (Lecture 10; one instance), Builder allows any number of instances — it makes construction easy and safe. Most commonly used creation pattern in real code.

Running example — HttpRequest: url, method (GET/POST/PUT/PATCH/DELETE), headers (map, e.g. Content-Type: application/json), queryParams (map), body, timeout; execute() sends it.

Four problems without a builder

1. Constructor telescoping (overloading):
One all-fields constructor forces dummy values, so you add (url), (url, method), (url, method, timeout)… — demo has 1- through 6-arg constructors with defaults (GET, 30 s). Every new field adds constructors; long same-typed argument lists are easy to misorder.
2. Mutability:
Setters let anyone change the object after creation. Removing them brings back problem 1.
3. Inconsistent state:
"Required in constructor, optional via setters" avoids telescoping, but nothing forces setters before execute(); a missing setBody() fails at runtime, not compile time.
4. Scattered validations:
The object may be half-built, so every user (execute(), …) must null-check fields.

The fixes conflict: no setters → telescoping; setters → mutability + inconsistent state; validation needed everywhere regardless.

1) Simple Builder

A Builder class sits between client and target and returns a finished, valid object; single responsibility: create one kind of object.

  • Target (HttpRequest): private constructor, no setters, keeps execute(); C++ friend class HttpRequestBuilder; grants field access.
  • Builder (HttpRequestBuilder) holds req:
    • Intermediate methods — withUrl(u), withMethod(m), withHeader(k, v), withQueryParam(k, v), withBody(b), withTimeout(t); each sets a field and return this;.
    • Terminal method — build(): all validations in one place (e.g. empty URL → throw), returns HttpRequest.
Why "return this" enables chaining:
Each with… returns the builder, so calls chain (repeat withHeader as needed); only build() returns HttpRequest. Omitting .build() in HttpRequest r = new HttpRequestBuilder().withUrl(u); is a compile error (no conversion from builder to target).

HttpRequest req = HttpRequestBuilder()
  .withUrl("https://api.example.com")
  .withMethod("POST")
  .withHeader("Content-Type", "application/json")
  .withQueryParam("key", "12345")
  .withBody("{\"name\": \"Aditya\"}")
  .withTimeout(60)
  .build();

Fixes: no telescoping (new field = one new with method); validation centralised in build(); no setters on the result (to change, build a new one); readable call. Missing required fields are still a runtime exception, but in one known place before use (demo: "Body is empty" from build()).

Correction: the lecture's builder isn't really immutable:
The builder keeps a pointer to the same req it returned, so builder.withUrl("other") after build() mutates the built request. Fix: builder keeps its own field copies; build() creates a new target via private constructor (new HttpRequest(this)), with final/const fields and copied collections. Each build() yields an independent object.
Java: static nested Builder, not package access:
Java has no friend; package-private fields expose them to the whole package. Standard idiom: public static class Builder nested in the target (can call the private constructor): new HttpRequest.Builder().url(u).build(). Real examples: Java 11 HttpRequest.newBuilder().uri(...).GET().build(), StringBuilder, Lombok @Builder. Languages with named/default args (Kotlin, Python) need builders less.

2) Builder with Director

A Director stores frequently-used configurations as methods and drives the builder — reusable builds/presets.

  • HttpRequestDirector::createGetRequest(url) → builder.withUrl(url).withMethod("GET").build().
  • HttpRequestDirector::createJsonPostRequest(url, jsonBody) → URL, POST, Content-Type and Accept: application/json, body, build().

Methods are static; clients can still use the builder directly. UML: Client → Director → Builder(s) → Target.

Classic (GoF) Director differs:
GoF Director receives a builder via an abstract builder interface and runs the same step sequence; a different concrete builder yields a different representation (e.g. HTML vs PDF). The lecture's static presets are closer to static factory methods over one builder — know both for interviews.

3) Step Builder

Simple builder allows any order and skipping (.withUrl(u).withBody(b).withMethod(m).build() compiles). Some objects need a fixed order (pizza: crust → sauce → toppings → cheese). Step builder gives:

  • Construction step by step, in order.
  • Required fields enforced by the compiler (no if (empty) throw in build()); optional fields still in any order.
How it works:
One interface per required step (pure abstract class in C++), each returning the next step's interface:
UrlStep.withUrl(url) → MethodStep
MethodStep.withMethod(m) → HeaderStep
HeaderStep.withHeader(k, v) → OptionalStep
OptionalStep.withBody(b) / withTimeout(t) → OptionalStep, and OptionalStep.build() → HttpRequest

One concrete HttpRequestStepBuilder implements all interfaces (multiple inheritance in C++; implements A, B, C, D in Java). Each method still return this;, but the declared return type is the next interface. Static getBuilder() returns new HttpRequestStepBuilder() typed as UrlStep.

IDE autocompletes only the next step's method; .withMethod("POST").withBody(...) → compile error "class HeaderStep has no member withBody". At OptionalStep, add body/timeout in any order or call build(). To make every field mandatory, give each its own step and put build() in a final BuildStep.

Why it works: reference type limits callable methods:
A parent-type reference to a child object exposes only the parent's methods. The object is always the full builder; the returned interface type decides what's visible. Only pattern in the course deliberately using multiple inheritance (of interfaces, which Java allows).

Definition & comparison

Standard definition:
Builder separates the construction of a complex object from its representation, so the same construction process can create different representations. Assembly steps live in the builder (and director), not in the object's constructors, so they vary independently.
The three flavours
FlavourAddsStill missing
Simple BuilderNo telescoping, centralised validation, no setters on the result, readable chainsOrder and required fields only checked at runtime in build()
Builder + DirectorReusable presets for common configurationsSame as simple builder for custom builds
Step BuilderFixed order and required fields enforced at compile time; optional fields still freeMore interfaces/boilerplate; order is rigid

Worth knowing

  • Don't overuse. 2–3 required fields → plain constructor is clearer. Use Builder for many (optional) params, invariants to validate, or immutability.
  • Required fields can go in the builder's constructor (new Builder(url, method)) — lighter than a step builder.
  • Builders aren't thread-safe; one builder per object, one caller.
  • Step-builder interfaces grow per required field; worth it when order/completeness really matter (SDKs/public APIs).

Lecture 29: Iterator Design Pattern ▶ Watch

Source: Code Army LLD playlist · "Iterator Design Pattern — design your own iterator"

Every collection is traversed differently

"Design your own iterator" is a common LLD question. Traversal differs per structure:

  • Linked list — temp = head; while (temp != null) { … temp = temp.next; }
  • Binary tree — level order, or inorder / preorder / postorder.
  • Playlist (Lecture 18) — depends on storage: vector (index loop), linked list, map…

Why not loop inside the class?

If Playlist (vector<Song>) loops directly in playEntirePlaylist(), getSongByName() etc., switching storage to a linked list forces rewriting every looping method.

Principle: separate traversal from business logic:
Playlist should know what to do with songs, not how to walk storage — mixing them breaks SRP (Lecture 5). A separate Iterator offers:
• hasNext() — is there another element?
• next() — return the next element and advance.
Methods use while (it.hasNext()) { s = it.next(); … }; changing storage only swaps the iterator (VectorIterator → LinkedListIterator).

Cost: slight verbosity, which languages hide behind for-each loops.

The pattern

  • Iterator<T> (interface) — hasNext() : bool, next() : T; generic since element type varies (int, Song).
  • Iterable<T> (interface) — getIterator() : Iterator<T>.
  • Concrete iterables — LinkedList (data, next), BinaryTree (data, left, right), Playlist (vector<Song>; Song = title + artist). getIterator() passes this: return new LinkedListIterator(this);
  • Concrete iterators — hold the collection reference + current position; know how to walk that structure.
The three concrete iterators:
LinkedListIterator — field current (starts at the head).
  hasNext(): return current != null;
  next(): val = current.data; current = current.next; return val;

BinaryTreeInorderIterator — iterative inorder with a stack (recursion can't pause after each element).
  constructor: pushLeft(root) — push the node and keep going left until null.
  hasNext(): return !stack.empty();
  next(): node = stack.top(); stack.pop(); pushLeft(node.right); return node.data;
  Preorder/postorder/level-order iterators are separate classes built the same way.

PlaylistIterator — fields songs (the vector) and index = 0.
  hasNext(): return index < songs.size();
  next(): return songs[index++];
Correction: hasNext = current.next != null skips the last node (1 → 2 → 3 prints 1, 2). Correct: current != null ("any element not yet returned?"). next() returns the value (data), not the node.

Demo: list 1→2→3 → 1 2 3; tree (root 2, left 1, right 3) inorder → 1 2 3; playlist prints title + artist. Same loop shape: it = x.getIterator(); while (it.hasNext()) print(it.next());

Standard UML: concrete iterable creates its concrete iterator; the iterator holds a reference back to its aggregate (arrows both ways).

Standard definition:
Iterator provides a way to access the elements of an aggregate object sequentially without exposing its underlying representation. Aggregate = any object holding many values (list, tree, playlist). Client knows only hasNext()/next().

Worth knowing

  • Real languages. Java: java.util.Iterator (hasNext, next, optional remove) + Iterable (for-each). C++ STL: begin()/end(), *it, ++it (range-for). Python: __iter__/__next__.
  • Beyond SRP: multiple simultaneous iterators with independent positions; multiple traversal orders without changing the collection.
  • Modifying while iterating: Java throws ConcurrentModificationException; C++ may invalidate iterators (UB).
  • Tree iterator cost: O(h) stack memory; next() amortised O(1) (LeetCode 173, "BST Iterator").
  • C++ demo memory: getIterator() returns a raw new-ed pointer → leak; return unique_ptr or by value.
  • next() when hasNext() is false dereferences null in the demo; real iterators throw (NoSuchElementException).

Homework / extensions

Add hasPrevious()/previous() to every iterator (one bidirectional getIterator(), or getForwardIterator()/getReverseIterator()). Hints: singly linked list can't step back cheaply (doubly linked list or stack of visited nodes); reverse inorder = mirror (push right, then go left). Java's ListIterator has hasPrevious/previous.

Lecture 30: Flyweight Design Pattern ▶ Watch

Source: Code Army LLD playlist · "Flyweight Design Pattern — saving RAM by sharing objects"

Millions of small objects eat RAM

Flyweight saves memory (RAM) when an app creates huge numbers of similar objects: create once, reuse/share. Interview cue: "is RAM a constraint? should these objects be lightweight?"

Example — asteroid shooter game. Each asteroid:

  • length, width, weight (int), color, texture, material (string)
  • posX, posY, velocityX, velocityY

~196 bytes each; 1 million (10 lakh) ≈ 187 MB.

Intrinsic vs extrinsic state

Size/weight/color/texture/material come from a small fixed set (e.g. length ∈ {10, 20, 30}, color ∈ {red, green, blue}), so many asteroids are identical in those; position and velocity differ per asteroid.

Split every object into two parts

Where the saving comes from:
Still a million AsteroidContexts, but each is 4 ints + 1 pointer; heavy strings exist once per kind. Saving ≈ (intrinsic size) × (objects − unique flyweights).
Classify by meaning, not coincidence:
Demo gives every asteroid velocity (1, 2), but velocity is still extrinsic. Ask: does it belong to the kind of thing or this particular thing?

The three pieces

  • AsteroidFlyweight — intrinsic fields only (constructor-set); render(posX, posY, vx, vy) takes extrinsic state as parameters.
  • AsteroidContext — posX, posY, velocityX, velocityY + flyweight pointer; render() calls flyweight->render(posX, posY, velocityX, velocityY). Client sees only contexts.
  • AsteroidFactory (flyweight factory) — reuses instead of creating; static unordered_map<string, AsteroidFlyweight*> pool.
AsteroidFactory::getAsteroid(length, width, weight, color, texture, material):
1. Build a key from all intrinsic values with a separator: "25_25_250_Red_Rocky_Iron" (_, | or , — anything that makes it unique).
2. If the key isn't in the pool → pool[key] = new AsteroidFlyweight(...).
3. Return pool[key] — the shared object, new or existing.
Helpers: getFlyweightCount() (pool size = number of unique flyweights), getTotalFlyweightMemory(), cleanup() (clears the pool).
Flyweights must be immutable:
Many contexts share one flyweight; mutating it changes all of them. Intrinsic fields const/final, no setters — treat as required.

Standard UML: extrinsic context holds a flyweight (intrinsic state); FlyweightFactory keeps a map and getFlyweight(key) returns existing or creates.

Demo: with vs without flyweight

spawnAsteroids(count): type = i % 3 picks one of (Red, Rocky, Iron, 25), (Blue, Metallic, Stone, 35), (Grey, Icy, Ice, 45); weight = size × 10; position (100 + i×50, 200 + i×30); velocity (1, 2). renderAll() prints first 5.

Standard definition:
Flyweight uses sharing to support large numbers of fine-grained objects efficiently. Intrinsic state is shared and stored in the flyweight; extrinsic state is supplied by the client (kept in a separate context).

Real-world uses

  • Open-world games (GTA) — identical trees/cars/pedestrians share model/texture/animation; only position/state differ. Paired with GPU instanced rendering.
  • Text editors (classic) — millions of characters, few dozen glyphs: share one object per glyph; position and formatting are extrinsic.
  • Languages — Java Integer.valueOf() caches −128…127; string literals interned: shared immutable instances.

Worth knowing

  • Only worth it when objects are very many, most state is shareable, and unique combinations are few (3 values × 5 fields ≤ 35 = 243; demo ties them to 3).
  • Trade-off: memory vs CPU/complexity — key building + hash lookup per creation, extrinsic state passed every call. A struct key with custom hash avoids string concatenation.
  • Not Singleton, not object pool. Singleton = one instance per class. Flyweight = one shared instance per unique intrinsic state, used by many at once. Object pool lends mutable objects to one user at a time and takes them back.
  • Factory's static map keeps flyweights alive until cleanup() and isn't thread-safe; lock it (or pre-create flyweights) for multi-threaded spawning.

Lecture 31: Build Splitwise Clone (Expense Sharing) ▶ Watch

Why it's asked

Expense sharing: someone pays, cost is split, balances tracked, settled later. Tests group management, blocking leave until settled, pluggable split types, and debt simplification (fewest payments).

Functional requirements

  • Join / leave a group; can't leave without settling all balances in it.
  • Add expense in a group ("U1 paid ₹800, split among U1–U4").
  • Settle (U2 pays U1 back) — only recorded; real transfer happens in Paytm/GPay.
  • Split strategies: equal (₹800/4 = ₹200), percentage, exact/unequal; new ones must be addable.
  • Individual expenses outside any group (one-on-one).
  • All group members notified on add/settle (Observer).
  • Enhancement: simplify debts (greedy).

Bottom-up UML

IDs everywhere: users/groups/expenses looked up by string ID → map<id, …>. Demo uses a static counter ("user" + ++nextUserId); real app: DB auto-increment or UUID.

  • userId, name, email

  • update(msg) prints (real app: notification engine).
  • updateBalance(other, amount) — balances[other] += amount; erase if abs < 0.01 (double).
  • getTotalOwed() (sum of negatives), getTotalOwing() (sum of positives).

  • EqualSplit — total / userIds.size() each.
  • ExactSplit — Split(userIds[i], values[i]).
  • PercentageSplit — Split(userIds[i], total × values[i] / 100).

Concrete observable; no abstract observable since there's only one (SRP cost of Observer accepted). Holds Users, not Observers (no casting); switch to Observer if e.g. a logger must listen.

Plus settleIndividualPayment, showUserBalance.

Debt simplification (greedy)

Group: Aditya, Rohit, Manish, Saurabh.

  • E1 — Aditya paid ₹800, equal among 4 → Rohit, Manish, Saurabh owe Aditya ₹200 each.
  • E2 — Manish paid ₹700, exact: Aditya 200, Saurabh 200, Manish 300 → Aditya, Saurabh owe Manish ₹200.

Manish↔Aditya ₹200 cancels in the map → 3 payments: Rohit→Aditya, Saurabh→Aditya, Saurabh→Manish (200 each).

Algorithm:
1. Net per person — for each positive entry [creditor][debtor] = x: net[creditor] += x; net[debtor] -= x (skip negatives: each debt is stored as +x and −x).
  Aditya +400, Manish +200, Saurabh −400, Rohit −200.
2. Creditors (net > 0) / debtors (net < 0), each sorted descending.
3. Greedy two-pointer — biggest creditor vs biggest debtor; pay = min(credit, debt); record; subtract; advance whichever hits 0.
  Saurabh → Aditya ₹400; Rohit → Manish ₹200.
4. Rebuild the balance map from payments.
Result: 3 → 2 payments.

Demo run

  1. 4 users + "Hostel" group; all notified of both expenses.
  2. Balances: Rohit owes Aditya 200; Saurabh owes Aditya 200 and Manish 200.
  3. Simplify → Saurabh owes Aditya 400; Rohit owes Manish 200.
  4. Individual: Rohit pays ₹40 coffee for himself + Saurabh (equal) → Saurabh owes Rohit ₹20 in individual sheets.
  5. Rohit tries to leave → rejected (owes Manish 200).
  6. Rohit settles ₹200 with Manish → leaves. Final: Saurabh owes Aditya ₹400.
Coffee amount: narration says ₹40, but a ₹40 equal split between two is ₹20 each → expected ₹20 (₹40 only with an exact split).

Gaps worth raising in an interview

  • Greedy isn't always minimal. ≤ (people − 1) payments, used by real apps; true minimum is NP-hard (subgroups with zero-sum nets, subset-sum-like).
  • Don't store money as double (0.1 + 0.2 != 0.3 → abs < 0.01 hacks). Use integer paise/cents or BigDecimal.
  • Rounding: ₹100/3 = 99.99; give leftover paisa to one person (e.g. payer) so splits sum to total.
  • Validate splits: percentages sum to 100, exact sums to total, userIds/values same length (TODOs in lecture).
  • Skip payer's own share — updateGroupBalance(A, A, x) is harmless but creates a self-entry.
  • Simplification rewrites who owes whom (Saurabh never owed Aditya ₹400 directly). Keep expense history intact; make it optional (Splitwise allows turning it off).
  • Group vs individual balances are separate; real app shows totals across all. Leaving checks only that group.
  • Individual expenses send no notification — add notifyUser(id) (homework).
  • Concurrent adds/settlements on a group need locking or a DB transaction around balance updates.

When to use

Object with a finite set of states and finite set of operations; each operation either transitions state or leaves it unchanged, and the same operation behaves differently per state.

The design

  • VendingState (abstract) — one method per operation, each takes the machine and returns the next state: insertCoin(machine, coin), selectItem(machine), dispense(machine), returnCoin(machine), refill(machine, qty), getStateName().

Standard definition:
State allows an object to alter its behaviour when its internal state changes. The object will appear to change its class.
Replaces: a big if/else/switch on current state in every method (adding a state = editing every method). With State, each state's rules live in one class.

Real-world uses

  • Vending machine (common interview Q; homework: card/UPI payment, item codes, change-return state).
  • Document workflow — Draft → Published → Archived → Deleted.
  • ATM — Idle → card inserted → PIN validated → transaction → dispensing (dispenser itself = CoR, L22).
  • Order status, traffic lights, media players, TCP connections.

Worth knowing

  • State vs Strategy — identical class diagrams; differ in intent: Strategy = client picks algorithm, doesn't change itself; State = states decide transitions.
  • Return next state vs context.setState() (GoF) — both work; returning keeps transitions explicit and the context in control.
  • States can be shared — stateless (data lives in machine), so pre-create and reuse; even across machines (flyweight-like, L30).
  • New operation touches every state (OCP cost); new state is cheap. Base class with default "not allowed" impl → states override only what they support.
  • States and context reference each other → C++ needs forward declarations.

Lecture 33: Build Tic Tac Toe Game ▶ Watch

Requirements

  • Scalable board — any n×n.
  • Standard rules, extensible — win = full row/column/diagonal; draw = full board, no winner. Custom rules pluggable later (no diagonal wins, k-in-a-row) via Strategy.
  • In-app notifications — "Aditya played (1, 1)", "Aditya wins".

Top-down design

Games: top-down (as in Tinder, L27) — start from Game, create smaller classes as needed.

Board — dumb object, SRP = manage cells; knows contents, not rules.

  • grid: vector<vector<Symbol*>>, size, emptyCell: Symbol('_').
  • Cells init to emptyCell not null → no null checks / null-pointer crashes (Null Object idea).
  • isCellEmpty(r, c) — false if out of bounds, else grid[r][c] == emptyCell.
  • placeMark(r, c, symbol) — bounds + empty check, set; returns bool.
  • getCell, getSize, getEmptyCell, display.

Symbol — wraps char mark, getMark().

Rule (abstract, Strategy) — isValidMove(board, r, c), checkWinCondition(board, symbol), checkDrawCondition(board). StandardRules:

  • isValidMove — board.isCellEmpty(r, c).
  • checkWin — any full row / column / main diagonal / anti-diagonal of symbol.
  • checkDraw — no empty cell (win checked first).

CustomRules could later be added. Game–Rule = composition.

Player — playerId, name, symbol, score (carries across games), incrementScore().

Turns: deque (queue) of players — a boolean isPlayer1Turn breaks with 3+ players. Front player moves, then pop_front() + push_back(); works for any N.

In-app notifications (Observer)

Shown inside the running app (vs email/SMS via external service), so the observer is a display class, not a player.

  • IObserver — update(message).
  • ConsoleNotifier — prints "[Notification] " + message. Later: logger, players (email).
  • Game = observable — observers, addObserver, removeObserver, notify(msg).

Game — the orchestrator

TicTacToeGame: board, players: deque<Player*>, rules, observers, gameOver; addPlayer, addObserver, notify, setRules, play().

play():
If < 2 players → error. notify("Game started").
while (!gameOver):
  1. board.display(); current = players.front(); read row, col.
  2. !rules.isValidMove(board, r, c) → "Invalid move", same player retries.
  3. board.placeMark(r, c, current.symbol); notify move.
  4. rules.checkWinCondition → "X wins!", incrementScore(), notify, gameOver = true.
  5. Else rules.checkDrawCondition → "draw", notify, gameOver = true.
  6. Else rotate: players.pop_front(); players.push_back(current);

Requirements

Same skeleton as Tic Tac Toe (L33): Game / Board / Player / Rules / in-app notifications; different rules and a few new classes.

  • Scalable board — 100 by default, any N.
  • Standard rules, extensible.
  • Board-setup strategies:

Key insight: the board isn't a grid

Top-down design

Lecture 35: Mediator Design Pattern (Chat Room) ▶ Watch

Source: Code Army LLD playlist · "Mediator Design Pattern — chat room example, Mediator vs Observer"

Problem: everyone talking to everyone

n objects that call each other → each holds n − 1 references, n(n − 1)/2 connections; every new object updates every list → tight coupling.

Fix: one object in the middle. Each object holds only the mediator; the mediator holds everyone. mediator.send(OB4, message) forwards (replies too). One list in the system → loose coupling.

Chat room without a mediator

User holds a list of Users (self-association, 1-to-many):

  • name, peers: vector<User*>, mutedUsers: vector<string>.
  • addPeer(user), mute(name).
  • send(msg) (broadcast) — per peer: skip if peer.isMuted(myName), else peer.receive(myName, msg).
  • sendTo(target, msg) (private) — same check for one target.
  • isMuted(name), receive(from, msg).

Demo: Rohan, Neha, Mohan need six addPeer calls. Rohan mutes Mohan; Rohan broadcasts; Mohan privately messages Neha.

Problem: memory/wiring grows as n²; every feature (mute, logging, private msgs) edits User and adds another per-user list.

The Mediator version

  • IMediator — registerColleague(c), send(from, msg), sendPrivate(from, to, msg).
  • Colleague (abstract) — mediated objects (work together, don't know each other). Holds mediator; constructor calls mediator.registerColleague(this). Declares send(msg), sendPrivate(to, msg), receive(from, msg), getName().
  • ChatMediator — the only place with lists:
    • colleagues.
    • mutes: vector<pair<string, string>> as (who muted, whom) + mute(who, whom) (concrete-only feature).
    • send(from, msg) — per colleague c: skip sender; skip if (c.name, from) in mutes; else c.receive(from, msg).
    • sendPrivate(from, to, msg) — find to; if (to, from) muted → "message muted"; else c.receive(from, msg).
  • User (concrete colleague) — name; send → mediator.send(name, msg); sendPrivate(to, msg) → mediator.sendPrivate(name, to, msg); receive prints.

Demo: one ChatMediator; users auto-register — no peer wiring. chatRoom.mute("Rohan", "Mohan"); same messages as before, same results.

Standard UML: Mediator (addColleague, send) ← ConcreteMediator (colleague list); Colleague (mediator, setMediator, send, receive) ← ConcreteColleague.

Standard definition:
Mediator defines an object that encapsulates how a set of objects interact, and promotes loose coupling by keeping objects from referring to each other explicitly.

Mediator vs Observer

Near-identical UML (hub, register, 1-to-many list, send/notify loop); differ in intent (like Bridge vs Strategy, L25):

Same shape, different purpose
ObserverMediator
PurposeTell dependents when my state changesLet peers talk to each other without knowing each other
DirectionOne-to-many, one way (subject → observers)Many-to-many, both ways, routed through the hub
ParticipantsObservers only listen (update)Colleagues both send and receive
Hub's own stateThe subject has state others care aboutThe mediator mostly holds routing/coordination rules
Typical useNotification systems (every "notify" requirement in this course)Chat rooms, in-game chat on chess.com-style apps, multiplayer matchmaking

Worth knowing

  • God-object risk — routing, muting, blocking, logging, rate limiting pile up. Keep it to coordination; split into helpers or per-room/concern mediators.
  • Mediator vs Facade (L17) — Facade: one-way entry for clients, subsystem unaware of it. Mediator: participants know and use it, two-way.
  • Name lookups are O(n) and assume uniqueness — use map<id, Colleague> and mutes as map<id, set<id>> (O(1)). sendPrivate to unknown user should error.
  • Registering in the constructor leaks a half-built this; separate register or a factory is safer.
  • Real-world: air traffic control (planes talk only to the tower), GUI dialogs (widgets ↔ dialog), chat/game servers. Mediators often use Observer internally.

Lecture 36: Prototype Design Pattern ▶ Watch

Source: Code Army LLD playlist · "Prototype Design Pattern — cloning objects, shallow vs deep copy"

Problem: expensive construction

When a constructor is expensive (DB connection, heavy calculation, loading files/images), repeated new repeats that cost. Prototype: build once, then create further objects by cloning — copying values is cheap.

Example: game NPCs (name, health, attack, defense), mostly near-identical. Without Prototype, new NPC("Alien", 30, 5, 2) and new NPC("Powerful Alien", 30, 5, 5) each re-run the expensive constructor.

C++ constructors: default A(), parameterized A(int a, int b), copy A(const A& other). Prototype is built on the copy constructor.

The pattern

  • Cloneable (aka Prototype; pure abstract) — clone() : Cloneable*.
  • NPC : Cloneable:
    • name, health, attack, defense.
    • Expensive constructor — used once to build the template.
    • Copy constructor NPC(const NPC& other) — copies fields, skips the expensive work.
    • clone() — return new NPC(*this);
    • Setters to tweak a clone; describe().
Usage:
NPC* alien = new NPC("Alien", 30, 5, 2);  // expensive, once
NPC* copy1 = dynamic_cast<NPC*>(alien->clone());  // cheap, identical
NPC* copy2 = dynamic_cast<NPC*>(alien->clone());
copy2->setName("Powerful Alien"); copy2->setHealth(50);  // small tweaks
dynamic_cast is needed because clone() returns Cloneable*.
Fits many near-identical objects (clone + a setter or two). Doesn't fit if every object is completely different — you'd reset every field anyway.

Standard UML: Client holds a Prototype and calls p.clone(); ConcretePrototype has copy constructor ConcretePrototype(prototype) and clone() = return new ConcretePrototype(this).

Shallow copy vs deep copy

  • Primitive fields (int x = 20) — copied by value; independent.
  • Shallow copy of a pointer field — this->s1 = other.s1; both share the same heap object; changes are visible through both. (Same for Java reference fields.)
  • Deep copy — this->s1 = new Student(*other.s1); clone owns its own copy; fully independent.
Standard definition:
Prototype lets you create new objects by copying (cloning) an existing instance. Use when creation is expensive (DB connections, complex calculations, network requests) or you need many near-identical objects (game NPCs).

Corrections & worth knowing

  • This Cloneable isn't a marker interface (the lecture calls it one). A marker interface has no methods. Java's java.lang.Cloneable is a marker: it just permits the protected Object.clone() (shallow, field-by-field). Effective Java recommends copy constructors/copy factories over clone().
  • Main benefit: polymorphic copying. Code holding a Cloneable*/Shape* can copy without knowing the concrete class; a copy constructor alone requires new ConcreteType(...). Hence clone() is virtual.
  • Prototype registry (GoF) — map of ready-made prototypes; registry.get("alien")->clone(). New variants = new entries, not new classes.
  • Saves time, not memory — each clone is a full object. To share heavy state use Flyweight (Lecture 30); combine: share the heavy part via pointers (deliberate shallow copy), copy the rest.
  • C++: covariant return (NPC* clone() const override) removes the dynamic_cast; return std::unique_ptr to avoid leaks; the implicit copy constructor is memberwise (shallow for raw pointers) → owning classes need a hand-written deep copy (Rule of Three/Five). std::string members copy deeply.

Requirements

Same game skeleton as Tic Tac Toe / Snake & Ladder (Lectures 33–34) + matchmaking + Mediator chat (Lecture 35). Interviews usually ask for one slice (engine, matchmaking or chat).

  • Concurrent matches — map matchId → Match.
  • Score-based matchmaking — all start at 1000; pair with the waiting user of closest score.
  • Standard chess rules, extensible to custom rule sets.
  • In-match chat (Mediator).
  • Quit loses points; winner gains, loser drops; draw = no change.

Flow: request match → waiting lobby → paired by score → match (board, pieces, chat) → alternate moves → win/loss/draw/quit → back to lobby.

Top-down design

GameManager (Singleton, facade/orchestrator) — activeMatches: map<matchId, Match*>, waitingLobby: vector<User*>, matchingStrategy (composition), matchCounter. Other methods look up the match and delegate.

Match — one game; also the chat Mediator:

  • matchId, whitePlayer, blackPlayer (two fields: two-player game), board, rules, currentTurn: Color, status: GameStatus (WAITING, IN_PROGRESS, COMPLETED, ABORTED).
  • moveHistory: vector<Move> (enables undo) and chatHistory: vector<Message>.
  • Constructor: builds Board (sets up 32 pieces), hardcodes StandardChessRules, white to move, IN_PROGRESS, setMediator(this) on both players.

User (chat Colleague) — userId, name, score (1000), increment/decrementScore; send(msg) → mediator.sendMessage(msg, this); receive(msg) prints.

Message — senderId, content, timestamp. ChatMediator (abstract) — sendMessage, addUser, removeUser. Match.sendMessage logs to chatHistory and calls receive on the other player; addUser empty; removeUser → quitGame.

Board, Position, Pieces

Board — manages pieces, not rules:

  • board: Piece*[8][8] + piecePositions: map<Position, Piece*> for fast lookup.
  • initializeBoard() — white back rank row 7, pawns row 6; black back rank row 0, pawns row 1.
  • placePiece, removePiece, getPiece, isOccupied, isOccupiedBySameColor(pos, color).
  • movePiece(from, to) — delete captured piece at to, update array + map, set hasMoved = true.
  • findKing(color) ({-1, -1} if absent), getAllPiecesOfColor(color), display() (ASCII, e.g. WK, BQ).

Position — row, col; isValid() (0–7); operator==; operator< (row, then col) — required for a std::map key (Java: equals/hashCode or compareTo); toChessNotation() (files a–h, ranks 1–8, e.g. e4).

Piece (abstract) — color (WHITE/BLACK), type: PieceType (KING, QUEEN, ROOK, BISHOP, KNIGHT, PAWN), hasMoved (pawn double-step), getPossibleMoves(pos, board), getSymbol() (K, Q, R, B, N, P). PieceFactory.createPiece(type, color) builds the subclass.

Rules (Strategy) and Move

Move — from, to, piece, capturedPiece.

ChessRules (abstract) → StandardChessRules:

  • isValidMove — to ∈ piece.getPossibleMoves(from) and !wouldMoveCauseCheck (no moving a pinned piece / into check).
  • wouldMoveCauseCheck — simulate the move, call isInCheck, undo, return result.
  • isInCheck(color) — find king; if any opponent piece's possible moves hit its square → true.
  • isCheckmate — in check and no piece has any isValidMove (return false at the first legal move found).
  • isStalemate — same scan, but not in check.

Match.makeMove(from, to, player)

Step by step:
1. Validate — status IN_PROGRESS; player's color = currentTurn; piece on from belongs to player.
2. Build Move(from, to, piece, board.getPiece(to)); if !rules.isValidMove → return false.
3. Execute — board.movePiece, push to moveHistory, board.display().
4. Check opponent — checkmate → endGame(player, "Checkmate"); else stalemate → end; else switch currentTurn and announce check if any.

quitGame(player) → endGame(opponent, "Quit"), quitter −50 extra. endGame(winner, reason) → COMPLETED; winner +30, loser −20 (no change without a winner).

Matchmaking (Strategy)

MatchingStrategy.findMatch(user, waitingUsers) → ScoreBasedMatching(tolerance = 100): among other waiting users, pick min |score − user.score| that is ≤ tolerance, else null.

GameManager.requestMatch(user) — no opponent → add to lobby; else remove opponent from lobby, create Match("match_" + ++counter, user, opponent), store in activeMatches. makeMove, quitMatch, sendChatMessage delegate to the match; COMPLETED matches are deleted from the map. displayActiveMatches() shows matches + lobby size.

Corrections & gaps worth raising

  • Stalemate is a draw. Demo calls endGame(currentPlayer, "Stalemate"), awarding a win; it should end with no winner, no score change.
  • Sliding pieces must stop after a capture — add the first enemy square, then break; otherwise Q/R/B slide through opponents.
  • Pawn rules:
    • Forward moves need an empty square (no capture straight ahead); double-step needs both squares empty.
    • Diagonal only onto an enemy piece.
    • isInCheck reuses getPossibleMoves, so pawn forward squares would count as attacks — generate "attacked squares" separately.
  • Missing rules (all fit the Strategy/rules design):
    • Special moves: castling (needs hasMoved), en passant, promotion.
    • Draws: threefold repetition, 50-move rule, insufficient material, draw offers.
    • Timers: chess clocks (loss on time).
  • Quit penalised twice — endGame (−20) + extra −50 = −70; pick one rule (requirements said quit −30 / win +50).
  • Matchmaking: real platforms use Elo/Glicko (change depends on opponent rating). Users outside tolerance wait forever → widen tolerance with wait time. Lobby scan is O(n); a multiset by score gives O(log n). Lock the lobby for concurrent requests.
  • Design nits: empty Match.addUser is an LSP smell; moveHistory enables undo (Command, Lecture 15) and PGN export; match.getBoard().display() in GameManager breaks least knowledge — prefer match.display().

Lecture 38: Visitor Design Pattern ▶ Watch

Source: Code Army LLD playlist · "Visitor Design Pattern — double dispatch, Visitor vs Strategy"

Problem: operations keep growing

Adding m3(), m4()… to a class per requirement violates OCP (constant modification) and SRP (many reasons to change), and hurts testability.

Example: DocumentElement → TextFile, Image, Video; calculateSize(), compress(), scanForVirus()… each added to the base and overridden in every subclass.

Key assumption — what varies?
Element types are stable; operations keep growing → pull operations out of the elements. If new element types were frequent, Visitor is the wrong choice.

The pattern

  • Elements — one method, accept(IVisitor v) → v.visit(this); in every class.
  • IVisitor — one overloaded visit per element type: visit(TextFile), visit(Image), visit(Video).
  • One concrete visitor per operation — SizeCalculationVisitor, CompressionVisitor, VirusScanningVisitor, each with per-type logic.

New operation (e.g. encryption) = one new visitor class; elements untouched.

Client code:
FileSystemItem* img = new ImageFile("sample.jpg");
img->accept(new SizeCalculationVisitor());  // "calculating size of image…"
img->accept(new CompressionVisitor());
img->accept(new VirusScanningVisitor());
video->accept(new CompressionVisitor());

Standard UML: IElement hierarchy (accept(v) → v.visit(this) per ConcreteElement) + IVisitor hierarchy (visit(ConcreteElement) per type, overridden by each ConcreteVisitor). Client holds both.

Double dispatch

The executed method depends on two runtime types (element + visitor); normal virtual calls are single dispatch.

  1. file1->accept(visitor) — virtual call selects the element's accept.
  2. v.visit(this) — virtual call selects the visitor; the type of this selects the overload (visit(TextFile*)).
Why every subclass repeats the one-line accept:
Overload resolution is compile time, using the static type of this. In TextFile::accept, this is TextFile*; in a base-class accept it'd be the base type and no overload matches.
Transcript slips: robot example's v.accept(this) should be v.visit(this); the size visitor "knows how to compress" should be "size".

Visitor vs Strategy

Strategy robot (Lecture 8): IRobot holds IFlyStrategy, ITalkStrategy, IWalkStrategy; FlyWithWings, FlyWithJet…

Which axis changes?
StrategyVisitor
FixedThe set of behaviours (fly, talk, walk)The set of element types (text, image, video)
GrowsWays to perform one behaviour (new fly styles)The number of operations (size, compress, scan, encrypt…)
Adding the thing that growsNew strategy subclassNew visitor class
Adding the fixed thingA new behaviour (swim) means editing IRobot — OCP breaksA new element type means editing every visitor
Who picksClient plugs a strategy into the contextClient passes a visitor to accept; double dispatch routes it

"What if we add swim?" — if behaviours keep being added, Visitor covers that axis. If both behaviours and implementations change, Strategy is usually still preferred (simpler; accept a small OCP break). The two can be combined.

Standard definition:
Visitor lets you add new operations to existing classes without changing their structure. It separates an operation from the objects it operates on.

Real-world uses

  • Compilers — AST with stable node types; type checking, optimisation, codegen, pretty-printing are visitors.
  • Game/rendering engines — render, collide, serialise over stable entity types.
  • Document processing — export one element tree to HTML, PDF, Markdown.

Rarely needed directly in LLD rounds, but explaining why Visitor, not Strategy for "growing operations" is a strong interview answer.

Worth knowing

  • Pairs with Composite (Lecture 19) — Folder::accept forwards to children; a stateful visitor sums e.g. totalSize over the tree.
  • Weakens encapsulation — elements must expose data (getters) to outside visitors.
  • Return values — visit is void, so results live in visitor fields (or use a generic visitor) → visitors are stateful; reuse/share carefully.
  • Modern alternative — sealed types + pattern matching (Java 21 sealed + switch patterns, C++ std::variant + std::visit): same benefit, less boilerplate, compiler flags missing cases.

Lecture 39: Memento Design Pattern ▶ Watch

Source: Code Army LLD playlist · "Memento Design Pattern — snapshots, undo, DB transaction rollback"

Snapshots for rollback

Snapshot an object's state as it changes (OB1 → OB1′ → OB1″) so you can roll back to a known-good state on error — i.e. undo.

Three roles

The terms sound heavy; the ideas are small
RoleWhat it isIn the demo
OriginatorThe object whose state changes; creates snapshots and restores from them.Database
MementoOne snapshot of the originator's state.DatabaseMemento
CaretakerStores mementos (one or a list) without looking inside.TransactionManager

Example: database transactions

A two-field update (roll 1001 → 1002, name Aditya → Abhay) failing halfway leaves an inconsistent state. Atomicity: all or none. beginTransaction → changes → commit or rollback; rollback needs the saved previous state (a memento). Applies to NoSQL or a plain map too.

  • Database (originator) — in-memory map<string, string> records:
    • insert, update, remove, displayRecords.
    • createMemento() — return new DatabaseMemento(records);
    • restoreFromMemento(m) — records = m.getState();
  • DatabaseMemento — own data map, copied in via constructor (or setState); getState().
  • TransactionManager (caretaker) — single backup (one level of rollback):
    • beginTransaction(db) — delete old backup; backup = db.createMemento().
    • commit() — delete backup, set null.
    • rollback(db) — if backup: db.restoreFromMemento(backup), delete it; else "no backup available".
The caretaker never looks inside:
It holds an opaque memento and hands it back on rollback; only the originator knows the state's structure. This preserves the originator's encapsulation.

Standard UML: Originator (state, createMemento(), restoreMemento(m)) → Memento (state, getState(), setState()) ← Caretaker (history: List<Memento>, add(originator) saves originator.createMemento(), undo(originator) → originator.restoreMemento(…)). Caretaker 1 → many mementos.

Demo run

  1. beginTransaction → insert Aditya, Rohit → commit.
  2. beginTransaction (snapshot: Aditya, Rohit) → insert Saurabh, Manish.
  3. Simulated error → rollback → back to Aditya, Rohit.
Standard definition:
Memento provides the ability to take a snapshot of an object at various points in time and restore it to a previous state (undo).

Real-world uses

  • DB transactions — commit / rollback.
  • Git — commits as restorable snapshots.
  • Editor undo (Ctrl+Z), game checkpoints, form drafts.

Corrections & worth knowing

  • Real DBs don't snapshot everything — they use undo/redo logs, WAL, MVCC. Memento fits best when state is small.
  • Deep-copy the state. C++ copies std::map by value; in Java this.data = dbData shares the map → use new HashMap<>(dbData), return a copy from getState(), make the memento immutable.
  • Protect contents — public getState() lets the caretaker read/tamper. GoF: "wide" interface for the originator, "narrow" for others (Java private nested class, C++ friend).
  • Multi-level undo/redo — undo stack + redo stack of mementos; cap history or store diffs to bound memory. Nested transactions = savepoints, one memento per level.
  • Memento vs Command (Lecture 15) — Command undoes via inverse operation (cheap, needs a correct inverse); Memento restores saved state (simple, reliable, memory-heavy). Often combined: a command stores a memento. vs Prototype (Lecture 36) — Prototype's copy is a new object; a memento is an opaque saved version of the same object.

Lecture 40: Anti-Patterns & the Null Object Pattern ▶ Watch

Source: Code Army LLD playlist · "Design anti-patterns and the Null Object pattern — series finale"

Part 1 — Anti-patterns

Anti-patterns: common habits that look fine when written and cause trouble later.

1. God object

One class with dozens of responsibilities that everything depends on; violates SRP, single point of breakage.

Aren't orchestrator classes god objects?
Not if they only delegate. A facade (Tomato, Splitwise, GameManager) forwarding calls to services is an entry point, like a controller layer routing /v1/addUser to services. It becomes a god object once methods do real work before delegating. Without it, clients must know every class.

2. Spaghetti code

Tangled dependencies (A → C → D → A), no clear entry/exit; tightly coupled, error-prone.

3. Hard-coding

Literal values in methods/constructors; use parameters, constants or config. Hard-code only what truly never changes.

4. Gold plating / over-engineering

Applying every pattern everywhere and handling scenarios that never happen. Strategy is for what varies, not every algorithm; unneeded abstraction adds complexity.

5. Repeating yourself (DRY violation)

Copy-pasted logic must be fixed in every copy; extract to one method/utility/hierarchy.

6. Constructor overloading (telescoping)

A constructor per argument combination. Fix: Builder (Lecture 28).

7. Overuse of getters/setters

Getters/setters exist for controlled, validated access; auto-generating them for every field defeats encapsulation. Expose only what's needed.

8. Premature optimisation

"Make it work, then make it fast." Correct brute force (O(n²)) first, optimise (O(n log n)) once it's correct and it matters.

9. Overusing inheritance

Deep/multiple inheritance makes code rigid. Strategy, Bridge, Visitor etc. replace it: inherit from abstractions, use composition (has-a) for concrete behaviour.

Terminology notes:
DRY is the principle; the anti-pattern is copy-paste programming. Gold plating = unrequested features; over-engineering = unnecessary complexity; counters: YAGNI, KISS. Hard-coded values = magic numbers/strings. Kent Beck: "make it work, make it right, make it fast"; Knuth: "premature optimisation is the root of all evil". Spaghetti code originally meant tangled control flow (gotos); system-level tangle = "big ball of mud".

Part 2 — Null Object pattern

Scattered if (obj == null) checks; miss one and you get a null-pointer exception. Principle: replace conditionals with polymorphism.

The pattern:
Add a NullObject subclass whose methods are no-ops or return sensible defaults (0, "", empty list). Store it wherever you'd store null; ac.m1() always works — no null check, no exception.

Already used

  • Strategy (Lecture 8) — NoFly: fly() does nothing, so s.fly() is always safe.
  • Command (Lecture 15) — remote buttons start with NoCommand; unassigned buttons do nothing. (Not recorded in the Lecture 15 notes; standard approach.)

Whenever a reference can legitimately be "nothing", consider a NoX/NullX implementation.

Corrections & worth knowing

  • Null ≠ dangling pointer (the lecture conflates them). Null points to nothing; dangling points to freed memory — worse, may appear to work.
  • Don't hide real errors. Right when absence is valid (no fly behaviour, unassigned button, disabled logger); wrong when absence is a bug (required user record) → fail fast or use Optional / std::optional.
  • Usually stateless → one shared instance (Singleton/flyweight-like). E.g. Collections.emptyList(), no-op logger, empty iterator.
  • LSP-compliant only if the no-op honours the interface contract (can't return garbage where a valid result is promised).
